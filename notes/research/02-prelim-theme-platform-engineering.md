## 0. 한 페이지 요약

1. **[공식]** 예선 주제는 "로컬 웹앱을 원터치로 하이퍼스케일러(AWS·GCP 등) 또는 온프레미스(로컬 PC·VM)에 배포하는 시스템을 AI를 활용해 만들기"였고, 평가 대상은 앱이 아니라 **배포 시스템 자체**였다. 배점은 완성도·데모 30, 클라우드 활용(환경 차이 흡수·이식성·환경 고유 기능 대응) 30, 팀 개발(설계 문서·대안·논의 과정) 20, 독창성 10, AI 활용 10.
2. **[추측]** 플랫폼 엔지니어링 용어로 바꾸면 이 주제는 "작은 **Internal Developer Platform(IDP)** 을 만들어라"이고, 그중에서도 핵심은 **앱 명세(워크로드 스펙)와 환경별 구현(리소스 프로비저닝)의 분리**다. 업계에서 Score·OAM/KubeVela·Radius·Crossplane이 각자 푸는 문제와 같다.
3. **[사실]** 우리 팀(Camellia)은 이 분리를 IR(Zod 스키마) + 프로필(capabilities) + 어댑터로 설계했다. 심사위원은 이 설계를 높게 봤지만, 세 군데를 짚었다: ① 스키마의 구체적인 설계 포인트를 못 봤다, ② DB·스토리지·환경 고유 기능으로 어떻게 확장하나, ③ 온프레미스가 이미지 한 개만 pull해서 IR이 덜 살았다. 코드를 보면 ②·③은 실제 구현 범위의 한계와 정확히 일치한다(5절).
4. **[추측]** 본선이 "한 단계 깊어진다면" 가능성이 높은 방향 3가지:
   - **가설 A. 상태(데이터)까지 옮기는 이식성**: DB·오브젝트 스토리지·큐를 포함한 다중 컴포넌트 앱을 환경 간에 배포·이동·이중화. 심사위원 질문 ②·③과 킥오프 슬라이드 16·18이 직접 가리킨다.
   - **가설 B. 여러 환경(클러스터)을 한 번에 다루는 배치·스케줄링**: "어디에 배포할지"를 정책·비용·가용 자원으로 자동 결정하고 여러 클러스터에 동시 전개. 프로젝트 목표의 "멀티 클러스터 스케줄링"과 연결.
   - **가설 C. Day-2 운영 자동화**: 점진 배포(카나리·블루그린)와 지표 기반 자동 롤백, 장애 감지·복구, 비용 최적화, 그리고 그걸 하는 AI 운영 에이전트.
5. **[없음]** 본선 주제에 대한 공식 정보는 이번 조사 범위에서 찾지 못했다. 위 가설은 전부 추측이다.

## 2. 주제 원문 정리 [공식, S1]

### 2.1 주제 문장 (슬라이드 15)

> ローカルで作成した Web アプリケーションを、ワンタッチでデプロイ。AI をフル活用した、Google Cloud・AWS などのハイパースケーラー、またはオンプレ環境（ローカル）へ簡単にデプロイできるシステムを作ってみよう！
>
> 로컬에서 개발한 웹 애플리케이션을 원터치로 배포. AI를 전적으로 활용해 Google Cloud, AWS 같은 하이퍼스케일러나 온프레미스(로컬) 환경으로 쉽게 배포할 수 있는 시스템을 만들어 봅시다!

### 2.2 주최 측이 던진 질문 (슬라이드 16·17)

이 질문 목록이 사실상 "풀어야 할 문제 목록"이다.

| # | 질문 (요약) | 플랫폼 엔지니어링 용어 [추측] |
|---|---|---|
| Q1 | 프레임워크가 무엇인가 (Rails, Express/Hono, SPA, Next.js) | 소스 분석·빌드 자동화 (buildpack) |
| Q2 | 어디에 배포하나 (Lambda/Cloud Functions, Fargate/Cloud Run, EC2/GCE) | 런타임 타깃 선택 (배치 결정) |
| Q3 | 로컬과 클라우드에서 데이터를 어떻게 보관하나 | 상태 저장 리소스 추상화 |
| Q4 | 클라우드와 온프레미스의 차이를 어떻게 메우나 | 이식성, 환경 추상화 |
| Q5 | CI/CD와 어떻게 연결하나, 마이그레이션은 | 전달 파이프라인, 스키마 마이그레이션 |
| 결론 | "코드를 자동으로 바꾸면서 인프라를 적절히 갖춰 주는 시스템" | AI가 개입하는 IDP |

### 2.3 "간단한 배포"의 예시 (슬라이드 18·19, 주최 측이 "하나의 예시일 뿐"이라고 명시)

- 넓은 범위: 여러 환경(온프레·각 회사 클라우드), 다양한 규모의 앱
- 대충 만든 앱도 프로덕션 품질 인프라로: **SQLite → 적절히 설정된 RDS**, 모니터링·시각화 도입
- 안전성: 배포 작업 로그, **롤백·블루그린·카나리**
- 비용 효율: AI 비용에 맞는 효과
- 팀 개발: **여러 명이 동시에 안전하게 배포**

### 2.4 제약 (슬라이드 20·21)

- 클라우드·AI 선택 자유. 자기 PC나 그 위 VM을 "온프레미스"로 간주해도 됨
- **평가 대상은 배포하는 시스템의 품질**이고 배포되는 앱의 품질이 아님

### 2.5 심사 기준 (슬라이드 40·41, 최우수·우수팀 선정용)

| 항목 | 배점 | 원문 요지 |
|---|---:|---|
| 완성도·데모 | 30 | 로컬과 클라우드 **양쪽** 배포를 그 자리에서 시연, 배포된 앱에 누구나 접근 가능 |
| 클라우드 활용 수준 | 30 | **환경 차이 흡수·이식성**이 설계에 반영됐나, **각 클라우드 고유 기능**에도 대응하나 |
| 팀 개발 | 20 | 설계가 문서화되고 **대안·논의 과정·고찰**과 함께 실현 가능성을 논의했나 |
| 독창성 | 10 | 대응 환경의 넓이, UX 등 |
| AI 활용 | 10 | AI 활용의 고민 |

추가 사실 [공식]:
- 본선 진출은 **개인 단위**로 결정, 팀 점수와 별도로 기술력·팀워크·커뮤니케이션·적극성을 본다 (슬라이드 42·43)
- 평가에는 최종 발표뿐 아니라 개발 중·중간 보고 정보도 포함 (슬라이드 40)
- 최종 발표 5분(설계 문서 2분 + 데모 3분), **슬라이드 금지, 설계 문서 + 데모로 발표**, 통역 있음, 한국어·일본어 선택 (슬라이드 32·33)
- 제출물에 "결론만이 아니라 다른 안과 왜 그 구현을 했는지 논의 과정"이 보이는 작업 메모를 요구 (슬라이드 26·27)

**[추측]** 30점짜리 "클라우드 활용"의 두 문장(이식성 + 고유 기능)은 서로 긴장 관계다. 추상화를 높이면 이식성은 좋아지지만 고유 기능을 못 쓰고, 고유 기능을 쓰면 이식성이 깨진다. 이 긴장을 어떻게 설계로 푸는지가 이 주제의 핵심 질문이고, 본선에서도 이어질 가능성이 높다고 본다.

## 3. 플랫폼 엔지니어링 관점의 분해

### 3.1 프레임: 이 주제는 "작은 IDP"다 [추측]

플랫폼 엔지니어링은 개발자가 인프라 세부를 몰라도 셀프서비스로 배포·운영할 수 있도록 내부 플랫폼(IDP)을 제품처럼 만드는 분야다. CNCF TAG App Delivery의 Platforms White Paper가 대표 정리 문서다 [재확인 필요: 문서 위치 https://tag-app-delivery.cncf.io/whitepapers/platforms/].

주제 문장 "원터치로 여러 환경에 배포"를 IDP 구성 요소로 펼치면 아래 12개 레이어가 된다. 각 레이어에 주최 측 질문(2.2), 우리 예선 구현, 업계 대표 도구를 붙였다.

| # | 레이어 | 이 레이어가 푸는 질문 | 주최 측 근거 | Camellia 예선 구현 [사실, S3] | 업계 대표 (4절 참조) |

| L11 | 거버넌스·감사·비용 | 누가 언제 뭘 했나, 얼마 드나 | 슬라이드 18 로그·비용 | 감사 로그(마이그레이션 010), 비용 추정(`packages/profiles/src/cost-estimate.ts`), 승인 게이트 (D-07) | OPA/Kyverno, Infracost |

### 3.3 이 주제의 핵심 기술 요소 6가지 [추측, 3.2에서 도출]

레이어는 12개지만 설계 판단이 갈리는 지점은 아래 6개로 모인다. 본선에서 어떤 주제가 나와도 이 6개는 질문받을 가능성이 높다.

| # | 핵심 요소 | 설계 판단의 축 | 대표 대안 |
|---|---|---|---|
| K1 | **추상화 수준** (IR에 무엇을 넣고 뺄지) | 앱 요구만 vs 인프라까지 | Score(앱 요구만) / Compose(컨테이너 수준) / Terraform(인프라 그대로) |
| K2 | **환경 고유 기능 수용** | 최소공통분모 vs 탈출구(escape hatch) | overrides 패치 / 리소스 타입별 "레시피" 교체 / 프로바이더 확장 모듈 |
| K3 | **상태(데이터) 이식** | 환경별 별도 DB vs 공유 vs 복제 | 환경마다 관리형 DB + 마이그레이션 / 복제(CDC) / 로컬 대체(SQLite) |
| K4 | **배치 결정** | 사람이 고름 vs 규칙 vs 최적화 | 수동 선택 / 규칙 엔진 / 비용·지연 점수화 |
| K5 | **전달 방식** | Push(오케스트레이터가 실행) vs Pull(GitOps, 에이전트) | Terraform apply 직접 / Argo CD 동기화 / 에이전트 롱 폴링 |
| K6 | **AI의 역할 경계** | AI가 판단만 vs 실행까지 | 분석·진단만(우리 D-05) / IaC 생성 / 에이전트가 API 도구 호출 |

### 4.2 레퍼런스에서 읽히는 업계의 답 [추측]

1. **"명세와 구현의 분리"는 업계 합의다.** Score, OAM, Radius, Crossplane, Humanitec이 모두 "개발자가 쓰는 추상 명세"와 "플랫폼 팀이 쓰는 환경별 구현"을 나눈다. 우리 IR 설계 방향은 업계 흐름과 맞다. 심사위원이 "スマート"라고 한 근거로 쓸 수 있다.
2. **고유 기능은 "리소스 타입 + 환경별 구현 교체"로 푼다.** 앱은 `type: postgres`만 말하고, AWS에서는 RDS 레시피, 온프레에서는 컨테이너 Postgres 레시피가 붙는다(Radius Recipe, Score provisioner, Crossplane Composition). 최소공통분모 문제를 피하는 표준 패턴이다.
3. **전달은 Pull(GitOps)로 수렴한다.** 여러 환경·방화벽 뒤 환경을 다룰수록 중앙에서 Push하기보다 각 환경이 원하는 상태를 끌어와 맞추는 방식이 유리하다. 우리 온프레 Agent가 이미 이 방식이다.

## 5. 심사위원 피드백 ↔ 레포 사실 대조

심사위원 코멘트(S2)와 코드(S3)를 맞대 보면, 지적이 실제 구현 한계와 정확히 겹친다. 본선 준비의 출발점으로 쓸 수 있도록 정리한다.

| # | 심사위원 코멘트 [공식, S2] | 레포에서 확인한 사실 [사실, S3] | 해석 [추측] |
|---|---|---|---|
| F1 | IR로 변환 후 배포하는 접근은 테마에 잘 맞는다. 다만 **구체적인 스키마 고안점**을 잠깐이라도 보고 싶었다 | IR 스키마는 8개 최상위 필드(`$ir_version`, `metadata`, `services`, `resources`, `deploy`, `overrides`, `expose`, `missing_resources_decisions`)와 `.describe()` 설명을 갖춘 428줄 Zod 코드 (`packages/ir-schema/src/schema.ts`). 팀원용 명세 문서도 있음 (`docs/ir-spec-for-team.md`, 726줄) | 설계는 있었는데 **발표 2분 안에 보여 주지 못했다**. 슬라이드 금지 형식이라 설계 문서에서 IR YAML 예시 한 화면을 바로 보여 주는 동선이 필요했다 |
| F2 | **DB·클라우드 스토리지·인프라 고유 기능**까지 다루려면 어떻게 확장하나 | 스키마의 리소스 타입은 `postgres`·`mysql`·`redis`·`object_storage` 4종. 그러나 프로필 capabilities는 ECS·온프레 `["postgres"]`, Lambda·정적 `[]` (`packages/profiles/src/*.ts`). ECS 어댑터는 PostgreSQL 1개만 허용 (`packages/adapters/src/aws-ecs.ts:32`). 환경 고유 기능용 `overrides` 필드는 스키마에 있지만 어댑터·워커 코드에서 참조하는 곳이 없음 (grep 기준) | 확장 경로(D-04 overrides, D-37·D-39 확장 모듈)는 **설계 문서에만 있고 구현은 Postgres 하나**. 업계 답(4.2의 2번: 리소스 타입별 레시피 교체)을 구현으로 보여 줄 수 있으면 이 질문에 정면으로 답할 수 있다 |
| F3 | 배포 대상 차이를 신경 쓰지 않는 IR은 스마트. 다만 **온프레가 단일 이미지 pull**인 점이 아쉽다. 온프레도 IR을 참조해 **여러 컨테이너를 협조**시키면 IR이 더 살 것 | 공통 플랜이 서비스 1개만 허용: `P0_SINGLE_HTTP_SERVICE_REQUIRED` (`packages/adapters/src/common.ts:19-29`). 온프레 Agent가 만드는 Compose 파일은 `services: app:` 하나 (`apps/onprem-agent/src/compose.ts:57-61`). DB는 온프레에서 `local_fallback: sqlite`로 대체 (`schema.ts`의 `local_fallback`, D-64) | 실제로는 **AWS도 앱 컨테이너는 1개**이고, AWS 쪽은 VPC·ALB·ECS·RDS가 함께 만들어져 "협조"처럼 보였다. 온프레는 앱 1개 + SQLite라 차이가 드러났다. IR의 `services`(다중), `depends_on`, `resources`를 온프레 Compose로 그대로 옮기면(앱 + Postgres 컨테이너 + 워커) 지적을 해소한다 |
| F4 | 배포된 앱 URL을 고정해서 뒷단을 의식하지 않게 한 점이 훌륭하다. URL 고정 덕분에 데모가 좋았다 | Cloudflare DNS·Named Tunnel로 `https://{subdomain}.camellia-deploy.app` 고정 (D-67), 헬스체크 통과 후 전환 | 강점. 본선에서도 유지할 가치가 있다 |
| F5 | **정적 분석으로 IR 작성 + AI 보완** 부분은 앞으로 더 확인하고 싶다 | 규칙 탐지기 6종 + AI는 못 찾은 칸만 채움 (`packages/analyzer/src/ai/fill-unresolved.ts`). 측정은 "4개 fixture 전부 IR valid, 배포 1회 평균 $0.025, 4.08초" (`docs/final-report-2026-09-30.md`) | "valid"(스키마 통과)는 있지만 "**정확도**"(맞는 값을 채웠나) 근거는 없었다. 본선에서 AI를 쓰면 "규칙만 vs 규칙+AI의 정답률" 같은 비교 숫자가 필요하다 |
| F6 | 일본어 발표가 대단하다, 완성도가 높다, 코로 연출이 귀엽다 | 콘솔 한·일 지원 (D-68) | 개인 평가(커뮤니케이션)에 긍정 요소 |

### 가설 A. 상태까지 옮기는 이식성: "앱 + 데이터 + 관리형 서비스"를 여러 환경에 [확신도: 높음]

**예상 문제 문장(예시)**: "DB·스토리지·캐시를 쓰는 다중 컴포넌트 앱을 클라우드와 온프레미스 어디에든 같은 명세로 배포하고, 환경 간에 데이터와 함께 이동·이중화하라."

**근거**

**핵심 기술 요소**
- 리소스 추상화: 리소스 타입별 환경 구현 교체 (Score provisioner, Radius Recipe, Crossplane Composition 패턴)
- 다중 컴포넌트 배치: 서비스 간 의존(`depends_on`)·서비스 디스커버리·내부 네트워크, 온프레 쪽 Compose 또는 k3s

- 측정 지표: **RPO(데이터 유실 허용량)·RTO(복구 시간)**, 전환 중 다운타임

### 6.4 세 가설의 관계 [추측]

- A는 예선의 직접 연장이라 가장 가능성이 높고, B·C는 A 위에 얹힌다. 예: "상태 있는 앱(A)을 여러 클러스터(B)에 배치하고 카나리로 운영(C)"
- 세 가설 모두에서 공통으로 질문받을 것: **명세(IR) 설계, 대안과 트레이드오프, 측정 숫자**. 이는 예선 심사 기준(팀 개발 20점: 대안·논의 과정)과도 일치한다
