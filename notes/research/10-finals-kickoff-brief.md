### 1.2 주제
- **Beyond Lock-In: Frictionless Cloud Management Across Platforms** 【사실: p13】.
- 예선 vs 본선 【사실: p14】:

| | 예선 "One Action, Infinite Clouds" | 본선 "Beyond Lock-In" |
|---|---|---|
| 무엇을 | 지금 손에 있는 앱을 퍼블릭 클라우드나 온프레에 올린다 | 프로덕션에서 가동 중인 시스템을 다른 환경에서도 동작하도록 이전한다 |
| 출발점 | 로컬에서 만든 앱 | 이미 프로덕션에서 가동 중인 시스템 |
| 핵심 질문 | 쉽고 확실하게 배포할 수 있는가 | **무중단으로 안전하게 이전하고 지킬 수 있는가** |

- 한 줄: "예선의 배포 시스템을 기반으로, 프로덕션 수준의 멀티 클라우드 관리 플랫폼으로" 【사실: p14】.
- 전체 그림 【사실: p15】: 관리 플랫폼(예선 확장) → 5개 기둥 [무중단 이전 / 보안·거버넌스 / 온프레 이전·동등 기능 재현 / AI 리소스·데이터 레지던시 / 비용·횡단 모니터링] → "AI 에이전트가 샌드박스에서 점검·코드 변경·이전 계획을 자유롭게 시도하고, 안전을 확인한 뒤 프로덕션에 반영" → 관리 대상 3종: 퍼블릭 클라우드 A(Google Cloud 등) / B(AWS·NAVER Cloud 등) / 온프레(자신의 PC·VM). 바닥 문구 "가동 중 이전·같은 기준으로 보호".

### 1.3 "프로덕션 운영에서 멀티 클라우드를 관리할 때 요구되는 것" 5문항 【사실: p16-17】
1. 가동 중인 앱을 멈추지 않고 다른 클라우드로 이전할 수 있는가 → 데이터 동기화, DNS·트래픽 전환, 롤백 절차.
2. 보안·거버넌스를 모든 환경에서 같은 수준으로 → GuardDuty, Security Command Center 등 클라우드마다 다른 기능을 어떻게 통일·시각화.
3. 온프레로 이전할 때 클라우드에서 당연하던 기능을 어떻게 재현 → IAM, 시크릿 관리, 감사 로그, 모니터링, 백업을 온프레에서 구현·시각화.
4. 앱이 쓰는 AI 서비스와 데이터를 어디에 두고 어떻게 옮기나 → Bedrock, Gemini Enterprise Agent Platform 등을 데이터 레지던시를 지키며 온프레로.
5. 이런 점검·수정을 AI에게 어디까지 안전하게 맡길 수 있나 → 샌드박스에서 시험한 뒤 프로덕션 반영 구조.
- 마무리: "예선의 배포 시스템을 기반으로, 이러한 과제를 해결하는 관리 플랫폼을 만들어 주세요" 【사실: p16-17】.

### 1.5 기대 산출물과 데모 필수 장면 【사실: p20-21】
- ① **멀티 클라우드 관리 플랫폼**(예선 배포 시스템 확장): 여러 환경의 상태·보안·비용·AI 리소스를 일원 관리, AI 에이전트가 샌드박스에서 점검·수정.
- ② **관리 대상인 가동 중 웹앱**: 예선 앱 그대로 써도 됨. 이전·보안 점검 대상으로 **실제로 가동해 둘 것**. **평가 대상은 앱이 아니라 플랫폼**.
- 최종 데모에서 보여 줬으면 하는 것: (a) 가동 중 앱을 클라우드 간 이전하는 모습 (b) 여러 환경의 보안·거버넌스 상태 시각화 (c) AI 에이전트가 샌드박스에서 점검·수정하는 모습.

### 3.2 무중단 이전의 표준 절차 (공개 가이드 하나 기준)
【사실: https://oneuptime.com/blog/post/2026-01-06-kubernetes-migrate-workloads-zero-downtime/view 】
1. 인벤토리(Deployment·Service·ConfigMap·Secret·PVC·Ingress·CRD, 외부 의존) → 2. 대상 클러스터 구축(ingress·cert-manager·모니터링 같은 버전) → 3. 시크릿 복제(Sealed Secrets 재암호화 또는 External Secrets + 외부 저장소) → 4. 데이터(Postgres 스트리밍 복제 + `pg_basebackup`, PVC는 Velero, 오브젝트는 `rclone`/`aws s3 sync`) → 5. 배포·스모크 테스트 → 6. DNS TTL 60초로 낮추고 Route 53 가중치 또는 Istio VirtualService 가중치, 선택적으로 미러링 → 7. **10→25→50→75→90→100%** 단계 전환, 단계마다 ~5분, Prometheus 5xx 1% 문턱 → 8. 구 환경 DNS 제거·정리.
- 롤백: 가중치를 구 환경 100%로, DB는 `pg_promote()`로 구 프라이머리 승격, 데이터는 Velero 백업 복원.
- 해커톤 축약 【추정】: 환경 2개만, DB는 1개(Postgres 복제 1쌍), 전환은 DNS 가중치 대신 **한 개의 글로벌 진입점**(Cloudflare LB/Tunnel 또는 자체 라우터)으로 하면 TTL 문제 없이 초 단위 전환·롤백이 데모에 보인다. Gold 팀도 Quick Tunnel로 공개했다【사실: 2.7】.
