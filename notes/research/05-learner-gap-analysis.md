## 0. 결론 먼저

본선 전까지 우선순위대로 채울 역량은 아래 6개다. 상세 근거는 2~3절.

| 순위 | 역량 | 한 줄 이유 |
|---|---|---|
| P0-1 | **Kubernetes를 손으로 다루기** (배포·롤아웃·롤백·오토스케일·프로브) | 예상 주제 6개 중 5개가 K8s 위에서 돌아가는데, 예선 레포에는 K8s가 전혀 없다 |
| P0-2 | **Terraform을 직접 짜고 state를 이해하기** | 예선에서 인프라 코드는 다른 팀원이 거의 다 썼다. 본선은 팀이 다시 짜일 가능성이 있어 혼자 설 수 있어야 한다 |
| P0-3 | **측정 루프** (부하 생성 → 메트릭 수집 → p50/p95로 말하기) | 목표 문장 자체가 "실측 숫자로 설명"이다 |
| P0-4 | **설계를 3분 안에 말하고 4분 Q&A를 버티기** | 예선 심사가 문서·대안·고찰에 20점, 피드백도 "스키마를 구체적으로 보여 달라"였다 |
| P1-1 | **GitOps 배포 파이프라인** (Argo CD + 카나리/롤백) | 킥오프 예시에 롤백·블루그린·카나리가 명시돼 있고, 예선은 카나리를 구현하지 않았다 |
| P1-2 | **주제별 1회 실습**: 서버리스(scale-to-zero), 멀티 클러스터(OCM), AI 추론 서빙, 장애 주입 | 본선 주제를 모르니 "한 번이라도 직접 띄워 본 경험 + 숫자 1개"를 주제마다 확보 |

버릴 것: GCP·Azure 실계정 실습, 서비스 메시 깊이 파기, Go로 컨트롤러 직접 작성, 커널·eBPF 튜닝. (5절)

## 2. 근거

### 2.1 예선 심사 기준과 형식 【사실】 (킥오프 PPT 슬라이드 23~42)

| 항목 | 배점 | 기준 원문 요지 |
|---|---|---|
| 완성도·데모 | 30 | 로컬과 클라우드 양쪽 배포를 그 자리에서 데모할 수 있는가, 배포된 앱에 누구나 접근 가능한가 |
| 클라우드 활용 수준 | 30 | 환경 차이 흡수·포터빌리티가 설계에 반영됐는가, 각 클라우드 고유 기능에 대응하는가 |
| 재미·독자성 | 10 | 독자적 고집 포인트 (대응 환경 폭, UX 등) |
| AI 활용 | 10 | AI 활용의 고안 |
| 팀 개발 | 20 | 설계가 문서화되고 **대안·논의 과정·고찰**과 함께 실현 가능성을 논의했는가 |

- 평가는 최종 발표만이 아니라 개발 중·중간 보고 정보도 포함한다.
- Day1 중간 보고: 팀당 7분 (발표 3분 + **Q&A 최대 4분**), 순차 통역.
- Day2 최종 발표: 5분 (설계 문서 2분 + 데모 3분), **슬라이드 금지**, 설계 문서 + 실제 데모로 발표. 목업 부분은 목업이라고 밝혀야 한다.
- 발표 언어는 한국어·일본어 중 선택, 통역용 토크 스크립트 제출.
- 본선 진출은 **팀이 아니라 개인 단위**로 정해지며, 개인 평가 방향은 "기술력, 팀워크·커뮤니케이션, 적극성 등". 결과는 **10/26 저녁 메일**, 10/27 23:59까지 회신.
  - 참고: 한국어 슬라이드(43)는 "본선에서 면접 전형으로 진출할 인원"이라고 번역돼 있지만, 일본어 원문(42)은 "予選から本選への通過結果"(예선→본선 통과 결과)다. 일본어 원문 기준으로 적었다.
- 모집 직종은 인프라 엔지니어(SDN 게이트웨이 등 법인 게이트웨이 서비스)와 클라우드 엔지니어(AWS/Azure/GCP 공통 기반 설계·구축). "스킬뿐 아니라 인간력도 본다".

【추정】 본선도 같은 운영사(Progate·KOREC)라면 "Q&A 비중이 크고, 슬라이드 대신 설계 문서와 실제 동작을 본다"는 형식이 유지될 가능성이 높다. 본선 심사 기준 자체는 【미확인】 (4번 스레드 결과로 보강 예정).

【추정】 본선 참가자가 개인 단위로 뽑히므로 본선 팀은 새로 짜일 가능성이 있다. 그러면 "예선 팀원이 맡던 인프라 영역"을 본선에서는 Jeong이 직접 해야 할 수 있다.

### 2.2 심사위원 피드백 → 무엇이 부족해 보였나

| 피드백 (요지) 【사용자】 | 드러난 갭 【추정】 | 이 문서의 대응 역량 |
|---|---|---|
| IR 접근은 좋다. **구체적인 스키마 고안점**을 잠깐이라도 보여 줬으면 | 설계의 핵심을 30초 안에 "실물(스키마 일부)"로 보여 주는 발표 기술 | P0-4 |
| DB·클라우드 스토리지·인프라 고유 기능까지 다루려면 **어떻게 확장**하나 | 리소스 추상화 확장 모델(모듈 합성, capability 매핑)을 구조로 설명하는 능력 | P0-2, P1-1 |
| 온프레미스가 **단일 이미지 pull**인 점이 아쉽다. 온프레미스도 IR을 보고 여러 컨테이너를 협조시켜 배포하면 IR이 더 산다 | 온프레미스에서도 클라우드와 같은 다중 서비스 오케스트레이션을 하는 런타임 경험 (= K8s 계열) | P0-1 |
| URL 고정으로 뒷단을 의식하지 않게 한 점, 데모가 좋았다 | (강점) 사용자 관점의 "끊김 없는 전환" 설계 | 유지 |
| 정적 분석으로 IR 작성 + AI 보완 부분은 **더 확인하고 싶다** | AI 보완 결과가 맞는지 보여 줄 **검증 숫자**(정확도·실패율)가 없었다 | P0-3 |
| 일본어 발표, 완성도 높음 | (강점) | 유지 |

메모: 예선 레포 `apps/onprem-agent/README.md`를 보면 Agent는 job별 Compose project를 만든다 【사실】. 그런데 피드백은 "단일 이미지 pull"로 받아들였다 【사용자】. 기능이 있어도 데모·설명에서 다중 서비스가 보이지 않았을 수 있다 【추정】. "있는 기능을 보이게 하는 것"도 갭이다.

## 3. 역량 갭 표 (우선순위 순)

"본선 당일 기준선"은 본선 시작 시점에 자료를 거의 안 보고 할 수 있어야 하는 수준이다.

| 순위 | 역량 | 현재 【추정】 | 본선 당일 기준선 | 완료 확인 방법 (숫자로) |
|---|---|---|---|---|
| **P0-1** | Kubernetes 기본 조작 | 없음 | 로컬 클러스터(kind)에 앱을 Deployment·Service·Ingress로 띄우고, 롤링 업데이트·롤백·HPA·readiness/liveness 프로브를 직접 설정·설명 | 이미지 교체 롤아웃 중 에러율 0% 확인, 롤백 소요 시간 측정, HPA가 부하에 맞춰 늘어나는 시간 측정 |
| **P0-2** | Terraform + state | 읽기 수준 (예선 레포에 1커밋) | 모듈 하나를 직접 작성해 plan/apply/destroy, 원격 state·lock의 의미, 모듈 output→input 연결 설명 | 로컬 프로바이더(kind·docker)로 apply·destroy를 처음부터 3회 반복, 매번 걸린 시간 기록. AWS plan은 **승인 후** |
| **P0-3** | 측정 루프 | 예선 팀의 측정 문서는 있으나 본인 역할 미확인 | k6로 부하 → Prometheus로 수집 → Grafana에서 p50/p95·에러율·리소스 사용률 읽기, PromQL 5개 정도 직접 작성 | 같은 앱에 대해 "튜닝 전/후" p95 비교표 1장 |
| **P0-4** | 설계 설명·Q&A | ADR 습관 있음 | 어떤 설계든 "목적 → 대안 2개 → 고른 이유 → 측정값 → 한계"를 3분에, 꼬리 질문 4분 대응. 핵심 스키마·다이어그램 1장을 30초 안에 보여 주기 | 매 실습마다 ADR 1개 + 3분 녹음. 예선 IR 스키마 설명 1페이지를 피드백 기준으로 다시 작성 |
| **P1-1** | GitOps 배포 파이프라인 | 없음 (예선 CD는 다른 팀원) | GitHub Actions로 이미지 빌드 → Argo CD가 매니페스트 동기화 → Argo Rollouts로 카나리 → 메트릭 기준 자동 롤백 | 카나리 중 일부러 에러를 넣어 자동 롤백이 몇 초 만에 끝나는지 측정 |
| **P1-2a** | 서버리스 on K8s | 없음 (예선에서 Lambda 프로필은 팀원 작업) | Knative Serving으로 scale-to-zero, 콜드 스타트 측정, 동시성 기반 오토스케일 설명. SpinKube(WASM)는 개념 + 1회 실행 | 콜드/웜 응답 시간, 0→N 스케일 시간 |
| **P1-2b** | 멀티 클러스터 | 없음 | kind 클러스터 2~3개 + OCM으로 Placement 규칙에 따라 워크로드 배치, 점수 기반 배치 개념 설명 | 클러스터 하나를 죽였을 때 재배치까지 걸린 시간 |
| **P1-2c** | AI 추론 서빙 | 없음 | vLLM(또는 CPU용 대체) 서버를 K8s에 띄우고 TTFT·처리량을 측정, KV 캐시·배치·라우팅이 왜 중요한지 설명, llm-d가 푸는 문제 설명 | 동시 요청 수에 따른 TTFT·토큰 처리량 그래프 |
| **P1-2d** | 장애 대응 | 예선에서 실패 진단·롤백 API 작성 경험 | Pod 강제 종료·노드 drain·네트워크 지연 주입 후 감지 → 원인 파악 → 복구, 런북 1장 | 감지까지 시간, 복구까지 시간 (MTTD/MTTR) |
| **P1-3** | 네트워크 기초 | SSL 핸드셰이크 문제를 고친 경험 1회 (#193) | VPC·서브넷·보안그룹·LB·DNS·TLS를 그림으로 설명, K8s Service/Ingress와 대응시키기 | 설명 1페이지 |
| P2 | 클라우드 고유 기능 확장 설계 (Crossplane 등) | 예선에서 IR `overrides` 설계 경험 | "DB·스토리지·고유 기능을 어떻게 확장하나"에 구조로 답하기 (Terraform 모듈 합성 vs Crossplane Composition 비교) | 비교 ADR 1개 |

## 4. 4.5주 일정안

전제 【추정】: 평일 2~3시간, 주말 하루 6시간 정도. 실제 가용 시간을 알려 주면 다시 조정한다.
전제 【사실: 프로젝트 지침】: AWS 리소스 생성·`terraform apply`(AWS)는 학습자 승인 없이 하지 않는다. 그래서 기본은 **로컬(kind, Docker)** 에서 하고, 클라우드 단계는 따로 표시한다.

| 기간 | 목표 | 산출물 (notes/에 커밋) |
|---|---|---|
| W1 10/6~10/12 | **P0-1** K8s 기본: kind 설치, 예선 샘플 앱을 Deployment·Service·Ingress로 배포, 롤링 업데이트·롤백·프로브·requests/limits. **P0-3** 시작: kube-prometheus-stack 설치, k6 부하 | 매니페스트, 롤아웃·롤백 측정표, ADR 1개 |
| W2 10/13~10/19 | **P0-2** Terraform: kind 클러스터와 그 위 리소스를 Terraform으로 생성·파괴, 모듈 분리, state 이해. **P0-3** HPA 실험으로 튜닝 전/후 p95 비교 | Terraform 모듈, p95 비교표, 3분 설명 녹음 |
| W3 10/20~10/26 | **P1-1** GitOps: Argo CD + Argo Rollouts 카나리 + 메트릭 기반 자동 롤백. **P0-4** 예선 IR 스키마 1페이지 재작성 (피드백 반영: 스키마 고안점, DB·스토리지 확장 방식, 온프레미스 다중 서비스) | 파이프라인 레포, 자동 롤백 측정값, IR 설명 1페이지 |
| 10/26 저녁 | 본선 진출 결과 메일 【사실】 | |
| W4 10/27~11/2 | **P1-2** 주제별 1회 실습: 서버리스(Knative), 멀티 클러스터(OCM), 장애 주입. 1·3번 스레드 결과에 따라 AI 추론을 넣거나 뺀다 | 주제별 측정값 1개 + ADR 1개씩 |
| 11/3~11/6 | 버퍼 + 모의 본선: 무작위 주제 1개를 골라 4시간 안에 설계 문서 + 동작 데모 + 3분 발표 + 예상 Q&A 10개 | 모의 본선 결과물 |

클라우드에서 해 보면 좋은 단계 (각각 **승인 필요**): EKS 또는 kOps로 클러스터 1회 생성·파괴, Terraform AWS plan/apply 1회. 비용 상한을 정하고 하루 안에 destroy하는 방식으로 제안할 예정.

## 5. 이번 4주에는 하지 않을 것

| 항목 | 이유 【추정】 |
|---|---|
| GCP·Azure 실계정 실습 | 비용·승인 부담 대비 효과가 작다. 멀티 클라우드는 "추상화 설계"로 답하고, 실습은 AWS + 로컬로 충분 |
| 서비스 메시(Istio 등) 깊이 | 카나리 트래픽 분할은 Argo Rollouts + Ingress로 대체 가능 |
| Go로 K8s 컨트롤러 직접 작성 | 4주 안에 언어 + 컨트롤러 패턴을 둘 다 익히기 어렵다. 컨트롤 플레인은 이미 익숙한 Java·TS로 짜고, Go는 읽기만 |
| 커널·eBPF 성능 튜닝 | 해커톤 2일 안에 보여 줄 수 있는 범위를 넘는다 |
| CKA 같은 자격증 준비 | 시험 범위가 본선 주제와 일부만 겹친다 |
