## 1. 한 줄 결론

**[추측]** 본선도 예선과 같은 Progate 운영 틀(설계 문서+라이브 데모, 슬라이드 금지, 중간보고+최종발표, 통역 있음)로 갈 가능성이 높고, 배점도 예선의 "완성도·데모 30 / 클라우드 활용 30 / 팀 개발(설계 문서화) 20 / 독창성 10 / AI 10" 구조를 크게 벗어나지 않을 것이다. 다만 채용 연결은 **팀 순위가 아니라 개인 평가**로 결정되므로, 개인이 설계 결정을 대안·트레이드오프로 설명하는 능력이 실제 승부처다.

## 2. 예선 평가 기준 (공식, 본선 추정의 기준점)

### 2.1 팀 심사 기준 100점 **[사실, S1 슬라이드 40–41]**

| 항목 | 배점 | 원문 요지 |
|---|---|---|
| 완성도·데모 | **30** | 배포 시스템이 실제로 동작하고, 로컬과 클라우드 양쪽 배포를 그 자리에서 시연할 수 있는가. 배포된 앱에 누구나 접근할 수 있는가 |
| 클라우드 활용 수준 | **30** | 환경 차이 흡수·포터빌리티가 설계에 반영됐는가. 각 클라우드 고유 기능에도 대응하는가 |
| 팀 개발 | **20** | 팀워크로 성과가 극대화됐는가. **설계가 문서화되어 대안·논의 과정·고찰과 함께** 실현 가능성을 논의하고 형태로 만들었는가 |
| 재미·독창성 | 10 | 독자적 고집 포인트(대응 환경의 폭, UX 등) |
| AI 활용 | 10 | AI 활용의 창의적 고민 |

- **[사실, S1 40]** "평가에는 최종 발표뿐 아니라 개발 중이나 중간 보고에서 얻은 정보도 포함". 즉 Notion 작업 기록과 중간보고도 채점 대상.
- **[사실, S1 20]** "배포하는 애플리케이션의 품질이 아니라, 배포하는 시스템 자체의 품질로 평가". 데모용 앱은 최소한이면 된다.
- **[사실, S1 18]** '간단한 배포'의 예시로 SQLite→적절히 설정된 RDS, 모니터링 도입·시각화, 작업 로그, 롤백·Blue-Green·Canary, 비용 대비 효과, 여러 명 동시 안전 배포를 듦. 정답이 아니라 방향 예시라고 명시.

### 2.2 개인 평가 (채용 연결의 실제 기준) **[사실, S1 42–43]**

- 선발 안내 대상자는 **팀 단위가 아니라 개인 단위**로 결정.
- 팀 심사 기준에 더해 **개인별 평가**를 하며, "팀 평가와 개인 평가가 반드시 일치하지는 않는다".
- 개인 평가 방향: **기술력, 팀워크·커뮤니케이션, 적극성 등**.
- **[사실, S1 8–9]** "스킬뿐만 아니라 '인간력'도 보고 있습니다".
- **[없음]** 개인 평가의 배점·세부 항목·평가자는 공개되지 않음.

> 주의 **[사실, S1 42 vs 43/46]**: 일본어판은 "예선→본선 통과 결과", 한국어판은 "본선에서 면접 전형으로 진출할 인원" / "특별 전형에 안내할 분"으로 번역되어 있어 의미가 다르다. 일본어판(원문으로 보임)과 2026 공고(S2: 예선 통과자 약 50명이 본선)를 함께 보면, 예선의 개인 평가는 **본선 진출자 선정**용으로 읽는 것이 맞다. **[추측]** 본선에서도 같은 방식의 개인 평가로 **면접 확약 대상**을 고를 것이다.

### 2.3 우리 팀 예선 피드백을 배점에 대응시키면 **[S4 사실 + 대응은 추측]**

| 심사위원 코멘트 (S4) | 해당 배점 항목 (추측) | 본선 시사점 (추측) |
|---|---|---|
| IR 접근이 테마에 잘 맞음. 다만 **구체적인 스키마 고안점**을 잠깐이라도 보고 싶었다 | 팀 개발(설계 문서화), 클라우드 활용 | 설계 문서에 실제 스키마/데이터 구조를 보여줘야 함. "개념"만으로는 부족 |
| DB·클라우드 스토리지·**인프라 고유 기능**까지 다루려면 어떻게 확장? | 클라우드 활용(고유 기능 대응) | 상태 있는 리소스와 벤더 고유 기능의 추상화가 질문 포인트 |
| 온프레가 **단일 이미지 pull**인 점이 아쉬움. 온프레도 IR로 여러 컨테이너 협조 배포를 | 클라우드 활용(포터빌리티), 완성도 | "모든 타깃이 같은 추상을 실제로 쓰는가"를 본다 |
| **URL 고정**으로 뒷단을 의식시키지 않은 점, 데모가 좋음 | 완성도·데모, 독창성(UX) | 데모 연출(전환이 보이지 않는 UX)이 점수가 됨 |
| 정적 분석→IR + **AI 보완** 부분은 더 확인하고 싶었다 | AI 활용 | AI가 무엇을 얼마나 정확하게 하는지 근거(검증·실측)가 필요 |
| **일본어로 발표할 수 있다는 것이 대단함** (복수 심사위원) | 개인 평가(커뮤니케이션) | 일본어 발표가 명확한 가산 인상 요인 |

## 3. 발표 형식

### 3.1 예선 형식 **[사실, S1 23–36]**

| 구분 | 형식 |
|---|---|
| Day1 중간보고 | 팀당 **7분 (보고 3분 + Q&A 최대 4분)**. 별실, 비공개. 준비 불필요, 개발 경과 자료로 "30초 시스템 설명 + 설계 개요·아키텍처도" |
| Day2 최종발표 | **5분 (설계 문서 설명 2분 + 데모 3분)**, 통역 시간 제외하고 타이머 측정, 초과 시 강제 종료 가능 |
| 발표 자료 | **슬라이드 금지.** 설계 문서 + 데모로 발표 |
| 데모 | 핵심 기능이 **모크가 아니라 실제로 동작**함을 보여줄 것. 모크가 있으면 모크라고 밝힐 것. 최종발표에서 실제 배포 장면을 보여줄 것 |
| 발표 구성 예시 | 테마(30초) → 왜 그 테마(30초) → 어필 포인트·기술(30초~1분) → 데모(어디까지 만들었나, 기술적 도전) |
| 제출물 ① (Day1 10:00) | GitHub 링크, 설계 문서·논의 메모 전체 링크, 발표용 자료 링크. **완성본을 따로 만들지 말고 작업 중 메모를 공유**, 결론뿐 아니라 **다른 안과 왜 그 구현을 택했는지** 회의록으로 남길 것 |
| 제출물 ② (Day2 13:00) | 발표 언어(한국어/일본어) + **통역용 토크 스크립트** |
| 도구 | Slack(팀 채널, Huddle의 AI 요약), Notion(모든 회의록·자료) |

Day2 일정 **[사실, S1 55]**: 개발 10:00–14:00 → 성과발표 15:00–16:30 → QA회·친목회 16:30–17:30 → 시상 17:30–18:00. Day1 중간보고 14:00–17:00. 회장은 18시에 닫힘.

### 3.2 본선 형식 추정

- **[사실, S2]** 본선은 11/7–8 서울, 예선 통과자 약 50명. 본선 킥오프는 공고마다 날짜가 다름(링커리어 "11/2 20:00", 콘테스트코리아 "10/30 20:00"). 메일 안내로 확인 필요.
- **[추측, 근거: S1·S5]** 슬라이드 금지 + 설계 문서 + 라이브 데모, 중간보고·최종발표 2회 구조는 유지될 가능성이 높다. Progate는 다른 해커톤에서도 "슬라이드 없이 데모로 발표", "완성도 중시(데모 50점)" 방식을 써 왔다(S5).
- **[추측]** 본선은 채용 직결 단계이므로 Q&A 비중이 커지고, "왜 이 설계인가, 대안은 무엇이었나"를 개인에게 묻는 질문이 늘 것이다. 근거: 예선 중간보고가 이미 Q&A 4분 > 보고 3분이었고, 개인 평가가 별도로 존재함.
- **[없음]** 본선의 발표 시간·배점·심사위원 구성·테마는 공개 자료에 없음.

## 4. 언어·통역

| 질문 | 답 | 근거 |
|---|---|---|
| 일본어 발표 필수? | **아니오.** 한국어/일본어 선택 | [사실, S1 32] "통역이 들어가므로 한국어·일본어 어느 쪽이든 괜찮다" |
| 통역 있음? | **있음. 순차 통역.** 통역사가 말할 수 있게 중간중간 끊어 말할 것 | [사실, S1 5, 30] |
| 통역 준비물 | 통역용 토크 스크립트 제출(기술 용어 정확한 번역용) | [사실, S1 28] |

| 일본어 발표가 실제로 유리? | **유리했다.** 예선 피드백에서 복수 심사위원이 일본어 발표를 따로 언급 | [사실, S4] |

**[추측]** 순차 통역이 들어가면 같은 5분 안에서도 한국어 발표는 끊어 말하는 리듬 때문에 전달 밀도가 떨어질 수 있다. 일본어 발표는 통역 없이 심사위원에게 바로 닿고, "인간력·커뮤니케이션" 개인 평가에도 유리하게 작용할 가능성이 높다. 반대로 Q&A에서 기술 질문을 일본어로 정확히 받아치지 못하면 역효과이므로, **발표는 일본어, 깊은 Q&A는 필요 시 통역 요청**이 현실적인 절충이다.

**[없음]** Q&A에서 개인이 언어를 바꿔도 되는지, 본선 통역 인원·방식은 명시되지 않음.

## 5. 팀 구성 방식

- **[사실, S2]** 지원은 팀 단위·개인 단위 모두 가능.
- **[사실, S1 1, 66]** 킥오프에서 출석을 확인한 뒤 **운영측이 최종 팀을 결정해 발표**("キックオフの出席を確認して最終チームを決定します。15分休憩後にチーム発表します"). 출석은 그 시점에 마감.
- **[사실, S1 61]** 킥오프와 개발일은 참가 필수. 결석 가능성이 있으면 참가 불가.
- **[사실, S1 69]** 킥오프 후반은 팀 MTG(자기소개, 다음 온라인 MTG 일정, 아이디어·역할 분담)에 쓰고 Notion에 기록.
- **[사실, S5]** Progate 다른 해커톤도 운영측이 팀을 배정했고, 한국 대회에서는 사전 팀과 랜덤 팀("野良チーム")이 섞여 있었다.
- **[사실, S1 42]** 본선 진출은 **개인 단위**.
- **[추측]** 본선 팀은 예선 팀을 유지하지 않고 **예선 통과자(서로 다른 팀 출신)를 운영측이 다시 섞어** 편성할 가능성이 높다. 근거: 진출이 개인 단위이고, 예선이 서울·부산 두 회차로 나뉘어 있어 기존 팀이 그대로 남기 어렵다. 따라서 **처음 만난 사람과 짧은 시간에 역할을 나누고 설계를 합의하는 능력**이 필요하다.
- **[없음]** 팀 인원 수, 팀 편성 기준(직무·언어 밸런스 등)은 공개되지 않음.

## 8. 본선 대비로 바로 쓸 수 있는 시사점 **[모두 추측]**

1. **설계 문서가 발표 자료다.** 슬라이드가 금지되므로, 처음부터 Notion 설계 문서를 "2분 안에 보여줄 수 있는 구조"(한 줄 요약 → 아키텍처도 → 핵심 스키마/결정 표)로 쓴다. 예선 피드백대로 **실제 스키마 한 조각**을 반드시 넣는다.
2. **결정 기록(ADR)을 작업 중에 남긴다.** 팀 개발 20점의 문구가 "대안·논의 과정·고찰"이고, 개발 중 기록도 채점에 들어간다. 사후 정리가 아니라 "안 A/B, 고른 이유, 버린 이유"를 그때그때 적는다.
3. **데모는 실제 동작 + 누구나 접근 가능 URL.** 30점 항목의 문구 그대로다. 고정 URL로 뒷단 전환을 숨기는 연출은 이미 호평받았으니 재사용 가치가 있다.
4. **"고유 기능·상태 있는 리소스"에 대한 답을 준비.** DB·스토리지·벤더 고유 기능을 어떻게 추상화하는지는 클라우드 활용 30점의 "각 클라우드 고유 기능 대응"과 예선 질문이 겹치는 지점이다.
5. **AI 부분은 근거와 숫자로.** "AI가 보완한다"에서 멈추지 말고 정확도·실패 사례·사람 검토 단계를 보여준다(예선 피드백).
6. **일본어로 2분 설계 설명 + 3분 데모 스크립트를 연습.** 통역용 스크립트 제출이 원래 요구되므로, 일본어 스크립트를 미리 써 두면 두 용도로 쓸 수 있다.
7. **개인 기여가 보이게.** 팀 순위와 개인 선발이 분리되어 있으므로, Notion·커밋·중간보고에서 자기 담당 결정이 드러나도록 한다.
