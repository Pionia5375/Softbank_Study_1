# 결정 기록 2026-10-06

## ADR-001 Lab 01 런타임 베이스 이미지 = `eclipse-temurin:21-jre`

- 상태: 채택 (2026-10-05 Lab 01부터 사용, 이유는 2026-10-06 기록. 작성 Claude, 리뷰 Jeong)
- 관련 파일: [labs/01-docker-basics/app/Dockerfile.multi](../labs/01-docker-basics/app/Dockerfile.multi) `ARG RUNTIME_IMAGE`

### 목적

멀티스테이지 이미지의 마지막 단계(실제로 실행되는 이미지)에 무엇을 깔지 정한다. 이 이미지가 kind, 나중엔 AWS 위에서 그대로 돈다.

### 후보와 측정

| 후보 | 베이스 크기 (압축, amd64) | 셸 | curl | HEALTHCHECK `curl -f` |
|---|---|---|---|---|
| A. `eclipse-temurin:21-jre` (Ubuntu, glibc) | 112 MB | 있음 | 있음 | 그대로 동작 (Lab 01에서 healthy 확인) |
| B. `eclipse-temurin:21-jre-alpine` (Alpine, musl) | 70 MB (A보다 -42MB) | 있음 (busybox) | 없음 【추정】 | 그대로는 unhealthy. wget 으로 바꿔야 함 |
| C. `gcr.io/distroless/java21-debian12` | 60 MB (A보다 -52MB) | 없음 | 없음 | 셸이 없어 명령 자체가 못 돈다 → unhealthy |

- 【사실】 베이스 크기는 2026-10-06 레지스트리 매니페스트 값 (Docker Hub tags API, gcr.io 매니페스트의 레이어 합). 내려받을 때의 압축 크기라 `docker images` 의 크기와는 다르다.
- 【사실】 우리 앱 이미지 A 버전 = 129.8 MB (Lab 01 `docker images`). B·C로 만든 앱 이미지 크기는 미측정.
- 셋 다 amd64, arm64 둘 다 제공한다 (매니페스트 확인).

### 고른 이유

- 얻는 것: 셸과 curl 이 있어서 Lab 01 HEALTHCHECK 가 그대로 돌고, 데모 중 문제가 나면 `docker exec` / `kubectl exec` 로 들어가 바로 확인할 수 있다. glibc 기반이라 JVM 호환 걱정이 없다.
- 왜 B·C 가 아닌가: 지금 단계는 "배우면서 자주 들여다보는" 단계다. B는 curl 이 없고 musl 이라 드물게 호환 문제가 난다 【추정】, C는 셸이 없어 안을 들여다볼 수 없다.
- 대가: 베이스가 B보다 42MB, C보다 52MB 크다. 노드가 이미지를 처음 받을 때 그만큼 더 오래 걸린다 (kind 는 `kind load` 라 영향 없음, AWS 에서 ECR pull 할 때 영향).

### 한계와 다시 볼 때

- K8s 에서는 Dockerfile HEALTHCHECK 를 안 쓰고, kubelet 이 바깥에서 HTTP 로 `/health` 를 찌른다 (httpGet probe). 그러면 이미지 안에 curl 이 필요 없어져 C(distroless)의 가장 큰 단점이 사라진다. → Lab 03 (probe) 이후 W2 CI/CD 단계에서 C로 바꿔 크기·pull 시간·취약점 수(trivy)를 재고 다시 결정한다.
- 취약점(CVE) 수는 아직 안 쟀다. 보안을 근거로 대야 하면 trivy 결과가 먼저 필요하다.
