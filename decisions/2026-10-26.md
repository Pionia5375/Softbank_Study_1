# 결정 기록 2026-10-26

## ADR-0xx 함수 scale-to-zero 도구 = Knative Serving 유지 (KubeElasti 불채택)

- 상태: 제안 (작성 Claude, 리뷰 Jeong). 근거 문서: [notes/research/09-kubeelasti-vs-knative.md](../notes/research/09-kubeelasti-vs-knative.md)
- 선택: Knative Serving (0↔N, KPA, activator) + gVisor RuntimeClass. poc/04 구성 그대로.
- 대안: KubeElasti(+KEDA/HPA+Prometheus), KEDA HTTP Add-on, 직접 구현(EndpointSlice 바꿔치기 + 큐 프록시), 둘 다 병행.
- 이유:
  - KubeElasti는 0↔1만 담당. FaaS 데모의 0→N을 위해 KEDA·Prometheus를 더 엮어야 함.
  - 【사실】 KubeElasti Resolver는 Pod Ready 확인을 sleep 폴링(Helm 기본 3초)으로 함 → 콜드 스타트에서 불리할 가능성 【추정】.
  - 【사실】 KubeElasti는 CNCF Sandbox(2026-01-03), v0.1.x, CRD v1alpha1, main 마지막 커밋 2026-08-12. Knative는 Graduated(2025-10-08).
  - Knative가 이미 PoC 04·05에 구성돼 있어 전환 비용만 큼.
- 측정값: 없음. 양쪽 콜드 스타트 미측정. KubeElasti 문서의 "200~800ms vs 300~1000ms"는 측정 조건이 없어 인용하지 않음.
- 다시 볼 조건: 본선 주제가 "기존 Deployment/Rollout에 scale-to-zero 붙여 비용 절감"이거나, Argo Rollouts 카나리와 0스케일을 한 앱에 같이 써야 할 때.
- 연결 심사 항목: 팀 개발(대안 문서화) 20, 클라우드 활용 30.
