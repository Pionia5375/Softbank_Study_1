쿠버네티스 인증서 지도

kubeadm 클러스터 한 대를 기준으로, 누가 어떤 인증서를 들고 누구와 이야기하는지, 그리고 요청 하나가 apiserver 안에서 어떤 검사를 거치는지를 그림으로 정리했다. 기준은 kubernetes.io 공식 문서이고, 경로는 kubeadm 기본값이다.

0. 인증서 기초: 세 가지만 알면 된다

쿠버네티스 컨트롤 플레인의 부품들은 모두 TLS로 이야기한다. TLS 연결에는 늘 서버와 클라이언트가 있다. 서버는 자기 인증서를 보여 주고, 클라이언트는 그 인증서가 자기가 믿는 CA가 서명한 것인지 확인한다. 쿠버네티스는 여기에 한 단계를 더해서 클라이언트도 인증서를 보여 주게 하는데, 이것을 mTLS라고 부른다. 서버는 자기가 믿는 CA 목록으로 클라이언트 인증서를 확인한다.

TLS
Transport Layer Security. 통신을 암호화하고 상대가 진짜인지 인증서로 확인하는 규약. HTTPS의 S.
CA
Certificate Authority. 다른 인증서에 서명해 "이 공개키는 이 이름의 것"이라고 보증하는 인증서와 키. 서명한 쪽을 발급자(Issuer)라고 한다.
mTLS
mutual TLS. 서버와 클라이언트가 서로 인증서를 확인하는 TLS.

그래서 각 부품의 설정에는 세 종류의 파일이 나온다. 내가 내미는 인증서(.crt), 그 인증서의 짝인 개인키(.key), 상대 인증서를 확인할 때 쓰는 CA 인증서(ca.crt)다. 옵션 이름에 cert/key가 붙으면 앞의 둘, ca나 trusted가 붙으면 마지막 것이다.

개인키
인증서 안 공개키와 짝을 이루는 비밀 키. 이걸 가진 쪽만 그 인증서의 주인 행세를 할 수 있어서 절대 밖으로 내보내지 않는다.

이 문서를 관통하는 규칙. 인증서는 그걸 쓰는 컴포넌트의 설정에 적혀 있다. apiserver가 etcd에 붙을 때 쓰는 인증서는 etcd가 아니라 apiserver의 manifest(/etc/kubernetes/manifests/kube-apiserver.yaml)에 있다. 반대로 etcd가 누구를 믿을지는 etcd의 manifest에 있다.

1. CA 세 개와 각 CA가 발급한 인증서

kubeadm은 /etc/kubernetes/pki/ 아래에 CA를 세 개 만든다. 클러스터 CA, etcd CA, front-proxy CA다. CA를 나누는 이유는 신뢰 범위를 나누기 위해서다. etcd는 etcd CA만 믿기 때문에, 클러스터 CA로 서명된 인증서(예: 관리자 인증서)를 가진 사람이라도 etcd에 직접 붙을 수 없다. 그리고 이 셋과 별개로 ServiceAccount 토큰을 서명하는 키 쌍 sa.key/sa.pub이 있다. 이건 인증서가 아니라 그냥 키 쌍이다.

ServiceAccount
파드 같은 프로그램이 apiserver를 부를 때 쓰는 계정. 사람 계정과 달리 쿠버네티스 오브젝트로 존재한다.

kubeconfig 파일들(admin.conf, scheduler.conf 등)은 /etc/kubernetes/ 바로 아래에 있고, 안에 client-certificate-data와 client-key-data가 base64로 박혀 있다. 그래서 pki/ 폴더만 보면 이 인증서들이 안 보인다. kubelet만 예외로, kubelet.conf가 /var/lib/kubelet/pki/kubelet-client-current.pem 파일을 가리키고 kubelet이 만료 전에 스스로 새 인증서를 받아 이 파일을 바꾼다.

base64
바이너리를 글자로 바꾸는 인코딩. 암호화가 아니라서 base64 -d로 바로 원래대로 돌아온다.

2. 연결마다 누가 서버고 누가 클라이언트인가

화살표는 클라이언트에서 서버 방향이다. 화살표 색은 그 연결에서 인증서를 확인하는 CA다.

6번은 처음 보면 헷갈린다. aggregation layer에서 apiserver는 사용자 요청을 확장 API 서버로 대신 전달하는 프록시 역할을 한다. 이때 "원래 요청한 사람은 누구"인지를 X-Remote-User, X-Remote-Group 헤더로 넘기는데, 확장 서버는 그 헤더를 front-proxy CA로 서명된 클라이언트 인증서(--requestheader-allowed-names=front-proxy-client)로 들어온 요청에서만 믿는다. 아무나 헤더를 붙여 사람 행세를 못 하게 하려고 CA를 따로 둔 것이다.

aggregation layer
apiserver 뒤에 별도 API 서버를 붙여 kubectl top(metrics.k8s.io) 같은 새 API를 같은 주소로 제공하는 구조.
프록시
요청을 받아서 다른 서버로 대신 보내 주는 중간 서버.

scheduler와 controller-manager는 static pod로 뜨고, 각자 manifest의 --kubeconfig 한 줄로 인증서를 받는다. 이 둘은 서버 인증서도 갖고 있지만(10259, 10257 포트의 헬스·메트릭용) kubeadm은 그걸 파일로 두지 않고 실행할 때 스스로 만든다.

static pod
apiserver를 거치지 않고 kubelet이 /etc/kubernetes/manifests/의 YAML 파일을 직접 읽어 띄우는 파드. 파일을 고치면 kubelet이 알아서 다시 띄운다.

3. 요청 하나가 거치는 길: 인증 → 인가 → 어드미션

TLS 연결이 맺어졌다고 끝이 아니다. apiserver는 요청마다 세 단계를 거친다. 인증은 "너는 누구냐"를 정하고, 인가는 "그 사람이 이 동작을 해도 되냐"를 정하고, 어드미션은 "허락된 요청이라도 내용이 규칙에 맞냐"를 보고 필요하면 고친다. 세 단계를 다 지나야 etcd에 저장된다.

kubeadm 클러스터의 apiserver manifest에는 --authorization-mode=Node,RBAC와 --enable-admission-plugins=NodeRestriction이 들어 있다. Node 인가자와 NodeRestriction은 짝이다. 하나는 kubelet이 읽을 수 있는 것을, 다른 하나는 kubelet이 고칠 수 있는 것을 자기 노드로 좁힌다. PSA는 기본으로 켜져 있어서 플래그 없이 네임스페이스 라벨만으로 쓴다.

Node 인가자
사용자명이 system:node:<노드이름>이고 그룹이 system:nodes인 요청에만 적용되는 인가 모듈. kubelet 인증서의 CN·O가 정확히 이 모양이다.
PSA
Pod Security Admission. 네임스페이스에 pod-security.kubernetes.io/enforce=baseline 같은 라벨을 달면 그 수준을 어기는 파드(예: privileged)를 거부한다. 수준은 privileged / baseline / restricted.

ServiceAccount 토큰은 어떻게 만들어지고 확인되나

그래서 ServiceAccount의 신원은 인증서가 아니라 JWT 토큰이다. 인증 단계에서 토큰이 통과하면 사용자명은 system:serviceaccount:<네임스페이스>:<이름>, 그룹은 system:serviceaccounts와 system:serviceaccounts:<네임스페이스>가 된다. 이후 인가는 사람과 똑같이 RBAC로 본다. 테넌트 격리에서 "네임스페이스마다 ServiceAccount 하나, RoleBinding은 그 네임스페이스 안에만"이 통하는 이유다.

JWT
JSON Web Token. 헤더·내용·서명 세 부분을 점으로 이은 문자열. 내용에 발급자, 대상, 만료 시각, 파드 이름이 들어 있고, 서명으로 위조를 막는다.

4. openssl로 인증서 읽기, 그리고 CN·O가 RBAC 신원이 되는 원리

인증서 파일은 PEM 형식이라 그냥 열면 알아볼 수 없다. openssl x509가 사람이 읽을 수 있게 풀어 준다.

PEM
-----BEGIN CERTIFICATE-----로 시작하는 base64 텍스트 형식. 안에 X.509라는 표준 구조의 인증서가 들어 있다.
# 전부 보기 (-noout: PEM 원문은 다시 찍지 않음)
openssl x509 -in /etc/kubernetes/pki/apiserver.crt -text -noout

# 필요한 줄만 골라 보기
openssl x509 -in <파일> -noout -subject -issuer -dates
openssl x509 -in <파일> -noout -ext subjectAltName

# kubeconfig 안에 박힌 인증서 보기 (admin.conf 예)
kubectl config view --raw -o jsonpath='{.users[0].user.client-certificate-data}' \
  | base64 -d | openssl x509 -noout -subject -issuer -dates

# kubeadm이 만든 인증서 만료일을 한 번에
kubeadm certs check-expiration

-text 출력에서 볼 곳은 다섯 군데다. 값은 일부러 비워 뒀다. 직접 찍어서 채워 봐.

Certificate:
    Data:
        ...
        Issuer: CN = <누가 서명했나 = CA의 CN>
        Validity
            Not Before: <발급 시각>
            Not After : <만료 시각>
        Subject: CN = <이 인증서의 이름>   (O = <조직> 이 붙기도 함)
        ...
        X509v3 extensions:
            X509v3 Extended Key Usage:
                TLS Web Server Authentication 또는 TLS Web Client Authentication
            X509v3 Subject Alternative Name:
                <이 서버로 접속할 때 쓸 수 있는 DNS 이름·IP 목록>

서버 인증서에서는 SAN이 중요하다. 클라이언트는 "내가 접속한 주소가 SAN 목록에 있는가"를 확인하기 때문에, apiserver를 새 IP나 도메인으로 부르려면 그 이름이 SAN에 있어야 한다. 클라이언트 인증서에서는 Subject가 중요하다.

SAN
Subject Alternative Name. 인증서가 유효한 호스트 이름과 IP 목록. 요즘 TLS 검사는 CN이 아니라 이 목록을 본다.

클라이언트 인증서로 들어온 요청에서 apiserver는 Subject의 CN을 사용자명으로, O(여러 개 가능)를 그룹으로 쓴다. 쿠버네티스에는 사람 계정을 저장하는 곳이 따로 없다. 클러스터 CA가 서명했다는 사실만으로 "CN이라는 사람, O라는 그룹 소속"으로 믿는다. 예를 들어 kubeadm v1.29부터 admin.conf의 인증서는 O = kubeadm:cluster-admins, CN = kubernetes-admin이고, kubeadm이 만든 ClusterRoleBinding kubeadm:cluster-admins가 이 그룹을 cluster-admin 역할에 묶어서 관리자가 된다. system:masters 그룹은 특별해서 RBAC를 아예 건너뛰는 슈퍼유저라, kubeadm은 그 그룹 인증서를 super-admin.conf에만 따로 둔다.

# 그룹이 어떤 역할에 묶였는지 확인
kubectl get clusterrolebinding kubeadm:cluster-admins -o yaml
# 그 신원으로 무엇을 할 수 있는지 시험
kubectl auth can-i create pods --as=jane --as-group=dev -n team-a

그래서 새 사용자를 만든다는 건, 개인키를 만들고 원하는 CN·O로 CSR을 만들어 클러스터 CA에 서명받은 뒤(CertificateSigningRequest 오브젝트를 approve), RoleBinding으로 그 CN이나 O에 권한을 주는 것이다. 인증서는 한 번 발급하면 만료 전까지 취소할 방법이 마땅치 않다는 점도 기억해 둬. 권한은 Binding을 지워서 거두고, 인증서 자체는 짧은 만료로 관리한다.

CSR
Certificate Signing Request. "이 공개키와 이 이름으로 인증서를 만들어 달라"는 요청서. 쿠버네티스에서는 controller-manager가 --cluster-signing-cert-file/key-file(클러스터 CA)로 서명한다.

5. 흔한 장애와 확인 순서

인증서 문제로 apiserver나 etcd가 죽으면 kubectl부터 안 된다(connection refused … :6443). 그래서 kubectl 대신 노드에서 컨테이너 런타임을 직접 본다. crictl이 그 도구다.

crictl
containerd 같은 CRI 런타임에 직접 묻는 CLI. 사용법은 docker 명령과 거의 같다. 노드에 docker가 없어도 쓸 수 있다.
# 1) 컨트롤 플레인 컨테이너가 떠 있나, 계속 죽고 있나 (-a: 종료된 것도)
crictl ps -a | grep -E 'kube-apiserver|etcd'
# 2) 죽은 컨테이너의 마지막 로그
crictl logs <컨테이너ID>
# 3) 컨테이너조차 안 뜨면 kubelet 쪽 로그 (manifest 문법 오류, 이미지 등)
journalctl -u kubelet --since "10 min ago" | tail -50
# 4) manifest에서 인증서 옵션만 모아 보기
grep -E 'cert|key|ca' /etc/kubernetes/manifests/kube-apiserver.yaml
# 5) 옵션이 가리키는 파일이 정말 있나
ls -l /etc/kubernetes/pki/ /etc/kubernetes/pki/etcd/
증상 (로그에 보이는 말)뜻어디를 보나

static pod manifest를 고치면 kubelet이 몇십 초 안에 컨테이너를 새로 띄운다. 고친 직후 crictl ps -a를 다시 보고 CREATED 시간이 바뀌었는지 확인해. manifest 백업을 /etc/kubernetes/manifests/ 안에 두면 kubelet이 그것도 파드로 띄우려 하니, 백업은 다른 폴더에 둔다.

정리

핵심 결정 3개 (쿠버네티스가 이렇게 설계한 이유와 대안)

  1. CA를 셋으로 나눔. 대안: CA 하나로 전부 서명. 버린 이유: 하나면 관리자 인증서로 etcd에 직접 붙어 모든 데이터를 읽을 수 있고, 아무 클라이언트 인증서로나 front-proxy 헤더를 위조할 수 있다. 대가는 관리할 CA와 옵션이 늘어나는 것.
  2. 사람 신원은 인증서 CN·O, 저장소 없음. 대안: OIDC(외부 로그인) 연동. 인증서는 설정이 단순하지만 취소가 어렵고, OIDC는 그룹 관리·회수가 쉽지만 외부 IdP가 필요하다. 본선 PoC처럼 사람 수가 적으면 인증서, 테넌트 사용자가 많아지면 OIDC.
  3. 파드 신원은 sa.key로 서명한 짧은 JWT. 대안: 예전 방식(Secret에 만료 없는 토큰). 버린 이유: 유출되면 영원히 쓰인다. projected 토큰은 만료·대상이 있고 kubelet이 갱신한다. FaaS 테넌트 격리 설계에서 "테넌트별 ServiceAccount + 네임스페이스 RoleBinding"의 근거가 된다.

셀프 연습 1개

랩 클러스터에서 그림 2의 7개 연결 중 3번(apiserver → etcd)을 골라, 클라이언트 쪽 옵션 3개와 서버 쪽 옵션 3개를 각각 manifest에서 찾아 적고, 각 파일의 Issuer를 openssl로 찍어서 "양쪽이 같은 CA를 가리키는지" 표로 채워 봐.

검증 명령과 기대 출력

ls /etc/kubernetes/pki /etc/kubernetes/pki/etcd
# 기대: ca.crt apiserver.crt apiserver-etcd-client.crt apiserver-kubelet-client.crt front-proxy-ca.crt front-proxy-client.crt sa.key sa.pub … / etcd/ 에 ca.crt server.crt peer.crt healthcheck-client.crt
openssl x509 -in /etc/kubernetes/pki/apiserver-etcd-client.crt -noout -issuer
openssl x509 -in /etc/kubernetes/pki/etcd/ca.crt -noout -subject
# 기대: 첫 줄의 issuer 와 둘째 줄의 subject 가 같은 CN (그래야 etcd가 apiserver를 믿는다)
kubectl auth can-i '*' '*' --all-namespaces
# 기대: yes (admin.conf 의 O 그룹이 cluster-admin 에 묶여 있으므로)
