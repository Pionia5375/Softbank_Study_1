점진 배포와 자동 롤백

새 버전을 사용자 일부에게만 먼저 보내고, Prometheus 지표로 "실제로 괜찮은지" 를 재서 나쁘면 사람 없이 되돌리는 구조를 설명할 수 있다. Argo Rollouts 의 카나리 단계, AnalysisRun 의 판정 알고리즘, Prometheus 가 숫자를 만드는 길, Argo CD 와 맞물릴 때 생기는 엇갈림까지 한 번에 따라간다.

이 장의 지도

이 절은 장 전체의 지도다. 무대는 쿠버네티스 클러스터다. 앱은 컨테이너로 포장되어 파드 안에서 돈다.

쿠버네티스(Kubernetes)
여러 서버(노드)를 하나로 묶어 컨테이너를 띄우고 관리하는 시스템.
클러스터
쿠버네티스가 하나로 묶어 관리하는 노드(서버)들의 묶음.
컨테이너
앱과 그 실행 환경을 한 덩어리로 포장한 프로세스.
파드(Pod)
컨테이너 하나 또는 몇 개를 한 서버에서 같이 띄우는 단위. 쿠버네티스가 다루는 가장 작은 실행 단위.

파드를 어떤 모양으로 몇 개 유지할지는 Deployment 가 선언하고, 요청은 Service 를 거쳐 파드로 가며, 이 리소스들은 namespace 로 나뉘어 놓인다. 선언은 모두 YAML 매니페스트로 적고, 적힌 "원하는 상태" 와 "실제 상태" 를 끊임없이 비교해 맞추는 일은 컨트롤러가 한다. 이 장의 Argo Rollouts 도 그런 컨트롤러 하나다.

Deployment
"이 모양의 파드를 N개 유지하라" 는 선언. 3절에서 속을 연다.
Service
파드 묶음에 고정된 주소를 주고 요청을 나눠 주는 리소스.

매니페스트(manifest)

컨트롤러(controller)
쿠버네티스 안에서 "원하는 상태" 와 "실제 상태" 를 끊임없이 비교해 맞추는 작은 프로그램.

전체 아키텍처에서 이 장이 맡는 곳은 "플랫폼 쪽 GitOps 갈래 안에서, 바뀐 버전이 클러스터에 퍼지는 방식" 이다. GitOps 의 컨트롤러가 01장의 Argo CD 다(01장 push 배포와 pull 배포). Argo CD 가 Git 의 YAML 을 클러스터에 맞춰 놓는 일까지 했다면, 이 장은 그 YAML 이 Deployment 대신 Rollout 일 때 무슨 일이 더 일어나는지를 다룬다. Rollout 은 Argo Rollouts 가 쿠버네티스에 추가하는 리소스 종류로, Deployment 와 같은 모양에 "새 버전을 어떤 단계로 퍼뜨릴지" 가 더 적혀 있다. 바뀐 파드 모양이 한 번에 100% 로 가지 않고 20% → 60% → 100% 로 퍼지는 동안 Prometheus 가 카나리 파드의 성공률을 재고, 나쁘면 Argo Rollouts 가 스스로 abort 한다. 아래 그림에서 지금 서비스 중인 버전의 파드 묶음을 stable, 시험 중인 새 버전의 묶음을 canary 라 부르고, 각 묶음은 RS 하나가 유지한다.

1. 롤링 업데이트로는 왜 부족한가

지도에서 이 장이 "일부에게 먼저 + 지표로 판정" 을 다룬다고 했다. 왜 그것이 필요한지부터 시작한다. 출발점은 쿠버네티스가 기본으로 주는 배포 방식이 무엇을 보고, 무엇을 못 보는가다.

readiness 는 "켜졌나" 를 본다, "맞게 답하나" 는 안 본다

쿠버네티스 Deployment 의 기본 배포 방식인 롤링 업데이트(RollingUpdate)는 새 파드를 몇 개 띄우고, 그 파드의 readinessProbe 가 통과하면 옛 파드를 몇 개 끄는 일을 반복한다(기본값으로는 전체의 25% 씩, 3절). 이 검사는 kubelet 이 주기적으로 컨테이너에 묻는 질문이다. 여기서 쓰는 판정 기준은 단 하나, 프로브가 통과했나 다.

readinessProbe
파드가 요청을 받을 준비가 됐는지 묻는 준비 상태 검사. 실패하면 그 파드는 Service 의 요청 대상에서 빠진다.
kubelet
각 노드에서 파드를 실제로 띄우고 지켜보는 쿠버네티스 에이전트.

프로브(probe)는 보통 /readyz 같은 가벼운 경로에 HTTP 요청을 하나 보내 2xx·3xx 가 오면 통과로 본다. 통과한 파드만 Endpoints 에 들어간다. 그런데 "앱이 켜져 있다" 와 "앱이 사용자 요청에 맞게 답한다" 는 다른 말이다. 요청 3개 중 1개에 500 을 돌려주는 버전, 특정 사용자 데이터에서만 깨지는 버전, 응답은 200 인데 내용이 틀린 버전은 모두 프로브를 대체로 통과한다. 그러면 롤링 업데이트는 끝까지 진행되어 사용자 100% 가 나쁜 버전을 만나고, 누군가 알아채고 kubectl rollout undo 를 칠 때까지 그 상태가 이어진다.

Endpoints
Service 가 요청을 보낼 파드 주소 목록. readiness 를 통과한 파드만 들어간다.
kubectl rollout undo
Deployment 를 직전 버전으로 되돌리는 명령.

그래서 필요한 것이 두 가지다.

  1. 폭발 반경(blast radius) 줄이기: 새 버전을 일부(예: 20%)에게만 먼저 보낸다. 이것이 카나리(canary)다.
  2. 판정 자동화: 그 일부에서 실제 사용자 요청의 성공률을 재서, 기준 미달이면 사람 없이 멈추고 되돌린다. 이것이 자동 분석(automated analysis)이다.

신호의 층: 무엇을 보면 "괜찮다" 고 말할 수 있나

배포의 성패를 판정할 수 있는 신호는 층이 있다. 아래로 갈수록 사용자 경험에 가깝고, 그만큼 재기 어렵다.

층신호누가 본다잡는 것못 잡는 것

liveness 프로브
컨테이너가 살아 있는지 묻는 검사. 실패하면 컨테이너를 재시작한다. readiness 는 "요청 받을 준비가 됐나" 를 묻고, 실패하면 Endpoints 에서 뺀다.
progressDeadlineSeconds

SLI(Service Level Indicator)
성공률·지연처럼 서비스 품질을 숫자로 나타낸 것.

롤링 업데이트는 1~3층만 쓴다. 이 장의 구성은 4층 신호를 배포 컨트롤러의 판정에 연결하는 것이다. 연결 고리는 세 개다. 새 버전 파드를 구분할 표지인 rollouts-pod-template-hash 라벨, 그 표지별로 요청을 세는 지표 저장소인 Prometheus, 지표를 읽고 진행·중단을 정하는 판정기인 AnalysisRun 이다.

라벨(label)
리소스에 붙이는 key=value 꼬리표. 쿠버네티스는 이것으로 리소스를 고른다.
AnalysisRun
Argo Rollouts 가 "판정 한 번" 을 기록하는 리소스. 6절.

피해 크기를 식으로: 비율 × 에러율 × 감지 시간

나쁜 버전 하나가 사용자에게 주는 피해(실패한 요청 수)는 대략 다음 곱으로 근사된다. 이 식이 이 장의 설정값, 즉 첫 setWeight, interval, failureLimit, scrape_interval 을 고르는 기준이다.

setWeight
카나리에 보낼 비율을 정하는 Rollout 의 단계. 첫 setWeight 가 첫 카나리 비율이다. 4절.
interval
분석이 지표를 재는 측정 간격. 6절.
failureLimit
불합격을 몇 번까지 허용할지. 이 수를 넘으면 분석이 실패로 끝난다. 6절.
scrape_interval
Prometheus 가 지표를 읽어 가는 주기. 8절.
피해 요청 수 ≈ 초당 요청 수 × 카나리 비율 × 나쁜 버전의 에러율 × 노출 시간
노출 시간   = 카나리 파드가 트래픽을 받기 시작 → 카나리 파드가 Endpoints 에서 빠질 때까지
            = (분석 시작 대기) + (판정 확정까지 측정 간격 × 필요한 불합격 수) + (abort 후 스케일 다운)

// 롤링 업데이트 (분석 없음)
노출 비율은 시간이 갈수록 0 → 100%, 노출 시간 = 사람이 알아챌 때까지 (상한 없음)

// 우리 02 설정을 대입 (값은 설정, 측정 아님)
카나리 비율    = 1/5 파드 = 20%
분석 시작 대기 = startingStep 1 에 도달 + initialDelay 30s
판정 확정      = 불합격 2번 (failureLimit 1 을 "넘어야" 하므로) → 첫 측정 + interval 15s × 1
에러율         = podinfo --random-error 의 설계상 약 1/3

이 식에서 보이는 손잡이는 넷이다. 비율을 줄이면(첫 단계 5%) 피해가 줄지만 같은 시간에 모이는 표본이 적어 판정이 흔들린다. 측정 간격을 줄이면 빨리 잡지만 Prometheus 가 그만큼 촘촘한 점을 가져야 한다(8·9절). 불합격 허용 수(failureLimit)를 줄이면 빨리 멈추지만 한 번 튄 값에도 멈춘다(오탐). 창 크기([1m])를 줄이면 최근 값에 민감해지지만 점이 모자라 "결과 없음" 이 늘어난다.

주의: 4층 신호로도 못 잡는 것

응답 코드는 200 인데 내용이 틀린 버그(예: 계산 결과 오류)는 2xx 비율로 못 잡는다. 이런 것은 배포 전 CI 테스트로 잡거나, 분석 단계에 Job 공급자로 스모크 테스트를 넣어 "정답과 비교" 해야 잡힌다. 08장(poc/06-fault-injection)의 대역 분석이 Job 공급자를 쓰는 예다(14절).

CI(Continuous Integration)
코드를 올릴 때마다 자동으로 돌리는 빌드·테스트.
Job 공급자
분석 공급자의 하나. 쿠버네티스 Job, 즉 "한 번 실행하고 끝나는 파드" 를 돌려 그 성공·실패로 판정한다.
스모크 테스트
핵심 기능 몇 개만 빠르게 확인하는 테스트.

증상: 배포는 "성공" 했는데 사용자 쪽 5xx 가 늘었다. 볼 곳: kubectl rollout status 는 성공, 에러는 서비스 로그·지표에만 보인다. 고치는 법: 롤링 업데이트를 유지한다면 사람이 kubectl rollout undo. 근본 해결은 판정에 4층 신호를 넣는 것(이 장 전체).

왜 이걸 골랐나 (대안)

readinessProbe 를 더 똑똑하게 만드는 방법(프로브가 실제 기능 경로를 호출)도 있다. 버린 이유: 프로브는 파드 하나 안에서 자기 자신만 보고, 실패하면 파드를 Endpoints 에서 빼 버린다. 즉 "배포를 멈추는" 게 아니라 "파드를 숨기는" 장치라서, 모든 새 파드가 같은 이유로 실패하면 서비스 전체가 비게 된다. 판정은 파드 밖(지표)에서, 버전 단위로 해야 한다.

2. 배포 전략 6가지

1절에서 "일부에게만 먼저, 지표로 판정" 이 필요하다는 것을 봤다. 그 방법을 고르기 전에, 배포 방식에는 어떤 선택지가 있고 카나리가 그중 어디에 있는지를 한 번 펼쳐 본다.

무엇을, 누구에게, 얼마나 빨리 바꾸나

배포 전략은 "옛 버전에서 새 버전으로 트래픽이 넘어가는 모양" 을 고르는 일이다. 세 가지 축으로 나눠 보면 정리된다: 동시에 두 버전이 도는가, 트래픽을 무엇으로 나누는가(파드 수, 비율, 요청 속성), 되돌리는 데 무엇이 필요한가. 이때 "무엇으로 나누나" 는 네트워크의 층으로 갈린다. 쿠버네티스 Service 는 L4 에 속해 연결 단위로만 나누고, 요청의 경로·헤더까지 보고 나누려면 L7 라우터가 따로 필요하다. 이 장에서는 그 L7 라우터를 트래픽 라우터(traffic router) 라 부른다.

L4
네트워크 4계층(전송층). TCP 연결 단위로 트래픽을 다루며, HTTP 요청의 내용은 보지 않는다.
L7
네트워크 7계층(응용층). HTTP 요청의 경로·헤더·쿠키를 읽어 요청 단위로 길을 나눌 수 있다.
재생성 (Recreate)
옛 버전을 전부 끄고 새 버전을 전부 켠다. 두 버전이 절대 같이 돌지 않는다. 그 사이 서비스가 멈춘다.
롤링 (Rolling Update)
파드를 몇 개씩 바꾼다. 중단은 없지만 판정이 프로브뿐이다. Deployment 기본값.
블루그린 (Blue-Green)
새 버전(그린)을 옆에 통째로 띄워 두고 확인한 뒤, 주소를 한 번에 그린으로 바꾼다. 주소를 바꾼다는 것은 Service 의 selector, 즉 "어떤 라벨의 파드로 요청을 보낼지" 적는 칸을 바꾸는 것이다. 되돌리기는 주소를 다시 블루로.
카나리 (Canary)
새 버전에 트래픽 일부만 보내고, 지표가 좋으면 비율을 올린다. 이 장의 선택.
A/B 테스트
요청 속성(헤더, 쿠키, 사용자 ID)으로 특정 집단만 새 버전으로 보낸다. 목적이 "안전" 보다 "비교 실험" 이다.
섀도 (Shadow, Mirroring)
실제 요청을 복사해 새 버전에도 보내되, 새 버전의 응답은 버린다. 사용자 피해 없이 실제 부하로 시험한다.

시간에 따른 새 버전 트래픽 비율

여섯 전략을 "가로축 시간, 세로축 새 버전이 받는 트래픽 비율" 로 그리면 차이가 선명해진다. 넓이(곡선 아래 면적)가 "나쁜 버전이었다면 사용자가 맞았을 에러의 양" 에 비례한다. 카나리의 핵심은 넓이를 작게 유지하면서, 판정할 만큼의 표본을 모으는 것이다.

각 전략이 기대는 쿠버네티스 부품이 다르다. 재생성·롤링은 Deployment 하나로 된다. 블루그린은 Service 의 selector 를 바꾸는 주체가 필요하다(Argo Rollouts 의 activeService/previewService). 카나리는 비율을 맞추는 주체가 필요하고, 정밀한 비율·A/B·섀도는 L7 트래픽 라우터가 필요하다. 예를 들면 Istio, Gateway API 구현체, AWS 의 ALB 같은 것들이다.

Istio
파드마다 작은 프록시를 끼워 트래픽을 다루는 서비스 메시.
Gateway API
쿠버네티스 표준 L7 라우팅 API. 이를 구현한 게이트웨이가 라우터 역할을 한다.
ALB(Application Load Balancer)
AWS 의 L7 로드밸런서.

3. Deployment 와 ReplicaSet 의 속

카나리를 고르기로 했다. 그런데 Argo Rollouts 가 하는 일은 결국 쿠버네티스 Deployment 가 하는 일을 더 잘게 쪼개고 사이에 판정을 끼운 것이다. 그래서 Deployment 가 안에서 무엇을 움직이는지를 먼저 알아야 4절의 Rollout 동작이 그대로 이해된다.

Deployment 는 ReplicaSet 을 관리하고, ReplicaSet 은 파드 개수를 관리한다

Argo Rollouts 를 이해하려면 먼저 그것이 흉내 내고 확장한 Deployment 의 구조를 알아야 한다. Rollout 도 결국 같은 부품(ReplicaSet)을 움직이기 때문이다.

  • ReplicaSet: "이 모양의 파드를 N개 유지" 만 안다. 모양은 template 에 적혀 있다. 파드가 죽으면 다시 만든다. 버전 개념이 없다. 어떤 파드가 자기 것인지는 selector 로 고른다.
  • Deployment: 파드 모양이 바뀌면 새 ReplicaSet 을 하나 더 만들고, 새 것은 늘리고 옛 것은 줄인다. 옛 ReplicaSet 은 되돌리기용으로 0개로 줄여서 revisionHistoryLimit 개까지 남겨 둔다.
  • pod-template-hash: 파드 모양의 지문. Deployment 컨트롤러가 template 을 해시해서 ReplicaSet 이름 끝과 라벨에 붙인다. 두 ReplicaSet 이 서로의 파드를 "내 것" 으로 착각하지 않게 하는 칸막이다.
template
파드 한 개의 명세. 이미지, 실행 인자, 환경변수, 프로브, 자원 요구량이 들어간다.
revisionHistoryLimit
옛 ReplicaSet 을 몇 개까지 남길지 정하는 칸. 기본 10.
해시(hash)
긴 내용을 짧은 문자열로 요약한 값. 내용이 같으면 같고, 조금이라도 다르면 거의 반드시 다르다.

롤링 업데이트의 두 손잡이: maxSurge 와 maxUnavailable

Deployment 컨트롤러는 "새 것 늘리기" 와 "옛 것 줄이기" 를 번갈아 하며 두 한도를 지킨다.

maxSurge (기본 25%)
원하는 개수(replicas)보다 최대 몇 개 더 떠 있어도 되나. 퍼센트면 올림. 새 ReplicaSet 을 늘릴 여유.
maxUnavailable (기본 25%)
원하는 개수보다 최대 몇 개 덜 준비돼 있어도 되나. 퍼센트면 내림. 옛 ReplicaSet 을 줄일 여유. 둘 다 0 이면 진행이 불가능해서 거부된다.
minReadySeconds (기본 0)
Ready 가 된 뒤 이만큼 계속 Ready 여야 "사용 가능(available)" 으로 센다.
progressDeadlineSeconds (기본 600)
이 시간 안에 진행이 없으면 조건 Progressing=False, reason ProgressDeadlineExceeded. 멈추기만 하고 되돌리지는 않는다.

해시와 스케일 계산 알고리즘

pod-template-hash 는 어떻게 만드나

함수 ComputeHash(template, collisionCount):
  h = FNV-32a 해시기                                       // 32비트 해시 함수. 보안용이 아니라 빠른 지문용
  h 에 template 전체를 결정적 순서로 출력해 넣는다   // 필드 순서가 항상 같게
  만약 collisionCount 가 있다: h 에 collisionCount 를 더 넣는다
  반환 안전 문자 인코딩(h.합계)                    // 모음·헷갈리는 글자 없는 짧은 문자열

// 성질
같은 template → 같은 해시 → 같은 ReplicaSet 을 재사용  // "되돌리기" 가 새 RS 를 안 만드는 이유
이름 충돌(다른 template 인데 같은 해시) → status.collisionCount++ 후 다시 계산

Deployment 는 이 값을 라벨 pod-template-hash 로, Argo Rollouts 는 같은 방식의 값을 라벨 rollouts-pod-template-hash 로 붙인다(키 이름이 다르다). "같은 모양 = 같은 해시" 라는 성질이 7절의 git revert 빠른 롤백, 14절의 "같은 해시로 다시 넣으면 지난 분석 결과가 재사용된다" 현상의 원인이다.

한 번의 동기화(sync)에서 하는 일

컨트롤러는 이벤트가 올 때마다(또는 주기적으로) 깨어나 "지금 상태를 원하는 상태에 맞추는 한 바퀴" 를 돈다. 이 한 바퀴를 동기화(sync) 또는 조정(reconcile)이라 한다. Deployment 컨트롤러의 한 바퀴는 다음과 같다.

함수 rolloutRolling(d):
  newRS, oldRSs = 해시로 찾기 또는 새로 만들기(d.template)
  maxSurge       = 올림(d.replicas × surge%)       // 5 × 25% = 1.25 → 2
  maxUnavailable = 내림(d.replicas × unavail%)     // 5 × 25% = 1.25 → 1

  // 1) 새 것 늘리기
  maxTotal = d.replicas + maxSurge                  // 7
  current  = 모든 RS 의 replicas 합
  만약 current < maxTotal:
      newRS.replicas += min(maxTotal - current, d.replicas - newRS.replicas)

  // 2) 옛 것 줄이기
  minAvailable = d.replicas - maxUnavailable        // 4
  먼저 옛 RS 중 준비 안 된 파드부터 정리               // 줄여도 가용성에 영향 없음
  canDrop = 전체 파드 - minAvailable - 새 RS 의 준비 안 된 파드
  만약 canDrop > 0: 옛 RS 들을 오래된 순서로 canDrop 만큼 줄임

  // 3) 상태 갱신
  만약 newRS.available == d.replicas 그리고 옛 RS 합 == 0: 완료
  만약 마지막 진행 후 progressDeadlineSeconds 경과: 조건 ProgressDeadlineExceeded
  옛 RS 를 revisionHistoryLimit 개만 남기고 삭제

여기에 "새 버전이 옳은가" 를 묻는 줄은 없다. Argo Rollouts 의 카나리는 이 루프의 1)과 2) 사이에 "단계(step)에서 멈춰 기다리기" 와 "분석 결과를 보고 되돌리기" 를 끼워 넣은 것이라고 보면 된다.

우리 PoC 에서는

왜 Deployment 를 그대로 안 쓰나 (대안)

Deployment 에 paused: true 를 걸고 사람이 조금씩 풀어 주는 "가난한 카나리" 도 가능하다. 버린 이유: 멈추는 지점이 replica 단위로 거칠고, 지표를 보고 스스로 되돌리는 장치가 없다. 판정과 되돌리기를 컨트롤러가 하려면 상태(현재 단계, abort 여부)를 저장할 리소스가 필요하고, 그게 Rollout CRD 다.

4. Argo Rollouts 의 구조

3절에서 Deployment 가 ReplicaSet 두 개를 늘리고 줄이며, 판정 기준은 프로브뿐이라는 것을 봤다. 이 절은 그 루프에 "단계에서 멈추기" 와 "판정 보고 되돌리기" 를 끼워 넣은 Argo Rollouts 의 부품을 본다.

Deployment 자리에 들어가는 Rollout, 그리고 그것을 움직이는 컨트롤러

Argo Rollouts 는 쿠버네티스에 CRD 로 새 리소스 종류를 추가하고, 그 리소스를 지켜보는 컨트롤러를 하나 띄운다. CRD 는 다섯 개다: Rollout, AnalysisTemplate, ClusterAnalysisTemplate, AnalysisRun, Experiment.

CRD(Custom Resource Definition)
쿠버네티스에 새 리소스 종류를 등록하는 선언. 등록된 종류는 API 서버와 kubectl 이 기본 리소스처럼 다룬다.
  • Rollout: Deployment 와 거의 같은 모양(replicas, selector, template)에 strategy.canary.steps 가 더해진 것.
  • 컨트롤러: API 서버에 "Rollout 이 바뀌면 알려 달라" 고 watch 로 등록해 두고, Rollout 의 template 이 바뀌면 새 ReplicaSet(canary)을 만들고, 지금 서비스 중인 것(stable)과 둘을 동시에 운영하며 steps 를 위에서부터 실행한다.
  • AnalysisRun: 컨트롤러가 AnalysisTemplate 을 틀로 찍어 내는 "판정 한 번" 의 기록. 결과가 Failed/Error 면 컨트롤러가 abort 한다.
watch
API 서버에 "이 리소스가 바뀌면 알려 달라" 고 구독하는 방식. 클라이언트가 이 구독과 캐시를 묶어 둔 것을 informer 라 부른다.

steps 실행과 비율 맞추기

Rollout 의 steps 는 spec 에 있고, 지금 몇 번째 단계인지는 status 에 있다. template 이 바뀌면 컨트롤러는 status.currentStepIndex 를 0 으로 두고 steps 를 하나씩 처리한다. 우리 steps 는 네 개다.

spec
쿠버네티스 리소스의 "원하는 상태". 사람이나 Git 이 쓴다.
status
리소스의 "관찰된 상태". 컨트롤러가 쓴다.
poc/02-rollouts/app/rollout.yaml발췌 (strategy)
strategy:
  canary:
    steps:
      - setWeight: 20          # step 0: 카나리 1개
      - pause: {duration: 60s} # step 1: 60초 지켜보기
      - setWeight: 60          # step 2: 카나리 3개
      - pause: {duration: 60s} # step 3
    analysis:                  # 백그라운드 분석
      templates:
        - templateName: success-rate
      startingStep: 1           # step 1(첫 pause)부터 시작
      args:
        - name: canary-hash
          valueFrom:
            podTemplateHashValue: Latest
  • setWeight: 20: 카나리 비율 목표 20%. 트래픽 라우터가 없으니 파드 수로 맞춘다: 5 × 20% = 1 → canary 1, stable 4. 공식 문서는 라우터 없이 파드 수로만 비율을 맞추는 이 방식을 basic canary 라 부른다.
  • pause: {duration: 60s}: 60초 대기. status.pauseConditions 에 CanaryPauseStep 이 들어가고 phase 가 Paused 가 된다. duration 을 빼면 사람이 promote 할 때까지 무한 대기.
  • setWeight: 60: 5 × 60% = 3 → canary 3, stable 2.
  • 마지막 step 이 끝나면 canary 를 100%(5개)로 올리고, status.stableRS 를 새 해시로 바꾼 뒤 옛 RS 를 0 으로. 이 순간이 "완전 승격(fully promoted)".
  • analysis + startingStep: 1: currentStepIndex 가 1 이 되는 순간 AnalysisRun 을 만들고, 승격이나 abort 까지 계속 돌린다.
  • podTemplateHashValue: Latest: 가장 새 ReplicaSet(=canary)의 rollouts-pod-template-hash 값을 인자로 넘긴다. Stable 이면 stable 해시.
phase
Rollout 전체의 상태를 한 단어로 적은 칸(status.phase). Healthy·Progressing·Paused·Degraded 중 하나. 5절.
promote
멈춰 있는 Rollout 을 다음 단계로 보내는 명령. 5절.
kube-proxy
노드마다 떠서 Service 의 가상 주소를 실제 파드 주소로 바꾸는 규칙을 관리하는 쿠버네티스 부품.
CNI(Container Network Interface)
파드 네트워크를 만드는 플러그인 규격. 이 PoC 의 CNI 는 Cilium 이고, 설정(kubeProxyReplacement=false)상 Service 처리는 kube-proxy 와 나눠 맡는다.

트래픽을 나누는 두 방법

SMI(Service Mesh Interface)
서비스 메시들의 공통 API 규격. TrafficSplit 리소스에 가중치를 적는다.

컨트롤러의 계산과 상태 필드

basic canary 의 파드 수 계산

공식 문서의 규칙: 트래픽 라우터가 없으면 마지막 setWeight 비율에 "가장 가까운 정수" 로 canary 파드 수를 맞추고, 거리가 같으면 올린다(10개에 41% → 4개). 그다음 maxSurge(기본 25%)·maxUnavailable(기본 25%)로 한 번에 움직일 수 있는 양을 제한한다. 이 두 칸은 basic canary 의 파드 수 계산에만 쓰이고, 트래픽 라우터를 쓸 때는 stable·canary 파드 수 계산에 쓰이지 않는다. 그때 maxUnavailable 은 옛 ReplicaSet 을 줄이는 속도 제한으로만 남는다.

함수 basicCanaryReplicas(rollout):
  R = spec.replicas                                  // 5
  w = 현재 단계까지의 마지막 setWeight (없으면 0)       // 20
  만약 완전 승격 상태: 반환 canary=R, stable=0
  만약 abort 상태:     w = 0
  canary 목표 = 가장 가까운 정수(R × w / 100), 동점이면 올림  // 1
  stable 목표 = R - canary 목표                          // 4
  // 전이 제한: Deployment 와 같은 surge/unavailable 규칙
  총합 ≤ R + 올림(R × maxSurge%),  사용 가능 ≥ R - 내림(R × maxUnavailable%)
  한도 안에서 canary 를 먼저 늘리고 stable 을 줄인다
  반환 canary, stable

백그라운드 분석 vs 인라인 분석

측정을 몇 번 하는지는 count 와 interval 의 조합이 정한다(6절에서 그림으로 다시 본다). count 를 비우거나 0 으로 두면 interval 이 있을 때는 끝없이 측정한다. 우리 백그라운드 분석이 이 경우라 승격이나 abort 때까지 돈다. interval 도 없으면 한 번만 측정하고 끝난다. 공식 문서의 인라인 분석 예제가 이 경우다. 공식 문서는 "step 안 분석에서 count 가 0 이면 실행되지 않는다" 고도 적어 두었다. 그리고 분석이 "중도 종료(terminate)" 되면, failureLimit 를 이미 넘은 경우가 아니면 Successful 로 끝난다(승격 때 백그라운드 분석이 그렇다).

5. Rollout 상태 기계

4절에서 Rollout 이 어떤 부품으로 단계를 밟는지 봤다. 이 절은 그 진행이 "지금 어떤 상태인가" 를 어떻게 한 단어로 표현하고, 사람이 어떤 버튼을 누를 수 있는지를 본다. 7절의 Argo CD 연동과 12절의 측정 스크립트가 모두 이 상태값을 읽는다.

네 가지 phase 와 사람이 누를 수 있는 버튼

Rollout 의 status.phase 는 네 값 중 하나다. Argo CD 도, 우리 스크립트도, 06 의 알림도 이 값을 읽는다.

Healthy
stable 이 지금 template 과 같다(완전 승격). 아무 일도 진행 중이 아니다.
Progressing
카나리 단계를 밟는 중, 또는 파드가 아직 준비되는 중.
Paused
pause step 에서 기다리는 중, 분석이 Inconclusive 라 사람 판단을 기다리는 중, 또는 수동 일시정지(spec.paused).
Degraded
abort 됐다(분석 실패, 사람이 abort), 또는 진행 기한 초과, 또는 spec 이 잘못됐다(InvalidSpec).

abort 하면 정확히 무엇이 바뀌나

abort 는 "새 버전을 버린다" 가 아니라 "이번 시도를 멈추고 stable 쪽으로 무게를 되돌린다" 다. spec(template)은 그대로라서, 컨트롤러는 계속 "원하는 template 은 v3-bad 인데 abort 상태라 0% 로 둔다" 를 유지한다.

abort 이후 Rollout 은 "Degraded 인 채로 안정" 된다. 다시 움직이게 하는 사건은 셋 중 하나다. retry 로 같은 template 을 다시 시도하거나, template 을 바꾸거나(새 해시로 새 시도, 또는 stable 해시로 되돌리기), 사람이 promote --full 을 치는 것이다. 진행 기한 초과(ProgressDeadlineExceeded)로 Degraded 가 된 경우는 abort 가 아니라서 canary 파드가 그대로 남는다. 그때도 abort 까지 하게 하려면 4절 표의 progressDeadlineAbort: true 를 켠다.

왜 abort 가 spec 을 안 바꾸나 (설계 의도)

컨트롤러가 spec 을 고치면 Git(원본)과 클러스터가 다르게 되고, Argo CD selfHeal 과 싸우게 된다. Rollouts 는 status 만 바꾸고 spec 은 사람(또는 Git)의 몫으로 남긴다. 이 분업 덕에 GitOps 와 함께 써도 서로 덮어쓰지 않는다. 대가로 "클러스터는 안전한데 Git 은 나쁜 상태" 가 남는다(7절).

함수 prometheus.Run(m):

③ 조건식 평가 (EvaluateResult)

함수 EvaluateResult(result, m):
  s = m.successCondition 있으면 식 평가(result), 오류면 반환 Error
  f = m.failureCondition 있으면 식 평가(result), 오류면 반환 Error
  경우 둘 다 없음:         반환 Successful        // 오류만 아니면 합격 (v1.10.1 소스. 공식 문서는 이 경우를 Inconclusive 예로 들지만 소스는 Successful)
  경우 성공 조건만 있음:     f = not s             // 우리 템플릿
  경우 실패 조건만 있음:     s = not f
  만약 f:                  반환 Failed
  만약 not s:              반환 Inconclusive      // 둘 다 있는데 어느 쪽도 참이 아님
  반환 Successful
// 식 언어: expr-lang (Go 용 식 평가 라이브러리). isNaN(), isInf(), len(), all(), default() 사용 가능

④ 카운터 갱신과 지표 판정

측정 결과에 따라:
  Successful   → count++, successful++,   consecutiveError = 0
  Failed       → count++, failed++,       consecutiveError = 0
  Inconclusive → count++, inconclusive++, consecutiveError = 0
  Error        → error++, consecutiveError++                 // count 는 안 늘어남

함수 지표_판정(m, r, terminating):
  만약 측정이 아직 없음: 반환 terminating ? Successful : Pending
  phase = ""
  만약 failureLimit ≥ 0 그리고 r.failed > failureLimit(기본 0):       phase = Failed
  만약 r.inconclusive > inconclusiveLimit(기본 0):                phase = Inconclusive
  만약 r.consecutiveError > consecutiveErrorLimit(기본 4):         phase = Error
  만약 phase != "": 반환 phase                // 뒤에 적힌 것이 이긴다: Error > Inconclusive > Failed
  만약 consecutiveSuccessLimit > 0 그리고 연속 합격 ≥ 그 값: 반환 Successful
  만약 count 있음 그리고 r.count ≥ count: 반환 Successful   // (consecutiveSuccessLimit 조합 규칙은 생략)
  만약 terminating: 반환 Successful                // 백그라운드 분석이 승격 때 끝나는 길
  반환 Running

AnalysisRun.phase = 모든 지표 판정 중 가장 나쁜 것
  순서(좋음 → 나쁨): Successful < Running < Pending < Inconclusive < Error < Failed

주의: Error 는 failureLimit 에 안 세어진다

Error 측정은 count 도 failed 도 안 올린다. 그래서 "나쁜 버전인데 질의가 가끔 비는" 경우 Failed 와 Error 가 섞여 판정이 늦어진다. 나쁜 podinfo 는 /metrics 응답에도 무작위 에러를 내서 긁기 점이 빠지기 때문에, 우리 템플릿은 창을 [30s] 가 아니라 [1m] 로 잡아 점이 빠져도 2개 이상 남게 했다(README 결정, 9·10절).

주의: count 와 failureLimit 를 같이 쓸 때의 검증

인라인 분석처럼 count 를 줄 때 count < failureLimit + consecutiveSuccessLimit 이면 컨트롤러가 "설정이 틀렸다" 며 AnalysisRun 을 Error 로 끝내고 Rollout 을 abort 한다. 06 README 가 대역에서 이 메시지(count (3) must be >= failureLimit + consecutiveSuccessLimit (5 + 0))를 확인했다. 설정 실수도 fail-closed 로 처리되는 예다.

7. Argo CD 와 함께 쓸 때

여기까지가 Argo Rollouts 혼자서 하는 일이다. 그런데 이 PoC 에서 Rollout 을 클러스터에 넣는 것은 사람이 아니라 01장의 Argo CD 다. 두 컨트롤러가 같은 리소스를 만질 때 무엇이 겹치고 무엇이 엇갈리는지를 본다.

Argo CD 는 "무엇을" 맞추고, Rollouts 는 "어떻게 퍼뜨릴지" 를 맡는다

두 컨트롤러는 같은 Rollout 리소스를 다른 칸에서 다룬다. Argo CD 는 Git 의 YAML(spec)과 클러스터의 spec 을 같게 만든다. Rollouts 는 그 spec 을 보고 ReplicaSet 을 움직이며 결과를 status 에 쓴다. Argo CD 는 status 를 읽어 Health 로만 보여 준다.

그래서 나쁜 배포가 abort 된 뒤에는 이상한 조합이 생긴다: Sync = Synced, Health = Degraded. Git 과 spec 은 같다(둘 다 나쁜 버전). 클러스터 파드는 안전하다(stable 100%). Argo CD 가 다시 밀어 넣을 것도 없다(이미 같으니까). 이 상태를 정리하는 정답은 Git 을 고치는 것, 즉 git revert 다.

8. Prometheus 의 속

6절의 분석은 Prometheus 에 질의해서 숫자를 받는다. 그 숫자가 어떻게 만들어지는지를 모르면 "빈 결과", "점이 모자람" 같은 15절의 사고를 이해할 수 없다. 이 절은 Prometheus 의 속을 한 번 끝까지 따라간다.

대상을 찾아, 주기적으로 긁어, 시계열로 쌓고, 질의에 답한다

Prometheus 는 pull 모델의 시계열 데이터베이스다. 앱이 지표를 보내는(push) 대신, Prometheus 가 정해진 주기(scrape_interval)마다 각 대상의 /metrics 를 HTTP 로 읽어 간다. 이 읽어 가기를 긁기(scrape)라 한다. 장점은 셋이다: 대상이 죽으면 Prometheus 가 대상마다 자동으로 만드는 up 지표가 0 이 되어 바로 드러나고, 앱은 숫자를 메모리에 들고만 있으면 되며, 수집 주기를 중앙에서 정한다.

시계열 데이터베이스
시계열(time series)은 "이름 + 라벨" 하나에 (시각, 값) 점들이 시간순으로 쌓인 것. 그런 시계열을 수십만 개 저장하고 질의하는 DB.

대상 찾기와 라벨 다듬기: kubernetes_sd + relabel

Prometheus 는 쿠버네티스 API 서버를 watch 해서 파드마다(선언된 컨테이너 포트마다) 대상 후보를 만든다. 후보에는 __meta_kubernetes_pod_* 라는 메타 라벨이 잔뜩 붙는다. 이름에 쓸 수 없는 문자(-, ., /)는 _ 로 바뀐다. 그래서 파드 라벨 rollouts-pod-template-hash 는 __meta_kubernetes_pod_label_rollouts_pod_template_hash 가 된다. 이어서 relabel 규칙이 위에서 아래로 실행되며 대상을 버리거나(keep/drop) 라벨을 고친다. __ 로 시작하는 라벨은 relabel 이 끝나면 버려진다.

prometheus-community/prometheus 차트 29.37.0 values.yaml · scrapeConfigs.kubernetes-pods차트 기본값 발췌 (레포 파일 아님)
kubernetes-pods:
  honor_labels: true
  kubernetes_sd_configs:
    - role: pod
  relabel_configs:
    - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
      action: keep
      regex: true                             # 주석 scrape: "true" 인 파드만 남김
    - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape_slow]
      action: drop                             # 느린 긁기용은 다른 job 이 담당
      regex: true
    # (scheme, path 주석 처리 생략)
    - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_port, __meta_kubernetes_pod_ip]
      action: replace
      regex: (\d+);((([0-9]+?)(\.|$)){4})
      replacement: $2:$1
      target_label: __address__                # 긁을 주소 = 파드IP:주석의 포트
    - action: labelmap
      regex: __meta_kubernetes_pod_label_(.+)   # 파드 라벨을 전부 지표 라벨로 복사
    - source_labels: [__meta_kubernetes_namespace]
      target_label: namespace
    - source_labels: [__meta_kubernetes_pod_name]
      target_label: pod
    - source_labels: [__meta_kubernetes_pod_phase]
      regex: Pending|Succeeded|Failed|Completed
      action: drop                             # 끝났거나 아직 안 뜬 파드는 안 긁음

위 발췌에서 뺀 것: IPv6 주소용 __address__ 규칙, 주석을 질의 파라미터로 바꾸는 labelmap, 마지막의 node 라벨 추가. 맨 위 honor_labels: true 는 긁어 온 지표에 대상 라벨과 같은 이름(예: namespace)이 이미 붙어 있으면 앱 쪽 값을 남기는 옵션이다. 기본값 false 면 대상 라벨이 이기고 앱 쪽 라벨은 exported_ 접두어로 밀린다. 그리고 scrape_timeout 은 scrape_interval 보다 클 수 없다(우리 5s ≤ 10s).

  • 시계열(series) = 지표 이름 + 라벨 집합. 라벨 값이 하나만 달라도 다른 시계열이다. podinfo 파드 5개 × path × status × method 만큼 http_request_duration_seconds_count 시계열이 생긴다.
  • 샘플 = (밀리초 타임스탬프, float64 값).
  • Counter: 늘기만 하는 누적값(재시작 때 0 으로 리셋). 그대로 보면 의미가 없고 rate()/increase() 로 변화량을 본다.
  • Gauge: 오르내리는 현재값(메모리, 큐 길이).
  • Histogram: 관측값을 구간별로 세는 묶음. 한 지표가 세 종류 시계열로 나온다: _bucket{le="0.005"}…(누적 구간 카운터), _sum(값 합계), _count(관측 횟수 = 요청 수). podinfo 의 http_request_duration_seconds 가 히스토그램이고, 우리는 그중 _count 만 "요청 수 카운터" 로 쓴다. 지연의 p95 를 보려면 _bucket 과 histogram_quantile() 을 쓴다(셀프 연습).
p95
95 백분위수. 요청 100개 중 느린 쪽 5개를 뺀 나머지의 최대 응답 시간.

  증가 = 마지막 값 - 첫 값
  각 인접 쌍 (a, b): 만약 b < a: 증가 += a          // 카운터 리셋(파드 재시작) 보정
  // 창 경계까지 외삽(extrapolation): 첫 점·끝 점이 경계에서 떨어진 만큼 늘림.
  // 단 간격이 평균 간격의 1.1배보다 크면 반 간격까지만 늘림. 카운터는 0 아래로 외삽하지 않음
  증가 = 외삽(증가, 첫 점 시각, 끝 점 시각, 창 경계)
  반환 증가 / W(초)                                      // 초당 평균 증가량

11. 부하 생성기

지표는 요청이 있어야 쌓인다. 실습 클러스터에는 실제 사용자가 없으므로 요청을 만드는 장치가 따로 필요하다.

분석은 "실제로 들어온 요청" 의 성공률을 본다. 요청이 없으면 판정도 없다

scripts/load.sh 는 fn-canary 안에 curl 파드 하나를 띄워 podinfo Service 에 초당 약 10개의 요청을 계속 보내는 "가짜 사용자" 다. 역할이 둘이다: 분석이 계산할 표본을 만들고, 사용자 쪽에서 본 에러 수(=롤백 효과를 재는 기준 숫자)를 로그로 남긴다.

Kourier
05장 Knative 의 인그레스 게이트웨이. 바깥에서 들어오는 요청이 지나는 문.

스크립트 한 줄씩

poc/02-rollouts/scripts/load.sh발췌
NS=${NS:-fn-canary}
URL=${URL:-http://podinfo.${NS}.svc.cluster.local/}
SLEEP=${SLEEP:-0.1}
case "${1:-}" in
  start)
    kubectl -n "$NS" delete pod load --ignore-not-found --wait=true >/dev/null
    kubectl -n "$NS" run load --image=curlimages/curl:8.23.0 --restart=Never \
      --labels=app=load --command -- sh -c \
      "while true; do c=\$(curl -s -o /dev/null -m 2 -w '%{http_code}' $URL); echo \"\$(date +%s) \$c\"; sleep $SLEEP; done"
    kubectl -n "$NS" wait --for=condition=Ready pod/load --timeout=60s ;;
  stats)
    kubectl -n "$NS" logs load | awk -v f="$FROM" -v t="$TO" '
      $1 >= f && $1 <= t { n++; if ($2 !~ /^2/) e++ }
      END { printf "requests=%d errors=%d error_pct=%.2f\n", n, e, (n ? 100*e/n : 0) }' ;;
  • --restart=Never: Deployment 가 아니라 한 번 뜨는 Pod. 로그가 한 파드에 이어 쌓인다.
  • --labels=app=load: app=podinfo 가 아니므로 Service selector 에도, 질의의 app="podinfo" 에도 안 걸린다.
  • -m 2: 2초 넘으면 포기하고 000. 타임아웃도 "2 로 시작 안 함" 이라 에러로 센다.
  • -w '%{http_code}', -o /dev/null: 본문은 버리고 상태코드만.
  • stats: awk 로 시작초·끝초 사이 줄만 세어 요청 수, 2xx 아닌 수, 비율을 낸다. measure-rollback 이 T0~T2 구간으로 부른다.
awk
텍스트를 한 줄씩 읽어 열 단위로 세고 계산하는 유닉스 도구.

설계 판단과 한계

부하 생성기의 요구:
  1. 카나리 파드에 요청이 반드시 닿을 것   → 초당 약 10 × 20% = 초당 약 2개가 카나리로 (기대값)
  2. 창 [1m] 안에 각 status 시계열이 증가할 것 → 1분에 카나리 요청 수십 개 수준
  3. 사용자 관점 에러를 분석과 독립적으로 셀 것 → Prometheus 가 아니라 클라이언트 로그
  4. 단순할 것 → 이미지 하나, 셸 한 줄

한계:
  - 직렬 요청 (동시성 1). 느린 응답이 있으면 초당 요청 수가 줄어든다
  - keep-alive(한 번 맺은 TCP 연결을 여러 요청에 재사용) 없음, 매번 새 연결 → kube-proxy/Cilium 이 연결마다 고르게 분배 → 파드 수 비율에 잘 맞음
  - 로그가 파드 안에만 있음 → 파드를 지우면 기록이 사라짐 (CSV 로 옮겨 둔다)

세 번째 요구가 중요하다. 분석이 "에러율 낮음" 이라고 해도, 그 판단이 맞았는지는 다른 눈(클라이언트)으로 확인해야 한다. 06의 프로브(probe.sh)도 같은 생각으로 만들어졌다.

주의: 연결 재사용이 있으면 비율이 틀어진다

HTTP keep-alive 를 쓰는 클라이언트(브라우저, 커넥션 풀)는 한 번 붙은 파드에 계속 요청한다. L4 Service 는 연결 단위로 나누므로, 실제 서비스에서는 파드 수 비율과 요청 비율이 어긋날 수 있다. 정확한 비율이 필요하면 L7 트래픽 라우터를 쓴다(4절 그림 2-10 의 B).

12. measure-rollback 의 논리

부하가 있고, 나쁜 버전이 있고, 분석이 있다. 이제 "얼마나 빨리 되돌리나" 를 재는 스크립트를 본다. 5절의 상태 필드, 6절의 AnalysisRun, 11절의 부하 로그가 여기서 합쳐진다.

세 개의 시각을 찍는다: 카나리 시작, abort, 카나리 0개

scripts/measure-rollback.sh N 은 나쁜 배포가 자동으로 멈추고 되돌아가기까지를 N회 잰다. 1회차는 사람이 나쁜 커밋을 push 하는 것을 기다리고, 2회차부터는 retry 로 같은 나쁜 카나리를 다시 시작한다.

15. 깨지면: 세 장면

지금까지는 "잘 될 때" 의 흐름이었다. 자동 롤백은 판정 장치가 멀쩡하다는 전제 위에 있다. 이 절은 그 전제가 깨지는 세 장면을 본다.

자동 롤백은 "분석이 맞는 곳을, 맞는 방식으로 본다" 는 전제 위에 있다

세 장면 모두 앱이 아니라 판정 장치가 고장 난 경우다. 처음 두 장면은 안전한 쪽으로, 즉 좋은 배포도 멈추는 거짓 양성으로 실패하고, 세 번째는 위험한 쪽으로, 즉 나쁜 배포가 통과하는 거짓 음성으로 실패한다.

거짓 양성(false positive)
문제가 없는데 "나쁘다" 고 판정하는 오류. 여기서는 좋은 배포가 abort 되는 것.
거짓 음성(false negative)
문제가 있는데 "괜찮다" 고 판정하는 오류. 여기서는 나쁜 배포가 승격되는 것.
장면원인AnalysisRun결과실패 방향
1. 주소 오타prometheus-svrError (연속 오류)좋은 배포도 abort안전 (fail-closed)
2. 부하 없음load 파드 없음Error (빈 결과) 또는 Failed (NaN)좋은 배포도 abort안전
3. 분석이 stable 을 봄Job 주소가 api-stableSuccessful나쁜 배포가 100%위험

장면 1: Prometheus 주소 오타 → fail-closed

02 README 4절의 실습. app/analysis-template.yaml 의 address 에서 prometheus-server 를 prometheus-svr 로 바꿔 push 한 뒤, 메시지만 바꾼 좋은 배포를 push 한다.

  • 증상: kubectl -n fn-canary get analysisrun -w 가 Running → Error. Rollout Degraded. 좋은 버전인데도.
  • 볼 곳: kubectl -n fn-canary get analysisrun <이름> -o jsonpath='{.status.message}{"\n"}' → consecutiveErrors (5) > consecutiveErrorLimit (4): … no such host. "no such host" 는 클러스터 안 DNS 인 CoreDNS 가 그 이름을 모른다는 뜻이다.
  • 고치는 법: 주소를 되돌려 push → kubectl argo rollouts retry rollout podinfo -n fn-canary.
  • fail-open 으로 바꾸려면: 조건식으로는 못 바꾼다(질의 오류는 식 평가 전에 Error). consecutiveErrorLimit 를 크게 올리면 "오래 기다렸다 결국 Error" 일 뿐이다. 진짜 fail-open 은 분석을 dryRun 으로 돌려 결과가 Rollout 에 영향을 주지 않게 하는 것이다. 데모·운영 모두 fail-closed 가 맞다: 판정을 못 하는 배포를 내보낼 이유가 없다.

장면 2: 부하 없음 → 빈 결과 또는 NaN

정리

핵심 개념 체크리스트

  • readinessProbe 는 파드가 Endpoints 에 들어갈지만 정하고, 배포의 옳고 그름은 판정하지 않는다.
  • 피해 ≈ 요청 수 × 카나리 비율 × 에러율 × 노출 시간. 설정값마다 이 식의 어느 항을 움직이는지 말할 수 있다.
  • Deployment 는 ReplicaSet 을, ReplicaSet 은 파드 개수를 관리한다. 같은 template 은 같은 해시다.
  • maxSurge 는 올림, maxUnavailable 은 내림. replicas 5 면 최대 7개, 최소 사용 가능 4개.
  • Rollout 은 stable·canary 두 ReplicaSet 을 운영하고 steps 를 실행한다. 트래픽 라우터가 없으면 파드 수로 비율을 근사한다(가장 가까운 정수, 동점 올림).
  • phase 네 가지(Healthy, Progressing, Paused, Degraded)와 promote·abort·retry·undo 의 차이(status 수정 vs spec 수정).
  • AnalysisRun 판정: failed > failureLimit → Failed, consecutiveError > consecutiveErrorLimit(기본 4) → Error, 둘 다 abort. Inconclusive → pause.
  • Error 측정은 count·failed 에 안 세고, 재시도 간격은 10초다. count 가 없으면 interval 이 있을 때 끝없이, 없을 때 한 번만 측정한다.
  • 빈 결과는 Error, 0/0 은 NaN → Failed. 질의 실패는 fail-closed.
  • abort 뒤 Argo CD 는 Synced + Degraded. git revert 는 template 을 stable 과 같게 만들어 단계 없이 Healthy.
  • Prometheus: kubernetes_sd → relabel(keep, labelmap) → 긁기 루프 → TSDB head → PromQL. 파드 라벨의 - 는 _ 로.
  • rate() 는 창 안에 점 2개 이상이 필요하다. 창 / 긁기 간격 = 점 수.
  • 06 은 같은 컨트롤러를 Job 공급자·canaryService 로 재사용하고, Prometheus 는 알림에 쓴다. 알림 규칙의 rollout_info{phase="Abort"} 는 status.phase 가 아니라 조건 reason 에서 계산된 값이다.

본선에서 떠올릴 패턴

판정과 실행의 분리

"진행할까" 를 정하는 장치(AnalysisRun)와 "움직이는" 장치(ReplicaSet 스케일)를 나눈다. 어떤 자동화든 판정 근거를 외부 지표로 두면 같은 구조가 된다: 오토스케일러, 서킷 브레이커, 배치 작업의 중단 조건.

폭발 반경 × 감지 시간

새 것을 일부에만 먼저. 기능 플래그, 테넌트 단위 점진 출시, 리전별 배포, DB 마이그레이션의 일부 샤드 먼저 — 모두 "비율 × 시간" 을 줄이는 같은 식이다.

fail-closed 기본값

판정 장치가 고장 나면 안전한 쪽으로. 인증(토큰 검증 실패 = 거부), 가드레일(정책 서버 무응답 = 차단), 07장의 MCP 5층 가드레일과 같은 생각이다.

선언과 상태의 분업

Git(spec)은 사람이, status 는 컨트롤러가 쓴다. 두 컨트롤러가 같은 칸을 쓰면 싸운다. 새 컨트롤러를 설계할 때 "누가 어느 칸의 주인인가" 를 먼저 정한다.

판정 장치도 시험한다

일부러 나쁜 버전을 넣어 abort 를 확인한다. 알림 규칙, 백업 복구, 보안 정책도 "실제로 막는지" 를 주입으로 확인해야 한다(08장).

표본이 있어야 통계가 있다

지표 기반 판정은 트래픽을 전제로 한다. 트래픽이 없는 대상(0→N 함수, 야간 배치)은 합성 요청(Job, 스모크 테스트)으로 표본을 만든다.
