GitOps와 Argo CD

git push 한 번이 어떻게 클러스터 안의 파드가 되는지, Argo CD 의 부품 일곱 개가 그 사이에서 각각 무엇을 하는지, 그리고 그 길이 끊겼을 때 어디를 보고 어떻게 고치는지를 말로 설명할 수 있게 된다. GitOps 는 "운영 상태의 정답을 Git 에 두고, 클러스터 안의 에이전트가 그 정답에 실제를 계속 맞추는 방식" 이다. 처음 보는 주제에서도 "원하는 상태를 적어 두고, 에이전트가 계속 맞춘다" 는 틀을 꺼내 쓸 수 있게 하는 것이 이 장의 목표다.

클러스터(cluster)
쿠버네티스가 하나로 묶어 관리하는 서버들.
파드(Pod)
쿠버네티스가 컨테이너를 띄우는 가장 작은 단위. 컨테이너는 프로그램과 그 실행 환경을 하나로 묶어 격리해 띄우는 단위다.
Argo CD
Git 을 읽어 클러스터를 그대로 맞추는 GitOps 도구. Argo 프로젝트의 CD, 즉 지속적 배포 부품.
에이전트(agent)
사람 대신 일하는 프로그램.
PoC 폴더 poc/01-argocd 핵심 기술 GitOps · Argo CD · Helm · App of Apps · ApplicationSet · AppProject 버전 차트 argo/argo-cd 10.10.5 = Argo CD v3.5.5

이 장의 지도

전체 PoC 는 kind 클러스터 faas 위에 플랫폼을 쌓고, 그 위에서 테넌트의 함수를 돌린다. 플랫폼은 Argo CD, Argo Rollouts(2장), Knative(5장), 테넌트 울타리(3장), 컨트롤 플레인(7장)으로 이루어진다.

kind
Kubernetes in Docker. 도커 컨테이너 하나하나를 노드로 삼아 노트북 안에 쿠버네티스 클러스터를 만드는 도구.
테넌트(tenant)
플랫폼을 나눠 쓰는 사용자 조직.
Argo Rollouts
파드를 조금씩 바꿔 가며 배포하는 점진 배포 도구.
Knative
쿠버네티스 위에서 HTTP 서비스를 요청이 없으면 0개까지 줄여 주는 서버리스 계층.
컨트롤 플레인
함수를 HTTP 로 받아 빌드하고 배포하는 우리 PoC 의 전용 API 서비스. 쿠버네티스 자체의 컨트롤 플레인(API 서버 등)과는 다른 말이다.

클러스터 안은 namespace 로 나뉘고, 각 namespace 안에 Deployment·Service 같은 리소스가 들어 있다. 이 장은 그중 플랫폼이 Git 에서 클러스터로 들어오는 길을 다룬다. 01 단계에서 세운 Argo CD 와 App of Apps(12절)는 이후 02~07 단계가 전부 그 위에 올라가는 바닥이다.

namespace(네임스페이스)
리소스를 묶어 나누는 논리적 칸막이. 그림의 fn-demo, tenant-a 같은 이름이 그것이다.

push 배포와 pull 배포

push 와 pull 은 무엇이 다른가

지금까지 실습(Lab 02~04, 07)에서는 맥에서 helm install, kubectl apply 를 직접 쳤다. kubectl 도 Helm 도 결국 API 서버에 요청을 보낸다. 클러스터 밖에서 클러스터 안으로 밀어 넣으니 push 방식이다. GitOps 는 방향을 뒤집는다. 클러스터 안에서 도는 프로그램, 즉 에이전트가 Git 을 읽어 와서 스스로 맞춘다. 그래서 pull 방식이다.

kubectl
클러스터의 API 서버에 명령을 보내는 CLI. apply 는 "이 YAML 대로 만들거나 고쳐라" 다.
Helm
쿠버네티스 YAML 묶음을 템플릿과 값으로 포장해 설치하는 패키지 도구. 그 묶음을 차트(chart)라고 부른다.
API 서버(kube-apiserver)
클러스터의 모든 리소스를 읽고 쓰는 유일한 창구. 뒤에는 그 리소스를 저장하는 키-값 DB etcd 가 있고, kubectl 도 Argo CD 도 여기에 요청한다.

달리 말하면 push 는 운영 서버에 SSH 로 들어가 실행 파일을 바꿔 끼우는 것이고, pull 은 서버 안에 "저장소의 최신 버전을 계속 보고 다르면 스스로 재배포하는 데몬" 을 두는 것이다. GitOps 는 그 데몬을 클러스터 전체에 하나 두는 모양이다.

핵심 차이는 세 가지다. (1) 정답이 어디 있나: push 는 사람의 기억과 터미널 기록, pull 은 Git. (2) 열쇠가 어디 있나: push 는 CI 나 사람이 클러스터 관리자 kubeconfig 를 가진다, pull 은 클러스터 안 에이전트만 가진다. (3) 끝나고도 지켜보나: push 는 명령이 끝나면 끝, pull 은 계속 비교한다.

CI(Continuous Integration)
빌드·테스트를 자동으로 돌리는 서버. GitHub Actions, Jenkins 등.
kubeconfig
클러스터 주소와 자격 증명이 든 파일. kubectl 이 이 파일로 접속한다.

시간 순서와 비교 축

두 방식의 동작을 시간 순서로 놓으면 차이가 더 분명하다. push 는 "한 번 실행되는 절차" 이고 pull 은 "끝나지 않는 반복" 이다. pull 쪽의 Argo CD 는 watch 로 받은 실제 상태를 메모리에 모아 두고, 주기마다 jitter 를 더해 Git 을 다시 본다.

jitter
주기에 무작위로 더하는 흔들림 시간.

pull 의 대가와 우리 PoC 의 경계

pull 이 공짜는 아니다. 세부적으로 따져야 할 대가와 경계는 다음과 같다.

  • 반영 지연: Argo CD 기본값은 120초 + 최대 60초 jitter 로 Git 을 본다. 데모 중에 push 하고 최악 3분을 기다릴 수 있다. 줄이는 법은 변경 감지 절에서 다룬다.
  • 비밀값: Git 에 Secret 평문을 넣을 수 없다. 실무에서는 Sealed Secrets, External Secrets, SOPS 같은 도구를 붙인다. 우리 PoC 의 레포는 public 이라 비밀값을 Git 에 두지 않는 구조로 짰다. Argo CD 의 admin 비밀번호는 설치 때 생긴 Secret 이고, 05 의 토큰은 클러스터 안에서 만든다.
  • 명령형 작업: 이미지 빌드, DB 마이그레이션, 일회성 Job 은 "원하는 상태" 로 표현하기 어렵다. Argo CD 는 훅(PreSync/PostSync)으로 일부를 품고, 나머지는 CI 나 별도 컨트롤러가 맡는다.
  • 부트스트랩: Argo CD 자신은 누가 까나. 결국 첫 한두 줄은 push 다 (부트스트랩 절).
  • 혼합형: 흔한 실무 모양은 "CI 가 이미지를 빌드하고 Git 의 이미지 태그만 바꾸는 커밋을 만든다 → Argo CD 가 pull" 이다. CI 는 레지스트리와 Git 쓰기 권한만 갖고 클러스터 권한은 없다.
Secret
쿠버네티스가 비밀번호·토큰을 담는 리소스. 기본은 base64 인코딩일 뿐 암호화가 아니다.
Job
한 번 돌고 끝나는 파드를 관리하는 쿠버네티스 리소스.
레지스트리(registry)
컨테이너 이미지 저장소.

우리 PoC 는 의도적으로 두 방식을 섞는다. 플랫폼(Argo CD 가 관리하는 모든 것)은 pull, 사용자 함수는 컨트롤 플레인(05)이 쿠버네티스 API 로 직접 만든다. 함수는 사용자가 HTTP 로 올리는 데이터이고 초 단위로 바뀌며, 버전 이력은 Knative Revision 과 감사 로그가 들고 있기 때문이다. 이 선택의 근거와 대가는 7장에서 자세히 본다 (7장 배포기).

Knative Revision
Knative 가 배포할 때마다 남기는, 바꿀 수 없는 스냅샷.
판단 이 변경을 GitOps 로 할까, API 직접으로 할까:
  만약 바꾸는 사람이 플랫폼 운영자이고, 변경이 드물고, 검토(PR)가 필요하다
    → Git 에 쓰고 Argo CD 가 pull   // 01~06 의 플랫폼 전부
  만약 바꾸는 주체가 최종 사용자·프로그램이고, 초 단위로 많이 바뀐다
    → 전용 API 가 검증 후 쿠버네티스 API 로 직접   // 05 컨트롤 플레인의 함수 배포
  만약 둘 다 해당하면
    → API 가 Git 에 커밋을 만들게 하고 Argo CD 가 pull   // 반영이 폴링만큼 늦어진다

우리 PoC 에서는

poc/01-argocd/README.md 1.1~1.2 절이 이 이야기를 한다. 01 단계 이후 kubectl apply 를 손으로 치는 것은 각 단계의 Application(4절) 또는 ApplicationSet(13절) 한 장씩뿐이고, 그 안의 워크로드는 전부 Argo CD 가 Git 에서 가져온다. 사용자 함수(tenant-a/hello)만 예외로 컨트롤 플레인이 직접 만든다 (poc/ANALYSIS.md 1절 "두 갈래").

Application
Argo CD 에 "이 Git 경로를 이 namespace 에 맞춰라" 라고 적는 리소스 한 장.
ApplicationSet
같은 틀로 Application 을 여러 장 찍어 내는 리소스.

깨지면 이렇게 보인다: "push 했는데 아무 일도 없다"

증상: 파일을 고쳤는데 클러스터가 그대로다. 볼 곳: kubectl -n argocd get application hello-fn -o jsonpath='{.status.sync.revision}' 와 git rev-parse origin/main 을 비교한다. 앞 명령의 -o jsonpath 는 Argo CD 가 마지막으로 적용한 커밋만 뽑는다. 같지 않으면 아직 폴링 전이거나, 애초에 push 를 안 했다. Argo CD 는 맥의 작업 폴더가 아니라 GitHub 를 읽는다. 고치는 법: push 했는지 확인 → kubectl -n argocd annotate application hello-fn argocd.argoproj.io/refresh=normal --overwrite 로 지금 다시 보게 한다. annotate 는 리소스에 어노테이션을 다는 명령이다. 이 장에서 리소스에 "주석을 단다" 고 쓴 것은 모두 이 어노테이션이다.

-o jsonpath
출력에서 원하는 필드만 뽑는 kubectl 옵션.
어노테이션(annotation)
리소스에 붙이는 키=값 메모. 라벨(label)이 리소스를 고르는 조건으로 쓰는 꼬리표라면, 어노테이션은 선택 조건이 아니라 도구가 읽는 메모다.

왜 이걸 골랐나 (대안)

OpenGitOps 4원칙

네 가지 원칙

"GitOps" 는 도구 이름이 아니라 원칙 묶음이다. CNCF 산하 OpenGitOps 프로젝트가 네 가지로 정리했다. 원문은 "GitOps 로 관리되는 시스템의 원하는 상태(desired state)는 다음을 만족해야 한다" 로 시작한다.

CNCF(Cloud Native Computing Foundation)
쿠버네티스를 맡아 관리하는 재단.
1. 선언적 (Declarative)
원하는 상태를 "어떻게" 가 아니라 "무엇" 으로 적는다. "파드를 하나 더 띄워라" 가 아니라 "replicas: 2".
2. 버전 관리·불변 (Versioned and Immutable)
원하는 상태를 바꿀 수 없고 이력이 전부 남는 저장소에 둔다. Git 커밋은 해시로 고정되어 고칠 수 없다.
3. 자동으로 끌어옴 (Pulled Automatically)
소프트웨어 에이전트가 저장소에서 원하는 상태를 스스로 가져간다. 사람이 밀어 넣지 않는다.
4. 계속 조정 (Continuously Reconciled)
에이전트가 실제 상태를 계속 관찰하고 원하는 상태를 적용하려고 시도한다.

원칙이 하나의 루프가 되는 방식

네 원칙은 하나의 루프로 이어진다. 1·2 가 "정답을 어디에 어떻게 두나", 3·4 가 "정답과 현실을 누가 어떻게 맞추나" 다.

아래 표의 부품 이름(repo-server, application-controller)은 다음 절에서 하나씩 설명한다. 여기서는 "원칙마다 맡는 부품이 따로 있다" 만 보면 된다.

원칙Argo CD 에서 맡는 것빠지면 생기는 일
1 선언적Application 의 source 가 가리키는 YAML·Helm 차트·Kustomize절차(스크립트)는 "지금 상태" 와 비교할 기준이 없다. 두 번 돌리면 결과가 달라질 수 있다
2 버전·불변targetRevision 을 커밋 SHA 로 바꿔 해석, status.sync.revision 에 기록어느 버전이 깔렸는지 모른다. 롤백 대상이 없다
3 자동 pullrepo-server(Git 읽기·렌더링), 폴링·webhook사람이 잊으면 반영이 안 된다. CI 에 클러스터 열쇠가 필요하다
4 계속 조정application-controller 의 비교 루프, automated sync, selfHeal한 번 맞춘 뒤 누가 바꾸면 끝. 드리프트가 쌓인다
Kustomize
YAML 을 템플릿 없이 덧씌우기(overlay)로 고치는 도구.
커밋 SHA
커밋 하나를 가리키는 40자리 해시 ID.

원칙의 경계와 PoC 에서 어긋나는 곳

원칙을 문자 그대로 적용하면 우리 PoC 에서 걸리는 지점이 몇 군데 있다. 심사에서 "그럼 이건 GitOps 가 아니지 않나" 라는 질문을 받을 수 있는 곳이다.

  • 브랜치는 움직이는 포인터다. targetRevision: main 은 매번 다른 커밋을 가리킨다. 원칙 2 의 "불변" 은 커밋 하나하나가 불변이라는 뜻이고, Argo CD 는 비교할 때마다 main 을 SHA 로 풀어서 status.sync.revision 에 적는다. 운영에서 더 엄격하게 하려면 태그나 SHA 를 고정한다.
  • 차트 버전 범위는 불변을 깬다. 예를 들어 targetRevision: "0.*" 처럼 범위를 적으면 Git 커밋은 그대로인데 차트 저장소에 새 0.x 차트가 올라오는 순간 다른 매니페스트가 렌더링된다. 07 의 node-termination-handler.yaml 은 처음 임시값 "0.*" 이었다가 OCI 레지스트리(oci://public.ecr.aws/aws-ec2/helm/aws-node-termination-handler)의 0.27.6 으로 고정했다.
  • 사용자 함수(05)는 원칙 2·3 을 일부러 포기한다. 함수 코드는 HTTP 로 들어오고 Git 에 커밋되지 않는다. 대신 이미지를 digest 로 고정해서 "같은 Revision 은 같은 바이트" 라는 불변성은 지킨다. 이력은 Knative Revision 과 감사 로그에 남는다.
  • Secret 과 일회성 Job은 원칙 1 로 표현하기 어렵다. 01 의 Argo CD admin 비밀번호(argocd-initial-admin-secret)는 Helm 설치 때 생기고 Git 에 없다.
digest
이미지 내용의 해시. @sha256:... 모양이라 태그와 달리 내용이 바뀌면 값도 바뀐다.

  불변       = 같은 커밋 SHA 로 렌더링하면 항상 같은 결과인가    // 버전 범위, randAlphaNum 이면 아님
  자동 pull  = R 을 바꾸는 주체가 클러스터 안 에이전트뿐인가    // 사람의 kubectl 은 드리프트
  계속 조정  = R 이 바뀌면 에이전트가 알아채고 되돌리는가      // selfHeal: true

우리 PoC 에서는

NTH(aws-node-termination-handler)
스팟 인스턴스 회수 예고를 받아 노드를 비우는 도구.

증상: Git 은 안 바뀌었는데 어느 날 Application 이 OutOfSync 가 되거나 다른 버전이 깔린다. 볼 곳: kubectl -n argocd get application <이름> -o yaml 의 spec.source.targetRevision 이 범위(0.*)나 HEAD 인지, 차트 템플릿에 randAlphaNum, now 같은 함수가 있는지. 고치는 법: 버전을 정확한 숫자로 고정하고, 무작위 값은 Secret 으로 미리 만들어 참조한다.

왜 이 원칙을 기준으로 삼나

도구(Argo CD, Flux)는 바뀌어도 원칙은 남는다. 본선에서 처음 보는 도구가 나오면 "이 도구는 원칙 3·4 를 하나?" 로 바로 분류할 수 있다. 예: Terraform 은 원칙 1·2 는 지키지만 3·4 는 사람이 apply 해야 하는 push 다 (07 단계가 Terraform 을 손으로 apply 하는 이유).

Argo CD 구조와 부품

부품 일곱 개, 한 장 그림

앞 절까지는 "무엇을 지키나" 였다. 이제 그걸 실제로 하는 소프트웨어의 안을 연다. Argo CD 는 프로그램 하나가 아니라 역할이 나뉜 부품 여러 개다. 우리 PoC 에서는 Helm 차트 argo/argo-cd 10.10.5 로 argocd namespace 에 깔고, dex 와 notifications 를 꺼서 파드 5개가 뜬다 (Deployment 4개 + StatefulSet 1개). 부품들이 주고받는 것은 Git 에서 렌더링한 매니페스트다.

StatefulSet
파드마다 고정된 번호와 이름을 주는 Deployment 의 변형.
매니페스트(manifest)
쿠버네티스 리소스 하나를 적은 YAML 문서.
gRPC
구글이 만든 바이너리 RPC 프로토콜.
redis(Redis)
메모리 키-값 저장소.

한 줄 요약: repo-server 는 "Git → YAML", application-controller 는 "YAML ↔ 클러스터", server 는 "사람 ↔ Argo CD". 이 셋만 기억하면 나머지(redis, applicationset-controller, dex, notifications)는 곁가지다. 특히 server 는 직접 배포하지 않는다. UI 의 Sync 버튼도 결국 Application 오브젝트에 "동기화 요청" 을 적을 뿐이고 실제 일은 controller 가 한다.

각 부품의 안쪽과 Sync 버튼의 흐름

각 부품이 안에서 하는 일을 조금 더 들어가 본다.

argocd-server

gRPC 와 REST 를 같은 포트로 여는 API 서버 + 웹 UI 정적 파일. 로그인(admin, SSO 토큰 발급), RBAC 검사, Git webhook 수신(/api/webhook), 저장소·클러스터 자격 증명 관리(쿠버네티스 Secret 으로 저장). 상태가 없어서 여러 개로 늘릴 수 있다.

SSO(Single Sign-On)
GitHub·Google 같은 외부 계정으로 한 번에 로그인하는 것.
RBAC(Role-Based Access Control)
역할 기반 권한 검사.

argocd-repo-server

Git 저장소를 로컬 폴더에 받아 두고(캐시), 입력(저장소 URL, 커밋, 경로, Helm values 등)을 받아 평범한 쿠버네티스 매니페스트 목록을 돌려준다. Helm, Kustomize, 평범한 YAML 폴더, 플러그인을 여기서 돌린다. 클러스터 자격 증명이 없다. 남이 만든 차트 템플릿이 여기서 실행되기 때문에 일부러 격리한 것이다.

플러그인(CMP, Config Management Plugin)
Helm·Kustomize 가 아닌 렌더링 도구를 붙이는 확장.

argocd-application-controller

쿠버네티스 컨트롤러다. Deployment 컨트롤러가 파드 수를 맞추듯, 원하는 상태와 실제를 계속 맞춘다. 관리 대상 클러스터의 리소스를 전부 watch 해서 메모리 캐시를 만들고, Application 마다 원하는 상태(repo-server 결과)와 비교해 Sync/Health 상태를 쓰고, 필요하면 sync 작업(apply, prune, 훅)을 한다. StatefulSet 인 이유는 클러스터 단위 샤딩 때문이다.

샤딩(sharding)
같은 부품의 복제본(replica)마다 맡을 클러스터를 나누는 것.

argocd-applicationset-controller

ApplicationSet 을 보고 generator(목록)를 계산해 Application 을 만들고 고치고 지운다. 워크로드에는 손대지 않는다. 만든 Application 의 실제 배포는 application-controller 몫이다. Git generator 는 기본 3분마다 다시 계산한다.

argocd-redis

캐시 전용 Redis. 렌더링된 매니페스트, 앱 리소스 트리, 클러스터 정보 등을 둔다. 공식 문서 표현으로 "언제 버려도 되는 캐시" 라서 지워져도 다시 계산할 뿐 상태를 잃지 않는다. 진짜 상태는 전부 쿠버네티스 오브젝트(Application, Secret, ConfigMap)에 있다.

ConfigMap
설정 값을 키=값으로 담는 리소스.

argocd-dex-server

GitHub·Google·LDAP 같은 외부 로그인(SSO)을 OIDC 로 바꿔 주는 중개 서버. 로컬에서는 admin 하나로 충분해서 dex.enabled: false.

OIDC(OpenID Connect)
외부 로그인 결과를 표준 토큰으로 받는 규약.

argocd-notifications-controller

Application 상태 변화를 보고 트리거·템플릿에 맞춰 Slack·메일·webhook 으로 알린다. PoC 에선 notifications.enabled: false. 06 의 알림은 Prometheus 의 Alertmanager 쪽에서 한다.

Prometheus
지표 수집기.
Alertmanager
Prometheus 의 알림 발송기.

UI 에서 Sync 버튼을 누르면 어떤 순서로 흐르는지 보면 역할 분담이 분명해진다.

kubectl 이 로컬 포트를 클러스터 안 서비스로 터널처럼 이어 주는 기능.

주의: 이 두 값은 단위가 붙은 문자열이다

공식 문서(argocd-cm.yaml)와 차트 기본값은 이 두 값을 120s, 60s 같은 Go duration 문자열(숫자 + 단위)로 적는다. 이 파일도 처음엔 120, 60 으로 단위 없이 적었다가 지금처럼 120s, 60s 로 고쳤다. 단위가 없으면 어떻게 되나: controller 는 이 값을 환경 변수 ARGOCD_RECONCILIATION_TIMEOUT 으로 받아 Go 의 duration 파서로 읽는데, 단위 없는 숫자(0 제외)는 파싱 오류라서 경고 로그를 남기고 기본값 120초로 돈다 (v3.5.5 소스 util/env 의 ParseDurationFromEnv). 파일 주석이 말하는 "차트 기본값(120s)" 이 바로 이것이다 (주석의 【추정】 표시는 소스로 확인된 셈이다). 180초는 기본 주기 120초에 jitter 최대 60초를 더한 최악 대기이지 기본 주기가 아니다. 정답본(solution/)은 60s, 0s 다. 그리고 이 값을 바꾼 뒤에는 application-controller 와 repo-server 를 재시작해야 반영된다 (kubectl -n argocd rollout restart statefulset argocd-application-controller, deploy argocd-repo-server). 두 프로그램이 시작할 때 환경 변수로 한 번 읽기 때문이다.

controller 안쪽을 의사코드로 쓰면 이렇다. 실제 구현은 argoproj/gitops-engine 라이브러리의 클러스터 캐시와 sync 엔진을 쓴다.

Application 한 장 읽기

Application 은 세 질문의 답이다

Application 은 Argo CD 가 쿠버네티스에 추가한 리소스 종류, 즉 CRD 다. apiVersion: argoproj.io/v1alpha1, kind: Application. 배포 하나의 설정을 담은 문서 한 장이고, 거기에 세 질문의 답을 적는다.

CRD(CustomResourceDefinition)
쿠버네티스에 새 리소스 종류를 등록하는 확장 기능. 등록하면 kubectl 과 API 서버가 기본 리소스처럼 다룬다.
  • project: 이 Application 이 속한 AppProject(14절)
  • source: 어느 Git 저장소의, 어느 커밋(브랜치·태그·SHA)의, 어느 폴더를 렌더링하나
  • destination: 어느 클러스터의, 어느 namespace 에 까나
  • syncPolicy: 다르면 자동으로 맞추나, 지우는 것까지 하나, 손으로 바꾼 것도 되돌리나
AppProject
Application 묶음 + 허용 범위. 어느 저장소에서 어느 namespace 로 무엇을 배포해도 되는지 적은 울타리.

spec, status, operation

쿠버네티스 오브젝트답게 Application 에는 사람이 쓰는 spec(원하는 것)과 controller 가 쓰는 status(관찰한 것)가 있고, 하나가 더 있다. operation 은 "지금 이 작업을 해라" 라는 일회성 명령 칸이다. UI 의 Sync 버튼, argocd app sync, 자동 동기화가 모두 여기에 적고, controller 가 작업을 끝내면 지우고 결과를 status.operationState 로 옮긴다.

status 필드내용언제 보나
sync.status, sync.revisionSynced / OutOfSync / Unknown, 그리고 비교에 쓴 커밋 SHA"push 한 게 반영됐나" 는 revision 을 git rev-parse 와 비교
health.statusHealthy / Progressing / Degraded / Suspended / Missing / Unknown파드가 실제로 도나
resources[]이 앱이 관리하는 리소스마다 종류·이름·sync 상태. 리소스별 health 는 v3 부터 기본적으로 여기 저장하지 않는다 (controller.resource.health.persist 기본 false. UI 의 리소스 트리나 argocd app get 으로 본다)어느 리소스가 OutOfSync 인지
operationState마지막 작업의 phase(Running/Succeeded/Failed/Error/Terminating), message, syncResultsync 실패 메시지 원문 (04 7단계가 이 칸을 읽는다)
history[]성공한 sync 기록 (기본 최근 10개, revisionHistoryLimit)언제 어느 커밋이 깔렸나
conditions[]ComparisonError, InvalidSpecError, SyncError, SharedResourceWarning 등Unknown·이상 상태의 원인
reconciledAt마지막으로 비교한 시각폴링이 도는지

조정 루프와 diff

루프 한 바퀴와 정규화

Argo CD 의 심장은 조정(reconcile) 루프다. 쿠버네티스의 Deployment 컨트롤러가 "파드 3개여야 하는데 2개네, 하나 더" 를 끝없이 반복하는 것과 같은 구조를, Git ↔ 클러스터 사이에 한 겹 더 씌웠다고 보면 된다.

여기서 가장 중요한 단어는 정규화(normalization)다. Git 의 YAML 과 클러스터에서 읽은 오브젝트는 그대로 비교하면 거의 항상 다르다. 클러스터 쪽에는 API 서버가 채운 기본값, status, metadata.managedFields, 다른 컨트롤러가 붙인 어노테이션이 있다. 그래서 양쪽을 같은 모양으로 다듬은 뒤에 비교한다.

metadata.managedFields
어느 도구가 어느 필드를 썼는지 API 서버가 기록하는 칸.

앱 하나의 비교 흐름과 3방향 비교

controller 가 앱 하나를 비교할 때의 결정 흐름이다.

비교는 리소스 단위다. 앱 안의 리소스 하나라도 다르면 앱 전체가 OutOfSync 다. 리소스별 결과는 세 종류다. (1) 양쪽에 있고 같다: Synced. (2) 양쪽에 있고 다르다: OutOfSync. (3) Git 에만 있다: OutOfSync(생성 필요). (4) 클러스터에만 있고 이 앱 소유 표시가 있다: OutOfSync + "지울 대상(requires pruning)".

위 그림의 요점: Argo CD 는 기본적으로 kubectl apply 와 같은 3방향 비교를 흉내 낸다. 그래서 다른 컨트롤러나 어드미션 웹훅이 새 필드를 더하는 것은 보통 차이가 아니지만, Git 이 적은 필드의 값을 바꾸는 것은 차이다. kubectl scale 이 OutOfSync 를 만드는 이유가 이것이다 (replicas 는 Git 이 적은 필드).

어드미션 웹훅(admission webhook)
API 서버가 리소스를 저장하기 전에 외부 서비스에 "고쳐도 되나, 바꿔 줄 것 있나" 를 묻는 장치. 값을 바꾸는 쪽을 변형(mutating) 웹훅이라 한다.

의사코드, 정규화, ignoreDifferences

조정 루프를 의사코드로 펼친다. 공식 문서의 동작 설명(Diffing, Reconcile Optimization, Resource Tracking)을 합친 것이고, 함수 이름은 설명을 위한 것이다.

함수 reconcile(app):
  // 1. 원하는 상태
  만약 needsGitRefresh(app):               // 주기 만료 / refresh 어노테이션 / spec 변경 / hard
    sha = repo.ResolveRevision(app.source.repoURL, app.source.targetRevision)
    desired = repo.GenerateManifest(app.source, sha)   // 키 (repo, sha, path, 렌더링 옵션) 로 redis 캐시
  아니면:
    sha, desired = 지난번 값
  // 2. 실제 상태
  live = clusterCache.리소스중(tracking-id 가 app 을 가리키는 것)
  // 3. 짝 맞추기: (group, kind, namespace, name) 로
  각 key ∈ desired ∪ live:
    d = normalize(desired[key])   // 기본값 채움, ignoreDifferences 적용, 알려진 변형 정리
    l = normalize(live[key])      // status, managedFields, resourceVersion, generation 등 제거
    만약 d 없음 그리고 l 있음 → OutOfSync, requiresPruning = true
    아니면 만약 l 없음        → OutOfSync (생성 필요)
    아니면 diff = threeWay(lastApplied(l), l, d)   // 또는 server-side diff
              상태 = diff 비었으면 Synced 아니면 OutOfSync
  // 4. health 는 리소스별로 판정 후 가장 나쁜 값
  app.status.health = worst(health(r) 각 r ∈ 앱의 직계 리소스)
  app.status.sync   = (모두 Synced ? Synced : OutOfSync), revision = sha
  app.status.reconciledAt = now
  // 5. 자동 동기화 판단 (자동 동기화 절)
  만약 shouldAutoSync(app): app.operation = sync(sha)

정규화가 하는 일

  • 항상 빼는 것: metadata.generation, resourceVersion, managedFields, status 대부분 (공식 문서 Reconcile Optimization, Diffing)
  • 알려진 종류별 변형 정리: 예를 들어 리소스 양(500m 와 0.5), 기본값이 채워지는 필드
  • 사용자가 지정한 무시: Application 의 spec.ignoreDifferences, 또는 argocd-cm 의 resource.customizations.ignoreDifferences.<group>_<kind> (시스템 전체)

ignoreDifferences 의 세 가지 지정 방법

아래 예시는 HPA 가 replicas 를 바꾸는 Deployment 를 가정한다 (PoC 에는 없음).

HPA(HorizontalPodAutoscaler)
부하에 따라 replicas 를 바꾸는 쿠버네티스 기본 오토스케일러.
HPA 가 replicas 를 바꾸는 Deployment 의 ignoreDifferences예시
spec:
  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers:            # RFC 6902 경로. 경로 안의 / 는 ~1 로 쓴다
        - /spec/replicas
    - group: apps
      kind: Deployment
      jqPathExpressions:       # 목록 원소를 내용으로 고를 때
        - .spec.template.spec.initContainers[] | select(.name == "injected")
    - group: "*"
      kind: "*"
      managedFieldsManagers:   # 이 관리자가 소유한 필드는 전부 무시
        - kube-controller-manager
  syncPolicy:
    syncOptions:
      - RespectIgnoreDifferences=true   # sync 할 때도 그 필드를 덮어쓰지 않음

중요한 함정: ignoreDifferences 는 기본적으로 비교에만 쓰인다. sync 가 일어나면 Git 의 값을 그대로 apply 해서 그 필드도 덮어쓴다. sync 때도 건드리지 않게 하려면 RespectIgnoreDifferences=true 를 같이 켠다 (이미 존재하는 리소스에만 효과).

비교 방식은 두 가지다. v3.5 의 기본은 위에서 본 클라이언트 측 3방향 비교(공식 문서의 Legacy)이고, Application 에 argocd.argoproj.io/compare-options: ServerSideDiff=true 를 달거나 argocd-cmd-params-cm 의 controller.diff.server.side: "true" 로 전체를 바꾸면 API 서버에 server-side apply 의 dry-run 을 보내 그 결과와 실제를 비교한다(Server-Side Diff). 후자는 v3.1 부터 정식(stable) 기능이지만 v3.5 에서도 여전히 선택 사항(opt-in)이다. 웹훅이 채우는 기본값까지 정확히 반영되는 대신 API 호출이 늘어나고, 변형 웹훅이 바꾸는 값까지 보려면 IncludeMutationWebhook=true 를 더 단다.

server-side apply(SSA)
API 서버가 필드 단위로 소유자를 기록하며 합쳐 주는 apply 방식.
dry-run
실제로 저장하지 않고 API 서버의 검증·병합만 받아 보는 시험 요청.

그리고 비교 횟수를 줄이는 장치가 있다. 리소스가 바뀔 때마다 앱 비교가 다시 도는데, 컨트롤러가 status 를 자주 고치는 리소스는 CPU 를 많이 먹는다. resource.ignoreResourceUpdatesEnabled(기본 true)와 resource.customizations.ignoreResourceUpdates.* 로 "이 필드만 바뀐 건 무시" 를 정할 수 있다. 무시는 health 가 안 바뀔 때에만 적용된다. 그리고 v3 부터는 argocd-cm 의 resource.exclusions 기본값으로 Endpoints, EndpointSlice, Lease 같은 자주 바뀌는 종류와 Cilium 의 CiliumIdentity·CiliumEndpoint·CiliumEndpointSlice 등을 아예 watch 대상에서 뺀다 (v3.0 업그레이드 문서. 바꾸거나 지울 수 있다).

Cilium
우리 클러스터의 CNI, 즉 파드 네트워크 플러그인.

우리 PoC 에서는

PoC 의 어느 Application 에도 ignoreDifferences 가 없다. HPA 를 안 쓰고, 대부분 쿠버네티스 기본 리소스라서 필요가 없었다. 스케일은 Knative autoscaler 가 Deployment 를 직접 다루는데, 그 Deployment 는 Knative 가 만든 것이라 Argo CD 추적 대상도 아니다. 05 의 함수 ksvc 는 애초에 Argo CD 가 아니라 컨트롤 플레인이 만든다.

깨지면 이렇게 보인다: sync 직후에도 OutOfSync

증상: Sync 는 Succeeded 인데 상태가 계속 OutOfSync, selfHeal 이면 몇 초마다 다시 sync 한다. 원인 후보: 변형 웹훅(mutating webhook)이나 컨트롤러가 Git 이 적은 필드를 고친다, 차트가 randAlphaNum 같은 무작위 값을 쓴다, Git 에 API 서버가 모르는 필드가 있어서 버려진다. 볼 곳: UI 의 앱 화면 → APP DIFF, 또는 argocd app diff <앱>. 고치는 법: Git 쪽을 실제 모양에 맞추거나(가장 좋음), 그 필드를 ignoreDifferences 로 빼고 필요하면 RespectIgnoreDifferences=true. 04 의 Knative Service 처럼 웹훅이 기본값을 채우는 리소스에서 이런 일이 생길 수 있다. 다만 기본(Legacy) 비교에서는 웹훅이 더한 필드는 차이로 치지 않으므로, Git 에 적은 값을 웹훅이 바꾸는 경우가 아니면 보통 Synced 로 안정된다 【확인 필요: faas-functions 가 sync 직후 Synced 로 안정되는지는 맥에서 argocd app diff faas-functions(또는 UI 의 APP DIFF)가 비어 있는지로 확정된다】.

두 축과 네 칸

  • Sync 상태: Git 과 클러스터가 같은가. Synced / OutOfSync / Unknown

왜 두 상태를 나눴나

"Git 과 같은가" 와 "잘 도는가" 는 고칠 사람과 고칠 곳이 다르기 때문이다. Synced + Degraded 는 Git(매니페스트) 쪽 버그라 개발자가 커밋으로 고치고, OutOfSync + Healthy 는 적용 경로(권한, 웹훅, 네트워크) 문제라 플랫폼 쪽이 본다. 한 칸으로 합치면 이 구분이 사라진다.

Sync 작업: 단계, 웨이브, 훅, 옵션

sync 는 순서가 있는 apply 다

sync 는 "원하는 상태를 클러스터에 적용하는 작업 한 번" 이다. 내부적으로는 kubectl apply 와 같은 동작을 리소스마다 하되, 순서를 정하고, 중간에 기다리고, 앞뒤에 훅을 끼울 수 있다.

대부분의 앱(우리 PoC 전부)은 훅도 웨이브도 안 쓴다. 그래도 순서 규칙의 맨 아래 칸(종류 순서)은 늘 작동한다. 예를 들어 05 의 platform-05 는 CreateNamespace 없이 Namespace 와 그 안의 Deployment 를 한 폴더에 두는데, Argo CD 가 Namespace 를 먼저 apply 하므로 문제가 없다.

sync 흐름, 순서 규칙, 훅

sync 작업 하나의 흐름이다.

순서 규칙(공식 문서): (1) 단계 (2) 웨이브, 작은 수 먼저, 기본 0, 음수 가능 (3) 종류: Namespace 같은 기반 리소스가 먼저, 그다음 일반 리소스, 마지막에 사용자 정의 리소스(CR) (4) 이름. 웨이브 사이 지연은 기본 2초이고 ARGOCD_SYNC_WAVE_DELAY 로 바꾼다. 다른 컨트롤러가 방금 apply 한 변경에 반응할 시간을 주고, 낡은 status 로 health 를 너무 빨리 판정하지 않으려는 장치다.

      만약 이번 이 비었음: 다음 웨이브
      정렬(이번, 종류 순서, 이름)
      각 t ∈ 이번: apply 또는 prune (prune 은 웨이브 역순으로 별도 처리)
      sleep(ARGOCD_SYNC_WAVE_DELAY = 2초)

자동 동기화, prune, selfHeal, retry

스위치 세 개

syncPolicy.automated 가 있으면 사람이 Sync 버튼을 누르지 않아도 OutOfSync 를 보면 sync 한다. 거기에 스위치 두 개가 더 붙는다.

  • 정리(prune): Git 에서 파일을 지우면 클러스터에서도 지울까. 기본은 안 지운다(안전 장치). 끄면 UI 에 "지울 대상" 표시만 하고 남겨 둔다.
  • 자동 치유(selfHeal): 누가 클러스터를 손으로 바꾸면 Git 대로 되돌릴까. 기본은 안 되돌린다. 끄면 OutOfSync 표시만 한다.
  • retry: sync 가 실패했을 때 지수 백오프로 다시 시도하는 규칙. 자동 동기화가 만든 작업은 따로 적지 않아도 기본 5회까지 재시도한다 (v3.5.5 소스 controller/appcontroller.go 가 자동 sync 의 operation 에 Retry: {Limit: 5} 를 넣는다). 백오프 기본값은 첫 대기 5초, 2배씩, 상한 3분이다 (pkg/apis/application/v1alpha1/application_defaults.go). 수동 sync 는 적지 않으면 재시도가 없다.
지수 백오프(exponential backoff)
기다리는 시간을 매번 곱해 늘리는 방식.

둘 다 켜면 "Git 과 정확히 같게" 가 보장되지만, 장애 중에 손으로 급히 고친 것도 되돌려진다. README 1절의 확인 질문이 이것이다: selfHeal: true 인데 장애 대응 중에 누가 kubectl scale --replicas=10 으로 늘리면, 몇 초 뒤 Git 의 값(2)으로 줄어든다. 사람은 늘렸다고 믿고 있는데 실제로는 줄어 있는 상태가 가장 위험하다.

자동 동기화 판단 규칙, 그리고 다시 안 하는 이유

자동 동기화가 "할지 말지" 를 정하는 규칙이다. 공식 문서의 Automated Sync Semantics 를 그대로 그림으로 옮겼다.

왜 같은 커밋에서 실패한 자동 동기화는 다시 안 하나

자동 동기화의 입력은 (커밋 SHA, 파라미터) 다. 입력이 같으면 렌더링 결과가 같고, 대부분 같은 이유로 또 실패한다. 이걸 무한히 다시 하면 API 서버와 웹훅을 계속 두드리는 뜨거운 루프(hot loop)가 된다. 그래서 Argo CD 는 재시도 한도(기본 5회, 백오프로 몇 분) 안에서만 다시 해 보고, 그 뒤에는 "이 조합은 이미 해 봤다" 를 기록해 두고 새 커밋이 오거나 사람이 직접 sync 할 때만 다시 한다. 그 상태의 앱에는 조건(conditions)에 "Failed last sync attempt to <SHA>" 가 남는다.

이 규칙이 04 7단계의 "고치기" 에 그대로 나온다. Knative 플래그를 고쳐도 Git 커밋은 그대로라서, 기본 5회 재시도가 이미 지났으면 자동으로는 다시 안 한다. 그래서 README 는 operation 칸을 직접 써서 "지금 sync" 를 요청한다.

  `kubectl -n argocd patch application faas-functions --type merge -p '{"operation":{"initiatedBy":{"username":"jeong"},"sync":{"revision":"main"}}}'`

깨지면 이렇게 보인다: 고쳤는데 계속 Failed

증상: 원인(권한, 웹훅, CRD 누락)을 고쳤는데 앱은 OutOfSync 에 마지막 작업 Failed 그대로. 이유: 같은 커밋으로 실패한 자동 동기화는 기본 재시도 5회를 다 쓴 뒤에는 다시 안 한다. 재시도 중이면 operationState.message 에 "Retrying attempt #N" 류가 보인다. 볼 곳: kubectl -n argocd get application X -o jsonpath='{.status.operationState.syncResult.revision}{" "}{.status.operationState.phase}'. 고치는 법: UI 의 SYNC 버튼, argocd app sync X, 또는 04 README 처럼 operation 칸 patch. 반복되는 문제라면 syncPolicy.retry 를 둔다.

왜 prune·selfHeal 을 둘 다 켰나 (대안)

선택: 둘 다 true. 클러스터를 지우고 다시 세우는 드릴(03·04 재생성, run-all)을 자주 하므로 "Git 과 정확히 같다" 가 가장 중요했다. 대안 (가) prune 끔: Git 에서 실수로 지운 파일이 운영 리소스를 날리는 걸 막는다. 대신 지울 것이 쌓인다. 테넌트 삭제(namespace 까지 지워짐)처럼 위험한 곳은 Prune=confirm 이 절충안이다. 대안 (나) selfHeal 끔: 장애 중 손으로 고친 것이 살아남는다. 대신 드리프트가 쌓이고 UI 에 OutOfSync 가 남는다. 대안 (다) 수동 Sync 버튼만: 데모 중 사람이 눌러야 한다.

주의: 장애 중 손으로 고칠 때

selfHeal 이 켜진 앱을 급히 손으로 고쳐야 하면 순서를 지킨다. (1) Git 에서 그 앱(root 가 있으면 root 도)의 automated 를 끄는 커밋을 push 하거나, 최소한 그 앱에 sync window 를 건다 (2) 손으로 고친다 (3) 고친 내용을 Git 에 반영한다 (4) 자동 동기화를 다시 켠다. 순서를 거꾸로 하면 고친 것이 몇 초 만에 사라진다.

엣지 케이스 몇 가지:

  • CreateNamespace 로 만든 namespace 는 추적 대상이 아니다. hello-fn 과 bye-fn 을 다 지워도 fn-demo namespace 는 남는다. 반대로 03 처럼 차트 안에 Namespace 매니페스트가 있으면 추적 대상이라 앱과 함께 지워진다 (03 의 "테넌트 삭제 = namespace 까지 지워진다").
  • root 에도 finalizer 가 있다. root 를 지우면 hello-fn, bye-fn Application 이 지워지고, 그들의 finalizer 가 다시 워크로드를 지운다. App of Apps 의 뿌리를 지우는 것은 전체를 지우는 것이다.
  • 대상이 사라졌는데 finalizer 가 남은 경우: 앱이 Terminating 에서 멈춘다. 공식 문서의 비연쇄 삭제 방법: kubectl patch app X -p '{"metadata": {"finalizers": null}}' --type merge 후 delete.
  • 두 앱이 같은 리소스를 만들면 주석이 마지막에 apply 한 앱으로 바뀌며 서로 뺏는다. 앱에 SharedResourceWarning 조건이 붙는다. FailOnSharedResource=true 로 막을 수 있다.
  • 여러 Argo CD 가 한 클러스터를 관리하면 installationID 를 서로 다르게 둔다.
  • 클러스터에만 있는 것을 차이로 치기 싫으면 리소스에 argocd.argoproj.io/compare-options: IgnoreExtraneous 를 단다 (UI 에만 보이고 OutOfSync 를 만들지 않는다).
  • 고아 리소스 찾기: AppProject 의 orphanedResources.warn: true 를 켜면 그 Project 의 namespace 안에서 어느 앱도 소유하지 않는 리소스를 UI 에 경고로 띄운다. PoC 에서는 안 썼고, 본선에서 "누가 손으로 만든 것" 을 찾을 때 쓴다.

왜 annotation 추적이 기본이 됐나

Helm 차트 상당수가 app.kubernetes.io/instance 라벨을 스스로 단다. 라벨 추적이면 Argo CD 가 같은 라벨의 남의 리소스를 자기 것으로 오해해 prune 할 수 있다. 주석은 Argo CD 만 쓰는 이름이라 충돌이 없다. v3 부터 기본값이 annotation 이다.

공식 문서

  • Resource Tracking
  • App Deletion (finalizer)
  • 쿠버네티스 Finalizers
  • 쿠버네티스 Garbage Collection (foreground/background)

Helm 차트와 YAML 폴더 렌더링

렌더링 먼저, apply 는 그다음

Argo CD 는 Git 폴더를 그대로 apply 하지 않고 먼저 렌더링한다. 폴더 모양을 보고 도구를 고른다: Chart.yaml 이 있으면 Helm, kustomization.yaml 이 있으면 Kustomize, 둘 다 없으면 YAML 파일 묶음(directory). 결과는 언제나 "평범한 쿠버네티스 매니페스트 목록" 이다.

가장 중요한 사실: Argo CD 는 helm install 이 아니라 helm template 만 쓴다. Helm 은 YAML 을 찍어 내는 틀로만 쓰이고, 설치·업그레이드·삭제(생명주기)는 Argo CD 가 맡는다. 그래서 Argo CD 로 깐 앱은 helm list 에 안 보이고, Helm 의 release Secret 도 없다. 반면 Argo CD 자신은 맥에서 helm install 로 깔았으므로 helm list -n argocd 에 보인다. 두 방식이 한 클러스터에 같이 있다.

Helm 값 합치기, directory 옵션, 도구 판별

Helm: 값이 어떻게 합쳐지나

helm template 과 helm install 의 차이에서 오는 동작 차이:

  • .Release.Name 은 기본으로 Application 이름이다 (helm.releaseName 으로 바꿀 수 있다). hello-fn 차트가 모든 이름을 {{ .Release.Name }} 으로 지어서, 같은 차트를 bye-fn·tenant-a-hello 로 재사용해도 이름이 안 겹친다.
  • .Release.Namespace 는 destination.namespace 다.
  • valuesObject 와 values 를 같이 적으면 valuesObject 만 쓰이고 values 는 무시된다 (공식 문서 Helm Value Precedence).
  • 클러스터에 묻는 lookup 함수는 렌더링 때 클러스터가 없으므로 빈 값을 돌려준다. repo-server 에 클러스터 열쇠가 없다는 앞 절의 설계와 같은 이야기다.
  • .Capabilities(API 버전, 쿠버네티스 버전)는 대상 클러스터 정보를 Argo CD 가 넘겨 준다.
  • Helm 훅은 Argo CD 훅으로 바뀐다 (sync 절의 표). 설치와 업그레이드를 구분하지 못한다.

directory: 평범한 YAML 폴더

  • 기본은 그 폴더 바로 아래 파일만 읽는다. 하위 폴더까지 읽으려면 directory.recurse: true (05 platform-05).
  • directory.exclude, include 는 glob 패턴이다. 여러 개면 {a.yaml,b.yaml} (06 fault-defenses). 파일 하나만 빼려면 그 파일 첫 줄에 # +argocd:skip-file-rendering 주석을 둘 수도 있다.
  • YAML 폴더에는 쿠버네티스 리소스만 있어야 한다. 리소스가 아닌 YAML(패치 조각, values 파일)이 섞이면 렌더링이 실패한다. 06 이 exclude 를 쓴 이유다.
  • directory 를 명시했는데 폴더 안에 Helm·Kustomize 파일이 있으면 실패한다.
glob 패턴
*, {a,b} 같은 파일 이름 패턴.

AppProject 와 Argo CD RBAC

Application 의 울타리

AppProject 는 Application 묶음 + 허용 범위다. "이 Project 의 Application 은 어느 저장소에서 가져와(sourceRepos), 어느 클러스터·namespace 에(destinations), 어떤 종류의 리소스를(whitelist/blacklist) 배포할 수 있나" 를 적는다. 03 의 울타리 6겹(Namespace, ResourceQuota, LimitRange, NetworkPolicy, 쿠버네티스 RBAC, 그리고 AppProject) 중 마지막 겹이 이것이다 (3장 AppProject).

NetworkPolicy
파드 사이 통신 허용 규칙.

default Project 는 자동으로 생기고 지울 수 없으며, 처음에는 "아무 저장소, 아무 목적지, 아무 종류" 를 허용한다. PoC 의 플랫폼 Application 은 전부 default 다. 테넌트가 쓰는 Application 만 테넌트 Project 에 넣었다.

검사 순서, 비대칭 목록, 권한 층 넷

controller 는 Application 을 비교·sync 할 때마다 Project 규칙을 검사한다.

종류 제한의 비대칭에 주의한다 (공식 문서): namespace 범위 리소스는 거부 목록(blacklist), 클러스터 범위 리소스는 허용 목록(whitelist)으로 다룬다. 그래서 03 의 clusterResourceWhitelist: [] 는 "클러스터 범위는 하나도 안 됨" (Namespace, ClusterRole, CRD 생성 금지)이고, namespaceResourceBlacklist 는 "이것들만 빼고 namespace 안의 것은 다 됨" 이다. 반대로 namespaceResourceWhitelist 를 쓰면 "이것들만 됨" 으로 바뀌고, 둘 다 적으면 "whitelist 에 있으면서 blacklist 에 없는 종류" 만 된다 (Namespace 는 클러스터 범위라 ClusterRole 과 함께 whitelist 쪽이다).

ClusterRole
클러스터 전체에 걸친 권한 정의.

Argo CD RBAC 은 사람(또는 토큰)이 Argo CD API 로 무엇을 할 수 있나를 정한다. Casbin 문법이고 argocd-rbac-cm 의 policy.csv 에 적는다. 기본 역할은 role:readonly, role:admin 둘이고, 로그인한 사람은 최소 policy.default 의 권한을 받는다 (deny 로도 못 막는다). 사용자는 두 길로 만든다: argocd-cm 의 accounts.<이름> 으로 로컬 계정(비밀번호 로그인이나 API 키 발급)을 두거나, 조직 로그인을 SSO(dex 또는 OIDC 제공자 직접 연결)로 붙인다. 공식 문서는 로컬 계정을 소수의 관리자·CI 용으로, 사람이 많으면 SSO 를 권한다. PoC 는 dex 를 끄고 admin 하나만 쓴다.

Casbin
접근 제어 규칙 라이브러리.

왜 울타리와 함수를 다른 Project 로 나눴나 (대안)

대안: 한 Project 에 울타리와 함수를 같이 두기. 그러면 테넌트가 자기 Application 으로 Quota 나 NetworkPolicy 를 지우거나 바꿀 수 있다. Project 를 나누면 "울타리는 플랫폼만, 함수는 테넌트" 가 Argo CD 수준에서 강제된다. 대가는 Application 이 테넌트당 둘(울타리, 함수)로 늘어난다는 것이다.

주의: AppProject 는 controller 의 자기 규칙이다

controller 의 ServiceAccount 는 차트 10.10.5 기본값(createClusterRoles: true, controller.clusterRoleRules.enabled: false)에서 apiGroups·resources·verbs 가 전부 * 인 ClusterRole 을 받는다. 즉 클러스터 전체 권한이다. AppProject 는 "controller 가 스스로 안 하기로 한 것" 이지 쿠버네티스가 막는 벽이 아니다. 더 강하게 하려면 Project 의 destinationServiceAccounts 기능을 쓴다. v3.5 에서 베타이고 기본은 꺼져 있다: argocd-cm 의 application.sync.impersonation.enabled: "true" 로 켜야 하며 차트 10.10.5 기본값은 false 다. 그리고 argocd namespace 에 배포할 수 있는 Project 는 사실상 관리자다 (Application 을 새로 만들 수 있으므로).

클러스터 등록과 destination

Argo CD 는 자기가 사는 클러스터(in-cluster, https://kubernetes.default.svc) 말고 다른 클러스터에도 배포할 수 있다. 다른 클러스터를 등록하면 그 주소와 자격 증명이 argocd namespace 의 Secret(라벨 argocd.argoproj.io/secret-type: cluster)으로 저장되고, Application 의 destination.server 나 destination.name 으로 고른다.

드리프트, 롤백, 깨뜨려 보기

드리프트 두 방향, 롤백은 revert

드리프트(drift) 는 Git 과 클러스터가 어긋난 상태다. 어긋나는 방향이 둘이고, 고치는 길도 둘이다.

GitOps 의 롤백은 git revert 다. Argo CD 에도 "이전 sync 이력으로 되돌리기(rollback)" 버튼이 있지만, 자동 동기화가 켜진 앱에서는 쓸 수 없다. 되돌려도 다음 비교에서 Git(=나쁜 커밋)으로 다시 맞추기 때문이다. 그래서 Git 쪽을 되돌리는 것이 유일하게 일관된 방법이다.

부트스트랩 문제

Argo CD 는 누가 까나

닭과 달걀 문제다. GitOps 는 "클러스터 안의 에이전트가 Git 을 pull 한다" 인데, 그 에이전트(Argo CD)는 누가 까나. 답: 처음 몇 줄은 push 로 한다. Helm 으로 Argo CD 를 깔고, root Application 하나를 kubectl apply 한다. 그다음부터는 Git 이 정답이다.

정리

핵심 개념 체크리스트

  • push 와 pull 의 차이를 열쇠 위치, 드리프트 감지, 감사 기록 세 축으로 말할 수 있다
  • OpenGitOps 4원칙(선언적, 버전·불변, 자동 pull, 계속 조정)과 각각을 맡는 Argo CD 부품을 짝지을 수 있다
  • repo-server 는 Git → YAML, application-controller 는 YAML ↔ 클러스터, server 는 사람 ↔ Argo CD 라고 한 줄로 말할 수 있다
  • repo-server 에 클러스터 열쇠가 없는 이유(남의 차트 템플릿이 실행되는 곳)를 안다
  • Application 의 source / destination / syncPolicy, 그리고 spec / status / operation 을 구분한다
  • 정규화와 3방향 비교 때문에 "다른 컨트롤러가 더한 필드" 는 차이가 아니고 "Git 이 적은 필드의 값 변경" 은 차이라는 것을 안다
  • ignoreDifferences 는 기본적으로 비교에만 쓰이고, sync 때도 지키려면 RespectIgnoreDifferences 가 필요하다
  • Sync 상태, Health 상태, 작업(operation) 상태 셋을 구분하고, 네 조합별로 고칠 곳을 안다
  • App of Apps 에서 root 의 health 는 자식 앱의 health 를 반영하지 않는다 (v1.8 이후)
  • Git 변경은 폴링(기본 120s + jitter 60s), refresh 주석, webhook 으로, 클러스터 변경은 watch 로 안다
  • normal refresh 와 hard refresh 의 차이(캐시를 버리나)를 안다
  • sync 순서 규칙: 단계 → 웨이브 → 종류 → 이름, 웨이브 사이 2초 + health 대기, prune 은 역순
  • 자동 동기화는 기본 5회(5초부터 2배, 상한 3분) 재시도한 뒤 같은 (커밋, 파라미터)로는 다시 시도하지 않는다는 것과, 다시 시키는 두 방법(수동 sync, 새 커밋)
  • prune 과 selfHeal 의 네 조합이 "Git 에서 삭제" 와 "kubectl 변경" 에 어떻게 반응하는지 안다
  • tracking-id 주석과 resources-finalizer 로 "내 것" 을 알아보고 연쇄 삭제한다
  • Argo CD 는 helm install 이 아니라 helm template 을 쓴다. 값 우선순위 parameters > valuesObject > values > valueFiles > 차트 기본값
  • ApplicationSet = generator + template. git files generator 는 파일 하나를 파라미터 묶음 하나로 만든다
  • AppProject 는 namespace 범위는 blacklist, 클러스터 범위는 whitelist 로 다룬다. 그리고 controller 의 자기 규칙이다
  • GitOps 의 롤백은 git revert 이고, 부트스트랩의 마지막 push 는 helm install argocd 와 root apply 두 줄이다
  • PoC 가 안 쓴 것 중 본선 후보: Server-Side Diff, sync window, orphanedResources, destinationServiceAccounts(가장), ApplicationSet 의 RollingSync, webhook

본선에서 떠올릴 패턴

원하는 상태 + 조정 루프

처음 보는 주제라도 "무엇이어야 하는가(선언)" 를 저장하고 "지금은 어떤가(관찰)" 와 계속 비교해 차이만 고치는 구조로 바꿀 수 있는지 먼저 본다. 예: 함수 레지스트리, 테넌트 요금제, DNS 레코드, 피처 플래그. 멱등한 apply 와 "비교 전 정규화" 가 핵심이다.

두 갈래 나누기

드물게 바뀌고 검토가 필요한 것(플랫폼)은 Git → pull, 자주 바뀌고 사용자가 만드는 것(함수)은 API → 직접. 한 시스템 안에서 경로를 나누고 각 경로의 이력이 어디 남는지 말할 수 있으면 된다.

공장 패턴 (틀 + 목록)

ApplicationSet 처럼 "파일 하나 추가 = 자원 묶음 하나" 로 만들면 온보딩이 PR 하나가 된다. 테넌트, 지역, 고객사, 환경 어디에나 쓴다.

같은 입력이면 재시도하지 않기

실패한 입력을 무한 반복하지 않는 규칙(hot loop 방지)은 배포, 메시지 처리, 빌드 어디에나 필요하다. 입력이 바뀌거나 사람이 개입할 때만 다시 한다. 재시도가 필요하면 백오프와 상한을 명시한다.

규칙과 벽을 구분

AppProject 는 controller 가 스스로 지키는 규칙이고, 쿠버네티스 RBAC 은 API 서버가 막는 벽이다. 보안 설계에서 "누가 강제하나" 를 층마다 적어 본다 (7장의 MCP 가드레일 5층과 같은 질문).

초록불의 의미 확인

Synced/Healthy 는 "Git 대로 있다, 리소스 자신은 괜찮다" 까지만 말한다. 실제로 요청이 닿는지는 다른 관측(curl, Hubble)으로 따로 확인한다 (03 B4).
