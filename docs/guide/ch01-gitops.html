GitOps와 Argo CD

git push 한 번이 어떻게 클러스터 안의 파드가 되는지, Argo CD 의 부품 일곱 개가 그 사이에서 각각 무엇을 하는지, 그리고 그 길이 끊겼을 때 어디를 보고 어떻게 고치는지를 말로 설명할 수 있게 된다. 처음 보는 주제에서도 "원하는 상태를 적어 두고, 에이전트가 계속 맞춘다" 는 틀을 꺼내 쓸 수 있게 하는 것이 이 장의 목표다.

PoC 폴더 poc/01-argocd 핵심 기술 GitOps · Argo CD · Helm · App of Apps · ApplicationSet · AppProject 버전 차트 argo/argo-cd 10.10.5 = Argo CD v3.5.5

이 장의 지도

전체 PoC 는 kind 클러스터 faas 위에 플랫폼(Argo CD, Rollouts, Knative, 테넌트 울타리, 컨트롤 플레인)을 쌓고, 그 위에서 테넌트의 함수를 돌린다. 이 장은 그중 플랫폼이 Git 에서 클러스터로 들어오는 길을 다룬다. 01 단계에서 세운 Argo CD 와 App of Apps 는 이후 02~07 단계가 전부 그 위에 올라가는 바닥이다.

  1. push 배포와 pull 배포: 밖에서 미는 배포와 안에서 끌어오는 배포의 차이, 그리고 우리 PoC 가 두 방식을 어디에 나눠 쓰는지
  2. OpenGitOps 4원칙: 선언적, 버전·불변, 자동 pull, 계속 조정. 각 원칙이 Argo CD 의 어느 부품에 해당하나
  3. Argo CD 구조와 부품: server, repo-server, application-controller, applicationset-controller, redis, dex, notifications 의 안쪽
  4. Application 한 장 읽기: source, destination, syncPolicy 와 status 필드를 한 줄씩
  5. 조정 루프와 diff: 원하는 상태와 실제 상태를 어떻게 비교하나: 정규화, 3방향 비교, ignoreDifferences
  6. Sync 상태와 Health 상태: 두 축이 따로 움직이는 이유와 상태 기계
  7. 변경 감지: 폴링, refresh, webhook: timeout.reconciliation + jitter, normal/hard refresh, git push 에서 파드 Ready 까지
  8. Sync 작업: 단계, 웨이브, 훅, 옵션: 적용 순서 규칙, PreSync/Sync/PostSync/SyncFail, CreateNamespace·ServerSideApply 등
  9. 자동 동기화, prune, selfHeal, retry: 왜 같은 커밋에서 실패한 자동 동기화는 다시 안 하나
  10. 리소스 추적과 finalizer: Argo CD 가 "내 것" 을 알아보는 방법과 지울 때의 연쇄
  11. Helm 차트와 YAML 폴더 렌더링: helm install 이 아니라 helm template. values 우선순위, directory recurse/exclude
  12. App of Apps: root 하나로 나머지를 세우는 구조와 PoC 의 Application 나무
  13. ApplicationSet: 틀 하나 + 목록 하나로 테넌트를 찍어 내는 공장 (03)
  14. AppProject 와 Argo CD RBAC: 테넌트가 남의 namespace 나 울타리를 못 건드리게 하는 Argo CD 쪽 벽 (03)
  15. 여러 클러스터: 로컬 kind 와 EC2 k3s 가 같은 Git 을 보는 방식 (07)
  16. 드리프트, 롤백, 깨뜨려 보기: README 5단계 세 실험: selfHeal, 라벨 불일치, prune
  17. 부트스트랩 문제: Argo CD 는 자기 자신을 어떻게 까나. run-all 의 순서
  18. 정리: 체크리스트, 결정 표, 본선에서 옮겨 쓸 패턴, 스스로 답해 볼 질문

읽는 법: 절마다 1단계(개괄) → 2단계(동작 원리) → 3단계(세부 로직) 순서다. 왼쪽 목차 아래 "3단계 숨기기" 버튼으로 세부 로직을 접고 처음엔 1·2단계만 훑어도 된다. 각 절 끝의 색 상자는 우리 PoC 에서 어디인지(초록), 깨지면 어떻게 보이는지(빨강), 왜 이걸 골랐는지(보라), 공식 문서(파랑)다.

push 배포와 pull 배포

push 와 pull 은 무엇이 다른가

지금까지 실습(Lab 02~04, 07)에서는 맥에서 helm install, kubectl apply 를 직접 쳤다. 클러스터 밖에서 클러스터 안으로 밀어 넣으니 push 방식이다. GitOps 는 방향을 뒤집는다. 클러스터 안에서 도는 프로그램(에이전트)이 Git 을 읽어 와서 스스로 맞춘다. 그래서 pull 방식이다.

Java/Spring 에 비유하면, push 는 운영 서버에 SSH 로 들어가 jar 를 바꿔 끼우는 것이고, pull 은 서버마다 "설정 저장소의 최신 버전을 계속 보고 다르면 스스로 재배포하는 데몬" 을 두는 것이다. Spring Cloud Config 의 설정 새로고침을 클러스터 전체로 넓힌 모양이다.

핵심 차이는 세 가지다. (1) 정답이 어디 있나: push 는 사람의 기억과 터미널 기록, pull 은 Git. (2) 열쇠가 어디 있나: push 는 CI·사람이 클러스터 관리자 kubeconfig 를 가진다, pull 은 클러스터 안 에이전트만 가진다. (3) 끝나고도 지켜보나: push 는 명령이 끝나면 끝, pull 은 계속 비교한다.

시간 순서와 비교 축

두 방식의 동작을 시간 순서로 놓으면 차이가 더 분명하다. push 는 "한 번 실행되는 절차" 이고 pull 은 "끝나지 않는 반복" 이다.

축push (CI 가 kubectl/helm)pull (Argo CD)
클러스터 열쇠CI·사람에게 관리자 kubeconfigArgo CD 의 ServiceAccount 만. 사람은 Git 쓰기 권한만
방화벽 방향CI → 클러스터 API 로 들어오는 연결 필요클러스터 → Git 으로 나가는 연결만. 클러스터 API 를 밖에 안 열어도 된다
드리프트감지 못 함계속 비교해서 OutOfSync 표시, selfHeal 이면 되돌림
감사 기록CI 로그 (흩어짐)git log + Argo CD 의 sync 이력
롤백이전 명령을 다시 재구성git revert 후 push
반영 속도즉시폴링 주기만큼 늦음 (webhook 으로 줄임)
명령형 단계 (DB 마이그레이션 등)자연스럽다훅(PreSync 등)이나 별도 컨트롤러로 바꿔야 한다

pull 의 대가와 우리 PoC 의 경계

pull 이 공짜는 아니다. 세부적으로 따져야 할 대가와 경계는 다음과 같다.

  • 반영 지연: Argo CD 기본값은 120초 + 최대 60초 jitter 로 Git 을 본다. 데모 중에 push 하고 최악 3분을 기다릴 수 있다. 줄이는 법은 변경 감지 절에서 다룬다.
  • 비밀값: Git 에 Secret 평문을 넣을 수 없다. 실무에서는 Sealed Secrets, External Secrets, SOPS 같은 도구를 붙인다. 우리 PoC 의 레포는 public 이라 비밀값을 Git 에 두지 않는 구조로 짰다 (Argo CD 의 admin 비밀번호는 설치 때 생긴 Secret, 05 의 토큰은 클러스터 안에서 만든다).
  • 명령형 작업: 이미지 빌드, DB 마이그레이션, 일회성 Job 은 "원하는 상태" 로 표현하기 어렵다. Argo CD 는 훅(PreSync/PostSync)으로 일부를 품고, 나머지는 CI 나 별도 컨트롤러가 맡는다.
  • 부트스트랩: Argo CD 자신은 누가 까나. 결국 첫 한두 줄은 push 다 (부트스트랩 절).
  • 혼합형: 흔한 실무 모양은 "CI 가 이미지를 빌드하고 Git 의 이미지 태그만 바꾸는 커밋을 만든다 → Argo CD 가 pull" 이다. CI 는 레지스트리와 Git 쓰기 권한만 갖고 클러스터 권한은 없다.

우리 PoC 는 의도적으로 두 방식을 섞는다. 플랫폼(Argo CD 가 관리하는 모든 것)은 pull, 사용자 함수는 컨트롤 플레인(05)이 쿠버네티스 API 로 직접 만든다. 함수는 사용자가 HTTP 로 올리는 데이터이고 초 단위로 바뀌며, 버전 이력은 Knative Revision 과 감사 로그가 들고 있기 때문이다. 이 선택의 근거와 대가는 7장에서 자세히 본다.

판단 이 변경을 GitOps 로 할까, API 직접으로 할까:
  만약 바꾸는 사람이 플랫폼 운영자이고, 변경이 드물고, 검토(PR)가 필요하다
    → Git 에 쓰고 Argo CD 가 pull   // 01~06 의 플랫폼 전부
  만약 바꾸는 주체가 최종 사용자·프로그램이고, 초 단위로 많이 바뀐다
    → 전용 API 가 검증 후 쿠버네티스 API 로 직접   // 05 컨트롤 플레인의 함수 배포
  만약 둘 다 해당하면
    → API 가 Git 에 커밋을 만들게 하고 Argo CD 가 pull   // 반영이 폴링만큼 늦어진다

깨지면 이렇게 보인다: "push 했는데 아무 일도 없다"

증상: 파일을 고쳤는데 클러스터가 그대로다. 볼 곳: kubectl -n argocd get application hello-fn -o jsonpath='{.status.sync.revision}' 와 git rev-parse origin/main 를 비교한다. 같지 않으면 아직 폴링 전이거나, 애초에 push 를 안 했다 (Argo CD 는 맥의 작업 폴더가 아니라 GitHub 를 읽는다). 고치는 법: push 했는지 확인 → kubectl -n argocd annotate application hello-fn argocd.argoproj.io/refresh=normal --overwrite 로 지금 다시 보게 한다.

왜 이걸 골랐나 (대안)

선택: pull 방식 GitOps (Argo CD). 대안 (가) CI 에서 kubectl apply/helm upgrade: CI 에 클러스터 관리자 권한을 줘야 하고 드리프트를 못 잡는다. 대안 (나) Flux: 같은 pull 방식이고 기능도 비슷하지만 기본 웹 UI 가 없어서 2분 데모에서 "지금 동기화 중" 장면을 보여 주기 어렵다 (poc/01-argocd/README.md 핵심 결정 1).

OpenGitOps 4원칙

네 가지 원칙

"GitOps" 는 도구 이름이 아니라 원칙 묶음이다. CNCF 산하 OpenGitOps 프로젝트가 네 가지로 정리했다. 원문은 "GitOps 로 관리되는 시스템의 원하는 상태(desired state)는 다음을 만족해야 한다" 로 시작한다.

1. 선언적 (Declarative)
원하는 상태를 "어떻게" 가 아니라 "무엇" 으로 적는다. "파드를 하나 더 띄워라" 가 아니라 "replicas: 2".
2. 버전 관리·불변 (Versioned and Immutable)
원하는 상태를 바꿀 수 없고 이력이 전부 남는 저장소에 둔다. Git 커밋은 해시로 고정되어 고칠 수 없다.
3. 자동으로 끌어옴 (Pulled Automatically)
소프트웨어 에이전트가 저장소에서 원하는 상태를 스스로 가져간다. 사람이 밀어 넣지 않는다.
4. 계속 조정 (Continuously Reconciled)
에이전트가 실제 상태를 계속 관찰하고 원하는 상태를 적용하려고 시도한다.

원칙이 하나의 루프가 되는 방식

네 원칙은 하나의 루프로 이어진다. 1·2 가 "정답을 어디에 어떻게 두나", 3·4 가 "정답과 현실을 누가 어떻게 맞추나" 다.

원칙Argo CD 에서 맡는 것빠지면 생기는 일
1 선언적Application 의 source 가 가리키는 YAML·Helm 차트·Kustomize절차(스크립트)는 "지금 상태" 와 비교할 기준이 없다. 두 번 돌리면 결과가 달라질 수 있다
2 버전·불변targetRevision 을 커밋 SHA 로 바꿔 해석, status.sync.revision 에 기록어느 버전이 깔렸는지 모른다. 롤백 대상이 없다
3 자동 pullrepo-server(Git 읽기·렌더링), 폴링·webhook사람이 잊으면 반영이 안 된다. CI 에 클러스터 열쇠가 필요하다
4 계속 조정application-controller 의 비교 루프, automated sync, selfHeal한 번 맞춘 뒤 누가 바꾸면 끝. 드리프트가 쌓인다

원칙의 경계와 PoC 에서 어긋나는 곳

원칙을 문자 그대로 적용하면 우리 PoC 에서 걸리는 지점이 몇 군데 있다. 심사에서 "그럼 이건 GitOps 가 아니지 않나" 라는 질문을 받을 수 있는 곳이다.

  • 브랜치는 움직이는 포인터다. targetRevision: main 은 매번 다른 커밋을 가리킨다. 원칙 2 의 "불변" 은 커밋 하나하나가 불변이라는 뜻이고, Argo CD 는 비교할 때마다 main 을 SHA 로 풀어서 status.sync.revision 에 적는다. 운영에서 더 엄격하게 하려면 태그나 SHA 를 고정한다.
  • 차트 버전 범위는 불변을 깬다. 07 의 node-termination-handler.yaml 은 targetRevision: "0.*" 이다. Git 커밋은 그대로인데 Helm 저장소에 새 0.x 차트가 올라오면 다른 매니페스트가 렌더링된다. 파일 주석도 이걸 임시값이라고 적어 두었다.
  • 사용자 함수(05)는 원칙 2·3 을 일부러 포기한다. 함수 코드는 HTTP 로 들어오고 Git 에 커밋되지 않는다. 대신 이미지를 digest(@sha256:...)로 고정해서 "같은 Revision 은 같은 바이트" 라는 불변성은 지킨다. 이력은 Knative Revision 과 감사 로그에 남는다.
  • Secret 과 일회성 Job은 원칙 1 로 표현하기 어렵다. 01 의 Argo CD admin 비밀번호(argocd-initial-admin-secret)는 Helm 설치 때 생기고 Git 에 없다.
검사 어떤 리소스 R 이 GitOps 원칙을 지키는가:
  선언적     = R 이 Git 의 YAML 로부터 렌더링되는가            // helm template, directory
  불변       = 같은 커밋 SHA 로 렌더링하면 항상 같은 결과인가    // 버전 범위, randAlphaNum 이면 아님
  자동 pull  = R 을 바꾸는 주체가 클러스터 안 에이전트뿐인가    // 사람의 kubectl 은 드리프트
  계속 조정  = R 이 바뀌면 에이전트가 알아채고 되돌리는가      // selfHeal: true

우리 PoC 에서는

01~06 의 플랫폼 Application 은 전부 targetRevision: main + automated: {prune: true, selfHeal: true} 다. 즉 원칙 4 를 가장 강하게 켠 상태다. 예외는 07 의 NTH 차트(버전 범위)와 05 의 사용자 함수(API 직접)다.

깨지면 이렇게 보인다: 같은 커밋인데 결과가 다르다

증상: Git 은 안 바뀌었는데 어느 날 Application 이 OutOfSync 가 되거나 다른 버전이 깔린다. 볼 곳: kubectl -n argocd get application <이름> -o yaml 의 spec.source.targetRevision 이 범위(0.*)나 HEAD 인지, 차트 템플릿에 randAlphaNum, now 같은 함수가 있는지. 고치는 법: 버전을 정확한 숫자로 고정하고, 무작위 값은 Secret 으로 미리 만들어 참조한다.

왜 이 원칙을 기준으로 삼나

도구(Argo CD, Flux)는 바뀌어도 원칙은 남는다. 본선에서 처음 보는 도구가 나오면 "이 도구는 원칙 3·4 를 하나?" 로 바로 분류할 수 있다. 예: Terraform 은 원칙 1·2 는 지키지만 3·4 는 사람이 apply 해야 하는 push 다 (07 단계가 Terraform 을 손으로 apply 하는 이유).
