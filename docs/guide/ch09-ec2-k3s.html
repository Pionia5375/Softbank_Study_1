EC2·k3s·Terraform: 로컬 PoC 를 진짜 VM 으로 옮기기

맥 안의 kind 클러스터를 AWS EC2 위 k3s 로 옮기는 설계를 코드 한 줄 단위로 읽는다. 다 읽고 나면 "노드가 진짜 컴퓨터가 되면 무엇이 새로 문제가 되는가(돈·사라짐·접속)" 를 설명하고, 같은 Terraform·k3s·GitOps 구조를 처음 보는 클라우드 과제에 옮겨 쓸 수 있다.

이 장의 전제: 코드만 있고, 실제로 만든 적은 없다

poc/07-ec2-k3s 는 클라우드 스레드에서 terraform validate 와 오프라인 렌더링(scripts/render-k3s.sh)까지만 검증했다. terraform apply(코드대로 AWS 리소스를 실제로 만드는 명령)·destroy(그것을 전부 지우는 명령)·FIS(AWS Fault Injection Service, 장애를 일부러 일으키는 AWS 서비스) 실험 시작은 Jeong 의 승인 뒤, Jeong 의 맥(로컬 세션)에서만 한다 (README 첫 줄, RUNBOOK 첫 줄). 그래서 이 장의 "이렇게 동작한다" 는 전부 코드와 공식 문서에서 읽어 낸 설계이고, 실측 숫자는 하나도 없다. 비용도 금액 대신 "무엇이 시간당으로 나가고 무엇이 아닌가" 의 구조로만 설명한다.

이 장의 지도

01~06 은 전부 맥 안의 kind(Kubernetes in Docker, 쿠버네티스 노드 하나를 Docker 컨테이너 하나로 띄워 주는 로컬용 도구)였다. kind 의 노드는 Docker 컨테이너라서 꺼지지도, 돈이 들지도, 인터넷에서 들어오지도 않았다. 07 은 같은 플랫폼(Git 을 보고 클러스터를 맞추는 Argo CD 와 그 위의 앱들, 그리고 노드를 역할별로 묶은 노드 풀(node pool) system·build·exec 구조)을 그대로 두고 노드를 만드는 방법만 바꾼다. 아래 그림에서 01~06 이 쌓은 층은 그대로 위에 얹히고, 맨 아래 "노드" 층이 Docker 컨테이너에서 EC2 가상 머신으로 바뀐다.

이 장의 절과 한 줄 요약이다. 표에 나오는 낯선 말(k3s 의 server·agent, Terraform 의 state, user_data, 인스턴스 프로파일, 시작 템플릿, NTH, FIS, SSM 같은 것)은 각 절에서 처음 나오는 자리에서 바로 설명하므로, 여기서는 "무슨 절이 있나" 만 보고 넘어가도 된다.

kind 에서 진짜 VM 으로: 무엇이 바뀌나

바뀌지 않는 것과 바뀌는 것

쿠버네티스 API 위쪽은 거의 그대로다. 매니페스트(manifest, "이런 리소스가 있어야 한다" 를 적은 YAML 파일), Helm 차트(매니페스트 묶음을 변수와 함께 포장한 패키지), Argo CD Application(Git 의 폴더 하나를 클러스터에 맞추라고 Argo CD 에 등록하는 단위), 노드 풀 라벨 키 pool 은 같은 파일을 쓴다. 바뀌는 것은 "노드를 어떻게 만들고, 어떻게 들어가고, 언제 없어지나" 이다.

README 1.1절은 새로 생기는 문제를 셋으로 정리한다.

  • 돈: VM 은 켜져 있는 동안 계속 과금된다. 끄는 걸 잊으면 계속 나간다.
  • 사라짐: 스팟 인스턴스(Spot Instance, EC2 의 남는 용량을 싸게 빌리는 구매 방식)는 AWS 가 그 용량이 필요해지면 2분 예고 뒤 회수한다. 노드가 진짜로 없어진다.
  • 접속: 맥에서 쿠버네티스 API 서버(kubectl 과 모든 구성 요소가 말을 거는 클러스터의 창구)까지 길을 내야 하고, 그 길을 아무나 못 쓰게 막아야 한다.

이 장의 모든 장치는 이 셋 중 하나에 대한 답이다. 돈 → 예산 알람·야간 0대 예약·같은 날 destroy·check-leftovers.sh(남은 과금 리소스를 찾는 스크립트). 사라짐 → ASG(Auto Scaling Group, 정해진 대수의 EC2 를 유지해 주는 AWS 의 관리자)·NTH(aws-node-termination-handler, 회수 예고를 보고 파드를 미리 옮기는 작은 프로그램)·PDB(PodDisruptionBudget, "한 번에 이만큼은 남겨 두라" 는 약속)·graceful node shutdown(OS 가 꺼질 때 kubelet 이 파드를 정리할 시간을 버는 쿠버네티스 기능). 접속 → SSM(AWS Systems Manager, 포트를 열지 않고 VM 에 들어가게 해 주는 서비스) 포트 포워딩(22·6443 은 안 연다). 이름만 먼저 보고, 각각은 해당 절에서 다시 설명한다.

한 장으로 비교

그림과 표를 읽기 전에, 이 장 내내 쓰는 쿠버네티스 말 몇 개를 짚는다. kubectl 은 API 서버에 명령을 보내는 CLI 이고, 어느 클러스터에 어떤 자격으로 붙을지는 kubeconfig 파일에 적힌다. 컨트롤 플레인은 API 서버·스케줄러(파드를 어느 노드에 둘지 정함)·컨트롤러 매니저(Deployment 같은 리소스가 원하는 상태를 유지하도록 돌리는 루프 모음)의 묶음이고(07장의 "컨트롤 플레인" Spring 서비스와는 다른 말), 그 상태는 etcd 라는 키-값 저장소에 들어간다. 노드마다 kubelet 이 있어 "이 노드에 이 파드를 띄워라" 를 실제로 실행하고, CNI(Container Network Interface) 플러그인이 파드에 IP 를 주고 노드 사이를 잇는다. taint 는 노드가 "이걸 견디는 파드만 와라" 고 거는 표시, toleration 은 파드가 "견딘다" 고 다는 표시다(세 낱말의 설계는 03장, 이 장에서는 노드 풀 절). 인그레스(Ingress) 는 "이 호스트·경로의 HTTP 요청은 이 Service 로" 라는 규칙이고, 그 규칙을 실제 프록시로 실행하는 것이 인그레스 컨트롤러(로컬은 Kourier, k3s 기본은 Traefik)다. NodePort 는 모든 노드의 같은 포트로 Service 를 여는 방식이다.

세부: "노드" 라는 말이 가리키는 것이 바뀐다

kind 노드는 맥의 Docker Desktop VM 하나 안에 있는 컨테이너다. 네 노드가 같은 커널, 같은 디스크, 같은 메모리 한도를 나눠 쓴다. 그래서 06 의 "노드 다운" 은 docker pause 로 컨테이너를 얼리는 흉내였고, 노드 하나가 메모리를 다 먹으면 다른 노드도 같이 느려졌다. 04 의 gVisor 함수 실행이 실패한 것도 kind 노드가 "컨테이너 안의 컨테이너 런타임" 이라 권한 제약이 있었기 때문이다 (04 README 9절 보충).

EC2 노드는 각자 하이퍼바이저(한 물리 서버를 여러 VM 으로 나누는 소프트웨어) 위 독립된 VM 이다. 커널·디스크(EBS, EC2 에 붙는 네트워크 블록 디스크)·네트워크 인터페이스(ENI)·퍼블릭 IP 가 노드마다 따로 있다. 그 결과 아래가 달라진다.

  • 장애 단위: 노드 하나가 진짜로 사라질 수 있다 (스팟 회수, 하드웨어 점검 이벤트). 대신 다른 노드에는 영향이 없다.
  • 부팅 경로: 노드는 AMI(Amazon Machine Image, 디스크 이미지)에서 부팅하고, user_data 스크립트(EC2 를 만들 때 함께 넣어 두는 텍스트. 우분투의 cloud-init 이 첫 부팅 때 root 로 실행한다)가 첫 부팅에 한 번 k3s 를 설치하고 조인한다. 새 노드는 사람 손 없이 같은 모양이 되어야 한다 → 라벨·taint 는 노드 스스로 붙인다.
  • 메타데이터: 노드 안에서 169.254.169.254 의 IMDS(Instance Metadata Service)를 읽을 수 있다. 스팟 회수 예고가 여기에 올라온다.
  • 네트워크 경계: 노드가 인터넷 주소를 가진다. 보안 그룹(security group, 인스턴스 앞에 붙는 허용 규칙 목록 = 방화벽)이 문을 닫지 않으면 인터넷 전체가 노드의 포트에 닿는다.
  • 수명 관리: 노드는 "만든 뒤 지우기" 까지가 한 세트다. Terraform state(Terraform 이 지금까지 만든 리소스의 목록과 실제 ID 를 적어 둔 파일)가 무엇을 만들었는지 기억하고, destroy 가 같은 목록을 지운다.

우리 PoC 에서는

노드 풀 라벨 키는 로컬과 같은 pool 을 쓰고 값도 system·build·exec 로 같다. 그래서 05 의 빌드 Job(한 번 돌고 끝나는 파드를 만드는 리소스) 템플릿이나 04 의 ksvc(Knative Service, 함수 하나를 뜻하는 Knative 리소스)처럼 nodeSelector: pool: exec(파드가 "이 라벨이 있는 노드로만" 가게 하는 필드)를 쓰는 매니페스트를 고치지 않고 가져올 수 있다. 새로 붙는 라벨은 capacity-type(spot / on-demand) 하나로, NTH 를 스팟 노드에만 띄우는 데 쓴다.

왜 이걸 골랐나 (대안)

목적은 "작년 본선 우승팀 구성(EC2 위 직접 쿠버네티스, 스팟 실행 노드, 빌드 노드 분리)을 우리 손으로 세우고, 생성·파괴·스팟 복구를 직접 겪는 것" 이다 (README 로드맵 줄). 관리형 EKS 는 노드 아래를 감춰서 이 목적에 맞지 않고, 로컬에서 스팟을 흉내 내는 것(06 의 docker pause)은 IMDS·ASG·NTH 경로를 전혀 지나지 않는다.

k3s 구조

앞 절에서 "노드를 만드는 방법" 이 바뀐다고 했다. 그 VM 위에 쿠버네티스를 올리는 도구가 k3s 다. 이 절은 k3s 가 무엇으로 이루어졌고 노드가 어떻게 붙는지를 보고, 다음 절에서 우리가 k3s 에 넘기는 설정 파일을 한 줄씩 읽는다.

k3s 는 무엇이고 왜 쓰나

k3s 는 Rancher(현재 SUSE)가 만든 CNCF(쿠버네티스를 관리하는 재단) 인증 쿠버네티스 배포판(distribution)이다. 핵심은 바이너리 하나에 API 서버, 스케줄러, 컨트롤러 매니저, kubelet, kube-proxy(Service 의 가상 IP 를 노드의 네트워크 규칙으로 풀어 주는 부품), containerd(컨테이너를 실제로 실행하는 런타임), flannel(CNI 플러그인), 그리고 클러스터 기본 부품을 넣어 둔 것이다. 설치는 curl -sfL https://get.k3s.io | sh - 한 줄이고, 설정은 /etc/rancher/k3s/config.yaml 파일 하나다.

노드 역할은 둘뿐이다.

server
k3s server 를 실행하는 호스트. 컨트롤 플레인과 데이터스토어를 k3s 가 관리한다. server 도 kubelet·컨테이너 런타임·CNI 를 돌리므로 파드를 받을 수 있다.
agent
k3s agent 를 실행하는 호스트. 데이터스토어·컨트롤 플레인 없이 kubelet·containerd·flannel·kube-proxy 만. "server 주소 + 토큰" 만 알면 붙는다.

k3s 는 안에서 어떻게 도나

(1) 바이너리 하나, 프로세스 하나

kubeadm 클러스터는 kube-apiserver·etcd·scheduler 를 각각 정적 파드(static pod, kubelet 이 API 서버 없이 노드의 파일에서 직접 띄우는 파드)로 띄운다. k3s server 는 이것들을 한 프로세스 안의 고루틴(Go 언어의 경량 스레드)으로 돌린다. 그래서 kubectl -n kube-system get pods 에 API 서버 파드가 안 보인다. 대신 systemd(리눅스가 부팅 때 서비스들을 띄우고 관리하는 기본 관리자) 서비스 k3s(server) 또는 k3s-agent(agent) 하나가 노드의 쿠버네티스 전부다. 로그도 journalctl -u k3s / journalctl -u k3s-agent(systemd 의 로그 보기 명령) 한 곳에 모인다.

(2) 데이터스토어: kine 과 SQLite, 그리고 etcd

쿠버네티스 API 서버는 etcd API 로 상태를 저장한다. k3s 는 kine 이라는 변환층을 넣어 etcd API 호출을 SQLite·MySQL·PostgreSQL 같은 일반 데이터베이스 호출로 바꾼다. 공식 문서의 구성은 셋이다.

(3) agent 가 붙는 과정 (조인)

agent 는 server 주소와 token 을 가지고 시작한다. 공식 문서 "How Agent Node Registration Works" 의 흐름은 아래와 같다.

(4) 패키지 부품과 자동 배포 매니페스트

server 는 /var/lib/rancher/k3s/server/manifests 에 있는 YAML 을 kubectl apply 처럼 자동 적용하고, 각각을 AddOn 커스텀 리소스(CRD 로 추가한 사용자 정의 리소스 종류)로 추적한다. coredns, traefik, local-storage, metrics-server 가 이 폴더에 들어 있다. servicelb 는 매니페스트 파일 없이 내장 컨트롤러로 돌지만 끌 때는 같은 방식으로 끈다. 끄는 법은 --disable=traefik (config.yaml 에서는 disable: [traefik]). 끌 수 있는 이름은 coredns, servicelb, traefik, local-storage, metrics-server, 그리고 containerd 의 추가 런타임 자동 감지를 끄는 runtimes 다. 같은 폴더에 내 YAML 을 두면 그것도 AddOn 으로 적용되고, 같은 이름에 .skip 을 붙인 빈 파일(traefik.yaml.skip)을 두면 그 매니페스트는 건너뛴다. 패키지 부품과 별개로 --disable-cloud-controller, --disable-kube-proxy, --disable-network-policy, --flannel-backend=none 같은 플래그가 k3s 안의 다른 부품을 끈다.

  • Traefik: 인그레스 컨트롤러(Ingress 규칙을 실행하는 HTTP 프록시). k3s 는 이것을 Helm 차트로 깔며, 차트 값을 바꾸려면 HelmChartConfig 리소스를 쓴다(아래 "깨지면" 에 예). 07 의 fn-sample Ingress 가 ingressClassName: traefik 으로 쓴다.
  • ServiceLB(klipper-lb): type: LoadBalancer 서비스(클라우드라면 외부 로드밸런서를 붙여 달라는 뜻의 Service 타입)마다 svclb-* DaemonSet(노드마다 파드 하나씩 두는 리소스)을 kube-system 에 만들어 노드의 호스트 포트(Traefik 이면 80/443)를 서비스로 넘긴다. 클라우드 로드밸런서가 없는 환경의 "가난한 LB" 다. 특정 노드에만 두려면 노드에 svccontroller.k3s.cattle.io/enablelb=true 라벨을 붙인다(라벨이 하나라도 있으면 그 노드들에만 뜬다).
  • local-path-provisioner: PVC(PersistentVolumeClaim, 파드가 디스크를 요청하는 리소스)를 노드 로컬 디스크 폴더로. 07 에서는 쓰지 않는다.
  • metrics-server: kubectl top(파드·노드의 CPU·메모리 사용량 보기). gVisor 오버헤드를 볼 때 쓴다.
  • CoreDNS: 클러스터 DNS. 파드가 my-svc.my-ns.svc 같은 이름을 물으면 Service IP 로 답한다.

(5) 네트워크: flannel, 네트워크 정책 컨트롤러, 노드 사이 포트

k3s 는 CNI 로 flannel 을 내장하고 기본 백엔드는 VXLAN 이다(노드 사이 UDP 8472 로 캡슐화). 다른 백엔드(host-gw, wireguard-native)는 flannel-backend 로 고르고, Cilium 같은 외부 CNI 를 쓰려면 flannel-backend: none 으로 끈 뒤 직접 깐다(server-config 템플릿 마지막 주석이 그 얘기다). flannel 자체는 NetworkPolicy(파드 사이 통신을 라벨 기준으로 허용·차단하는 쿠버네티스 리소스)를 집행하지 못하므로, k3s 는 kube-router 의 정책 부분만 떼어 낸 내장 네트워크 정책 컨트롤러를 함께 돌린다. 끄려면 disable-network-policy: true. PoC 에서는 NetworkPolicy 를 쓰지 않는다(03 의 테넌트 울타리는 Cilium 정책이라 EC2 에는 오지 않는다, 04장). 본선에서 flannel 을 그대로 두고 표준 NetworkPolicy 만 쓴다면 이 내장 컨트롤러로 충분하고, L7 정책이나 Hubble 같은 관측이 필요해지면 그때 Cilium 으로 바꾼다.

노드 사이에 열려 있어야 하는 포트는 공식 문서 "Requirements" 의 표 그대로다. 우리 보안 그룹은 "같은 그룹끼리 전부" 한 줄로 이것을 덮는다(네트워크 절).

(6) 내장 클라우드 컨트롤러는 AWS 를 모른다

그림 9-3 의 "내장 cloud-controller" 는 k3s 가 넣어 둔 뼈대(stub) 클라우드 프로바이더다. 노드의 주소와 providerID 를 채우고 ServiceLB 를 돌리는 데까지만 하고, "이 VM 이 아직 존재하나" 를 클라우드 API 에 묻지 않는다(언제나 "존재한다" 고 답한다). 그래서 EC2 가 스팟 노드를 회수해도 그 Node 오브젝트는 NotReady 로 남고, 사람이 kubectl delete node 로 지운다. EKS 나 AWS 클라우드 프로바이더를 깐 클러스터는 이 자리에서 죽은 Node 를 자동으로 지운다. 바꾸려면 disable-cloud-controller: true 로 뼈대를 끄고 AWS cloud-provider 를 따로 깔아야 하며, 노드 역할에 EC2 조회 권한이 생긴다(IAM 절의 "권한을 더하는 순간" 이 이것이다).

세부 로직: 설정 파일 규칙, 토큰, 노드 비밀번호, CriticalAddonsOnly

설정 파일 규칙 (공식 문서 Configuration File)

  • 기본 경로 /etc/rancher/k3s/config.yaml. 명령줄 플래그 --node-label 은 YAML 키 node-label 이 된다 (앞의 -- 를 뺀 이름).
  • 여러 번 쓸 수 있는 플래그(node-label, node-taint, kubelet-arg, disable)는 YAML 리스트로 쓴다.
  • 명령줄과 파일이 둘 다 있으면 명령줄이 이긴다. 리스트 값은 합쳐지지 않고 명령줄의 리스트가 파일의 리스트를 통째로 대체한다. 추가로 /etc/rancher/k3s/config.yaml.d/*.yaml 를 이름(알파벳) 순으로 읽어 합치는데, 뒤 파일의 같은 키가 앞 값을 덮어쓰고, 리스트 키에 + 를 붙이면(node-label+:) 대체가 아니라 덧붙이기가 된다. 우리는 파일 하나만 쓰므로 이 규칙에 걸릴 일은 없지만, 본선에서 "공통 설정 + 풀별 추가 라벨" 을 나눌 때 쓸 수 있다.
  • node-label·node-taint 는 노드를 처음 등록할 때만 붙는다(공식 문서 "Node Labels and Taints": 등록 뒤 k3s 설정으로는 바꿀 수 없고, 바꾸려면 kubectl label·kubectl taint 로 직접). k3s 는 이 값을 kubelet 의 --node-labels·--register-with-taints 로 넘기므로, Node 오브젝트가 생기는 순간 라벨·taint 가 함께 붙는다. 우리 노드는 user_data 가 첫 부팅에만 돌고, 바꾸려면 노드를 새로 만들기 때문에 이 성질과 잘 맞는다.

토큰

server 의 token 은 클러스터 조인용 공유 비밀이다. agent 는 같은 값을 token 에 넣는다. 공식 문서(k3s token)는 토큰 형식을 둘로 나눈다. 보안 토큰은 K10<CA 인증서의 해시>::<사용자>:<비밀> 꼴로, 앞의 해시 덕분에 agent 가 "내가 붙은 server 의 CA(인증 기관, 클러스터 인증서를 서명하는 루트)가 진짜인가" 를 검증할 수 있다. server 가 만든 /var/lib/rancher/k3s/server/token 파일이 이 형식이다. 짧은 토큰은 비밀 문자열뿐이라 CA 해시가 없고, agent 는 처음 연결한 server 의 CA 를 검증 없이 그대로 믿는다. 우리는 Terraform 의 random_password 로 만든 48자 문자열을 server·agent 양쪽 token 에 넣으니 짧은 토큰 방식이다. 같은 VPC 사설 IP 로만 붙으므로 중간자 위험은 낮다고 보고 받아들였다. 그 밖에 k3s token create 로 유효 기간이 있는 임시 조인 토큰(bootstrap token)을 만들 수 있고, k3s token rotate 로 server 토큰을 바꿀 수 있다. PoC 에서는 안 쓰고, 본선에서 "노드를 추가하는 사람에게 영구 토큰을 주고 싶지 않을 때" 쓴다.

노드 비밀번호 (node-password)

agent 는 처음 붙을 때 무작위 노드 비밀번호를 만들어 /etc/rancher/node/password 에 두고, 클러스터는 그 해시를 kube-system 의 Secret(비밀값을 담는 쿠버네티스 리소스) <노드이름>.node-password.k3s 에 저장한다. 같은 노드 이름으로 다시 등록하려면 같은 비밀번호여야 한다. 다른 VM 이 같은 이름으로 들어와 그 노드 행세를 하는 것을 막는 장치다. Node 오브젝트를 지우면 이 Secret 도 같이 지워진다.

조인 요청(노드이름 N, 토큰 T, 비밀번호 P):
  만약 T 가 server 토큰과 다름 → 거절
  만약 Secret "N.node-password.k3s" 가 있음:
      만약 hash(P) ≠ 저장된 해시 → 거절   // 같은 이름의 새 VM 은 여기서 막힌다
  아니면 Secret 생성
  인증서 발급 → kubelet 시작 → Node 등록 (config.yaml 의 라벨·taint)

이게 스팟과 만나면 엣지 케이스가 생긴다. EC2 우분투의 호스트 이름은 사설 IP 에서 나온다(ip-10-70-1-23 꼴). 회수된 노드의 Node 오브젝트는 k3s 에 클라우드 컨트롤러가 없어서 NotReady 로 남는다. 교체 VM 이 우연히 같은 사설 IP 를 받으면(/24 서브넷 안에서 무작위로 고르므로 드물지만 0 은 아니다) 같은 노드 이름으로 새 비밀번호를 들고 와서 조인이 거절된다. 그때 agent 로그에 찍히는 문구는 k3s 소스(pkg/agent/config/config.go)에 있다: Node password rejected, duplicate hostname or contents of '/etc/rancher/node/password' may not match server node-passwd entry, try enabling a unique node name with the --with-node-id flag. 그래서 런북 D 의 "실험 사이에 NotReady 노드를 kubectl delete node" 는 단순한 정리가 아니라 이 충돌도 막는다. 공식 문서는 이름을 자주 재사용하면 --with-node-id 로 노드 이름 뒤에 고유 ID 를 붙이라고 권한다.

CriticalAddonsOnly 는 누가 견디나 (소스로 확인)

k3s 레포의 manifests/coredns.yaml, local-storage.yaml, metrics-server/metrics-server-deployment.yaml, traefik.yaml 은 모두 key: CriticalAddonsOnly, operator: Exists toleration 을 갖는다. ServiceLB 의 svclb DaemonSet 도 코드(pkg/cloudprovider/servicelb.go)에서 같은 toleration 과 control-plane toleration 을 넣는다. README 1.4절의 【추정】("부품별 toleration") 은 이렇게 소스로 확인된다.

다만 toleration 은 "가도 된다" 일 뿐 "거기로 가라" 가 아니다. 이 부품들에는 system 노드를 고르는 nodeSelector 가 없다. 그래서 exec(taint 없음) 노드에도 뜰 수 있다. 처음엔 server 가 먼저 떠서 거기 몰리겠지만, 재시작·재배치 때 exec 스팟 노드로 갈 수 있고 그러면 스팟 회수 때 Traefik 이나 CoreDNS 가 같이 이동한다(네 매니페스트의 nodeSelector 는 kubernetes.io/os: linux 뿐이라는 것을 k3s 레포 manifests/ 에서 확인했다. 실제 어디에 떴는지는 apply 당일 kubectl -n kube-system get pods -o wide 로 본다). 반대로 svclb 는 pool=build taint 를 견디지 못하므로 build 노드에는 svclb 파드가 없다 → build 노드 IP:80 은 응답하지 않는다.

스케줄러가 파드 p 를 노드 n 에 둘 수 있나:
  n 의 taint 중 effect 가 NoSchedule/NoExecute 인 것 전부에 대해
      p 의 toleration 중 하나가 (key 같음) 그리고 (operator Exists 또는 value 같음) 그리고 (effect 비었거나 같음) → 통과
      아니면 → 이 노드 탈락 ("untolerated taint")
  p 의 nodeSelector 라벨이 n 에 전부 있나 아니면 탈락 ("didn't match node selector")
  // toleration 만 있고 nodeSelector 가 없으면: 테인트 노드와 무테인트 노드 둘 다 후보

우리 PoC 에서는

k3s 는 기본 부품을 하나도 끄지 않는다 (server-config.yaml.tftpl 마지막 주석). flannel 그대로, Traefik 그대로, ServiceLB 그대로. 로컬의 Cilium·Kourier 와 다르지만, 07 의 목표는 "노드 풀이 진짜 VM 에서 동작하나" 이지 "네트워크 정책이 같은가" 가 아니라서 기본값으로 시작한다. gVisor 측정용 gvisor-ec2.sh platform 은 Kourier 서비스를 ClusterIP(클러스터 안에서만 닿는 Service 타입)로 바꿔서 ServiceLB 가 노드 80 번을 두고 Traefik 과 다투지 않게 한다.

  • agent 가 안 붙음: kubectl get nodes 가 1대뿐. 볼 곳은 agent 노드의 sudo journalctl -u k3s-agent -n 50 와 /var/log/k3s-bootstrap.log. 흔한 원인은 토큰 불일치, server 주소 오타, 보안 그룹이 노드끼리 6443 을 막음(우리 코드는 self 규칙으로 전부 허용).

왜 k3s 를 골랐나 (대안)

kubeadm: CKA 시험 방식이라 공부에는 좋지만, 노드마다 containerd 설치 → kubeadm init/join → CNI 설치 단계가 많아 user_data 가 길어지고 당일 시간을 다 쓴다. EKS: 컨트롤 플레인을 AWS 가 운영해 편하지만 컨트롤 플레인 요금이 따로 붙고 생성이 길며, "VM 위 직접 구축" 을 보여 주는 목적과 어긋난다. k3s: 설치 한 줄, 설정 파일 하나, 라벨·taint 를 설정 파일에 바로 쓸 수 있다. 대가는 AWS 를 아는 클라우드 컨트롤러가 없어서 죽은 노드 정리, 로드밸런서 연동을 직접 해야 한다는 것. 자세한 표는 결정 표.

우리 k3s 설정 템플릿 한 줄씩

k3s 의 구조와 설정 파일 규칙을 알았으니, 우리 노드가 첫 부팅 때 k3s 에 실제로 무엇을 넘기는지 파일 단위로 본다. 이 절의 파일들은 다음 절의 Terraform 이 값을 채워 EC2 에 넣는다.

템플릿 세 개가 하는 일

poc/07-ec2-k3s/k3s/ 의 세 파일은 EC2 가 첫 부팅 때 실행할 스크립트의 재료다. 확장자 .tftpl 은 "Terraform 템플릿" 이라는 뜻으로, ${이름} 자리를 Terraform 이 채운다.

server-config.yaml.tftpl

system 노드의 config.yaml. 토큰, kubeconfig 권한, 라벨 2개, taint 1개.

agent-config.yaml.tftpl

exec·build 노드 공용 config.yaml. server 주소, 토큰, 라벨 2개, build 일 때만 taint, graceful shutdown 용 kubelet 설정 파일 경로(처음엔 플래그로 잘못 적혀 있었다. 아래 경고).

install.sh.tftpl

user_data 본체. 위 둘 중 하나를 config.yaml 로 쓰고, 공식 설치 스크립트로 server 또는 agent 를 설치.

README 는 이 세 파일을 "Jeong 이 빈칸을 채우는 파일" 로 설명하지만, 10/20 에 정답본(solution/k3s/)으로 덮어써서 지금은 두 폴더 내용이 같다 (diff -r k3s solution/k3s 차이 없음).

첫 부팅에 무엇이 어떤 순서로 도나

EC2 의 우분투 AMI 에는 cloud-init(첫 부팅 때 user_data 를 읽어 실행하는 표준 프로그램)이 들어 있다. 아래 순서의 heredoc 은 셸에서 여러 줄 텍스트를 파일에 그대로 쓰는 문법이다.

템플릿은 Terraform 안에서 두 겹으로 채워진다. 먼저 설정 템플릿을 채워 YAML 문자열을 만들고, 그 문자열을 설치 스크립트 템플릿의 ${config} 자리에 통째로 넣는다.

세 파일을 한 줄씩

poc/07-ec2-k3s/k3s/server-config.yaml.tftpl주석 일부 생략
token: "${token}"
write-kubeconfig-mode: "0600"
node-label:
  - "pool=system"
  - "capacity-type=on-demand"
node-taint:
  - "CriticalAddonsOnly=true:NoExecute"
# 끄는 기본 부품 없음. traefik, servicelb, local-storage, metrics-server 그대로 쓴다.
# Cilium 으로 바꾸려면 flannel-backend: "none", disable-network-policy: true 가 필요하다
token
조인 비밀. k3s.tf 가 random_password.k3s_token.result 를 넣는다. 큰따옴표로 감싸 YAML 이 특수문자를 오해하지 않게 한다 (생성 시 special = false 라 실제로는 영숫자뿐).
write-kubeconfig-mode
/etc/rancher/k3s/k3s.yaml 파일 권한. 0600 = root 만. get-kubeconfig.sh 는 SSM Run Command(노드에 들어가지 않고 명령 한 줄을 원격 실행하는 SSM 기능. 접속 절)로 root 권한으로 읽으므로 이 값으로 충분하고, 노드 안 일반 사용자에게 관리자 kubeconfig 를 노출하지 않는다.
node-label
pool=system 은 Argo CD 가 nodeSelector 로 고르는 이름표. capacity-type=on-demand 는 NTH 를 이 노드에 안 띄우는 기준(NTH 는 capacity-type: spot 만 고른다).
node-taint
CriticalAddonsOnly=true:NoExecute. NoSchedule 은 "새로 못 온다" 만, NoExecute 는 "이미 있던 것도 쫓아낸다" 까지다. k3s 는 이 값을 kubelet 의 --register-with-taints 로 넘겨 Node 오브젝트가 생기는 순간 taint 가 함께 붙으므로 "taint 가 붙기 전 파드가 들어오는 틈" 은 없다. NoExecute 의 실제 효과는 누군가 나중에 taint 를 지웠다가 다시 붙이거나 toleration 을 뺀 파드가 남아 있을 때도 내보낸다는 것이고, 평소에는 NoSchedule 과 같다. 목적은 일반 파드가 컨트롤 플레인 노드의 메모리를 먹다가 API 서버가 OOM(Out of Memory, 메모리가 모자라 커널이 프로세스를 죽이는 일)으로 죽는 걸 막는 것이다.

server: "${server_url}"
token: "${token}"

node-label:
  - "pool=${pool}"
  - "capacity-type=${capacity_type}"

%{ if pool == "build" ~}
node-taint:
  - "pool=build:NoSchedule"
%{ endif ~}
# (실행 노드에는 taint 를 안 건다 = 아무 설정 없는 파드의 기본 착지점. README 결정 3)

# 주의: shutdownGracePeriod 는 kubelet 의 "명령줄 플래그" 가 아니라 KubeletConfiguration 파일의 필드다.
#   kubelet-arg 에 "shutdown-grace-period=60s" 처럼 적으면 kubelet 이 unknown flag 로 죽고 노드가 영영 Ready 가 안 된다.
#   그래서 install.sh 가 /etc/rancher/k3s/kubelet.yaml 을 먼저 쓰고, 여기서는 그 파일을 config= 로 넘긴다.
kubelet-arg:
  - "config=/etc/rancher/k3s/kubelet.yaml"
server
https://<server 사설 IP>:6443. 공개 IP 가 아니라 사설 IP 라 보안 그룹 self 규칙 안에서만 오간다.
pool=${pool}
한 파일로 두 풀을 만든다. k3s.tf 의 for 식이 exec, build 를 넣는다.
capacity-type=${capacity_type}
변수 exec_capacity_type 에서 온다. 값을 spot 으로 고정해 버리면 누군가 exec_capacity_type = "on-demand" 로 바꾼 날 라벨이 거짓말을 하게 되고, NTH 가 온디맨드 노드에 떠서 쓸데없이 도는 정도로 끝나지만 비용 집계·배치 판단이 틀어진다 (README 4.1 확인 질문).
%{ if pool == "build" ~}
Terraform 문자열 지시문(directive). 조건이 참일 때만 그 사이 줄이 남는다. ~ 는 지시문 옆의 공백·줄바꿈을 지워 빈 줄이 안 생기게 한다.
kubelet-arg
kubelet 에 그대로 넘기는 명령줄 인자(-- 를 뺀 이름). 여기서는 config=/etc/rancher/k3s/kubelet.yaml 하나로, kubelet 설정 파일(KubeletConfiguration) 경로를 넘긴다. 그 파일은 install.sh 가 agent 역할일 때만 써 주며, 내용은 "OS 종료를 kubelet 이 최대 60초 늦추며 파드를 정리하고, 그중 마지막 10초는 중요 파드 몫" 이다(graceful node shutdown, 원리는 스팟 회수 절). 왜 플래그가 아니라 파일인가: kubelet 에는 --shutdown-grace-period 라는 플래그가 없고, 이 기능은 설정 파일 필드 shutdownGracePeriod·shutdownGracePeriodCriticalPods 로만 켤 수 있다. 처음 레포는 이것을 플래그로 적었다가 이 검수에서 고쳤다(아래 경고).

있었던 레포 버그: 플래그로 적은 kubelet-arg 로는 agent 가 클러스터에 붙지 못했다 (10/20 고침)

고치기 전 agent-config.yaml.tftpl 은 kubelet-arg: ["shutdown-grace-period=60s", "shutdown-grace-period-critical-pods=10s"] 였다. kubelet 은 모르는 플래그를 받으면 시작하지 못하고 failed to parse kubelet flag: unknown flag: --shutdown-grace-period 로 끝난다(kubelet 소스 cmd/kubelet/app/server.go. kubelet 의 플래그 목록 options.go 에 shutdown 관련 플래그는 없다). k3s 는 kubelet-arg 값을 검사 없이 그대로 kubelet 에 붙이고, kubelet 이 죽으면 agent 프로세스 전체를 내린다(pkg/agent/run.go: kubelet 시작 실패 → RequestShutdown). 그 상태로 apply 했다면 exec·build 노드가 영영 Ready 가 되지 않았을 것이고, 증상은 "노드가 1대뿐", 볼 곳은 agent 의 journalctl -u k3s-agent 였다. render-k3s.sh 는 bash 문법과 YAML 모양만 보므로 이 오류를 잡지 못한다(렌더 결과가 YAML 로 멀쩡해 보이는 것이 함정이었다). 한 번도 apply 한 적이 없어 실제로 겪지는 않았고, 공식 문서·소스 대조로 찾았다.

고친 방법은 kubelet 설정 파일을 따로 쓰고 그 경로만 kubelet-arg 로 넘기는 것이다. 최근 k3s 는 kubelet 설정을 드롭인 폴더 /var/lib/rancher/k3s/agent/etc/kubelet.conf.d/ 로 관리한다: 자기 기본값을 00-k3s-defaults.conf 로 쓰고, kubelet-arg: ["config=경로"] 로 받은 파일을 10-cli-config.conf 로 복사하며, config-dir=폴더 는 20-cli-config-dir/ 로 복사한 뒤 kubelet 에 --config-dir 로 이 폴더를 넘긴다(소스 pkg/agent/config/config.go). 뒤 번호가 앞 번호를 덮으므로 내 값이 k3s 기본값을 이긴다. 그 밖의 kubelet-arg 는 플래그로 그대로 붙는다. 지금 레포(k3s/ 와 solution/k3s/ 동일)는 install.sh 가 agent 역할일 때 /etc/rancher/k3s/kubelet.yaml 을 쓰고, agent-config 가 그 경로를 config= 로 넘긴다(아래 install.sh 발췌).

poc/07-ec2-k3s/k3s/install.sh.tftpl주석 일부 생략
#!/bin/bash
set -euo pipefail
exec > >(tee -a /var/log/k3s-bootstrap.log) 2>&1
echo "[bootstrap] role=${role} start $(date -u +%Y-%m-%dT%H:%M:%SZ)"

mkdir -p /etc/rancher/k3s
cat > /etc/rancher/k3s/config.yaml <<'K3SCONFIG'
${config}
K3SCONFIG
chmod 600 /etc/rancher/k3s/config.yaml

%{ if role == "agent" ~}
cat > /etc/rancher/k3s/kubelet.yaml <<'KUBELET'
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
shutdownGracePeriod: 60s
shutdownGracePeriodCriticalPods: 10s
KUBELET
%{ endif ~}

curl -sfL https://get.k3s.io | INSTALL_K3S_CHANNEL='${k3s_channel}' sh -s - ${role}

echo "[bootstrap] role=${role} done $(date -u +%Y-%m-%dT%H:%M:%SZ)"
  1. set -euo pipefail: 실패한 명령이 있으면 멈춤(-e), 정의 안 된 변수는 에러(-u), 파이프 중간 실패도 실패(pipefail). curl | sh 에서 curl 이 실패해도 그냥 넘어가는 일을 막는다.
  2. exec > >(tee -a …) 2>&1: 이후 모든 표준 출력·에러를 로그 파일에도 쓴다. cloud-init 로그(/var/log/cloud-init-output.log)에도 남지만 우리 전용 파일이 찾기 쉽다.
  3. $(date …): 셸의 명령 치환. Terraform 은 ${ 와 %{ 만 해석하므로 $( 와 %Y 는 그대로 통과한다.
  4. <<'K3SCONFIG': 따옴표 붙은 heredoc 이라 bash 가 안의 $ 를 해석하지 않는다. 토큰에 $ 가 섞여도 안전. Terraform 이 이미 ${config} 를 채운 뒤라 bash 가 볼 땐 순수한 YAML 이다.
  5. chmod 600: 토큰이 들어 있는 파일이라 root 만.
  6. %{ if role == "agent" ~} … %{ endif ~}: agent 역할일 때만 kubelet 설정 파일을 쓴다. server 에는 agent-config 가 없으니 이 파일을 가리키는 kubelet-arg 도 없고, 파일도 안 만든다. 'KUBELET' heredoc 안은 Terraform 자리표시자가 없는 순수 YAML 이다.
  7. INSTALL_K3S_CHANNEL: 설치 스크립트 환경 변수. stable 채널이면 설치 시점의 안정판이 깔린다. 그래서 같은 코드라도 날짜에 따라 버전이 다를 수 있고, measure.sh ready 가 실제 버전을 CSV 메모에 남긴다. 버전을 고정하려면 INSTALL_K3S_VERSION 을 쓴다.
  8. sh -s - ${role}: 표준 입력으로 받은 스크립트에 인자 server 또는 agent 를 넘긴다. 설치 스크립트는 이 인자로 서비스 이름(k3s/k3s-agent)을 정하고, /etc/rancher/k3s/config.yaml 은 k3s 가 시작할 때 스스로 읽는다.

우리 PoC 에서는

Terraform 의 k3s_template_dir 변수(기본 ../../k3s)로 템플릿 폴더를 바꿀 수 있다. 막혔을 때 ../../solution/k3s 로 정답본을 쓰게 하려던 손잡이인데, 지금은 두 폴더가 같다. gvisor.sh.tftpl 은 Claude 작성 파일이라 이 변수와 상관없이 terraform/cluster/ 에 있다.

깨지면 이렇게 보인다

  • 템플릿에 정의 안 된 자리표시자: terraform plan 단계에서 vars map does not contain key "…" 에러와 줄 번호. AWS 에 닿기 전에 잡힌다. render-k3s.sh 로 미리 볼 수 있다.
  • 주석 안의 ${: 주석이라도 Terraform 이 해석한다. 문법 설명은 말로 쓴다 (README 1.5 함정 2).
  • 셸 변수에 중괄호: ${VAR} 를 Terraform 이 가로챈다. $${VAR} 로 이스케이프. 우리 install 스크립트와 gvisor 스크립트는 중괄호 없는 $VAR 만 써서 해당 없음.
  • YAML 들여쓰기 오류: plan 은 통과하지만 노드에서 k3s 가 시작하지 못한다. 증상은 노드 수 부족, 볼 곳은 /var/log/k3s-bootstrap.log 와 journalctl -u k3s-agent.
  • agent 노드가 Ready 가 안 되고 journalctl 에 unknown flag: kubelet-arg 에 kubelet 이 모르는 플래그가 있다(고치기 전 레포가 이랬다). 설정 파일 필드는 config= 로 넘긴다.

왜 이렇게 했나 (대안)

config.yaml 파일 대 설치 명령 인자(INSTALL_K3S_EXEC="--node-label …"): 파일이면 노드에 들어가 cat 한 번으로 설정 전체가 보이고, 템플릿 조건문으로 풀별 차이를 깔끔하게 표현할 수 있다. user_data 에 직접 대 미리 구운 AMI(Packer): AMI 를 구우면 부팅이 빨라지지만 빌드 파이프라인이 하나 더 생긴다. 하루짜리 PoC 에는 user_data 가 맞다.

Taints and Tolerations

Terraform 기초와 우리 모듈의 그래프

템플릿에 값을 채우고 그것을 EC2 에 user_data 로 넣어 주는 주체가 Terraform 이다. 이 절은 Terraform 의 낱말(provider, resource, state …)과 우리 terraform/cluster 가 만드는 리소스들의 의존 관계를 본다. 다음 세 절(네트워크, IAM, 노드 풀)은 그 리소스들을 층별로 읽는다.

Terraform 은 무엇이고 왜 쓰나

Terraform 은 HashiCorp 의 IaC(Infrastructure as Code, 인프라를 코드 파일로 선언하고 도구가 맞추게 하는 방식) 도구다. 파일 문법은 HCL(HashiCorp Configuration Language)이다. 01 의 Argo CD 가 "Git 의 매니페스트 = 클러스터의 정답" 이었다면, Terraform 은 ".tf 파일 = 클라우드 리소스의 정답" 이다. 둘 다 선언형이다: "VPC 를 만들어라" 가 아니라 "VPC 가 이런 모양으로 있어야 한다" 를 적고, 도구가 현재 상태와 비교해 차이를 메운다.

Argo CD 와 크게 다른 점 하나: Argo CD 는 클러스터를 계속 감시하며 맞추지만(조정 루프), Terraform 은 사람이 명령할 때만 한 번 비교하고 바꾼다. 그 사이의 "내가 무엇을 만들었나" 기억은 state 파일에 둔다.

구성 요소와 흐름

provider
특정 API 를 아는 플러그인. versions.tf 의 required_providers 에 hashicorp/aws ~> 6.0, hashicorp/random ~> 3.6. terraform init 이 내려받고 .terraform.lock.hcl 에 정확한 버전과 해시를 고정한다. default_tags 로 모든 리소스에 Project=poc07, ManagedBy=terraform, Owner=jeong 태그를 붙인다.
resource
Terraform 이 만들고 관리하는 것. resource "aws_vpc" "this" 의 주소는 aws_vpc.this. 생성·변경·삭제가 모두 Terraform 몫.
data source
이미 있는 것을 읽기만 한다. data "aws_ami" "ubuntu"(Canonical 의 최신 우분투 24.04), data "aws_availability_zones", data "aws_iam_policy_document"(JSON 정책을 HCL 로 쓰는 도우미). 지우지 않는다.
variable / output
입력 손잡이와 결과값. variables.tf 의 기본값이 곧 "기본 구성" 이다. outputs.tf 의 server_instance_id, region, fis_template_id 를 스크립트들이 terraform output -raw 로 읽는다.
locals
이름 붙인 계산식. local.azs, local.server_user_data, local.agent_user_data.
module
재사용 가능한 .tf 묶음. modules/node-pool 을 pools.tf 에서 값만 바꿔 두 번 부른다. 루트 모듈(terraform/cluster) 안의 자식 모듈이다.
state
주소(module.exec_pool.aws_autoscaling_group.this)와 실제 ID(ASG 이름 등)·속성의 대응표. 우리는 원격 백엔드(backend, state 를 어디에 두나: 로컬 파일 또는 S3 같은 원격 저장소) 없이 로컬 파일 terraform.tfstate. 민감 값이 평문으로 들어간다(k3s 토큰). 그래서 .gitignore 에 *.tfstate 가 있다.

plan / apply / destroy 수명 주기

  1. terraform init: provider 와 모듈을 .terraform/ 에 받고 잠금 파일 생성. 한 번만.
  2. terraform validate: 문법·타입만. AWS 자격 증명 없이 된다. 클라우드 스레드가 여기까지 했다.
  3. terraform plan -out=day.tfplan: data source 조회(AMI·AZ) 때문에 자격 증명이 필요하다. 만들 것 목록을 보고 RUNBOOK B 의 체크(ASG 2개, NAT 없음, 22·6443 규칙 없음)를 한다. 결과를 파일로 저장하면 apply 가 정확히 그 계획만 실행한다.
  4. terraform apply: 그래프 순서로 생성. measure.sh up 은 -auto-approve 로 실행하면서 시간을 잰다.
  5. terraform destroy: state 에 있는 것 전부를 의존성 역순으로 삭제. measure.sh down.

세부 로직: 의존성 그래프, state 잠금, templatefile 규칙

의존성 그래프

Terraform 은 식 안의 참조(aws_vpc.this.id 같은)를 읽어 방향 그래프(DAG)를 만든다. 참조가 없는데 순서가 필요하면 depends_on 으로 명시한다. 서로 의존하지 않는 노드는 병렬로 만든다(기본 동시성 10). 우리 terraform/cluster 의 그래프는 다음과 같다.

state 와 잠금(locking)

  • 로컬 백엔드는 같은 폴더의 terraform.tfstate 하나에 쓰고, 실행 중엔 .terraform.tfstate.lock.info 로 같은 기계 안의 동시 실행을 막는다. 다른 사람·다른 기계와의 동시 실행은 못 막는다.
  • 팀이 같이 쓰려면 원격 백엔드(예: S3)를 쓴다. S3 백엔드의 use_lockfile = true 는 S3 자체에 .tflock 잠금 파일을 둬서 DynamoDB 테이블 없이 잠근다. Terraform 1.10 에서 실험 기능으로 들어왔고 1.11 에서 정식(GA)이 되면서 DynamoDB 인자들이 deprecated 됐다(각 버전 CHANGELOG). 우리 required_version = ">= 1.10" 은 본선 팀 계정에서 이 방식을 쓸 여지를 남긴다.
  • state 를 잃으면 Terraform 은 만든 것을 모른다 → destroy 가 아무것도 안 지운다. 그때는 check-leftovers.sh 가 태그로 찾아 주는 목록을 손으로 지워야 한다. state 는 커밋하지 않지만 지우지도 않는다.

lifecycle 메타 인자 (PoC 에서는 안 씀)

모든 resource 블록에 넣을 수 있는 lifecycle { … } 는 "Terraform 이 이 리소스를 다룰 때의 예외 규칙" 이다. 우리 코드에는 하나도 없지만, 본선에서 클러스터를 며칠 운영하면 바로 필요해진다.

  • ignore_changes = [desired_capacity]: 야간 예약이 ASG 를 0대로 내리면 다음 날 plan 이 "desired 0 → 2" 변경을 보여 준다. 하루짜리엔 그게 곧 "아침에 다시 켜기" 라 괜찮지만, 오토스케일러나 예약이 대수를 바꾸는 운영 클러스터에서는 이 인자로 Terraform 이 그 필드를 못 본 척하게 한다.
  • prevent_destroy = true: destroy 나 교체가 이 리소스를 지우려 하면 에러로 멈춘다. 예산 리소스나 state 버킷에 건다.
  • create_before_destroy = true: 교체할 때 새것을 먼저 만들고 옛것을 지운다. 시작 템플릿처럼 다른 리소스가 참조하는 것에 유용하다. 이름이 고정된 리소스(IAM 역할 이름 등)에는 충돌이 난다.
  • replace_triggered_by: "저것이 바뀌면 이것을 교체" 를 명시한다. 명령줄로는 terraform apply -replace=aws_instance.server 가 한 번짜리 같은 효과다.

templatefile 규칙

templatefile(path, vars):
  파일을 읽는다 (plan 시점에 존재해야 함. 실행 중 생성된 파일은 못 읽음)
  각 ${식} → vars 안의 이름만 참조 가능. 없는 이름이면 에러
  각 %{ if 조건 } … %{ else } … %{ endif } → 조건부 텍스트
  각 %{ for x in 목록 } … %{ endfor } → 반복 텍스트
  ~ 가 지시문 옆에 있으면 그쪽 공백·줄바꿈 제거
  $${ → 문자 그대로 "${",  %%{ → "%{"
  결과는 문자열 (YAML·JSON 검사는 안 함 → render-k3s.sh 가 대신)

user_data 쪽 규칙도 하나 있다. aws_instance.user_data 는 평문을 받으면 provider 가 알아서 base64 로 바꾸지만, aws_launch_template.user_data 는 base64 문자열을 요구한다. 그래서 모듈이 base64encode(var.user_data) 를 한다. user_data 는 base64 로 바꾸기 전 원문 기준 16 KB 한도가 있다(EC2 공식 문서). gVisor 스크립트를 붙여도 이 한도 안쪽이다.

우리 PoC 에서는

루트 모듈은 둘이다. terraform/budget(예산 알람 하나, 먼저 만들고 계속 둠)과 terraform/cluster(당일 만들고 당일 지움). state 도 따로라서 cluster 를 destroy 해도 예산은 남는다. 스크립트들은 terraform -chdir=terraform/cluster output -raw … 로 state 에서 값을 읽기 때문에, 맥의 state 파일이 사실상 "지금 떠 있는 클러스터의 주소록" 이다.

깨지면 이렇게 보인다

  • plan 이 NAT 게이트웨이나 22/6443 규칙을 보여 줌: 누군가 코드를 바꿨다. RUNBOOK B 규칙대로 멈춘다.
  • state 파일을 지움: destroy 가 "0 destroyed". 리소스는 그대로 과금 중. check-leftovers.sh 로 찾아 손으로 지운다.
  • apply 중간 실패: 이미 만든 것은 state 에 남는다. 원인을 고치고 다시 apply 하면 남은 것만 만든다. 그대로 두고 자리를 뜨면 반쪽 클러스터가 과금된다.

왜 Terraform 인가 (대안)

콘솔 클릭: 다음 날 같은 것을 다시 못 만들고, 무엇을 만들었는지 목록이 없어 지우다 빠뜨린다. AWS CLI 스크립트: 만들기는 되지만 "이미 있으면 건너뛰기" 와 역순 삭제를 직접 짜야 한다. CloudFormation: AWS 전용이고 상태는 AWS 가 관리해 편하지만, 본선 팀원 경험과 문서 양에서 Terraform 이 앞선다. eksctl: EKS 전용. Terraform 은 plan 으로 "만들기 전에 보기" 가 되고, destroy 가 state 기준으로 빠짐없이 지운다는 점이 하루짜리 실습의 비용 통제에 결정적이다.

AWS 네트워크 배치

Terraform 이 만드는 것 중 가장 아래층인 네트워크부터 읽는다. 앞 절의 의존성 그래프에서 VPC·서브넷·보안 그룹이 server 와 노드 풀보다 먼저 만들어지는 이유가 이 절이다.

무엇을 만들고 왜

terraform/cluster/network.tf 와 security.tf 가 만드는 것은 단순하다. VPC(Virtual Private Cloud, 내 전용 사설 네트워크) 하나, 그 안에 가용 영역(AZ, 같은 리전 안 서로 다른 데이터센터) 두 곳에 퍼블릭 서브넷 하나씩, 인터넷 게이트웨이(IGW) 하나, 보안 그룹 하나. NAT 게이트웨이(사설 IP 만 가진 노드가 밖으로 나갈 때 주소를 바꿔 주는 관리형 장치)와 프라이빗 서브넷(인터넷에서 직접 닿지 않는 서브넷)은 만들지 않는다.

원칙 두 줄: 나가는 길은 열고(k3s 설치, 이미지, GitHub, SSM 엔드포인트), 들어오는 길은 80/443 만, 내 IP 만(허용 범위는 CIDR, 즉 1.2.3.4/32 처럼 "IP 범위" 로 적는다). SSH(22)와 k3s API(6443)는 인터넷에 열지 않고 SSM 으로 들어간다.

패킷 하나가 지나가는 길

보안 그룹(Security Group)은 인스턴스의 네트워크 인터페이스(ENI) 앞에 붙는 상태 저장(stateful) 방화벽이다. 허용 규칙만 있고(거부 규칙 없음), 허용된 연결의 응답은 자동으로 통과한다. 그래서 "나감 전부 허용" 이 있으면 노드가 밖으로 연 연결(SSM, 이미지 받기)의 응답은 들어오는 규칙 없이도 돌아온다.

NAT 를 안 쓰는 대가

정석은 노드를 프라이빗 서브넷에 두고 NAT 게이트웨이로만 밖에 나가게 하는 것이다. NAT 게이트웨이는 켜져 있는 시간과 처리량 모두로 과금되고, 이 실습 규모에서는 그 고정 비용이 EC2 전부보다 크다 (network.tf 주석). 그래서 노드에 퍼블릭 IP 를 주고(map_public_ip_on_launch = true) 들어오는 문을 보안 그룹으로 닫았다. 대가는 셋이다.

  • 노드마다 퍼블릭 IPv4 가 생기고, 퍼블릭 IPv4 는 개수와 시간으로 과금된다.
  • 보안 그룹 한 장이 유일한 벽이다. 실수로 0.0.0.0/0 을 ingress_cidrs 에 넣으면 함수가 인터넷 전체에 열린다.
  • 노드가 인터넷 주소를 가지므로 포트 스캔 대상이 된다. 22·6443 은 규칙이 없어서 응답조차 없다(버려짐).

서브넷을 두 AZ 로 나눈 이유는 고가용성이 아니라 스팟 재고다 (network.tf 주석). 스팟 용량은 AZ·인스턴스 타입 조합(용량 풀)마다 따로라서, 한 AZ 에 없으면 다른 AZ 에서 받는다. server 는 첫 서브넷에 고정이라 그 AZ 가 장애면 클러스터 API 가 같이 멈춘다.

깨지면 이렇게 보인다

  • curl <IP>/fn 응답 없음 (타임아웃): 내 IP 가 바뀌어 ingress_cidrs 와 다름. curl -s https://checkip.amazonaws.com 으로 확인 → tfvars 수정 → apply (SG 규칙만 바뀜).
  • build 노드 IP 로 curl 하면 연결 거부: build 노드에는 svclb 파드가 없다(taint). 정상. exec 노드 IP 를 쓴다.
  • 노드가 클러스터에 안 붙고 SSM 에도 안 보임: 라우트 테이블(서브넷의 패킷이 어디로 갈지 적은 표) 연결 전에 부팅해 바깥에 못 나갔을 수 있다. server 는 depends_on = [aws_route_table_association.public] 로 막아 두었다.

왜 이렇게 했나 (대안)

프라이빗 서브넷 + NAT: 노드가 인터넷 주소를 안 가져 정석이지만, NAT 의 고정 비용이 하루짜리 실습 전체보다 크다. 프라이빗 + VPC 엔드포인트(SSM, ECR, S3): NAT 없이 AWS 서비스엔 닿지만 GitHub·get.k3s.io 같은 외부엔 못 나간다. IPv6 전용 + Egress-only IGW: 퍼블릭 IPv4 비용이 없지만 k3s·flannel·외부 레지스트리의 IPv6 지원을 하나하나 확인해야 한다. 본선(팀 계정, 며칠 운영)에서는 프라이빗 + NAT 를 다시 검토한다 (README 7절 비교 시나리오).

IAM: 인스턴스 프로파일, SSM, FIS 역할

네트워크가 "길" 이라면 IAM 은 "열쇠" 다. 노드가 SSM 에 등록하고, FIS 가 EC2 를 건드릴 수 있는 권한이 어디서 오는지 본다.

누가 어떤 권한으로 AWS API 를 부르나

IAM(Identity and Access Management) 역할(role)은 "이 권한 묶음을 누가 잠깐 빌려 쓸 수 있나" 다. 사람이 아니라 서비스가 빌려 쓴다. 우리 코드에는 역할이 둘이다.

poc07-node (노드 역할)

빌려 쓰는 쪽: EC2(ec2.amazonaws.com). 권한: AWS 관리형 정책 AmazonSSMManagedInstanceCore 하나. SSM 에이전트가 Systems Manager 에 등록하고 세션·명령을 받는 데 필요한 최소 권한이다.

poc07-fis (실험 역할)

빌려 쓰는 쪽: FIS(fis.amazonaws.com). 권한: AWSFaultInjectionSimulatorEC2Access. 스팟 회수 경고를 보내는 EC2 API 를 부를 수 있다. enable_fis = false 면 안 만든다.

EC2 는 역할을 직접 붙이지 못하고 인스턴스 프로파일(instance profile)이라는 그릇에 담아 붙인다. server 의 iam_instance_profile 과 Launch Template 의 iam_instance_profile { name } 이 같은 프로파일을 가리킨다.

역할을 빌려 쓰는 원리

  1. 신뢰 정책(assume role policy): 역할 쪽에 "누가 이 역할을 맡을 수 있나". data "aws_iam_policy_document" "ec2_assume" 이 sts:AssumeRole 을 Service: ec2.amazonaws.com 에게 허락한다.
  2. 권한 정책: 역할을 맡은 뒤 할 수 있는 것. aws_iam_role_policy_attachment 로 관리형 정책을 붙인다.
  3. 임시 자격 증명: 노드 안의 프로그램(SSM 에이전트)은 IMDS 의 iam/security-credentials/ 경로에서 자동으로 갱신되는 임시 키를 받는다. 키를 파일에 넣거나 user_data 에 적을 일이 없다.

IMDS 설정도 같이 본다. server 와 Launch Template 모두 http_tokens = "required"(IMDSv2 강제)와 http_put_response_hop_limit = 2 다. IMDSv2 는 PUT 으로 세션 토큰을 먼저 받아야 해서 SSRF(Server-Side Request Forgery, 서버가 공격자 대신 내부 주소로 요청을 보내게 만드는 공격) 같은 단순 GET 공격으로 자격을 빼가기 어렵다. hop limit(기본값 1)을 2 로 올리면 그 토큰 응답이 네트워크 홉 하나를 더 넘을 수 있어서, 호스트 네트워크를 안 쓰는 파드(노드 안에서 한 번 더 라우팅되는 파드 네트워크)에서도 IMDS 에 닿게 한다. 반대로 말하면 아무 파드나 노드 역할 자격을 읽을 수 있다는 뜻이고, 그래서 노드 역할 권한을 SSM 하나로 좁게 둔 것이 중요하다.

노드 풀 모듈: Launch Template + Auto Scaling Group

네트워크와 권한이 준비됐으니 그 위에 노드를 올린다. system 노드는 aws_instance 한 대지만, exec·build 는 "사라지면 다시 채워지는" 풀이어야 해서 모듈로 묶었다.

풀 하나 = 설계도 하나 + 관리자 하나

terraform/modules/node-pool 은 노드 풀 하나를 만든다. Launch Template(시작 템플릿)은 "이런 모양의 인스턴스" 설계도(AMI, 타입, user_data, 프로파일, 보안 그룹, 디스크, 태그)이고, Auto Scaling Group(ASG)은 "그걸 항상 desired 대 유지" 하는 관리자다. 스팟이 회수되면 ASG 가 새 스팟을 받아 오고, 새 노드는 같은 user_data 로 k3s agent 를 깔고 같은 라벨로 스스로 붙는다.

시스템 노드만 ASG 가 아니라 aws_instance 다. server 가 새로 뜨면 빈 SQLite 의 빈 클러스터라서 "자동 교체" 가 의미가 없기 때문이다 (server.tf 주석).

스팟은 싸지만 사라진다

스팟 인스턴스는 EC2 의 남는 용량을 할인된 값에 빌리는 구매 방식이다. AWS 가 그 용량이 필요해지면 2분 전에 예고(Spot Instance interruption notice)하고 인스턴스를 회수한다(우리 ASG 기본 동작은 종료). 그보다 앞서 "회수 위험이 높아졌다" 는 리밸런스 권고(rebalance recommendation)가 올 수도 있다. 둘 다 인스턴스 메타데이터(IMDS)와 EventBridge(AWS 의 이벤트 버스. 서비스가 내는 사건을 규칙으로 골라 다른 서비스로 보낸다) 이벤트로 알 수 있다. 회수 때 인스턴스를 종료할지, 중지할지, 최대 절전할지는 스팟 요청의 "중단 동작" 으로 고르는데 ASG 가 만든 스팟은 종료만 쓴다.

우리 설계는 이 2분을 쓰는 장치와, 2분을 못 쓰더라도 마지막에 정리하는 장치를 겹쳐 둔다.

  1. NTH(aws-node-termination-handler): AWS 가 만든 작은 프로그램. 스팟 노드마다 DaemonSet 파드 하나가 IMDS 를 지켜보다가 회수 예고가 뜨면 노드를 cordon(새 파드 금지) + drain(파드를 PDB 를 지키며 내보내기).
  2. PDB(PodDisruptionBudget): drain 같은 "자발적 중단" 때 지켜야 할 최소 파드 수. fn-sample 을 한꺼번에 내보내지 않게 "최소 1개는 살아 있게" (08장 방어 3종).
  3. topologySpreadConstraints(파드를 노드마다 고르게 흩는 규칙): 애초에 두 파드를 서로 다른 exec 노드에 흩어 둔다. 한 노드가 빠져도 한쪽은 응답한다. fn-sample 은 06 단계가 고른 최종 조합(DoNotSchedule + nodeTaintsPolicy: Honor + matchLabelKeys)을 그대로 쓴다(08장).
  4. tolerationSeconds 20: 노드가 갑자기 죽었을 때(NTH 가 못 본 경우) 파드가 쫓겨나기까지 기다리는 시간을 기본 300초에서 20초로 줄인다. 역시 06 의 방어 조합이다.
  5. ASG: 줄어든 대수를 새 스팟으로 채운다(capacity rebalance 면 미리).
  6. graceful node shutdown: 그래도 남은 파드는 OS 가 꺼질 때 kubelet 이 최대 60초 동안 정상 종료시킨다(값은 템플릿 절의 kubelet 설정 파일에서 온다).

의사코드의 Eviction 은 "PDB 를 지키면서 이 파드를 내보내 달라" 는 API 요청이고, SIGTERM 은 "곧 끝내라" 는 신호, SIGKILL 은 강제 종료, 그 사이 기다리는 시간이 파드의 terminationGracePeriodSeconds(기본 30초)다. 06 단계에서 본 함정도 여기 그대로다: PDB minAvailable 을 replicas 와 같게(2) 두면 허용 중단 수가 늘 0 이라 drain 이 끝나지 않고, 2분 뒤 노드가 그냥 꺼진다 = 예고 없는 장애와 같아진다 (06 README 4.4, ANALYSIS B12). 흩어 놓기의 세 필드 뜻: whenUnsatisfiable: DoNotSchedule 은 "고르게 못 흩으면 아예 안 띄운다"(ScheduleAnyway 는 "그래도 띄운다"), nodeTaintsPolicy: Honor 는 파드가 못 견디는 taint 가 붙은 노드(죽어서 unreachable taint 가 붙은 노드, cordon 된 노드)를 "흩을 자리" 로 세지 않게 하고, matchLabelKeys: [pod-template-hash] 는 롤링 배포 중 옛 ReplicaSet 의 파드를 안 세서 새 파드끼리만 고르게 흩는다. 세 필드가 왜 같이 있어야 하는지는 08장 방어 3종이 실험으로 보여 준다.

graceful node shutdown

  • kubelet 은 systemd-logind 의 inhibitor lock(지연 잠금: "끄기 전에 나한테 시간을 달라")을 잡아 OS 종료를 shutdownGracePeriod(우리 60s)까지 늦춘다. 종료 이벤트를 받으면 일반 파드를 먼저, 그다음 중요 파드(system-cluster-critical·system-node-critical 우선순위 클래스)를 종료한다. 중요 파드 몫이 shutdownGracePeriodCriticalPods(우리 10s) 이고, 일반 파드는 그 차이(50초) 안에 끝나야 한다. 두 값은 install.sh 가 쓰는 /etc/rancher/k3s/kubelet.yaml(KubeletConfiguration)의 필드이지 플래그가 아니다(템플릿 절).
  • systemd-logind 의 InhibitDelayMaxSec(기본 5초)가 이보다 짧으면 kubelet 이 스스로 /etc/systemd/logind.conf.d/99-kubelet.conf 에 더 큰 값을 쓰고 logind 를 다시 읽게 한다(kubelet 소스 nodeshutdown_manager_linux.go). 그래서 따로 손볼 것은 없다. 다만 공식 문서는 우분투·데비안의 unattended-upgrades 패키지가 이 값을 30초로 바꿔 둘 수 있다고 경고하니, 당일 systemd-inhibit --list 로 kubelet 의 잠금이 보이는지 확인한다. 이 관리자가 시작에 실패해도 kubelet 은 그냥 계속 뜬다(치명적이지 않은 부품으로 취급).
  • 이렇게 종료된 파드는 Failed 상태, 사유(reason) Terminated, 메시지 Pod was terminated in response to imminent node shutdown. 로 남는다(공식 문서). Deployment 는 새 파드를 다른 노드에 만든다.
  • EC2 가 스팟을 회수할 때 OS 에 ACPI(하드웨어가 OS 에 "전원을 끈다" 고 알리는 표준) 종료 신호를 주어 systemd 종료 절차가 돌고 inhibitor 가 효과를 내는지, 아니면 하이퍼바이저가 바로 끄는지는 【확인 필요: AWS 문서 "Spot Instance interruptions" 의 종료 절차 설명과, 당일 회수된 노드의 journalctl -u k3s-agent 에 shutdown manager 로그가 남는지로 확정】. 그래서 README 도 이걸 "이중 안전장치" 로만 둔다.

AWS FIS 로 스팟 회수 연습하기

회수 흐름을 설계했으면 그 흐름이 정말 그렇게 도는지 봐야 한다. 진짜 회수는 언제 올지 모르므로, AWS 가 제공하는 "일부러 회수하기" 를 쓴다.

진짜 회수 예고를 일부러 보낸다

AWS FIS(Fault Injection Service)는 장애를 일부러 일으키는 관리형 서비스다. 06 단계가 docker pause 로 노드 죽음을 흉내 냈다면, FIS 의 aws:ec2:send-spot-instance-interruptions 액션은 진짜 스팟 회수 예고를 대상 인스턴스에 보내고 정해진 시간 뒤 인스턴스를 회수한다. 그래서 IMDS → NTH → drain → ASG 교체 경로를 실제와 똑같이 지난다.

실험 템플릿(experiment template)은 "무엇을(액션), 누구에게(대상), 어떤 권한으로(역할), 언제 멈추나(중지 조건)" 한 장이다. 템플릿을 만드는 것은 무료이고, 실험을 실행할 때 액션 시간만큼 과금된다.

measure.sh spot 이 하는 일

세부: 템플릿 코드와 엣지 케이스

poc/07-ec2-k3s/terraform/cluster/fis.tf발췌
resource "aws_fis_experiment_template" "spot_interrupt" {
  count    = var.enable_fis ? 1 : 0
  role_arn = aws_iam_role.fis[0].arn
  action {
    name      = "interrupt-one-exec-node"
    action_id = "aws:ec2:send-spot-instance-interruptions"
    parameter { key = "durationBeforeInterruption"  value = "PT2M" }
    target    { key = "SpotInstances"  value = "exec-spot" }
  }
  target {
    name           = "exec-spot"
    resource_type  = "aws:ec2:spot-instance"
    selection_mode = "COUNT(1)"
    resource_tag { key = "Pool"     value = "exec" }
    resource_tag { key = "Project"  value = var.project }
    filter { path = "State.Name"  values = ["running"] }
  }
  stop_condition { source = "none" }
}
  • count = var.enable_fis ? 1 : 0: 조건부 리소스. 그래서 참조가 aws_iam_role.fis[0], output 도 var.enable_fis ? …[0].id : "". measure.sh 는 빈 문자열이면 "enable_fis=false 로 만들어졌다" 로 멈춘다.
  • durationBeforeInterruption = "PT2M": ISO 8601 기간 표기(PT2M = 2분). 액션 시작부터 실제 회수까지의 시간으로, 허용 범위는 2분(PT2M)에서 15분(PT15M)까지다. 공식 액션 문서: 액션이 시작되면 리밸런스 권고를 즉시 보내고, 회수 2분 전에 회수 예고를 보낸다. 우리는 2분이라 권고와 예고가 사실상 동시에 간다. 길게 주면 "권고 → 예고" 사이의 capacity rebalance 동작을 따로 볼 수 있다.
  • selection_mode = "COUNT(1)": 조건에 맞는 것 중 1대만 무작위로. ALL 이면 exec 2대를 동시에 회수해 함수가 완전히 끊긴다.
  • resource_tag 두 개: 설계 의도는 "두 태그를 모두 가진 인스턴스만" 이다 【확인 필요: 여러 resource_tag 가 AND 로 묶이는지는 FIS 사용자 가이드 Targets 페이지의 "Resource tags" 절 문구로 확정한다. 이번 검수에서는 그 문구를 직접 보지 못했다】. 어느 쪽이든 Project 태그는 같은 계정의 다른 실습 인스턴스를 건드리지 않게 하는 안전장치이고, 실험 전 aws ec2 describe-instances --filters Name=tag:Pool,Values=exec Name=tag:Project,Values=poc07 로 후보를 눈으로 확인하면 된다.
  • filter State.Name = running: 막 종료 중인 인스턴스를 고르지 않게.
  • stop_condition source = "none": FIS 는 중지 조건을 최소 하나 요구해서, "없음" 을 명시적으로 쓴다. 운영에서는 CloudWatch 알람(예: 오류율)을 걸어 실험이 선을 넘으면 자동 중단한다.

맥에서 클러스터에 닿기: SSM 포트 포워딩

여기까지가 클러스터를 만들고 지키는 이야기였다. 이제 맥에서 그 클러스터에 kubectl 로 닿는 길이다. 네트워크 절에서 22·6443 을 닫았으니 다른 길이 필요하다.

6443 을 열지 않고 kubectl 쓰기

SSM(AWS Systems Manager)의 Session Manager 는 노드 안의 SSM 에이전트가 밖으로 AWS 의 SSM 엔드포인트에 연결을 열어 두고, 그 연결 위로 셸이나 포트를 실어 나르는 기능이다. 들어오는 포트가 하나도 필요 없다. AWS-StartPortForwardingSession 문서를 쓰면 맥의 로컬 포트를 노드의 포트로 이어 준다.

두 스크립트의 순서

세부: 스크립트 줄 단위

poc/07-ec2-k3s/scripts/tunnel.sh발췌
ID=$($TF output -raw server_instance_id)
REGION=$($TF output -raw region)
LOCAL_PORT=${LOCAL_PORT:-6443}
aws ssm start-session --region "$REGION" --target "$ID" \
  --document-name AWS-StartPortForwardingSession \
  --parameters "{\"portNumber\":[\"6443\"],\"localPortNumber\":[\"$LOCAL_PORT\"]}"
  • portNumber 는 노드 쪽 포트, localPortNumber 는 맥 쪽 포트. 맥 6443 이 이미 쓰이면 LOCAL_PORT=16443 ./scripts/tunnel.sh 로 바꾸고 kubeconfig 의 서버 주소도 맞춰야 한다.
  • 원격 호스트로의 포워딩(AWS-StartPortForwardingSessionToRemoteHost)도 있다. server 를 거쳐 다른 노드의 포트로 갈 때 쓴다 (예: exec 노드 10250). 우리는 쓰지 않는다.
  • 세션에는 유휴 시간 제한이 있다. Session Manager 환경 설정(preferences)의 "Idle session timeout" 은 기본 20분, 1~60분 사이로 바꿀 수 있다(공식 문서). 포트 포워딩 세션도 세션이므로 같은 설정의 적용을 받는 것으로 보이지만 【확인 필요: 터널 위로 트래픽이 흐르는 동안을 "활동" 으로 치는지는 Session Manager preferences 문서의 idle timeout 설명과 당일 터널 관찰로 확정】. 끊기면 kubectl 이 connection refused → 터널을 다시 켠다 (README 8절).
poc/07-ec2-k3s/scripts/get-kubeconfig.sh발췌
CMD_ID=$(aws ssm send-command --region "$REGION" --instance-ids "$ID" \
  --document-name AWS-RunShellScript \
  --parameters 'commands=["cat /etc/rancher/k3s/k3s.yaml"]' \
  --query 'Command.CommandId' --output text)
sleep 3
STATUS=$(aws ssm get-command-invocation … --query 'Status' --output text)
if [ "$STATUS" = "Success" ]; then
  aws ssm get-command-invocation … --query 'StandardOutputContent' --output text > "$OUT"
  chmod 600 "$OUT"
  kubectl --kubeconfig "$OUT" config rename-context default poc07
  • Run Command 는 root 로 실행되어 0600 파일도 읽는다. 파일이 아직 없으면(k3s 설치 중) cat 이 실패 → Status 가 Failed → 5초 뒤 재시도.
  • StandardOutputContent 는 API 레퍼런스대로 플러그인이 stdout 에 쓴 앞 24,000자까지만 돌려준다. k3s.yaml 은 CA·클라이언트 인증서·키를 base64 로 담아도 수 KB 라 여유가 있다. 그보다 긴 파일을 가져올 때는 Run Command 의 S3 출력(--output-s3-bucket-name)으로 받는다.
  • 이 kubeconfig 는 클러스터 관리자 자격(client cert)이다. 런북 F 는 destroy 후 rm kubeconfig.

EC2 위 gVisor: 진짜 커널에서 runc 와 비교

선택 과제다. 06장에서 kind 노드 안에 깔다 만 gVisor(runsc, 컨테이너의 시스템 호출을 사용자 공간 커널이 가로채 호스트 커널을 보호하는 샌드박스 런타임, 06장)를 진짜 VM 에서 끝까지 돌려 본다.

왜 여기서 다시 하나

04 단계에서 gVisor(runsc)는 kind 노드에 설치까지는 됐지만, kind 노드가 "컨테이너 안의 컨테이너 런타임" 이라 함수 실행이 권한 문제로 실패했다 (04 README 9절 보충). EC2 노드는 진짜 리눅스 VM 이라 그 제약이 없을 것이다(README 도 추정으로 적었고, 당일 gvisor-ec2.sh check 로 확인한다). 그래서 runc(표준 컨테이너 런타임) 대 gVisor 콜드 스타트(함수 파드가 0개일 때 첫 요청이 파드가 뜨기까지 기다리는 시간, 05장) 비교는 07 의 선택 과제(RUNBOOK H)로 옮겼다. 켜는 손잡이는 enable_gvisor = true 하나다.

설치와 등록이 첫 부팅에 일어난다

스팟이 회수돼 ASG 가 새 노드를 띄워도 같은 user_data 라서 gVisor 가 다시 깔린다. 04 의 RuntimeClass(파드가 어느 컨테이너 런타임으로 돌지 고르는 리소스. handler: runsc, scheduling.nodeSelector: pool=exec)와 ksvc 는 그대로 쓰고, 이미지만 ttl.sh(로그인 없는 공개 임시 레지스트리)에 올린 amd64(인텔·AMD 64비트. 애플 실리콘 맥은 arm64 라 따로 빌드해야 한다) 이미지로 바꾼다.

핵심 개념 체크리스트

  • 노드가 VM 이 되면 새로 생기는 문제 셋(돈, 사라짐, 접속)과 각각의 대응을 말할 수 있다
  • k3s server 와 agent 의 차이, 단일 server 의 SQLite(kine) 와 HA 의 내장 etcd 차이를 설명할 수 있다
  • agent 조인에 필요한 두 값(server 주소, 토큰)과 node-password 가 막는 것을 안다
  • config.yaml 의 node-label·node-taint·kubelet-arg 가 각각 무엇을 하는지, 그리고 kubelet 설정 파일 필드와 플래그가 왜 다른 길인지 우리 템플릿으로 설명할 수 있다
  • CriticalAddonsOnly 는 k3s 부품이 견디는 키이고, toleration 은 끌어당기지 않는다는 점을 안다
  • Terraform 의 provider·resource·data·variable·output·module·state 를 한 문장씩 말할 수 있다
  • plan / apply / destroy 와 의존성 그래프, destroy 가 역순이라는 점을 안다
  • templatefile 두 겹과 ${·%{·$${ 규칙, Launch Template 의 base64 요구를 안다
  • VPC·서브넷·IGW·보안 그룹으로 "나감은 열고 들어옴은 80/443 내 IP 만" 을 표현하는 법을 안다
  • 인스턴스 프로파일, SSM 코어 정책, FIS 역할의 신뢰·권한 관계를 그릴 수 있다

본선에서 떠올릴 패턴

  • "기본 착지점에는 taint 를 걸지 않는다": 어떤 스케줄링·라우팅 문제든 "대부분이 가는 곳은 열어 두고, 예외인 소수만 표시해서 들여보낸다". 큐 라우팅, 기능 플래그, 네트워크 정책(default deny 뒤 예외 허용)에도 같은 생각이 쓰인다.
  • "노드는 스스로 같은 모양이 된다": 사람이 만진 설정은 교체 때 사라진다. 설정을 부팅 경로(user_data, AMI, 설정 파일)에 넣으면 자동 교체가 공짜가 된다. 서버리스·오토스케일 주제에서 "새 인스턴스가 어떻게 같은 모양이 되나" 를 먼저 묻는다.
  • "예고를 쓰는 장치 + 놓친 것을 받는 장치": NTH(2분 예고) + graceful shutdown(마지막 60초). 배포(카나리 + 자동 롤백), 결제(재시도 + 정산 배치)에도 "앞에서 막기 + 뒤에서 줍기" 두 겹을 둔다.
  • "들어오는 문 없이 접속": 에이전트가 밖으로 연결을 열고 그 위로 제어를 실어 나르는 구조(SSM, Argo CD pull, 클라우드 에이전트). 보안 질문이 나오면 "인바운드 포트 0" 을 먼저 제안한다.
  • "비용은 destroy 가 본체, 알람은 보조": 늦게 오는 신호(알람)에 안전을 맡기지 않는다. 사고를 막는 건 절차의 마지막 줄과 그걸 확인하는 스크립트다.
  • "같은 Git, 다른 클러스터": 환경을 늘릴 때 설정을 복사하지 말고 같은 소스를 가리키게 하고, 차이만 덧씌운다(values 두 겹). 멀티 리전·스테이징 질문에 그대로 쓴다.
