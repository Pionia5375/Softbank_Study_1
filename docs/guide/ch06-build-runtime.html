1. 컨테이너 이미지란 무엇인가 (OCI)

이미지 = "파일 묶음 몇 개 + 실행 방법 메모 + 목차"

컨테이너 이미지(container image)는 마법 같은 것이 아니다. 세 종류의 파일을 레지스트리에 올려 둔 것이다.

  • 레이어(layer): 파일 시스템 조각. 각각 하나의 tar 묶음(보통 gzip 압축)이다. "이 레이어에서 추가·변경·삭제된 파일"만 들어 있다.
  • 설정(config): JSON 한 장. 어떤 CPU 종류(architecture)·OS 용인지, 실행할 명령(Entrypoint/Cmd), 환경 변수, 실행 사용자(User), 레이어 순서(diff_ids).
  • 매니페스트(manifest): JSON 한 장. "이 이미지는 이 설정 + 이 레이어들" 이라는 목차. 각 항목을 이름이 아니라 digest(내용의 sha256 해시)로 가리킨다.

이 형식은 OCI(Open Container Initiative)의 Image Format Specification 이 표준으로 정했다. Docker 이미지 형식(Docker Image Manifest V2 Schema 2)과 거의 같고, containerd·Docker·kaniko·레지스트리가 모두 이 형식을 주고받는다.

Java 개발자에게 익숙한 비유: 레이어는 jar 안의 파일 묶음, 설정은 MANIFEST.MF 의 Main-Class, 매니페스트는 "이 버전은 이 체크섬의 jar 들로 이루어진다"는 Maven 의 lock 파일과 비슷하다. 단 하나 다른 점은, 이미지의 모든 연결이 체크섬 자체가 주소라는 것이다(내용 주소 지정, content-addressable).

digest
sha256: + 바이트의 SHA-256 해시 16진수 64자. 내용이 1비트라도 바뀌면 다른 값. 그래서 "이름"이자 "무결성 검사"다.
태그(tag)
v1, latest 같은 사람용 이름. 레지스트리 안에서 "태그 → 매니페스트 digest" 를 가리키는 포인터일 뿐이고, 언제든 다른 매니페스트로 옮길 수 있다.
저장소(repository)
fn/hello, tenant-a/hello 처럼 이미지들을 묶는 이름. 레지스트리 주소 + 저장소 + 태그 또는 digest 가 이미지 참조(reference)다.

세 객체가 서로를 가리키는 법

레이어는 "전체 파일 시스템"이 아니라 차이(diff) 다. 컨테이너를 띄울 때 노드의 containerd 는 레이어들을 아래에서 위로 겹쳐(overlayfs 같은 스냅샷 도구, snapshotter) 하나의 루트 파일 시스템으로 보여 준다. 아래 레이어의 파일을 지우려면, 위 레이어에 .wh. 로 시작하는 빈 파일(whiteout, 삭제 표시)을 넣는다.

멀티 아키텍처: 이미지 인덱스

같은 python:3.12-slim 이 인텔 맥에서도, 애플 실리콘 맥에서도 돈다. 비결은 이미지 인덱스(image index), Docker 용어로는 manifest list 다. 태그가 매니페스트 대신 인덱스를 가리키고, 인덱스는 플랫폼(os/architecture/variant)마다 매니페스트 하나씩을 나열한다. pull 하는 쪽(containerd)이 자기 플랫폼에 맞는 항목을 고른다.

digest 규칙

  • 형식은 알고리즘:16진수. 실무에서는 거의 sha256. 레지스트리와 클라이언트는 받은 바이트의 해시를 다시 계산해서 digest 와 다르면 버린다.
  • 매니페스트 digest 는 매니페스트 JSON 바이트 그대로의 해시다. JSON 을 예쁘게 다시 쓰면(공백·키 순서) digest 가 바뀐다. 그래서 레지스트리는 받은 바이트를 손대지 않고 저장한다.
  • 레이어 descriptor 의 digest 는 압축된 tar 의 해시, 설정의 rootfs.diff_ids 는 압축을 푼 tar 의 해시다. 압축 방식이 달라도 같은 파일 내용이면 diff_id 는 같다. 노드는 diff_id 로 "이미 풀어 둔 레이어"를 재사용한다.
  • 설정의 digest 를 "이미지 ID" 라고 부르기도 한다(docker images 의 IMAGE ID). 매니페스트 digest(RepoDigests)와 다른 값이다.

레이어 tar 의 세부

  • tar 안의 경로는 루트 기준 상대 경로(app/server.py). 파일 권한·소유자(uid/gid)·수정 시각이 tar 헤더에 들어간다. 그래서 같은 파일이라도 시각이 다르면 다른 레이어 digest 가 된다. 재현 가능한 빌드(reproducible build)를 원하면 시각을 고정해야 한다(kaniko --reproducible).
  • 삭제: 위 레이어에 경로/.wh.파일이름. 폴더 안 전체를 지우고 새로 채우려면 불투명 표시 폴더/.wh..wh..opq.
  • 매니페스트의 layers 배열 순서 = 적용 순서(첫 번째가 맨 아래). 설정의 diff_ids 순서와 같아야 한다.
  • 컨테이너 실행 정보(Cmd, Env, User, WorkingDir, ExposedPorts)는 레이어가 아니라 설정에 들어간다. 그래서 Dockerfile 의 ENV, USER, CMD 는 레이어를 만들지 않는다(4절 그림 6-8).

2. 레지스트리 프로토콜 (OCI Distribution, Docker Registry HTTP API v2)

레지스트리는 "digest 로 찾는 파일 서버 + 태그 표"

레지스트리(registry)는 이미지를 저장하고 나눠 주는 HTTP 서버다. Docker Hub, Amazon ECR, GitHub Container Registry, 그리고 우리 PoC 의 registry:2 컨테이너가 모두 같은 HTTP 규약을 말한다. 이 규약이 Docker Registry HTTP API v2 이고, 지금은 OCI Distribution Specification 으로 표준화됐다.

레지스트리 안에는 두 가지만 있다.

  • blob: digest 로 찾는 바이트 덩어리. 레이어와 설정이 여기 들어간다. 경로 /v2/<저장소>/blobs/<digest>.
  • manifest: 매니페스트(또는 인덱스) JSON. 태그나 digest 로 찾는다. 경로 /v2/<저장소>/manifests/<태그 또는 digest>.

그래서 push 는 "blob 을 먼저 다 올리고, 마지막에 매니페스트를 올린다", pull 은 "매니페스트를 먼저 받고, 거기 적힌 blob 을 받는다" 가 전부다. 매니페스트를 마지막에 올리는 이유: 매니페스트가 가리키는 blob 이 레지스트리에 하나라도 없으면 레지스트리가 매니페스트를 거절하기 때문이다(반쯤 올라간 이미지가 보이지 않게).

push 와 pull 을 HTTP 요청으로

kaniko 가 빌드를 마치고 kind-registry:5000/fn/hello:v1 로 올릴 때 오가는 요청이다. 이미 있는 blob 은 HEAD 로 확인하고 건너뛴다(그래서 베이스 레이어는 다시 안 올라간다).

3. 우리 레지스트리 배치: 한 저장소, 두 이름

왜 이름이 둘인가

kind 클러스터의 "노드"는 맥(정확히는 Docker Desktop 의 리눅스 VM) 위의 Docker 컨테이너다. 레지스트리도 같은 VM 위의 Docker 컨테이너 kind-registry 다. 같은 저장소를 누가 어디서 부르느냐에 따라 보이는 주소가 다르다.

  • 맥에서: localhost:5001. docker run -p 127.0.0.1:5001:5000 포트 매핑 덕분이다. curl, docker push(Docker Hub 미러 채우기)가 쓴다.
  • 클러스터 안 파드(kaniko)에서: kind-registry:5000. 레지스트리를 kind 노드들과 같은 Docker 네트워크 kind 에 붙였기 때문에, Docker 의 내장 DNS 가 컨테이너 이름을 풀어 준다. 파드 안의 localhost 는 파드 자신이라 localhost:5001 은 거기서 아무 뜻이 없다.
  • 노드의 containerd 에서: 둘 다 쓸 수 있다. setup.sh 가 노드마다 hosts.toml 을 넣어 "localhost:5001 도 kind-registry:5000 도 실제로는 http://kind-registry:5000 에서 받아라" 라고 알려 두었다.

05 가 "push 는 kind-registry:5000, ksvc 에는 localhost:5001" 로 쓰는 것은 kind 공식 문서(local registry)의 관례를 따른 것이다. 04 의 ksvc 는 kind-registry:5000 을 그대로 쓴다. 노드에서는 둘 다 같은 곳으로 간다.

배치도: 누가 어느 이름으로 어디에 닿나

세 군데의 설정이 맞물린다

  1. kind-config 의 containerdConfigPatches: containerd 에게 "레지스트리별 설정은 /etc/containerd/certs.d 폴더에서 읽어라" (config_path).
  2. setup.sh 의 hosts.toml: 그 폴더 아래 레지스트리 이름마다 폴더를 만들고 hosts.toml 을 둔다. 내용은 "이 이름의 이미지는 http://kind-registry:5000 에서 pull·resolve".
  3. Knative config-deployment: registries-skipping-tag-resolving 에 두 이름을 넣어 Knative 가 태그를 digest 로 바꾸려고 레지스트리에 묻지 않게.

3번이 왜 필요한가: Knative Serving 은 Revision 을 만들 때 image: ...:v1 처럼 태그로 적힌 이미지를 레지스트리에 물어 digest 로 바꿔 Revision 에 고정한다(태그가 나중에 바뀌어도 그 Revision 은 같은 이미지를 쓰게). 이 일은 노드의 containerd 가 아니라 knative-serving 의 controller 파드가 직접 HTTP 로 하는데, 기본이 https 라서 http 전용 kind-registry 에 실패하고 Revision 이 Ready 가 되지 않는다. 그래서 이 두 레지스트리는 건너뛰게 했다. 대가는 04 처럼 태그로 적은 ksvc 의 Revision 이 태그에 묶인다는 것이다.

4. Dockerfile 과 멀티 스테이지 빌드

Dockerfile = 레이어를 만드는 조리법

Dockerfile 의 한 줄 한 줄은 "이전 상태 위에서 무언가를 하고, 바뀐 파일을 레이어로 남겨라" 또는 "설정에 이 값을 적어라" 둘 중 하나다.

  • 레이어를 만드는 줄: RUN, COPY, ADD (그리고 WORKDIR 이 새 폴더를 만들 때).
  • 설정만 바꾸는 줄: ENV, USER, CMD, ENTRYPOINT, EXPOSE, LABEL.

멀티 스테이지 빌드(multi-stage build)는 FROM 을 여러 번 써서, 앞 단계(컴파일러가 든 큰 이미지)에서 만든 결과물만 뒤 단계(작은 실행용 이미지)로 COPY --from 하는 방법이다. 최종 이미지에는 마지막 단계만 남는다. 컴파일러·소스·캐시는 버려진다. 함수 플랫폼에서는 이미지가 작을수록 콜드 스타트 때 받는 바이트가 줄고, 공격 표면(셸·패키지 관리자)도 줄어든다.

Go hello: 두 단계

Python 런타임: 한 단계, 레이어는 베이스 위에 1장

05 의 함수 이미지는 멀티 스테이지가 아니다. 파이썬은 컴파일 결과물만 따로 뽑기 어렵고(인터프리터와 표준 라이브러리가 실행에 필요), 사용자 코드가 외부 패키지를 쓰지 않는 PoC 범위에서는 python:3.12-slim 위에 파일 두 개를 얹는 것으로 충분하다. 패키지 설치(pip install)가 생기면 그때 "빌드 단계에서 wheel 을 만들고 실행 단계에는 결과만" 으로 멀티 스테이지를 쓴다.

5. Kaniko: Docker 데몬 없이 클러스터 안에서 빌드

무엇이고 왜 쓰나

맥에서 docker build 를 하면 실제 일은 Docker 데몬(dockerd, root 권한 프로세스)이 한다. 쿠버네티스 파드 안에는 데몬이 없다. 데몬을 쓰는 방법은 두 가지인데 둘 다 위험하다.

  • 노드의 Docker 소켓을 파드에 마운트: 그 파드는 노드의 dockerd 에게 "호스트 / 를 마운트한 privileged 컨테이너를 띄워라" 를 시킬 수 있다 = 노드 root.
  • Docker-in-Docker: 파드 안에 dockerd 를 띄운다. dockerd 가 cgroup·마운트를 만들려면 privileged: true 가 필요하다 = 역시 노드 root 에 가깝다.

Kaniko(Google 이 만든 도구, 원본 저장소는 2025-06-03 보관됨)는 데몬 없이 자기 컨테이너의 루트 파일 시스템 위에서 직접 Dockerfile 을 실행한다. 베이스 이미지를 자기 / 에 풀고, RUN 을 자기 프로세스로 실행하고, 바뀐 파일을 tar 로 묶어 레이어를 만들고, 레지스트리 API 로 push 한다. 특권(privileged)이 필요 없고, 평범한 Job 파드 하나로 빌드가 끝난다.

Java 로 비유하면, 빌드 서버에 원격 셸을 열어 주는 대신 "빌드만 하고 결과를 아티팩트 저장소에 올리고 끝나는 일회용 컨테이너" 를 띄우는 것이다.

6. 빌드 재료 넣기: ConfigMap 과 심볼릭 링크

소스를 kaniko 파드에 어떻게 넘기나

kaniko 는 빌드 재료(context)를 자기 컨테이너 안의 폴더나 tar 파일, 또는 S3·GCS·Git 에서 읽는다. PoC 는 외부 저장소 없이 끝내려고 ConfigMap 에 소스를 넣고 파드에 볼륨으로 붙인다. ConfigMap 한 개는 최대 1MiB 라서 함수 코드 몇 개에는 충분하다.

함정이 하나 있다. 쿠버네티스는 ConfigMap 볼륨의 파일을 "진짜 파일" 로 두지 않고 심볼릭 링크로 둔다(갱신을 원자적으로 하려고). kaniko 의 COPY 는 링크를 따라가지 않고 링크 자체를 이미지에 복사한다. 그러면 이미지 안에서 go.mod 가 "어디에도 없는 곳을 가리키는 링크" 가 되어 빌드가 깨진다. 04 와 05 는 이 같은 문제를 서로 다른 방법으로 피한다.

04: tar.gz 하나로

build.sh 가 소스 폴더를 context.tar.gz 로 묶어 ConfigMap 에 넣고, kaniko 에 --context=tar://.... kaniko 가 tar 를 열 때 파일 하나(링크)를 읽는 것은 문제가 없고, 압축을 푼 결과는 진짜 파일이다.

05: initContainer cp -L

busybox initContainer 가 cp -L /src/* /workspace/ 로 링크를 따라가 내용을 복사(emptyDir)한 다음 kaniko 가 dir:///workspace 를 쓴다. 컨트롤 플레인이 파일별로 ConfigMap 키를 만들 수 있어 tar 를 만들 필요가 없다.

ConfigMap 볼륨의 실제 모양

05 에서 Job 과 ConfigMap 을 만드는 순서도 볼 만하다. Job 을 먼저 만들고, 그 Job 을 주인(ownerReference)으로 하는 ConfigMap 을 만든다. Job 이 TTL 로 지워지면 쿠버네티스 가비지 컬렉터가 ConfigMap 도 같이 지운다. 파드가 ConfigMap 보다 먼저 스케줄되면 kubelet 이 볼륨을 못 붙여 ContainerCreating 에서 잠깐 기다렸다가 다시 시도한다.

7. 빌드 Job 설계

빌드는 "한 번 돌고 끝나는 일" → Job

쿠버네티스 Job 은 "파드를 띄워서 성공으로 끝날 때까지 책임진다" 는 리소스다. 빌드 Job 을 설계할 때 정할 것은 다섯 가지다: 어디서(namespace, 노드 풀), 실패하면(backoffLimit), 얼마나 오래(activeDeadlineSeconds), 끝나면 언제 치우나(ttlSecondsAfterFinished), 얼마나 쓰나(resources).

주의: 05 의 시계 불일치

두 시계의 순서가 중요하다. 컨트롤 플레인의 build-timeout 이 Job 의 activeDeadlineSeconds 보다 짧으면, 기다림이 먼저 끝나 waitUntilCondition 이 예외를 던지고 감사 로그에 deploy.apply error 가 남는다. 그런데 Job 은 계속 돌다가 성공할 수 있고, 성공해도 ksvc 를 만들 스레드가 이미 없다(같은 코드로 다시 POST 하면 Job 이 재사용되고 새 스레드가 digest 를 읽어 이어 간다). 처음 PoC 는 5m 대 600초라 정확히 이 틈이 있었고, 가이드를 쓰면서 build-timeout: 11m 으로 고쳤다. 이제는 쿠버네티스가 먼저 Job 을 끝내고(성공 또는 DeadlineExceeded), 컨트롤 플레인은 그 결과를 읽는다. 원칙: 바깥에서 기다리는 쪽의 시계가 안쪽 작업의 마감보다 길어야 한다. 07장 알려진 한계(메모리에만 있는 대기 스레드)와는 별개로 남는 문제다.

필드별 세부 (Job 공식 문서 기준)

  • backoffLimit: 실패한 파드 수가 이 값을 넘으면 Job 을 Failed 로. 기본 6. 재시도 간격은 10초, 20초, 40초 … 최대 6분의 지수 백오프. 0 이면 첫 실패가 곧 Job 실패. podFailurePolicy 로 "종료 코드 1 은 재시도 안 함, 노드 장애(DisruptionTarget)는 재시도" 처럼 나눌 수 있다. 빌드에 쓰기 좋은 확장안이다.
  • activeDeadlineSeconds: Job 이 시작된 뒤 전체 경과 시간. 파드가 Pending 인 시간도 포함한다. 넘으면 실행 중 파드를 모두 종료하고 reason DeadlineExceeded. backoffLimit 보다 우선한다.
  • ttlSecondsAfterFinished: Complete 또는 Failed 가 된 시각부터 셈. TTL 컨트롤러가 Job 을 지우고, 연쇄 삭제(cascading)로 파드도 지운다. 05 는 ConfigMap 의 owner 가 Job 이라 ConfigMap 도 지워진다. 0 이면 끝나자마자 삭제(그러면 05 의 digest 읽기가 경쟁에 진다).
  • restartPolicy: Never: Job 의 파드는 Always 를 쓸 수 없다. OnFailure 는 같은 파드에서 컨테이너를 다시 띄워 로그가 덮이고, termination-log 도 마지막 시도 것만 남는다.
  • requests / limits: 스케줄러는 requests 만 보고 자리를 계산한다. build 노드에 빌드 N개가 동시에 들어가려면 N × 500m ≤ 노드 할당 가능 CPU. limits.cpu 는 CFS quota(100ms 마다 상한)로 지켜지고, limits.memory 를 넘으면 OOMKilled(종료 코드 137) → backoffLimit 0 이라 바로 BUILD_FAILED. Go 컴파일은 메모리를 꽤 쓰므로 04 는 2Gi 로 넉넉하게 잡았다.
  • labels: 05 는 faas.poc/tenant, faas.poc/function, faas.poc/build-id 를 Job 과 파드 템플릿 둘 다에 붙인다. 상태 조회가 Job 을 라벨로 찾고(latestBuild), digest 읽기는 Job controller 가 자동으로 붙이는 job-name 라벨로 파드를 찾는다.

8. digest 고정: 빌드에서 Revision 까지

태그는 거짓말을 할 수 있다

"Revision 3 = 이 코드" 가 영원히 참이어야 롤백을 믿을 수 있다. 그런데 Revision 이 hello:latest 같은 태그를 가리키면, 누군가 그 태그에 다른 이미지를 push 한 순간부터 Revision 3 의 파드가 새로 뜰 때(스케일 아웃, 노드 장애 후 재배치, 콜드 스타트) 다른 코드를 받는다. 쿠버네티스는 이것을 알아채지 못한다. 그래서 05 는 kaniko 가 push 한 매니페스트의 digest 를 받아 ksvc 에 image@sha256:... 로 넣는다.

태그가 거짓말하는 경우를 정리하면:

  • 같은 태그로 다시 push(04 에서 build.sh v1 을 두 번).
  • 베이스 이미지 태그(python:3.12-slim)가 상류에서 갱신.
  • 노드마다 받은 시각이 달라서 같은 Deployment 의 파드들이 서로 다른 이미지를 돌림(imagePullPolicy: IfNotPresent + 이미 캐시된 노드).
  • 레지스트리 침해나 실수로 태그가 악성 이미지로 바뀜(공급망 공격).

/** kaniko 의 --digest-file=/dev/termination-log 덕분에, 끝난 컨테이너 상태의 message 에 digest 가 들어 있다 */
private String readDigest(String jobName) {
    List<Pod> pods = k8s.pods().inNamespace(props.buildNamespace()).withLabel("job-name", jobName).list().getItems();
    return pods.stream()
            .flatMap(p -> p.getStatus() == null || p.getStatus().getContainerStatuses() == null
                    ? java.util.stream.Stream.<ContainerStatus>empty()
                    : p.getStatus().getContainerStatuses().stream())
            .filter(cs -> KANIKO_CONTAINER.equals(cs.getName()))
            .map(cs -> cs.getState() == null || cs.getState().getTerminated() == null ? null : cs.getState().getTerminated().getMessage())
            .filter(Objects::nonNull)
            .map(String::trim)
            .filter(m -> m.startsWith("sha256:"))
            .findFirst()
            .orElseThrow(() -> new IllegalStateException("빌드 파드에서 digest 를 못 찾았다. ..."));
}

  • initContainer(copy-source)도 containerStatuses 가 아닌 initContainerStatuses 에 있어서 섞이지 않는다. 그래도 이름 kaniko 로 한 번 더 거른다.
  • trim() + startsWith("sha256:"): 줄바꿈이나 다른 에러 문구가 들어 있으면 버린다. 실패한 컨테이너의 termination message 는 에러 문구일 수 있다.
  • 못 찾으면 예외 → 감사 로그 deploy.apply error. 템플릿에서 컨테이너 이름을 바꾸거나 --digest-file 을 빼면 바로 여기서 터진다(테스트가 이걸 검사한다).

9. 빌드 방식의 대안

"빌드 파드가 노드에 무엇을 요구하나" 로 비교

네 가지 대안의 동작 원리

BuildKit (rootless)
Docker 의 새 빌드 엔진. 빌드를 DAG(의존 그래프)로 풀어 독립 단계를 병렬로 돌리고, 캐시를 내용 해시로 정교하게 관리한다(--export-cache type=registry). rootless 모드는 buildkitd 를 일반 사용자로 띄우고 user namespace 안에서 "가짜 root" 로 파일 소유자를 다룬다. 파드에서 돌리려면 공식 예시대로 seccomp·AppArmor 를 Unconfined 로 풀어야 한다(user namespace 와 마운트를 만들 시스템 콜이 기본 프로필에 막혀 있어서). 04 결정 2 에서 "본선에서 바꿀 1순위 후보".
Cloud Native Buildpacks
Dockerfile 없이 소스를 보고 언어를 감지(detect)해서 "빌더 이미지"가 정해진 레이어를 만든다(Heroku·Cloud Foundry 계보, pack, kpack). 베이스 OS 레이어만 갈아 끼우는 rebase 가 된다. FaaS 의 "코드만 올리면 된다" 와 가장 잘 맞지만 빌더 이미지가 크고 첫 빌드가 무겁다. Knative Functions(func)가 이 방식을 쓴다.
외부 CI (GitHub Actions 등)
클러스터 밖에서 docker build 후 push. 클러스터에 빌드 부하가 없고 도구가 성숙했다. 하지만 사용자 코드가 Git 에 있어야 하고(우리는 HTTP 로 코드를 받는다), 왕복이 길고, "남의 코드를 실행하는 곳" 이 CI 러너로 옮겨 갈 뿐 격리 문제는 그대로다.
Docker 소켓
가장 쉽고 가장 위험하다. 소켓에 쓸 수 있는 파드는 docker run --privileged -v /:/host 를 시킬 수 있다. 또 쿠버네티스 1.24 에서 dockershim 이 빠진 뒤 노드에는 보통 dockerd 자체가 없다(kind 노드도 containerd 만 있다).

10. 컨테이너 런타임 스택: kubelet 에서 커널까지

컨테이너는 "칸막이 친 프로세스" 다

컨테이너는 VM 이 아니다. 리눅스 프로세스 하나에 커널 기능 몇 가지로 칸막이를 친 것이다. 컨테이너 안 프로그램이 파일을 열거나 소켓을 만들면 그 시스템 콜(system call, 커널에 하는 부탁)은 노드의 커널이 직접 받는다. 그래서 커널에 버그가 하나 있으면, 그 버그를 건드리는 컨테이너 하나가 노드 전체를 차지할 수 있다(컨테이너 탈출, container escape).

쿠버네티스에서 파드가 실제 프로세스가 되기까지는 여러 층을 거친다.

  1. kubelet: 노드의 에이전트. "이 파드를 띄워라" 를 API 서버에서 받는다.
  2. CRI(Container Runtime Interface): kubelet 이 런타임에게 말하는 gRPC 규약. 쿠버네티스는 이 규약만 알고 구현은 모른다.
  3. containerd: CRI 를 구현한 데몬. 이미지 pull, 스냅샷, 컨테이너 수명을 관리한다.
  4. shim(containerd-shim-*-v2): 컨테이너(정확히는 파드 샌드박스)마다 하나씩 뜨는 작은 중간 프로세스. containerd 가 재시작해도 컨테이너가 살아 있게 한다.
  5. OCI 런타임: 실제로 칸막이를 치고 프로세스를 띄우는 도구. 기본은 runc, gVisor 는 runsc.
  6. 리눅스 커널: namespace, cgroup, capability, seccomp, LSM(AppArmor/SELinux).

RuntimeClass(11절)는 4~5층의 "어느 shim/런타임을 쓸까" 를 파드마다 고르게 해 주는 장치다.

11. RuntimeClass: 파드마다 런타임 고르기

이름 하나로 "어떤 샌드박스" 를 고른다

RuntimeClass 는 클러스터 전체 리소스(namespace 없음)로, "이 이름을 고른 파드는 노드의 이 런타임 설정(handler)으로 띄워라" 를 정의한다. 파드(우리는 ksvc 의 template)에 runtimeClassName: gvisor 한 줄을 쓰면 그 파드만 gVisor 로 돈다. 나머지 파드는 기본(runc)이다.

필드는 세 개뿐이다.

  • handler: 노드의 CRI 런타임 설정 이름. containerd 에서는 runtimes.<handler> 표의 이름. 우리는 runsc.
  • scheduling: 이 런타임이 깔린 노드로만 가게 nodeSelector·tolerations 를 자동으로 붙여 준다. 우리는 exec 풀.
  • overhead: 앱 컨테이너 말고 런타임 자체(Sentry 등)가 먹는 자원. 스케줄러와 쿼터가 더해서 계산한다.

깨지면 이렇게 보인다

  • 증상: 파드 생성 자체가 거절, 이벤트 pod rejected: RuntimeClass "gvisor" not found. 고치는 법: kubectl get runtimeclass, kubectl apply -f platform/runtimeclass-gvisor.yaml.
  • 증상: FailedCreatePodSandBox ... no runtime for "runsc" is configured. 원인: 그 노드 containerd 에 표가 없음(설치 안 된 노드로 갔거나 containerd 재시작 전). 볼 곳: kubectl get pod -o wide 의 노드, docker exec <노드> grep -A1 runtimes.runsc /etc/containerd/config.toml.
  • 증상: 파드 Pending, Insufficient memory. 원인: overhead 가 더해져 노드에 자리가 없음. 볼 곳: kubectl get pod -o jsonpath='{.spec.overhead}'.

왜 이걸 골랐나 (대안)

  • RuntimeClass: 함수마다(또는 테넌트마다) 런타임을 한 줄로 바꾼다. 플랫폼 코드는 그대로. 설계 문서 문장: "격리 런타임은 RuntimeClass 한 줄로 갈아 끼우는 구조".
  • 대안 (가) containerd 기본 런타임을 runsc 로: 노드의 모든 파드(Cilium 에이전트, kube-proxy 류 포함)가 gVisor 로 돌아 호환성 문제가 난다. (나) 노드 풀 전체를 gVisor 전용: 07 결정에서 "실행 풀 전체 vs 전용 풀" 로 다룬다.

12. gVisor: 사용자 공간 커널

컨테이너와 커널 사이에 "가짜 커널" 을 하나 더

gVisor(Google 오픈소스, OCI 런타임 이름 runsc)는 Go 로 작성된 애플리케이션 커널(application kernel)이다. 리눅스와 비슷한 인터페이스(시스템 콜, /proc, 파일 시스템, 네트워크 스택)를 사용자 공간 프로세스로 구현한다. 이 프로세스가 Sentry 다.

  • 앱이 open(), socket() 같은 시스템 콜을 하면 호스트 커널이 아니라 Sentry 가 받아서 직접 처리한다. 공식 문서 표현으로 "Sentry 는 시스템 콜을 호스트 커널로 넘기지 않는다".
  • Sentry 자신은 호스트 커널에 좁고 정해진 목록의 시스템 콜만 쓸 수 있다(seccomp 로 묶임). 앱이 커널 버그를 노리려면 먼저 Sentry 를 뚫고, 그다음 좁은 목록으로 호스트 커널을 뚫어야 한다 → 심층 방어(defense in depth).
  • 파일 접근은 별도 프로세스 Gofer 가 중개한다(또는 directfs 모드에서 Gofer 가 넘겨준 파일 디스크립터로 Sentry 가 직접).

VM(Kata, Firecracker)처럼 하드웨어 가상화를 쓰지 않으므로 중첩 가상화가 없는 곳(일반 클라우드 VM, Docker Desktop 의 리눅스 VM 안 kind 노드)에서도 돈다. 대신 시스템 콜이 많은 일(파일·네트워크 I/O)은 느려지고, 리눅스의 모든 기능을 구현하지는 않아 일부 프로그램과 호환되지 않는다.

FaaS 에 맞는 이유: "남이 올린 코드" 를 "우리 노드" 에서 돌린다. 작년 본선 2위 팀(Green)도 Knative + gVisor 조합이었다(04 README).

파일 시스템: Gofer 와 directfs

  • 원래 구조: Sentry 는 파일을 직접 열 수 없고, 컨테이너마다 뜨는 Gofer 프로세스에게 프로토콜(예전 9P, 지금 LISAFS)로 요청한다. Gofer 가 호스트에서 열고 결과를 돌려준다.
  • directfs: Gofer 가 컨테이너 rootfs 의 디렉터리 FD 를 Sentry 에 넘겨주고, Sentry 가 그 FD 아래에서 openat 류를 직접 한다(seccomp 로 상대 경로 열기만 허용). 왕복이 줄어 빠르다. 최근 릴리스에서 기본으로 켜져 있다고 알려져 있다 【확인 필요: 20261012.0 기본값】.
  • 오버레이: rootfs 위에 메모리 기반 쓰기 레이어(overlay)를 두어, 컨테이너가 쓴 파일이 호스트 디스크로 가지 않게 하는 설정이 있다. 그래서 함수의 ?work=io(작은 파일 만들고 지우기)가 gVisor 에서 어느 경로를 타는지가 성능 차이를 결정한다 【확인 필요: 우리 설정의 overlay 기본값】.

네트워크: netstack vs host

  • 기본은 netstack: Sentry 안의 사용자 공간 TCP/IP 스택. 앱의 소켓은 Sentry 안에만 있고, Sentry 는 파드 네트워크 namespace 의 인터페이스에 패킷 단위로 읽고 쓴다(AF_PACKET 등). 호스트 커널의 TCP 코드가 앱 입력에 노출되지 않는다.
  • --network=host: 소켓 시스템 콜을 호스트로 넘긴다. 빠르지만 격리가 약해진다. 쿠버네티스 파드는 CNI(우리 Cilium)가 만든 namespace 안이므로 netstack 이 그 namespace 의 veth 에 붙는다. Cilium 의 eBPF 정책은 veth 바깥(호스트 쪽)에서 적용되므로 gVisor 와 같이 동작한다 【확인 필요: Cilium + gVisor 조합에서 소켓 단위 기능(socket LB)의 동작】.

비용과 호환성

  • 시스템 콜이 많은 일: 모든 시스템 콜이 가로채기 + Sentry 처리를 거친다. 계산만 하는 함수(?work=cpu)는 거의 같고, 작은 파일을 많이 만들고 지우는 함수(?work=io)나 네트워크 왕복이 많은 함수는 느려진다. 04 의 hello 함수가 이 두 모드를 가진 이유다.
  • 메모리: 파드마다 Sentry·Gofer 프로세스가 더 뜬다 → RuntimeClass overhead.
  • 시작: 샌드박스(Sentry) 기동이 더해져 콜드 스타트가 길어진다.
  • 호환성: 리눅스 시스템 콜 전부를 구현하지 않는다(공식 문서의 호환성 표). 특수 ioctl, 일부 /proc·/sys 파일, 커널 모듈, eBPF 프로그램 로드 같은 것은 안 된다. 일반 웹 함수(Go net/http, 파이썬 http.server)는 문제가 없다.
  • 관측: uname -r 이 gVisor 가 흉내 내는 버전(04 README 의 추정 4.4.0)을 돌려주고, dmesg 에 gVisor 의 농담 같은 시작 메시지가 나온다. 함수 응답의 kernel 칸으로 runc/gVisor 를 구분하는 원리.

왜 gVisor 를 골랐나 (대안)

  • runc + seccomp + Pod Security: 가볍지만 커널 공유가 그대로. 우리 ksvc 의 securityContext 는 이미 이 수준이다. 그 위에 한 겹이 더 필요했다.
  • Kata Containers / Firecracker: 진짜 VM(게스트 커널)이라 격리가 더 강하지만 하드웨어 가상화가 필요하다(14절).
  • WASM: 시작이 아주 빠르지만 언어·라이브러리 제약이 크다(14절).
  • gVisor 는 "VM 없이 커널 표면을 줄인다" 는 중간 지점이고, RuntimeClass 한 줄로 켜고 끌 수 있어 측정 비교가 쉽다.

  1. 노드 CPU 종류에 맞는 gVisor 묶음(runsc, containerd-shim-runsc-v1, gvisor-bin/)을 받아 무결성(sha512)을 확인하고 노드의 /usr/local/bin 에 넣는다. 04 README 는 2026-07 부터 배포가 이 세 개 묶음이라 옛 블로그처럼 runsc 하나만 복사하면 안 돈다고 적었다(설치 문서 기준, 이 장에서 다시 확인하지는 못했다 【확인 필요】).
  2. 노드 containerd 설정에 runtimes.runsc 표를 추가하고 containerd 를 재시작한다.
  3. 클러스터에 RuntimeClass gvisor 를 만든다(11절).

kind 에서는 노드가 컨테이너라 맥에서 docker cp/docker exec 로 넣는다. EC2 에서는 노드가 진짜 VM 이라 첫 부팅 스크립트(user_data)가 노드 안에서 직접 한다.

중첩 가상화 그림

대안별 세부와 판단

  • Kata Containers: 쿠버네티스에서 RuntimeClass handler kata(또는 kata-qemu, kata-fc)로 쓴다. containerd 의 containerd-shim-kata-v2 가 파드마다 경량 VM(QEMU, Cloud Hypervisor, Firecracker 중 하나)을 띄우고 그 안에서 게스트 커널 + kata-agent 가 컨테이너를 만든다. 우리 구조(RuntimeClass 한 줄)와 그대로 맞물리는 것이 장점이다. 맥의 Docker Desktop VM 은 중첩 가상화를 내주지 않는다 【확인 필요: Docker Desktop 최신판의 /dev/kvm 노출 여부】.
  • Firecracker: AWS Lambda·Fargate 의 기반 VMM. 부팅이 매우 빠르고 장치 모델이 최소다. 단독으로는 쿠버네티스 런타임이 아니고 Kata 의 하이퍼바이저나 firecracker-containerd 로 붙인다. EC2 에서는 .metal 인스턴스(또는 중첩 가상화를 허용하는 일부 유형)가 필요하다.
  • WASM(WebAssembly): 코드를 WASM 바이트코드로 빌드하고 Wasmtime·WasmEdge 같은 런타임이 실행한다. containerd 에는 runwasi 계열 shim 으로 붙어 RuntimeClass 로 고를 수 있다. 시작이 매우 빠르고 메모리가 작으며, 기능 기반 보안(파일·네트워크를 명시적으로 허가)이라 격리가 강하다. 대가: 사용자 코드를 WASM 으로 다시 빌드해야 하고, 파이썬처럼 인터프리터가 필요한 언어나 네이티브 라이브러리·스레드·소켓을 쓰는 코드는 제약이 크다. 작년 우승팀(Blue)이 WASM 을 썼다(04 README 결정 3).
선택 격리_런타임(환경, 함수):
  if 함수가 WASM 으로 빌드 가능 and 콜드 스타트가 최우선: WASM shim
  elif 노드에 /dev/kvm (베어메탈) and 가장 강한 격리 필요: Kata (+ Firecracker)
  elif 일반 VM 또는 kind: gVisor (systrap)          // 우리
  else: runc + seccomp + PSA restricted + 노드 풀 분리
  // 어느 것이든 RuntimeClass 의 handler 만 바꾸면 위 층은 그대로

왜 Kata/Firecracker/WASM 을 안 골랐나

Kata·Firecracker 는 로컬 kind 에서 못 돌려 "만들고 재 보기" 가 불가능하고, EC2 에서도 비싼 베어메탈이 필요하다. WASM 은 "코드만 올리면 된다" 는 약속을 "WASM 으로 빌드되는 코드만" 으로 좁힌다. gVisor 는 두 환경 모두에서 RuntimeClass 한 줄로 켜고 끌 수 있었다. 설계 문서에는 "격리 등급을 테넌트 요금제별 RuntimeClass 로(기본 gVisor, 프리미엄 Kata 전용 풀)" 를 확장안으로 적을 수 있다.

  • 볼 곳 (04 README 9절 순서): ① kubectl -n fn-runtime describe pod -l serving.knative.dev/service=hello-gvisor | tail -5 ② docker exec faas-worker3 journalctl -u containerd --no-pager | grep -i runsc | tail -20.
  • 흔한 원인 (README 의 추정): (가) arch 불일치(장면 3) (나) gvisor-bin/ 누락 (다) systrap 이 VM 커널에서 막힘 → runsc 설정에 platform = "ptrace" 시도(runtimes.runsc.options.ConfigPath 가 가리키는 runsc.toml). Claude 컨테이너에서 실제로 본 원인은 CAP_SYS_RESOURCE 없음(shim 이 oom_score_adj 를 못 씀)과 cgroup v1 이었다.
  • 시간 상자: 30분 넘으면 범위를 줄인다. hello-gvisor 두 파일의 runtimeClassName 만 주석 처리하고 runc 로 측정, gVisor 측정은 07(EC2)로. 설계 문서 문장은 "격리 런타임은 RuntimeClass 한 줄로 갈아 끼우는 구조, 측정은 EC2 에서".

장면 3. arch 불일치 (aarch64)

깨지면 이렇게 보인다

  • 증상 A (gVisor 바이너리): 애플 실리콘 맥에서 runsc 가 exec format error 또는 shim 이 시작 못 함. 볼 곳: docker exec faas-worker3 file /usr/local/bin/runsc(file 이 없으면 uname -m 과 캐시 폴더 이름 비교). 원인: 캐시 폴더에 다른 arch 판이 남음. install-gvisor.sh 는 노드 arch 로 폴더를 나누므로 정상 경로에서는 생기지 않는다.
  • 증상 B (함수 이미지): 07 의 x86_64 노드에서 함수 파드가 CrashLoopBackOff, 로그 exec format error, 또는 pull 단계에서 no matching manifest for linux/amd64. 원인: 맥(arm64)에서 빌드한 단일 arch 이미지. 고치는 법: docker buildx build --platform linux/amd64(07 gvisor-ec2.sh image), 또는 두 arch 를 인덱스로 묶어 push.
  • 클러스터 안 kaniko 빌드는 빌드 노드의 arch 로 만들고 같은 클러스터의 exec 노드도 같은 arch 라서 kind 안에서는 이 문제가 나지 않는다. 노드 풀마다 arch 가 다른 클라우드(Graviton 빌드 + x86 실행)에서는 다시 나타난다.

장면 4. gVisor 파드가 runsc 없는 노드로

깨지면 이렇게 보인다

  • 증상: FailedCreatePodSandBox ... no runtime for "runsc" is configured, 노드 칸이 build 나 system.
  • 어떻게 그렇게 되나: ANALYSIS 의 B8 실험. RuntimeClass 의 scheduling.nodeSelector 와 ksvc 의 nodeSelector 를 둘 다 지운다. 그래도 exec·build 에는 taint 가 있어 toleration 없는 파드는 못 가는데, RuntimeClass 의 toleration(pool=exec)이 남아 있으면 exec 로는 갈 수 있고, taint 가 없는 system 노드에는 누구나 갈 수 있다 → system 노드로 가서 실패한다.
  • 마지막 벽: 스케줄 단계에서는 아무것도 막지 않는다. 마지막 벽은 노드 containerd 의 "모르는 handler" 오류뿐이다(실패로 막힘, fail-closed: runc 로 몰래 바꿔 띄우지 않는다는 점은 좋은 성질).
  • 고치는 법: RuntimeClass scheduling 복구. 더 튼튼하게는 노드 라벨 runtime/gvisor=true 를 설치 스크립트가 붙이고 RuntimeClass 가 그 라벨을 고르게 하면 "설치된 노드" 와 "고르는 조건" 이 한 곳에서 맞물린다.

장면 5. 같은 태그 덮어쓰기

깨지면 이렇게 보인다

  • 증상: 04 에서 main.go 를 고치고 build.sh v1 을 다시 돌렸는데 함수 응답이 그대로이거나, 어떤 파드는 새 코드 어떤 파드는 옛 코드. ksvc 를 바꾸지 않았으니 새 Revision 도 없다.
  • 왜: 태그 v1 은 새 매니페스트로 옮겨졌지만(2절 PUT 덮어쓰기), Knative 는 이 레지스트리의 태그 해석을 건너뛰므로 Revision 은 "태그 v1" 에 묶여 있다. 노드는 imagePullPolicy(태그가 latest 가 아니면 기본 IfNotPresent)에 따라 이미 받은 옛 이미지를 그대로 쓰고, 이미지가 없는 새 노드에서 뜬 파드만 새 이미지를 받는다.
  • 볼 곳: curl -s localhost:5001/v2/fn/hello/tags/list, 노드에서 docker exec faas-worker3 crictl images | grep fn/hello 의 IMAGE ID 비교.
  • 고치는 법: 빌드마다 새 태그(v2)와 ksvc 이미지 변경 → 새 Revision. 근본적으로는 05 처럼 digest 고정.

정리

핵심 개념 체크리스트

  • 이미지 = 매니페스트(목차) + 설정(JSON) + 레이어(tar 변경분). 연결은 전부 digest.
  • 레이어 digest 는 압축본, diff_id 는 압축 해제본의 sha256. 매니페스트 digest 가 이미지의 진짜 이름.
  • 이미지 인덱스 = 플랫폼별 매니페스트 목록. 노드가 자기 arch 를 고른다.
  • 태그는 레지스트리 안의 움직이는 포인터. 매니페스트 PUT 은 같은 태그를 덮어쓴다.
  • push = blob(HEAD → POST → PATCH → PUT?digest) 다음 매니페스트 PUT. pull = 매니페스트 GET 다음 blob GET.
  • localhost:5001(맥, 노드 hosts.toml)과 kind-registry:5000(Docker 네트워크 이름)은 같은 저장소. hosts.toml 이 http 미러로 바꾼다.
  • Knative 태그 해석을 건너뛰면 태그 참조 Revision 이 태그에 묶인다 → digest 로 넣으면 문제가 없다.
  • 멀티 스테이지: 컴파일러는 버리고 결과물만. ENV/USER/CMD 는 레이어가 아니라 설정.
  • kaniko = 데몬 없이 자기 루트에 베이스를 풀고, 명령마다 스냅샷 → 레이어 → push. 특권 불필요, 그러나 보안 경계는 아님.
  • ConfigMap 볼륨 파일은 심볼릭 링크 → tar.gz 또는 cp -L.
  • 빌드 Job: backoffLimit 0, activeDeadlineSeconds, ttlSecondsAfterFinished, requests 작게 limits 크게, build 풀.
  • digest 고정: --digest-file=/dev/termination-log → 파드 상태 → image@sha256.
  • kubelet → CRI → containerd → shim v2 → OCI 런타임(runc/runsc) → 커널.
  • RuntimeClass: handler(노드 런타임 이름), scheduling(자동 nodeSelector·toleration), overhead(스케줄·쿼터·cgroup).
  • gVisor: Sentry(사용자 공간 커널) + Gofer/directfs + 플랫폼(systrap 기본) + netstack. 호스트 표면 축소 = 심층 방어. 비용은 시스템 콜 많은 일, 메모리, 시작, 호환성.
  • Kata/Firecracker 는 /dev/kvm(중첩 가상화) 필요 → kind 불가, EC2 는 베어메탈. gVisor 는 둘 다 가능.

본선에서 떠올릴 패턴

내용 주소 지정

"이름 대신 내용의 해시로 가리키면 캐시·검증·재현이 공짜로 따라온다." 설정 배포, ML 모델 버전, 데이터셋, 함수 코드 아카이브 어디에나. 해커톤 주제가 "버전 관리"·"롤백" 이면 digest 고정을 그대로 옮긴다.

2단계 커밋 (blob 먼저, 목차 나중)

레지스트리는 내용이 다 올라간 뒤에만 매니페스트를 받는다. 파일 업로드 API, 대용량 결과 저장, 이벤트 소싱의 스냅샷에도 같은 순서를 쓰면 "반쯤 보이는 상태" 가 없다.

결과값을 상태로 꺼내기

termination-log 처럼 "일회성 작업의 출력 하나" 를 오케스트레이터 상태에 실어 나르면 별도 저장소가 필요 없다. Job → 다음 단계 연결(예: 학습 Job → 모델 digest → 서빙)에 그대로.

표면 줄이기

gVisor 의 핵심은 "신뢰 못 할 입력이 닿는 인터페이스를 좁히고, 좁힌 곳을 검사한다". API 게이트웨이, MCP 도구 설계(도구 3개 + 가드레일, 07장), 테넌트 RBAC 모두 같은 사고다.

한 줄로 갈아 끼우는 구조

RuntimeClass·storageClass·ingressClass 처럼 "이름 하나로 구현을 고른다" 는 쿠버네티스의 반복 패턴. 새 기술(다른 샌드박스, 다른 빌더)을 제안할 때 "어디 한 줄만 바꾸면 되는가" 로 설명한다.

권한 없이 하는 법 찾기

Docker 소켓 → kaniko, 특권 컨테이너 → user namespace. "이 일에 정말 root 가 필요한가" 를 먼저 묻는 습관이 심사 Q&A 의 보안 질문에 가장 잘 먹힌다.
