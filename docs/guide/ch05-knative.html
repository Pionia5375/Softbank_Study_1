이 장의 지도

전체 아키텍처에서 이 장이 맡는 곳은 "요청이 함수 파드에 닿기까지"와 "파드 수를 0 과 N 사이에서 움직이는 일"이다. 무대는 맥 위의 kind 클러스터다(kind = Kubernetes in Docker, Docker 컨테이너 하나를 쿠버네티스 노드 하나로 쓰는 로컬 클러스터 도구. 노드는 클러스터를 이루는 기계 하나이고, 여기서는 control-plane 노드 1대와 워커 3대다). 맥의 localhost:8081 로 들어온 요청은 control-plane 노드의 NodePort 31080(NodePort = 모든 노드의 같은 포트를 열어 클러스터 안 Service 로 넘겨 주는 방식) 을 지나 Kourier 로 간다. Kourier 는 Knative 전용 입구로, 범용 L7 프록시 서버 Envoy 하나와 그 Envoy 에 설정을 넣어 주는 작은 컨트롤러로 이루어진다. Envoy 는 HTTP 요청의 Host 헤더(어느 호스트 이름으로 보낸 요청인지 적는 칸. 진짜 DNS 가 없어도 이 값만 맞추면 된다)를 보고 어느 함수인지 고른다. 함수 파드가 있으면 파드로, 없으면 activator(파드가 없을 때 요청을 대신 받아 두었다가 파드가 뜨면 넘기는 Knative 부품)로 간다.

노드는 역할별로 풀(pool, 같은 역할의 노드 묶음. 라벨 pool=system|build|exec)로 나뉜다. 함수 파드는 exec 풀에만 뜨고, Knative 부품은 전부 system 풀에 뜬다. build·exec 풀에는 taint(노드에 거는 "출입 금지" 표시. 그 taint 를 견딘다고 toleration 을 적은 파드만 올 수 있다)가 걸려 있어서, toleration 이 없는 플랫폼 부품은 자연히 system 풀로 모인다. 함수는 namespace(쿠버네티스 안에서 이름과 권한을 나누는 칸)별로 산다: 04 의 측정용 함수 3개는 fn-runtime, 05 의 사용자 함수는 테넌트 namespace tenant-a. 04 함수는 Argo CD(Git 에 둔 YAML 을 클러스터에 맞춰 적용해 주는 GitOps 도구, 01장)가 Git 에서 적용하고, 05 함수는 컨트롤 플레인(이 PoC 에서는 함수 배포 API 를 가진 Spring Boot 서비스를 뜻한다, 07장)이 쿠버네티스 API 로 직접 적용한다. 위 칩에 적힌 나머지 두 이름도 미리 풀어 두면, KPA(Knative Pod Autoscaler)는 요청 수를 보고 파드 수를 정하는 Knative 의 오토스케일러이고, queue-proxy 는 함수 파드마다 옆에 붙어 요청을 세고 상한을 지키는 작은 프록시다. 둘 다 아래에 절이 하나씩 있다.

서버리스와 FaaS

서버리스는 "서버가 없다"가 아니라 "서버 수를 사용자가 정하지 않는다"

서버리스(serverless)는 서버를 몇 대 띄울지, 언제 줄일지를 사용자가 아니라 플랫폼이 요청량을 보고 정하는 운영 모델이다. 그중 FaaS(Function as a Service)는 사용자가 "함수 코드" 만 올리면 빌드·배포·스케일·격리를 플랫폼이 다 하는 형태다. Spring 에 비유하면, 개발자는 @RestController 메서드 하나만 쓰고 톰캣을 몇 개 띄울지, 로드 밸런서에 어떻게 붙일지는 전혀 신경 쓰지 않는 상태다.

핵심 성질은 셋이다.

  • 요청 기반 스케일: 동시에 처리 중인 요청 수(또는 초당 요청 수)를 보고 인스턴스(여기서는 함수를 돌리는 파드) 수를 정한다. CPU 사용률을 보는 쿠버네티스 기본 오토스케일러 HPA(Horizontal Pod Autoscaler, CPU·메모리 사용률로 파드 수를 늘리고 줄이는 컨트롤러)와 다르다. Knative 의 오토스케일러는 KPA(Knative Pod Autoscaler)라 부르고, 이 장의 "KPA 오토스케일링 알고리즘" 절에서 자세히 본다.
  • 0 까지 줄이기(scale-to-zero): 요청이 없으면 인스턴스를 0개로. 쉬는 함수는 자원을 먹지 않는다.
  • 콜드 스타트(cold start): 0개일 때 온 첫 요청은 인스턴스가 뜰 때까지 기다린다. 0 까지 줄이는 대가다.

0 까지 줄이는 일의 경제학

항상 켜 두는 서버는 "가장 바쁠 때" 기준으로 자리를 잡는다. 요청이 뜸한 함수 수백 개가 각자 파드 하나씩 쥐고 있으면, 노드 메모리는 대부분 쉬는 프로세스가 차지한다. 0 까지 줄이면 그 자리를 다른 함수가 쓴다. 멀티테넌트 FaaS 에서는 "함수 수 × 최소 파드 수 × 파드 메모리" 가 곧 노드 대수이므로, 최소 파드 수를 0 으로 할 수 있느냐가 비용 구조를 바꾼다.

대가는 두 가지다. 첫째, 콜드 스타트 지연이 사용자에게 보인다. 둘째, 0 에서 1 로 가는 동안 요청을 어딘가 붙잡아 둘 장치가 필요하다. Knative 에서 그 장치가 activator 다. 그래서 설계 질문은 언제나 "이 함수는 콜드 스타트를 감수할 만큼 뜸한가" 이고, 아니면 min-scale(파드 수의 하한을 정하는 주석. 1 이면 요청이 없어도 파드 하나를 켜 둔다)로 웜 파드(warm pod, 이미 떠 있어서 바로 응답할 수 있는 파드)를 남긴다.

다른 서버리스 플랫폼과 무엇이 같고 다른가

같은 문제(요청 기반 스케일, 0 까지 줄임, 콜드 스타트 중 요청 보관)를 서로 다른 층에서 푼다. 비교 기준은 "스케일 단위", "0 일 때 요청을 누가 잡나", "버전·트래픽 분할", "격리 단위" 다.

왜 Knative 인가 (대안)

작년 본선 주제가 FaaS 였고 상위 팀이 Knative + gVisor 조합이었다(04 README). 우리가 필요한 것은 (1) 0↔N, (2) 0 일 때 요청 보관, (3) 버전별 트래픽 분할(롤백), (4) 노드 풀 고정이다. KEDA HTTP add-on 은 (1)(2)는 되지만 (3)이 없다. OpenFaaS 는 (3)이 약하고 0 까지 줄이기가 상용판 기능이다(공식 비교표 기준, 위 표 참고). 직접 만들기는 본선 시간 안에 못 한다. 자세한 표는 결정 표.

Knative Serving 자원 모델

앞 절에서 "코드만 올리면 플랫폼이 0↔N 을 맡는다" 는 그림을 봤다. 이제 그 약속이 Knative 안에서 어떤 객체로 표현되는지부터 본다. 뒤의 모든 절(부품, 요청 경로, 오토스케일링)은 여기서 나오는 네 객체 이름을 전제로 한다.

한 장을 넣으면 네 종류가 생긴다

우리가 쓰는 것은 kind: Service (apiVersion serving.knative.dev/v1) 한 장뿐이다. 쿠버네티스 YAML 에서 kind 는 객체의 종류, apiVersion 은 그 종류가 속한 API 그룹과 버전이다. 쿠버네티스 기본 리소스 Service(파드 집합에 고정 이름·IP 를 주는 것)와 이름이 같아 헷갈리므로 Knative 의 것은 kubectl 에서 ksvc 로 줄여 부른다. Knative controller(Knative 가 설치하는 프로그램. 객체를 지켜보다가 거기서 파생되는 객체를 만들고 상태를 적는다)는 이 한 장을 둘로 쪼갠다. "무엇을 돌릴까"(컨테이너 이미지·환경 변수·자원) 는 Configuration 에, "요청을 어디로 보낼까"(몇 % 를 어느 버전으로) 는 Route 에 넘긴다. Configuration 은 spec.template 이 바뀔 때마다 Revision 을 하나씩 새로 만든다. Revision 은 그 순간의 코드·설정 스냅샷이고, 한 번 만들어지면 바뀌지 않는다.

Spring 에 비유하면 Revision 은 "빌드된 jar 하나 + 그 jar 의 application.yml" 이고, Route 는 "로드 밸런서의 가중치 표" 다. 롤백은 jar 를 다시 빌드하는 게 아니라 가중치 표만 예전 jar 쪽으로 돌리는 일이 된다.

누가 어떤 필드의 주인인가

Service 는 두 자식의 "주인 노릇" 만 한다. Service 의 spec.template 은 Configuration 의 spec.template 으로 그대로 복사되고, Service 의 spec.traffic 은 Route 의 spec.traffic 으로 복사된다. 그래서 Configuration 이나 Route 를 직접 고치면 Service controller 가 다시 덮어쓴다. 고칠 곳은 언제나 ksvc 다.

Revision 이름은 <서비스>-<5자리 세대 번호> 다. 우리 함수는 hello-runc-00001, 05 의 tenant-a/hello 는 hello-00001, hello-00002 … 로 쌓인다. 세대 번호는 Configuration 의 metadata.generation(쿠버네티스가 spec 이 바뀔 때마다 1씩 올리는 번호)이고 Revision 의 라벨(label, 객체에 붙이는 key=value 꼬리표. 조회와 선택의 기준이 된다) serving.knative.dev/configurationGeneration 에도 남는다. 05 의 MCP rollback(운영 에이전트가 트래픽을 옛 Revision 으로 돌리는 도구, MCP 절)은 이 라벨로 Revision 을 정렬한다.

Revision 이 하나 생기면 그 아래로 쿠버네티스 객체가 딸린다.

  • Deployment: 쿠버네티스가 같은 파드를 N개 유지해 주는 기본 리소스. 파드 수(replicas)를 Knative 가 올리고 내린다.
  • PodAutoscaler(PA, autoscaling.internal.knative.dev): KPA 가 판단 결과(원하는 파드 수 desiredScale, 실제 수 actualScale)를 적는 Knative 내부 객체.
  • ServerlessService(SKS, networking.internal.knative.dev): 쿠버네티스 Service 를 관리하는 Knative 내부 객체. 쿠버네티스 Service 는 파드 집합에 고정된 이름과 IP 를 주는 리소스이고, 그 이름 뒤에 실제로 연결된 파드 IP:포트 목록을 endpoints 라 한다. SKS 는 Service 두 개(공개용 <revision>, 내부용 <revision>-private)를 만들고, 공개용의 endpoints 를 함수 파드 IP 로 채울지 activator IP 로 채울지 바꾼다(요청 경로 절).
  • Route 쪽에서는 KIngress 가 생긴다. Ingress 는 "밖에서 들어온 요청을 호스트·경로에 따라 어느 Service 로 보낼지" 적는 규칙 객체인데, Knative 는 쿠버네티스 표준 Ingress 대신 자기 종류(networking.internal.knative.dev/v1alpha1 Ingress, 줄여서 KIngress)를 쓰고, 설치된 네트워크 층(우리는 Kourier)이 그것을 Envoy 설정으로 번역한다. Route 는 또 자기 이름의 쿠버네티스 Service(hello, type ExternalName)를 만들어 클러스터 안에서 hello.tenant-a.svc.cluster.local 로 부를 수 있게 한다(네트워크 층 절).

바뀌지 않는 Revision, latestRevision, 트래픽 분할, 태그

불변성 (immutability)

Revision 의 spec 은 만들어진 뒤 바뀌지 않는다. 그래서 "Revision 3 = 이 이미지 + 이 설정" 이 영원히 참이다. 이것이 롤백을 믿을 만하게 만드는 전제인데, 이미지를 태그(:v1)로 적으면 그 전제가 흔들린다. 태그는 나중에 다른 이미지로 옮겨 붙일 수 있기 때문이다. Knative 가 Revision 을 만들 때 태그를 digest(이미지 내용 전체의 sha256 해시. 내용이 같으면 같고, 한 글자라도 다르면 다르다. @sha256:…)로 바꿔 Revision status 에 적어 두는 이유다(설정 맵 절의 태그 해석). spec.template 의 어떤 칸이든(주석 한 줄이라도) 바뀌면 새 Revision 이 생긴다. 이름을 직접 정하려면 spec.template.metadata.name 을 쓸 수 있지만, 그 이름이 이미 있으면 거절된다.

latestRevision 과 Ready

latestCreatedRevisionName 은 가장 최근에 만든 Revision, latestReadyRevisionName 은 그중 Ready 가 된 가장 최근 Revision 이다. 새 Revision 이 Ready 가 안 되면(파드가 Pending(갈 노드가 없어 대기 중), 이미지 못 받음, 준비 확인(readiness probe, "요청 받을 준비가 됐나" 를 주기적으로 묻는 검사) 실패) 둘이 갈라지고, latestRevision: true 트래픽은 계속 이전 Ready Revision 으로 간다. 이 성질 때문에 "새 배포가 망가져도 옛 버전이 계속 응답" 한다 (깨지면 절의 toleration 시나리오).

트래픽 분할과 태그

spec.traffic 은 목록이고 percent 합이 100 이어야 한다. 각 항목은 셋 중 하나로 대상을 고른다: revisionName(고정), configurationName, latestRevision: true(최신 Ready 를 따라감). tag 를 붙이면 그 대상만 받는 별도 주소가 생긴다. 주소 모양은 config-network(Knative 의 네트워크 설정을 담은 ConfigMap. ConfigMap 은 설정값을 key-value 로 담는 쿠버네티스 기본 객체다. 설정 맵 절)의 tag-template(기본 {{.Tag}}-{{.Name}})과 domain-template(기본 {{.Name}}.{{.Namespace}}.{{.Domain}}) 을 합친 것이다. percent 0 + tag 조합은 "운영 트래픽은 안 주고 시험용 주소만 여는" 다크 런치(dark launch)다.

함수 Route 재조정(route):
  targets = []
  각 t in route.spec.traffic:
    만약 t.latestRevision:  rev = configuration.status.latestReadyRevisionName
    아니면:               rev = t.revisionName
    만약 rev 가 Ready 아님: route.status.Ready = False  // 그래도 기존 KIngress 는 안 지운다
    targets.add(rev, t.percent, t.tag)
  확인 sum(percent) == 100
  KIngress 규칙 = [ 기본 호스트 → targets 전부 (비율대로) ]
               + [ 태그마다 "tag-name.ns.domain" → 그 rev 100% ]
  KIngress 를 apply  // net-kourier-controller 가 받아서 Envoy 로

트래픽을 한 번에 옮기지 않고 서서히 옮기는 손잡이도 있다. Service 나 Route 의 주석 serving.knative.dev/rollout-duration(또는 config-network 의 rollout-duration, 기본 0 = 즉시)에 시간을 주면, latestRevision: true 대상의 트래픽이 그 시간에 걸쳐 새 Revision 으로 옮겨 간다. 우리 PoC 는 쓰지 않는다(플랫폼 배포의 카나리는 02장 Argo Rollouts 가 맡고, 함수는 즉시 전환). 본선에서 "함수 배포도 점진 전환이 되나" 를 물으면 이 주석 한 줄이 답이다.

Revision 은 쌓이기만 하지 않는다. config-gc(Revision 가비지 컬렉션 설정 ConfigMap)의 기본값(retain-since-create-time 48h, retain-since-last-active-time 15h, min-non-active-revisions 20, max-non-active-revisions 1000) 에 따라 트래픽을 안 받는 오래된 Revision 은 지워진다. 그래서 "몇 달 전 Revision 으로 롤백" 은 보장되지 않는다. 지우면 안 되는 Revision 에는 주석 serving.knative.dev/no-gc: "true" 를 붙인다.

우리 PoC 에서는

깨지면 이렇게 보인다

증상: kubectl get ksvc 의 LATESTCREATED 와 LATESTREADY 가 다르다. 함수는 응답하는데 새 코드가 아니다. 볼 곳: kubectl -n tenant-a get revisions 에서 READY 가 False 인 Revision 의 REASON, kubectl describe revision <이름>. 고치는 법: 원인(이미지, 스케줄, 준비 확인)을 고친 새 template 을 다시 apply 한다. 망가진 Revision 을 지울 필요는 없다.

자원 모델 절에서 "무엇이 만들어지나" 를 봤다. 이 절은 "누가 만들고 누가 요청을 나르나", 즉 Knative 를 설치하면 클러스터에 뜨는 프로그램들이다.

결정하는 쪽과 요청을 나르는 쪽

Knative 부품은 두 무리로 나뉜다. 컨트롤 플레인(control plane)은 객체를 보고 다른 객체를 만들거나 숫자를 정한다. 요청 자체는 만지지 않는다. 데이터 플레인(data plane)은 실제 HTTP 요청이 지나가는 길이다. 단, activator 는 둘 다에 걸친다: 요청을 나르면서(데이터) autoscaler 에 수요 신호를 보낸다(컨트롤).

controller

Service → Configuration·Route → Revision → Deployment·PodAutoscaler·SKS 를 만드는 재조정 루프(reconcile loop, "원하는 상태" 와 "실제 상태" 를 비교해 차이를 메우는 반복) 묶음.

webhook

승인 웹훅(admission webhook). API 서버(쿠버네티스의 중심 REST 서버. 모든 객체는 여기를 거쳐 저장소 etcd 에 쓰인다)가 객체를 저장하기 직전에 외부 프로그램을 불러 검사·수정을 맡기는 장치다. ksvc 의 기본값을 채우고, 기능 플래그 위반을 여기서 거절한다.

autoscaler

queue-proxy 지표를 1초마다 긁어 모으고, 2초마다 PodAutoscaler 의 원하는 파드 수를 정한다 (KPA).

activator

파드가 0개이거나 여유가 모자랄 때 요청을 받아 잡아 두고, 파드가 생기면 넘긴다.

net-kourier-controller

KIngress 를 Envoy 설정으로 번역해 xDS(Envoy 가 외부 서버에서 설정을 실시간으로 받아 가는 API 묶음)로 밀어 준다. knative-serving 에 뜬다.

queue-proxy

함수 파드마다 붙는 옆 컨테이너, 즉 사이드카(sidecar: 한 파드 안에서 주 컨테이너 옆에 같이 뜨는 보조 컨테이너. 같은 네트워크 공간을 쓰므로 localhost 로 주 컨테이너를 부른다). 요청을 세고, 상한을 지키고, 준비를 확인한다.

한 장으로 보는 전체 구조

요청이 지나가는 순서는 늘 같다: Envoy(Kourier 게이트웨이) → (필요하면 activator) → 파드 안 queue-proxy(:8012) → user-container(:8080). 함수 코드는 queue-proxy 뒤에 숨어 있어서, Knative 는 코드를 한 줄도 고치지 않고 요청 수를 세고 상한을 지킬 수 있다. 이게 사이드카(sidecar) 방식의 힘이다.

(2) autoscaler 가 "이 Revision 에 activator 몇 개를 붙일지(activator 부분 집합 크기)" 를 정한다. 식은 max(2, ceil((준비된 파드 수 × 파드당 total + TBC) / activator-capacity)) 다. activator-capacity 는 activator 하나가 감당한다고 보는 동시 요청 수(기본 100), TBC 는 target-burst-capacity(미리 대비할 폭주분, KPA 절)이고, TBC 가 0 이면 늘 2개다. 요청 경로: 파드가 있을 때와 0개일 때

부품 이름을 알았으니, 요청 하나가 그 부품들을 어떤 순서로 지나는지 본다. 핵심은 "파드가 있을 때" 와 "0개일 때" 길이 어디서 갈라지는가다.

입구는 같고, 갈림길은 하나

Envoy 는 함수 주소(Host 헤더)를 보고 그 Revision 의 공개용 쿠버네티스 Service 로 보낸다. 갈림길은 그 Service 의 endpoints 목록(Service 이름 뒤에 실제로 연결된 IP:포트 목록)에 무엇이 들어 있느냐다. 파드 IP 가 들어 있으면 요청은 파드로 바로 가고(serve 모드), activator IP 가 들어 있으면 activator 로 간다(proxy 모드). 이 목록을 바꾸는 것이 ServerlessService(SKS) 이고, 언제 바꿀지 정하는 것이 PodAutoscaler(KPA) 다. Envoy 설정은 바뀌지 않는다는 점이 중요하다. 그래서 전환이 빠르다.

0 → 1: 첫 요청이 응답을 받기까지

N → 0: 요청이 끊긴 뒤 사라지기까지

SKS 모드를 고르는 규칙과 상태 기계

KPA 재조정기(pkg/reconciler/autoscaling/kpa, autoscaler 파드 안에서 도는 루프)는 매번 다음을 정한다. 아래에서 want 는 autoscaler 가 원하는 파드 수이고, EBC(Excess Burst Capacity, 여유 용량)는 "지금 파드들의 총 용량 − 미리 대비할 폭주분 − 지금 처리 중인 양" 으로, 음수면 파드만으로는 폭주를 못 받는다는 뜻이다(계산은 KPA 절). 기본은 proxy 이고, 두 조건이 모두 참일 때만 serve 로 바꾼다.

함수 SKS 모드 정하기(pa, decider):
  mode = PROXY
  만약 want == 알수없음 그리고 pa 가 inactive:   // autoscaler 재시작 직후, 이전에 0 이었음
      mode = PROXY
  아니고 만약 want > 0 그리고 decider.ExcessBurstCapacity >= 0:
      mode = SERVE                                // 파드가 있고 여유도 충분할 때만 activator 를 뺀다
  activator 개수 = computeNumActivators(ready 파드 수, decider)  // 최소 2
  SKS.spec.mode = mode
  SKS.spec.numActivators = activator 개수

scale-to-zero 의 정확한 조건은 kpa/scaler.go 의 handleScaleToZero 에 있다. autoscaler 가 0 을 원해도 바로 0 이 되지 않고, PodAutoscaler 의 Active 상태에 따라 갈린다. (a) enable-scale-to-zero 가 false 면 1 에서 멈춘다. (b) Active=True(요청을 받던 중)면, Active 로 지낸 시간이 stable window 이상일 때만 Active=False(inactive) 로 바꾼다. 그 전까지는 1개까지만 줄이고 기다린다. (c) Active=False 면, 먼저 공개 Service 로 프로브를 보내 activator 가 정말 경로에 있는지 확인한다(TBC 가 -1 이면 늘 있으니 생략). 확인되면 inactive 로 지낸 시간이 max(scale-to-zero-grace-period, scale-to-zero-pod-retention-period) 이상이거나, SKS 가 proxy 모드로 grace period 이상 있었을 때 0 으로 간다. (d) Active=Unknown(0 → 1 로 깨우는 중)인데 progress-deadline(기본 600s) + 30초(activationTimeoutBuffer) 안에 파드가 준비되지 않으면 "활성화 실패" 로 보고 다시 0 으로 내린다.

왜 이런 구조인가 (대안)

대안은 Envoy 설정 자체를 "파드 있음 / 없음" 에 따라 바꾸는 것이다. 그러면 0 경계마다 xDS 갱신이 Envoy 전체에 퍼져야 하고 반영 지연이 생긴다. Knative 는 Envoy 는 그대로 두고 Revision 마다 쿠버네티스 Service 의 endpoints 만 바꾼다. 경계가 Revision 단위로 좁아지고, 바꾸는 주체도 SKS 하나로 모인다.

KPA 오토스케일링 알고리즘

요청 경로 절에서 "autoscaler 가 원하는 파드 수(want)" 와 "여유 용량(EBC)" 이 경로를 바꾼다는 것을 봤다. 이 절은 그 두 숫자를 autoscaler 가 어떻게 계산하는지다.

"파드 하나에 동시 요청 몇 개" 를 맞추는 온도 조절기

KPA(Knative Pod Autoscaler, autoscaler 파드 안에서 Revision 마다 파드 수를 정하는 알고리즘)는 HPA 처럼 CPU 를 보지 않고 동시에 처리 중인 요청 수(concurrency, 동시성: 어느 순간에 아직 응답을 돌려주지 않은 요청의 개수. 요청이 길수록, 많이 겹칠수록 커진다)를 본다. 목표가 "파드 하나당 동시 요청 7개" 이고 지금 전체 동시 요청이 21개면 파드 3개가 필요하다. 이 나눗셈을 2초마다 한다. 다만 순간 숫자가 아니라 지난 60초 평균(stable window)을 쓰고, 갑자기 몰리면 지난 6초 평균(panic window)으로 빨리 반응한다. HPA 와 달리 0 까지 내려갈 수 있다는 점이 가장 큰 차이다.

지표, 목표, 두 가지 모드

지표: concurrency 와 rps

주석 autoscaling.knative.dev/metric 으로 고른다. 기본은 concurrency(동시 처리 중인 요청 수), 다른 하나는 rps(초당 요청 수)다. KPA 는 이 둘만 쓴다. cpu·memory·커스텀 지표는 HPA 클래스(autoscaling.knative.dev/class: hpa.autoscaling.knative.dev)에서만 되고, 그 경우 0 까지 줄이기가 안 된다. 요청 하나가 오래 걸리는 함수는 concurrency 가 정확하고, 아주 짧은 요청이 쏟아지는 함수는 rps 가 더 안정적이다.

목표: target 과 70%

목표값은 ResolveMetricTarget 이 정한다. 순서는 이렇다.

  1. 기본 total = containerConcurrency (0 이면 config-autoscaler 의 container-concurrency-target-default, 기본 100).
  2. 주석 autoscaling.knative.dev/target 이 있으면 total = 그 값. 단 containerConcurrency 가 0 이 아니면 둘 중 작은 값.
  3. 실제 목표 = total × 사용률 (하한 0.01). 사용률은 container-concurrency-target-percentage(기본 70) 또는 주석 autoscaling.knative.dev/target-utilization-percentage. rps 지표일 때는 total 이 requests-per-second-target-default(기본 200)에서 시작하고 사용률은 같은 70% 다.

그래서 우리 04 ksvc(target 10, containerConcurrency 0)는 파드당 7, 05 템플릿(target 주석 없음, containerConcurrency 10)도 파드당 7 을 목표로 한다. 70% 는 "꽉 차기 전에 미리 늘려서 대기를 피하는" 여유다. target 은 부드러운 상한(soft limit, 평균을 맞출 뿐 넘을 수 있다), containerConcurrency 는 단단한 상한(hard limit, queue-proxy 가 넘는 요청을 줄 세운다)이다.

stable 모드와 panic 모드

의사코드, 0 의 경계, 그리고 activator 가 경로에 남는 조건

지표를 긁는 쪽도 알아 둔다. autoscaler 는 파드가 3개 이하면 전부, 그보다 많으면 통계적 표본(populationMeanSampleSize)만 골라 긁고 그 평균을 전체로 본다. 파드 수백 개를 매초 다 긁지 않기 위해서다. 우리 함수는 max-scale 5 라 거의 전부 긁는다.

target-burst-capacity(TBC): activator 가 언제 경로에 남나

EBC 가 음수면 SKS 는 proxy 모드로 남는다. 즉 activator 가 계속 요청을 받는다. 기본 TBC 211 은 "갑자기 211 개 요청이 몰려도 파드 앞에서 줄 서지 않게 하겠다" 는 뜻이다. 파드 몇 개의 총 용량이 211 보다 작으면 activator 가 계속 앞에 서서, 바쁜 파드를 피해 여유 있는 파드로 나눠 주고 넘치는 요청은 자기가 잡아 둔다. 값을 바꾸는 법: config-autoscaler target-burst-capacity 또는 주석 autoscaling.knative.dev/target-burst-capacity. 0 = 0개일 때만 activator, -1 = 항상 activator.

주의: 주석 이름의 옛 표기

옛 문서와 config 설명에는 autoscaling.knative.dev/minScale, maxScale, initialScale 처럼 낙타 표기가 남아 있다. 지금 공식 표기는 min-scale, max-scale, initial-scale 이고 우리 코드도 이 표기를 쓴다. v1.23 소스(pkg/apis/autoscaling/register.go 의 kmap.KeyPriority)는 둘 다 읽되 하이픈 표기를 우선한다. 단 target, window, metric, class, activation-scale 은 하이픈 표기 하나뿐이다.

edge case 셋. (1) 새 Revision 은 initial-scale 1 로 파드 하나를 띄우고 Ready 를 확인한다. 그래서 0 인 함수라도 배포 직후 잠깐 파드가 보이고, stable window 뒤 다시 0 이 된다(04 README 6단계 "처음 만들 때 잠깐 뜨고"). (2) min-scale 은 Revision 이 트래픽을 받을 수 있을 때만 지켜진다. PodAutoscaler 의 spec.reachability 가 Unreachable(Revision 라벨 routingState 가 reserve, 즉 어떤 Route 도 가리키지 않음)이면 ScaleBounds 가 하한을 0 으로 본다(v1.23 pa_lifecycle.go). 그래서 트래픽 0% 인 예비 Revision 은 min-scale 이 있어도 0 으로 내려가고, 앞의 의사코드처럼 줄이기 한도도 없어 한 번에 0 이 된다. 그래서 05 MCP scale 은 traffic 이 고정돼 있으면 거절한다. (3) window 를 짧게 하면 0 으로 빨리 가지만 지표가 흔들려서 파드 수가 출렁인다. 측정 편의를 위한 값이지 운영값이 아니다.

왜 KPA (대안)

HPA 클래스는 CPU·메모리로 늘리는 익숙한 방식이지만 0 까지 못 내리고, 지표 반영이 metrics-server(파드의 CPU·메모리 사용량을 모아 주는 쿠버네티스 부가 부품) 주기에 묶여 느리다. 함수는 "요청이 몇 개 걸려 있나" 가 부하를 가장 직접 보여 주는 숫자라 concurrency 기반 KPA 가 맞다. 대가는 지표가 queue-proxy 에서만 나온다는 점(사이드카 필수)이다.

queue-proxy: 파드 안의 문지기

KPA 가 보는 "동시 요청 수" 는 어디서 오나. 파드마다 붙는 작은 프록시 queue-proxy 가 센다. 이 절은 그 프록시가 하는 네 가지 일이다.

함수 코드 앞에 서는 작은 프록시

Knative 는 Revision 의 Deployment 를 만들 때 우리 컨테이너(user-container) 옆에 queue-proxy 컨테이너를 끼워 넣는다. 04 README 6단계 확인 질문의 답이 이것이다: 파드가 2/2(준비된 컨테이너 수 / 전체 컨테이너 수)로 보이는 이유. 파드로 들어오는 요청은 전부 queue-proxy 를 먼저 지난다. 그래서 queue-proxy 는 (1) 지금 몇 개를 처리 중인지 세고, (2) 상한을 넘는 요청을 줄 세우고, (3) 함수가 준비됐는지 확인하고, (4) 파드가 꺼질 때 처리 중인 요청을 끝까지 마무리한다.

네 가지 역할

동시성 상한 (breaker, 회로 차단기처럼 동시에 통과하는 요청 수를 막는 부품)
containerConcurrency 가 0 이 아니면 그 수만큼만 user-container 로 동시에 보낸다. 넘치는 요청은 queue-proxy 안에서 줄을 선다(이름이 queue-proxy 인 이유). 줄 길이에도 상한이 있다: containerConcurrency 의 10배. 그것마저 넘치면 503 "pending request queue full" 을 돌려준다. 0 이면 상한 없이 다 통과시킨다. activator 도 같은 값을 알고 있어서, proxy 모드에서는 파드마다 같은 상한의 breaker 를 두고 분배 방식도 값에 따라 바꾼다: 0(상한 없음)이면 파드 둘을 무작위로 골라 덜 바쁜 쪽(power of two choices), 3 이하면 첫 번째로 빈 파드, 4 이상이면 round-robin 이다(v1.23 activator/net/throttler.go). 그래서 04 함수(0)와 05 함수(10)는 activator 안에서 다르게 분배된다.

준비 확인 (readiness)
kubelet 의 readinessProbe(쿠버네티스가 "요청 받을 준비가 됐나" 를 주기적으로 묻는 검사. 실패하면 그 파드는 Service 의 endpoints 에서 빠진다)는 queue-proxy 를 향한다(:8012 에 헤더 K-Network-Probe: queue). queue-proxy 는 user-container 의 TCP 포트(ksvc 에 readinessProbe 를 안 적었을 때의 기본값. 적었으면 그 프로브)를 대신 확인하고, 통과하면 준비됐다고 답한다. 프로브에 periodSeconds 를 안 적으면(0) queue-proxy 가 50ms 간격·100ms 타임아웃으로 촘촘히 확인한다(aggressive probing, pkg/queue/readiness). kubelet 의 최소 주기(1초)보다 촘촘해서 콜드 스타트를 줄이는 장치다. livenessProbe 와 startupProbe 는 kubelet 이 user-container 에 직접 보낸다.
타임아웃과 우아한 종료
timeoutSeconds(요청 하나의 전체 시간 한도)를 넘는 요청을 504 로 끊는다. 비슷한 한도가 둘 더 있다: responseStartTimeoutSeconds(첫 응답 바이트까지)와 idleTimeoutSeconds(데이터가 안 흐르는 시간). 파드가 종료될 때는 프로브에 실패를 답해 endpoints 에서 빠지고, 처리 중인 요청이 끝날 때까지 기다린 뒤 끝난다.

네트워크 층: KIngress 와 Kourier

지금까지는 클러스터 안, 즉 Envoy 에서 파드까지였다. 이 절은 그 앞이다. Route 가 적은 규칙이 어떻게 Envoy 의 설정이 되고, 맥의 curl 이 어떻게 Envoy 까지 오나.

Knative 는 입구를 갈아 끼울 수 있게 만들었다

Istio 가 대표) 없이 Knative 에 필요한 것만 한다.

기능 플래그: 왜 nodeSelector 하나 쓰는 데 허락이 필요한가

Knative 는 ksvc 의 Pod 스펙 중 "어떤 노드에서든 같은 방식으로 돌 수 있는" 칸만 기본 허용한다. nodeSelector(파드를 특정 라벨의 노드로만 보내는 조건)·tolerations·runtimeClassName·affinity(노드나 다른 파드와 가깝게·멀게 두는 조건) 같은 칸은 함수를 특정 노드에 묶거나 실행 방식을 바꾸므로 운영자가 명시적으로 켜야 한다. 플래그가 꺼져 있으면 webhook 이 저장 전에 거절한다. 거절은 "그 apply 한 번" 만 실패시키고, 이미 떠 있는 Revision 은 건드리지 않는다.

태그를 digest 로: config-deployment 와 http 레지스트리

Revision 이 만들어질 때 controller 는 컨테이너 이미지가 태그(:v1)면 레지스트리에 물어 digest 로 바꾸고 Revision status 에 적는다. Deployment 는 이 digest 로 만들어진다. 그래서 나중에 누가 같은 태그에 다른 이미지를 올려도, 이미 있는 Revision 의 새 파드는 원래 이미지를 받는다. 불변 Revision 을 지키는 장치다.

건너뛰기의 대가는 04 의 함수 3개에 그대로 남는다. kind-registry:5000/fn/hello:v1 은 태그 그대로 Revision 에 들어가므로, 누군가 같은 v1 태그로 다시 빌드해 올리면, 다음에 0 → 1 로 뜨는 파드는 새 이미지를 받을 수 있다(노드에 옛 이미지가 캐시돼 있으면 옛 것을 쓸 수도 있다. imagePullPolicy(파드를 띄울 때 이미지를 다시 받을지 정하는 칸)의 기본값은 태그가 latest 가 아니면 IfNotPresent, 즉 "있으면 안 받음"). 같은 Revision 인데 파드마다 다른 코드가 돌 수 있다는 뜻이다. 그래서 04 README 는 "빌드마다 새 태그" 를 규칙으로 정했고, 05 는 kaniko 의 digest 를 받아 @sha256 으로 고정한다(06장).

config-deployment 의 다른 키도 알아 둔다: progress-deadline(기본 600s, Revision 의 파드가 이 시간 안에 준비 안 되면 실패), queue-sidecar-cpu-request(기본 25m), runtime-class-name(라벨 셀렉터로 Revision 들에 RuntimeClass 를 일괄 지정하는 키. 값은 YAML 맵으로 gvisor: {selector: {use-gvisor: "please"}} 처럼 "RuntimeClass 이름: 그 이름을 받을 Revision 라벨 조건" 을 적고, 키가 빈 문자열이면 조건에 안 걸린 Revision 의 기본값이다. 우리는 ksvc 에 직접 runtimeClassName 을 적는 쪽을 골랐다).

"READY" 와 "응답이 온다" 는 다르다

Knative 장애의 대부분은 "겉보기 정상" 이다. 새 Revision 이 망가져도 옛 Revision 이 응답하고, ksvc 가 READY 여도 네트워크가 막혀 있으면 요청은 닿지 않는다. 그래서 확인은 언제나 세 층으로 한다: (1) 객체 상태(get ksvc,revisions), (2) 파드 상태(get pods -o wide, describe), (3) 실제 요청(curl -H Host, Hubble).

시나리오 3 자세히: 왜 READY 인데 안 닿나

ksvc 의 Ready 는 "Revision 파드가 준비 확인을 통과했고 Route·KIngress 가 설정됐다" 는 뜻이다. 그런데 준비 확인은 kubelet → queue-proxy, 즉 파드가 도는 노드에서 파드로 가는 트래픽이다. 쿠버네티스 NetworkPolicy 문서는 "파드가 도는 노드와의 트래픽은 항상 허용" 이라고 못 박고 Cilium 도 그 규칙을 지키므로, default-deny 가 있어도 프로브는 통과한다(04장 8절). 반면 실제 요청은 다른 namespace(kourier-system 의 Envoy, knative-serving 의 activator)에서 출발한다. 03 의 default-deny(모든 파드를 고르고 허용 규칙은 비운 정책. 그 위에 허용을 쌓는다)는 같은 namespace 와 DNS 만 열어 두므로 이 요청들이 떨어진다. autoscaler 의 지표 긁기(:9090)도 knative-serving 에서 출발하므로 같이 막힌다.

poc/03-tenant-isolation/tenants/tenant-a.yaml발췌
# 5단계 Knative 함수(tenant-a/hello)가 이 namespace 에 뜬다. 요청은 kourier-system(입구)이나
# knative-serving(activator: 파드가 0개일 때 요청을 잡아 두는 곳)을 거쳐 들어오고, autoscaler(knative-serving)가
# queue-proxy 지표를 긁으러 들어온다. 이 둘을 안 열면 default-deny 에 막혀 ksvc 가 READY 여도 curl 이 응답을 못 받는다.
network:
  allowFromNamespaces: [knative-serving, kourier-system]

이 규칙은 namespace 단위로 연다(namespaceSelector = 상대 파드의 namespace 라벨로 고르는 조건. kubernetes.io/metadata.name 은 쿠버네티스가 모든 namespace 에 자동으로 붙이는 이름 라벨). 더 좁히려면 podSelector(상대 파드 자체의 라벨로 고르는 조건)를 붙여 activator·autoscaler·Envoy 파드만 열 수 있다. 다만 Knative 업그레이드로 라벨이 바뀌면 같이 깨진다는 대가가 있다.

시나리오 2: toleration 빠짐 (ANALYSIS B7)

ksvc 에서 tolerations 를 지우면 webhook 은 통과한다(칸이 없는 것은 위반이 아니다). 새 Revision 의 파드는 nodeSelector 로 exec 노드만 고르는데 그 노드의 taint 를 못 넘으니 Pending 이다. Revision 은 progress-deadline(기본 600s) 동안 Ready 를 기다리다 실패로 표시된다. 그동안 Route 의 latestRevision 은 옛 Ready Revision 을 가리키므로 트래픽은 끊기지 않는다. 단, 옛 Revision 이 0 으로 내려가 있으면 그 Revision 의 콜드 스타트는 정상 동작한다(옛 Revision 의 스펙엔 toleration 이 있다).

시나리오 4: http 레지스트리와 태그 해석

setup.sh 4/5 의 patch 가 빠지면, 04 의 kind-registry:5000/fn/hello:v1 은 태그라서 controller 가 digest 를 물으러 간다. kind-registry 는 TLS 가 없으므로 질의가 실패하고, Revision 의 조건 ContainerHealthy 가 False(이유 ContainerMissing, 메시지 Unable to fetch image "kind-registry:5000/fn/hello:v1": failed to resolve image to digest: …)가 되어 Ready 가 되지 못한다(v1.23 reconciler/revision/revision.go, revision_lifecycle.go). 05 는 digest(@sha256) 로 주므로 이 문제를 겪지 않는다. 같은 문제가 본선 환경(사설 레지스트리, 자체 서명 인증서)에서도 날 수 있다: 해결은 건너뛰기 목록, controller Deployment 에 CA(인증 기관) 인증서를 마운트하고 SSL_CERT_DIR 로 알려 주기(공식 Tag resolution 문서), 또는 처음부터 digest 배포.

정리

핵심 개념 체크리스트

  • ksvc 한 장이 Configuration·Route 로 갈라지고, template 변경마다 바뀌지 않는 Revision 이 생긴다는 것을 그림으로 그릴 수 있다.
  • latestCreated 와 latestReady 가 갈라질 때 트래픽이 어디로 가는지 말할 수 있다.
  • 트래픽 분할, 태그 주소, percent 0 다크 런치를 설명할 수 있다.
  • controller, webhook, autoscaler, activator, net-kourier-controller, queue-proxy, Envoy 가 각각 무엇을 하는지 한 줄씩 말할 수 있다.
  • SKS 의 serve/proxy 모드가 "공개 Service 의 endpoints 내용" 이라는 것을 안다.
  • scale-to-zero 순서(activator 를 먼저 넣고, 확인하고, 그다음 0)를 설명할 수 있다.
  • KPA 목표 = target(또는 containerConcurrency) × 70% 를 계산할 수 있다.
  • stable 60초, panic 6초, panic 기준 200%, panic 중 줄이지 않음을 안다.
  • target-burst-capacity 와 EBC 로 activator 가 경로에 남는 조건을 설명할 수 있다.
  • queue-proxy 의 네 역할(상한, 지표, 준비 확인, 종료)과 포트를 안다.
  • KIngress → net-kourier-controller → xDS → Envoy, Host 헤더 라우팅, config-domain 을 설명할 수 있다.
  • 기능 플래그가 webhook 에서 막는다는 것, 태그 해석이 http 레지스트리에서 실패한다는 것을 안다.
  • 콜드 스타트 구간과 각 구간을 줄이는 수단을 말할 수 있다.
  • MCP scale = min-scale 주석(새 Revision), rollback = traffic 고정(새 Revision 없음)을 구분한다.
  • "READY 인데 안 닿음" 을 NetworkPolicy 로 설명할 수 있다.

본선에서 떠올릴 패턴

  • 불변 버전 + 포인터: Revision(불변) 과 Route(가중치 포인터)를 나누면 배포·롤백·카나리가 전부 "포인터 바꾸기" 가 된다. 모델 서빙(모델 버전), 설정 배포, DB 스키마 마이그레이션 뷰 전환에도 같은 모양을 쓴다.
  • 0 경계에는 버퍼가 필요하다: 대상이 없을 때 요청을 잡아 둘 무언가(activator, 큐, 대기열)를 두고, 대상을 없애기 전에 버퍼를 먼저 경로에 넣는다. 배치 워커를 0 으로 줄이는 설계(KEDA + 큐)에 그대로 옮겨진다.
  • 사이드카로 계측·상한: 사용자 코드를 고치지 않고 앞에 작은 프록시를 둬서 세고, 막고, 준비를 확인한다. AI 에이전트 도구 호출 앞의 가드레일 프록시도 같은 구조다.
  • 두 창 오토스케일링: 느린 평균(안정)과 빠른 평균(급증)을 따로 보고, 급증 중엔 줄이지 않는다. 비용 경보, 레이트 리미터 설계에도 쓴다.
  • 필드 주인 나누기: 한 객체를 두 주체가 고치면 필드 단위로 주인을 정하고(server-side apply), 겹치는 칸은 누가 이기는지 명시한다.
  • READY ≠ 닿음: 상태 객체가 아니라 실제 요청으로 검증하는 합성 프로브(get_metrics 의 probe)를 둔다.
