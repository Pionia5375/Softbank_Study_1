1. 쿠버네티스 네트워크 모델

모델은 무엇이고 왜 이렇게 정했나

쿠버네티스는 네트워크를 직접 구현하지 않는다. 대신 "어떤 모양이어야 하는가" 라는 모델(약속) 만 정하고, 실제 배선은 네트워크 플러그인(CNI 플러그인)에게 맡긴다. 공식 문서가 정한 약속은 세 줄이다.

  1. 클러스터 안의 모든 파드는 클러스터 전체에서 유일한 자기 IP 를 갖는다. 파드 안의 컨테이너들은 그 IP 와 네트워크 namespace 를 같이 쓴다 (그래서 같은 파드의 컨테이너끼리는 localhost 로 부른다. Knative 함수 파드의 queue-proxy 가 사용자 컨테이너를 localhost:8080 으로 부르는 것이 이 경우다).
  2. 모든 파드는 어느 노드에 있든 다른 모든 파드와 NAT(주소 변환) 없이 직접 통신할 수 있다. 보낸 쪽 IP 가 받는 쪽에 그대로 보인다.
  3. 노드 위의 에이전트(kubelet, 시스템 데몬)는 그 노드의 모든 파드와 통신할 수 있다.

왜 이렇게 정했나. Docker 초기 방식은 컨테이너마다 노드 포트를 하나씩 빌려 와 "노드IP:무작위 포트" 로 서로 부르게 했다. 그러면 프로그램이 자기 주소를 모르고, 포트 충돌을 사람이 관리해야 한다. 쿠버네티스는 파드를 "IP 하나 가진 작은 VM" 처럼 다루게 해서 이 문제를 없앴다. 대가는 누군가 파드 IP 를 나눠 주고(IPAM), 노드 사이로 파드 패킷을 실어 날라야 한다는 것이다. 그 일이 CNI 플러그인 몫이고, 우리 PoC 에서는 Cilium 이다.

이 약속에는 "막는다" 는 말이 없다. 기본은 전부 열림 이다. 그래서 테넌트를 나누려면 NetworkPolicy 로 닫아야 하고, 그 정책을 실제로 집행하는 것도 CNI 다 (8절).

모델을 실제로 만드는 두 가지 방식

파드 IP 는 실제 물리망(우리 경우 Docker 네트워크 kind)이 모르는 주소다. 다른 노드의 파드로 보내려면 두 방법 중 하나를 쓴다.

오버레이 (overlay, 터널)
파드 패킷을 통째로 노드 IP 패킷 안에 한 번 더 싸서(캡슐화) 보내고, 받는 노드가 벗긴다. VXLAN(UDP 8472), Geneve(UDP 6081) 가 대표. 물리망은 노드 IP 만 알면 되니 어디서나 돈다. 대가는 헤더만큼 MTU 가 줄고 싸고 벗기는 비용이 든다.
네이티브 라우팅 (native routing)
파드 대역을 물리망 라우터가 알게 한다 (노드에 정적 경로, BGP, 클라우드 경로표). 캡슐화가 없어 빠르지만 물리망을 손댈 수 있어야 한다. AWS VPC CNI 는 아예 VPC IP 를 파드에 준다.

Cilium CLI(cilium install)는 클러스터 종류를 알아본다. 소스(cilium-cli install/autodetect.go, install/helm.go)를 보면 kind 로 판단하면 데이터패스를 터널(기본 VXLAN) 로, IPAM 을 ipam.mode=kubernetes(노드 객체의 spec.podCIDR 를 그대로 쓰기)로 정한다. 그래서 우리 파드 IP 는 kind 기본 파드 대역 10.244.0.0/16 에서 나온다. 【확인 필요: 우리가 쓰는 v1.20.3 CLI 에서도 같은 기본값인지 cilium config view | grep -E "routing-mode|tunnel-protocol|ipam" 로 본다】

2. 리눅스 부품: namespace, veth, bridge, 라우팅, netfilter, conntrack

모든 CNI 는 같은 커널 부품으로 만든다

Cilium 이든 kindnet 이든 Calico 든, 파드 네트워크는 리눅스 커널이 이미 가진 부품 몇 개를 조립한 것이다. 이 부품을 알면 어떤 CNI 를 만나도 "패킷이 어디로 지나가고 어디서 버려질 수 있나" 를 그릴 수 있다.

network namespace
네트워크 장치·IP·라우팅 표·방화벽 규칙의 독립된 사본. 파드 하나 = netns 하나. 파드 안에서 ip addr 을 치면 그 파드의 eth0 과 lo 만 보인다.
veth pair
양 끝이 연결된 가상 랜선. 한쪽 끝을 파드 netns 에(eth0), 다른 끝을 노드 netns 에(Cilium 은 lxcXXXX 라는 이름) 둔다. 한쪽에 넣으면 다른 쪽으로 나온다.
bridge
커널 안의 가상 스위치. 여러 veth 를 꽂아 같은 L2 로 묶는다 (Docker 의 docker0, CNI bridge 플러그인의 cni0). Cilium 은 bridge 를 쓰지 않는다.
라우팅 표
"목적지 IP 가 이 대역이면 이 장치로" 의 목록. kindnet 은 파드마다 /32 경로와 노드마다 파드 대역 경로를 깐다.
netfilter / iptables
커널 IP 처리 경로의 다섯 군데 훅(PREROUTING, INPUT, FORWARD, OUTPUT, POSTROUTING)에 규칙을 거는 틀. kube-proxy 의 Service 주소 변환(DNAT)과 많은 CNI 의 NetworkPolicy 가 여기에 걸린다.
conntrack
연결 추적 표. "이 패킷은 이미 허락된 연결의 답장인가" 를 기억한다. 정책이 "들어오는 것만" 허용해도 답장이 나갈 수 있는 이유, DNAT 된 연결의 답장 주소를 되돌리는 근거.

노드 안에서 파드 패킷이 지나가는 두 가지 배선

netfilter 훅과 conntrack 의 자리

stateDiagram-v2
  [*] --> NEW: 첫 패킷 (SYN)
  NEW --> ESTABLISHED: 반대 방향 답장을 봄
  ESTABLISHED --> ESTABLISHED: 같은 5-튜플의 패킷
  ESTABLISHED --> CLOSING: FIN 또는 RST
  CLOSING --> [*]: 시간 초과로 표에서 지움
  NEW --> [*]: 답장 없이 시간 초과 (정책 drop 이면 여기)

conntrack 은 연결을 (출발 IP, 출발 포트, 도착 IP, 도착 포트, 프로토콜) 다섯 값으로 식별한다. NetworkPolicy 공식 문서의 "허용된 연결의 답장은 암묵적으로 허용된다" 가 이 표 덕분이다. Cilium 은 커널 netfilter conntrack 대신 자기 eBPF 맵에 연결 추적 표 를 따로 둔다 (7절). 정책에 막혀 SYN 이 버려지면 연결은 NEW 에서 더 나아가지 못하고, 보낸 쪽은 거절(RST)도 받지 못한 채 재전송만 하다 시간 초과가 된다. 그래서 막힌 연결이 "Connection refused" 가 아니라 타임아웃 으로 보인다 (test-isolation.sh 가 3초를 기준으로 BLOCKED 를 판정하는 이유).

kind 노드에서 직접 확인하는 법과 패킷 경로 의사코드

kind 노드는 컨테이너라서 docker exec 로 노드 netns 에 들어갈 수 있다. 04 setup.sh 가 레지스트리 설정을 노드마다 넣을 때 쓰는 방식과 같다.

for n in $(kind get nodes --name "$CLUSTER"); do
  for r in kind-registry:5000 localhost:5001; do
    docker exec "$n" mkdir -p "/etc/containerd/certs.d/$r"
    printf '[host."http://kind-registry:5000"]\n  capabilities = ["pull", "resolve"]\n' |
      docker exec -i "$n" cp /dev/stdin "/etc/containerd/certs.d/$r/hosts.toml"
  done
done

왜 이걸 골랐나 (대안)

bridge + iptables 방식은 규칙이 체인 안에서 위에서 아래로 차례로 평가된다. 서비스·정책이 늘면 규칙 수가 늘고, 하나 바꿀 때 표 전체를 다시 쓰는 일이 생긴다. Cilium 의 veth 별 eBPF 는 해시 맵을 한 번 찾아 결정한다. 이 PoC 규모에선 차이를 재지 않았다 (03 README 1.5 【추정】). 고른 이유는 성능보다 Hubble·L7·identity 기반 정책이다 (정리 절 결정 표).

3. CNI 와 파드가 생길 때 일어나는 일 (kind 에서 kindnet 대신 Cilium)

CNI 는 "규격 + 실행 파일" 이다

CNI(Container Network Interface)는 컨테이너 런타임과 네트워크 플러그인 사이의 약속 문서 다. 내용은 단순하다. 런타임(우리는 kind 노드 안의 containerd)이 파드용 network namespace 를 만든 뒤, 노드 디스크의 설정 파일(/etc/cni/net.d/*.conflist)이 가리키는 플러그인 실행 파일(/opt/cni/bin/…)을 환경 변수와 표준 입력(JSON)으로 부른다. 플러그인은 그 netns 에 인터페이스를 만들고 IP 를 주고, 결과를 JSON 으로 돌려준다. 이게 전부다.

그래서 "CNI 를 바꾼다" 는 것은 노드의 /etc/cni/net.d 에 어떤 설정 파일이 있고 그게 어떤 실행 파일을 부르느냐를 바꾸는 일이다. Cilium 은 DaemonSet 파드가 뜨면서 이 두 파일을 노드에 깔아 넣는다.

kind 는 기본으로 자기 CNI 인 kindnet 을 깐다. 03 단계 kind-config.yaml 의 disableDefaultCNI: true 는 "kindnet 을 깔지 마" 라는 뜻이다. 그러면 클러스터가 처음 뜰 때 노드에 CNI 설정이 없어서 노드가 NotReady 로 보인다. 고장이 아니라 "파드 네트워크를 만들 사람이 아직 없다" 는 정상 상태이고, cilium install 이 끝나면 Ready 로 바뀐다 (RUN-ALL.md 의 platform 기대 출력이 이 모습이다).

왜 CNI 를 깔기 전에는 노드가 NotReady 인가

kubelet 은 노드 상태를 보고할 때 컨테이너 런타임의 상태(RuntimeReady, NetworkReady)를 함께 본다. containerd 의 CRI 플러그인은 CNI 설정 디렉터리에 쓸 만한 설정이 없으면 NetworkReady=false(사유 NetworkPluginNotReady, "cni plugin not initialized")를 내고, kubelet 은 노드 조건 Ready 를 False 로 둔다. 이 상태에서는 hostNetwork: true 파드(노드 네트워크를 그대로 쓰는 파드. kube-proxy, cilium 에이전트 자신)만 뜰 수 있고, CoreDNS 같은 일반 파드는 Pending 으로 기다린다. Cilium 에이전트가 hostNetwork 파드이기 때문에 이 닭과 달걀 문제가 풀린다.

플러그인 체이닝과 IPAM 위임

  • 체이닝(chaining): 하나의 conflist 에 플러그인을 여러 개 줄 세운다. 예: 주 플러그인(인터페이스·IP) → portmap(hostPort) → bandwidth(속도 제한). Cilium 은 다른 CNI 위에 정책만 얹는 "chaining 모드" 도 지원한다 (AWS VPC CNI + Cilium 정책 같은 조합).
  • IPAM 위임: 주 플러그인이 IP 배정만 다른 플러그인(host-local, dhcp 등)에 맡길 수 있다. 위임받은 플러그인도 같은 규격으로 실행된다. Cilium 은 IPAM 을 에이전트 안에서 직접 한다 (모드: cluster-pool 기본, kind 에서는 CLI 가 kubernetes 로 바꿈, 클라우드는 eni·azure 등).

4. Service: ClusterIP·NodePort·LoadBalancer, kube-proxy 와 Cilium

Service 는 "움직이는 파드 앞의 고정 주소" 다

파드 IP 는 파드가 다시 뜰 때마다 바뀐다. Knative 함수 파드는 0개와 N개를 오가니 더하다. Service 는 라벨 선택자로 고른 파드 묶음 앞에 바뀌지 않는 가상 IP(ClusterIP)와 DNS 이름 을 붙인다. 가상 IP 는 어떤 장치에도 실제로 붙어 있지 않다. 그 주소로 가는 패킷을 누군가 중간에서 진짜 파드 IP 로 바꿔(DNAT) 줘야 한다. 그 "누군가" 가 각 노드의 kube-proxy(iptables·ipvs·nftables 규칙)이거나, Cilium 같은 CNI 의 eBPF 서비스 처리 다.

ClusterIP (기본)
클러스터 안에서만 닿는 가상 IP. kind 기본 대역 10.96.0.0/16 에서 받는다. 예: iso-echo.tenant-b, kube-dns(10.96.0.10).
NodePort
ClusterIP 에 더해, 모든 노드 의 같은 포트(기본 범위 30000~32767)로 들어온 것을 서비스로 보낸다. 우리 Kourier 입구가 31080.
LoadBalancer
NodePort 에 더해, 클라우드의 외부 로드밸런서를 붙인다 (클라우드 컨트롤러가 만들어 줌). kind 에는 이걸 만들어 줄 사람이 없어서 Kourier 를 NodePort 로 바꿨다.
EndpointSlice
Service 가 고른 파드들의 실제 IP·포트·준비 상태 목록. 컨트롤러가 파드 변화를 보고 갱신하고, kube-proxy 와 Cilium 은 이걸 읽어 규칙을 만든다.

5. DNS: CoreDNS, resolv.conf, ndots, 그리고 default-deny

파드는 이름을 어떻게 IP 로 바꾸나

kubelet 은 파드를 만들 때 파드 안 /etc/resolv.conf 를 써 넣는다. 기본 정책(dnsPolicy: ClusterFirst)에서 내용은 이렇다.

nameserver 10.96.0.10                         # kube-dns Service 의 ClusterIP (kind 기본 대역 기준)
search tenant-a.svc.cluster.local svc.cluster.local cluster.local   # + 노드의 search 목록
options ndots:5

질의는 kube-system 의 CoreDNS 파드(라벨 k8s-app: kube-dns)가 받는다. CoreDNS 는 cluster.local 아래 이름(<서비스>.<ns>.svc.cluster.local)은 쿠버네티스 API 를 보고 직접 답하고, 나머지는 위(노드의 resolv.conf)로 넘긴다. 그래서 같은 namespace 에서는 iso-echo, 다른 namespace 는 iso-echo.tenant-b 만 써도 된다.

여기서 테넌트 격리와 부딪친다. NetworkPolicy 로 나가는 것(egress)을 전부 막으면 DNS 질의(UDP/TCP 53)도 막힌다. 이름으로 부르면 실패하는데 IP 로 부르면 되는, 처음 보는 사람을 가장 헷갈리게 하는 장애가 여기서 나온다. 그래서 우리 차트는 default-deny 와 함께 allow-dns 를 꼭 둔다.

6. eBPF 기초: 커널 안에 안전하게 코드를 꽂는 법

eBPF 는 무엇이고 왜 네트워크가 이걸 쓰나

eBPF 는 리눅스 커널 소스를 고치거나 커널 모듈을 올리지 않고도, 커널 안의 정해진 지점(훅)에 작은 프로그램을 붙여 실행하게 하는 기술이다. 비유하면 커널이라는 서버에 "이벤트 핸들러" 를 등록하는 것과 같다. 패킷이 장치에 도착할 때, 소켓이 연결할 때, 어떤 커널 함수가 불릴 때 그 핸들러가 돈다.

왜 안전한가. 프로그램은 붙기 전에 커널의 검증기(verifier) 를 통과해야 한다. 끝나지 않는 루프, 범위 밖 메모리 접근, 확인 안 한 널 포인터가 있으면 거절된다. 왜 빠른가. 통과한 바이트코드는 JIT 컴파일러가 그 CPU 의 기계어로 바꾼다. 상태는 어떻게 갖나. 커널과 사용자 공간이 같이 읽고 쓰는 맵(map) 이라는 키·값 저장소를 쓴다. Cilium 에이전트(사용자 공간)는 맵에 "이 IP 는 identity 몇", "이 identity 에서 포트 8012 허용" 같은 표를 써 두고, 패킷마다 도는 eBPF 프로그램은 그 표를 찾아보기만 한다.

헬퍼(helper) 는 eBPF 프로그램이 부를 수 있는 커널 함수 목록이다 (bpf_map_lookup_elem, bpf_skb_store_bytes, bpf_redirect, bpf_perf_event_output, bpf_ktime_get_ns 등). 프로그램 종류마다 부를 수 있는 헬퍼가 정해져 있다. 최근에는 헬퍼 대신 kfunc(커널이 내보낸 함수)도 쓴다. tc 프로그램의 반환값은 TC_ACT_OK(계속), TC_ACT_SHOT(버림), TC_ACT_REDIRECT(다른 장치로) 같은 결과 코드다. Cilium 이 정책으로 패킷을 버리는 것은 결국 TC_ACT_SHOT 을 돌려주는 일이다.

  • 경로 시뮬레이션: 검증기는 프로그램을 실제로 돌리지 않고, 가능한 모든 분기를 따라가며 레지스터마다 "무슨 종류의 값(컨텍스트 포인터, 맵 값 포인터 또는 NULL, 스칼라)이고 범위가 얼마인가" 를 추적한다. 패킷 데이터를 읽으려면 먼저 data + 오프셋 <= data_end 비교를 해야 통과한다.
  • 한도: 스택 512바이트, 검증기가 처리하는 명령 수 상한(현재 100만), 루프는 커널 5.3 부터 상한이 증명되는 경우만 허용. 큰 로직은 tail call(다른 프로그램으로 점프, 사슬 최대 33번)과 bpf-to-bpf 함수 호출로 나눈다. Cilium 의 정책 검사가 별도 프로그램으로 tail call 되는 이유다.
  • JIT: x86-64, arm64 등에서 바이트코드를 기계어로 바꾼다. 맥 Docker Desktop(Apple Silicon)의 리눅스 VM 은 arm64 다. JIT 가 꺼져 있으면 인터프리터로 돈다.
  • CO-RE(Compile Once, Run Everywhere): 커널 버전마다 구조체 배치가 달라도, 커널이 내보내는 타입 정보(BTF)를 보고 로더(libbpf)가 필드 오프셋을 적재 때 고쳐 준다. 관측 도구에서 중요하다. Cilium 의 데이터패스는 오랫동안 노드에서 직접 컴파일하는 방식이었고, 최근 버전은 미리 컴파일한 객체에 설정 값을 적재 때 넣는 쪽으로 옮겨 가고 있다 【확인 필요: v1.20 의 정확한 방식】.
  • 고정(pinning): 맵을 /sys/fs/bpf 에 파일처럼 걸어 두면 에이전트가 재시작해도 맵(정책·연결 상태)이 살아 있다. 그래서 cilium-agent 를 재시작해도 이미 맺은 연결과 정책 집행이 끊기지 않는다.

왜 이걸 골랐나 (대안)

iptables 는 수십 년 된 검증된 도구지만 규칙이 순서대로 평가되고, 규칙 하나를 바꿀 때 표를 다시 써야 하는 경우가 많다. eBPF 는 해시 맵 조회로 판단하고 맵 원소만 바꾼다. 대가는 디버깅이 어렵다는 것(iptables-save 처럼 한눈에 안 보임)인데, 그 빈칸을 Hubble 과 cilium-dbg 가 메운다. 본선에서 "eBPF 의 위험은?" 이 나오면: 커널 버전 의존, 검증기 한도, 관측 도구 없이는 블랙박스.

7. Cilium 구조와 데이터패스

Cilium 은 무엇으로 이루어졌나

Cilium 은 eBPF 위에 만든 CNI 다. 파드에 IP 를 주고(3절), 서비스 주소를 바꾸고(4절), NetworkPolicy 를 집행하고(8절), 흐름을 기록한다(10절). 가장 중요한 생각은 하나다. 정책을 IP 가 아니라 "identity(보안 신원)" 로 판단한다. 파드 IP 는 계속 바뀌지만, 같은 라벨을 가진 파드들은 같은 숫자 identity 를 공유한다. 정책 맵에는 IP 가 아니라 이 숫자가 들어간다.

엔드포인트, identity, ipcache, 정책 맵

엔드포인트 (endpoint)
Cilium 이 관리하는 네트워크 단위. 보통 파드 하나 = 엔드포인트 하나. 노드 안에서 숫자 ID 를 갖고, 엔드포인트마다 자기 정책 맵을 갖는다. CiliumEndpoint CRD 로 다른 노드에도 알려진다.
identity
"보안에 의미 있는 라벨" 묶음에 붙는 클러스터 전역 숫자. 파드 라벨 + namespace 이름(io.kubernetes.pod.namespace) + namespace 라벨 + 서비스어카운트 등이 들어가고, pod-template-hash 처럼 매번 바뀌는 라벨은 빠진다. 같은 Deployment 의 파드 10개는 identity 하나를 공유한다.
예약 identity
1 host(이 노드), 2 world(클러스터 밖), 3 unmanaged, 4 health, 5 init(아직 모름), 6 remote-node, 7 kube-apiserver, 8 ingress. 0 은 unknown. 일반 identity 는 그보다 큰 번호.
ipcache
IP(또는 CIDR) → identity (+ 그 IP 가 있는 노드, 터널 끝점) 표. eBPF LPM 맵이다. 다른 노드 파드의 IP 를 보고 identity 를 알아내는 데 쓴다.
정책 맵
엔드포인트마다 하나. 키 = (상대 identity, 포트, 프로토콜, 방향), 값 = 허용 / 거부 / L7 프록시로 보냄. 정책 계산은 에이전트가 미리 해 두고, 데이터패스는 키 하나를 찾기만 한다.

깨지면 이렇게 보인다

증상: 정책을 바꿨는데 몇 초 동안 예전처럼 동작한다. 원인: 에이전트가 새 정책을 계산해 맵에 넣기까지 시간이 걸린다. 공식 문서도 "새 정책이 언제 적용됐는지 API 로는 알 수 없다" 고 한다. 볼 곳: cilium-dbg endpoint list 의 STATUS 가 ready 인지, regenerating 이면 기다린다. 측정 스크립트가 정책 변경 직후 바로 재지 않는 이유다.

왜 이걸 골랐나 (대안)

IP 기반 방화벽(iptables 의 출발 IP 규칙)은 파드가 다시 뜰 때마다 규칙을 고쳐야 한다. Knative 처럼 파드가 0↔N 을 오가면 규칙이 계속 흔들린다. identity 기반은 같은 라벨의 파드가 몇 개든 키 하나로 끝나고, 새 파드는 ipcache 한 줄만 추가된다. 대가는 identity 가 라벨에서 나오므로 라벨을 바꿀 수 있는 사람이 정책을 우회할 수 있다 는 점이다. 그래서 테넌트 RBAC 에서 namespace 라벨 수정 권한을 주지 않는다 (3장 RBAC).

8. NetworkPolicy 의미론과 우리 정책 4장

NetworkPolicy 는 "허용 목록" 이고, 막는 건 CNI 다

NetworkPolicy 는 쿠버네티스 API 에 저장되는 규칙 문서 다. API 서버는 저장만 하고, 집행은 CNI 가 한다. 공식 문서도 "이를 구현하는 컨트롤러 없이 NetworkPolicy 를 만들면 아무 효과가 없다" 고 쓴다. 에러도 안 나서 더 위험하다. 06 단계에서 kindnet 이 커널 문제로 정책을 무시했는데 YAML 은 멀쩡히 들어가 있었던 것이 정확히 그 경우다.

읽는 법은 네 줄이면 된다.

  1. 파드는 기본으로 열려 있다 (격리 안 됨).
  2. 어떤 정책이 그 파드를 podSelector 로 고르고 policyTypes 에 방향(Ingress/Egress)을 적으면, 그 방향은 격리 된다. 이제 허용 목록에 있는 것만 통과한다.
  3. 여러 정책이 같은 파드를 고르면 허용 목록은 합집합 이다. "막는" 규칙은 없고, 정책끼리 충돌하지 않으며, 순서도 상관없다.
  4. 연결 하나가 되려면 보내는 파드의 egress 와 받는 파드의 ingress 가 둘 다 허용해야 한다. 허용된 연결의 답장은 자동으로 허용된다.

정책고르는 파드방향허용한 줄 해설
default-deny-all전부In, Out없음두 방향을 격리 상태로 만든다. 허용 목록이 비었으니 이 정책 혼자서는 "전부 막기"
allow-same-namespace전부In, Out같은 ns 파드from/to: podSelector: {} 에 namespaceSelector 가 없으니 "정책이 있는 namespace 안의 모든 파드"
allow-dns전부Outkube-system 의 kube-dns 파드, 53 UDP/TCP5절. AND 선택자
allow-from-namespaces전부Invalues 에 적은 namespace 의 모든 파드, 모든 포트목록이 비면 {{- if }} 때문에 아예 렌더링되지 않는다. 목록 항목마다 - namespaceSelector 를 따로 만드니 namespace 끼리는 OR

합치면 tenant-a 파드의 최종 허용은 이렇다. 들어오기 = 같은 ns ∪ knative-serving ∪ kourier-system (+ 노드 자신). 나가기 = 같은 ns ∪ CoreDNS:53. 인터넷, API 서버, 다른 테넌트, 169.254.169.254 는 나가기에 없으니 막힌다 (06 s4 의 N3·N4).

재미있는 점 하나. allow-same-namespace 가 이미 같은 파드들을 고르고 두 방향 다 policyTypes 에 적었으므로, 이것만 있어도 두 방향이 격리된다. 즉 default-deny-all 은 의미상 중복 이다. 그래도 두는 이유는 의도를 드러내고, 누군가 allow 정책을 지우거나 고쳐도 "기본 거부" 가 남게 하는 안전띠다. 거꾸로, 공격자 쪽 정책을 "지워서" 실험할 때는 default-deny-all 하나만 지우면 아무것도 바뀌지 않는다는 뜻이기도 하다 (12절).

9. CiliumNetworkPolicy: L7 HTTP 정책과 FQDN 정책

표준 정책이 못 하는 것을 Cilium 전용 정책으로

표준 NetworkPolicy 는 L3/L4(IP, 포트)까지만 본다. "tenant-b 의 함수를 GET 으로만 부르게" 나 "api.github.com 으로만 나가게" 는 쓸 수 없다. Cilium 은 자기 CRD CiliumNetworkPolicy(CNP) 와 클러스터 전체용 CiliumClusterwideNetworkPolicy(CCNP) 로 이걸 더한다.

L7 규칙

toPorts.rules.http 에 메서드·경로·헤더를 적는다. 해당 포트의 트래픽은 Envoy 프록시로 넘어가 HTTP 를 해석한 뒤 판단한다. 안 맞으면 HTTP 403.

FQDN 규칙

toFQDNs 에 도메인 이름을 적는다. Cilium 의 DNS 프록시가 질의 응답을 엿보고 그 이름의 IP 만 열어 준다.

엔티티와 거부 규칙

fromEntities: [world, cluster, host, kube-apiserver] 같은 예약 identity 로 고르기, ingressDeny·egressDeny 로 명시적 거부(거부가 허용보다 우선).

표준 정책과 CNP 는 같은 파드에 함께 걸 수 있고, 허용은 합집합, 거부 규칙은 허용보다 우선한다. 우리 PoC 의 기본은 표준 NetworkPolicy 이고, CNP 는 03 README 9절의 셀프 연습(L7)으로만 다룬다. 레포에는 CNP 파일이 없다.

L7 판단은 어디서 일어나나: Envoy 로 돌려보내기

FQDN 정책의 동작

toFQDNs 는 IP 가 계속 바뀌는 바깥 서비스용이다. 동작 순서: ① 같은 정책에 DNS 규칙(toPorts: 53, rules.dns: matchPattern)을 함께 적어 파드의 DNS 질의가 Cilium DNS 프록시를 거치게 한다. ② 프록시가 응답을 보고 "api.github.com = 이 IP 들" 을 배운다. ③ 그 IP 들에 FQDN 선택자용 identity 를 붙여 ipcache 에 넣고, 정책 맵에 허용으로 넣는다. ④ DNS TTL 이 지나면 지운다. 그래서 파드가 DNS 를 거치지 않고 IP 를 직접 쓰면 열리지 않는다.

10. Hubble: 버려진 패킷을 증거로 보기

Hubble 은 무엇을 보여 주나

NetworkPolicy 가 막은 연결은 보내는 쪽에서 "타임아웃" 으로만 보인다. 왜 막혔는지, 어디서 막혔는지는 알 수 없다. Hubble 은 Cilium 데이터패스가 이미 내는 이벤트(전달, 버림, 정책 판정, L7)를 모아 "흐름(flow)" 기록으로 보여 준다. 한 줄 모양은 이렇다 (03 README 1.6).

tenant-a/iso-client → tenant-b/iso-echo-xxx:5678 ... Policy denied DROPPED (TCP Flags: SYN)

데모에서 "막혔다" 를 타임아웃이 아니라 누가, 누구에게, 무슨 포트로, 무슨 이유로 DROPPED 인지 보여 줄 수 있다. 이것이 kindnet 대신 Cilium 을 고른 첫째 이유다.

(가) kubectl port-forward svc/kourier: 설정은 없지만 API 서버를 거치는 터널이라 측정 숫자가 오염되고 끊기기 쉽다 (05 README 가 안 열릴 때의 대안으로 적어 둠). (나) MetalLB·cloud-provider-kind 로 LoadBalancer 흉내: 더 실제와 닮았지만 부품이 하나 는다. (다) extraPortMappings + NodePort(현재): kind 공식 방법이고 클러스터를 만들 때 한 번 정하면 끝. 8080 은 Argo CD UI 가 써서 8081 을 골랐다.

본선에서 떠올릴 패턴

규칙과 집행을 나눠 본다

NetworkPolicy(규칙) 와 CNI(집행)처럼, 어떤 주제든 "누가 선언하고 누가 실제로 막나" 를 나눈다. RBAC(API 서버), PSA(admission), Quota(API 서버) 도 같은 질문으로 읽힌다. 집행자가 없으면 규칙은 조용히 무용지물이다.

기본 거부 + 좁은 허용 + 합집합

방화벽, IAM, S3 버킷 정책, API 게이트웨이 어디든 "전부 막고 필요한 것만 연다" 로 설계하고, 허용이 더해지는 방식인지 거부가 이기는 방식인지 먼저 확인한다.

IP 대신 신원으로

Cilium identity 처럼, 바뀌는 주소 대신 라벨·서비스어카운트·워크로드 신원으로 정책을 건다. 서비스 메시 mTLS(SPIFFE), AWS 보안 그룹 참조도 같은 생각이다. 대가: 신원을 바꿀 수 있는 권한이 곧 정책 우회 권한.

READY 와 실제 도달은 다르다

컨트롤 플레인의 상태(Ready, Synced)는 데이터 플레인의 도달을 보장하지 않는다. 검증은 항상 끝에서 끝으로(curl, 침범 실험) 하고, 관측(Hubble)으로 증거를 남긴다.

양쪽에 벽

출발지 egress 와 도착지 ingress 를 둘 다 막으면 한쪽 설정이 사라져도 버틴다 (06 깨뜨리기). 다층 방어를 설명할 때 이 그림을 쓴다.

홉별로 주소가 바뀌는 곳을 표로

요청 길을 홉으로 쪼개 "누가 주소를 바꾸나, 어디서 검사하나, 끊기면 어디를 보나" 를 표로 만들면, 처음 보는 아키텍처의 장애 질문에도 같은 틀로 답할 수 있다.
