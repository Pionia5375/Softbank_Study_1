멀티테넌시 모델

멀티테넌시는 무엇이고 왜 필요한가

테넌트(tenant)는 플랫폼을 빌려 쓰는 손님 한 팀이다. 우리 FaaS 로 치면 "함수를 올리는 회사 하나". 멀티테넌시(multi-tenancy)는 여러 테넌트가 클러스터 하나를 같이 쓰는 것이다. 클러스터를 손님마다 따로 주면 안전하지만, 클러스터마다 컨트롤 플레인과 최소 노드 비용이 붙어서 손님 수만큼 비용과 운영 부담이 곱해진다.

같이 쓰면 싸지만 세 가지가 무섭다. ① 엿보기·공격: A 가 B 의 함수를 부르거나 B 의 로그를 읽는다. ② 옆집 소음(noisy neighbor): A 의 무한 루프가 같은 노드의 B 를 느리게 한다. ③ 탈출: A 의 컨테이너가 노드를 장악해 모든 테넌트를 본다. 그래서 울타리를 여러 겹 친다. 한 겹이 뚫려도 다음 겹이 막도록.

쿠버네티스 공식 문서는 두 축으로 나눈다. soft 멀티테넌시는 테넌트끼리 어느 정도 믿는 경우(한 회사 안의 여러 팀)로, 실수와 자원 다툼을 막는 게 목적이다. hard 멀티테넌시는 서로 믿지 않는 경우(서로 다른 고객, 남이 쓴 코드를 돌리는 FaaS)로, 악의적인 공격까지 막아야 한다. 공식 문서는 이 둘을 딱 나뉜 범주가 아니라 연속된 스펙트럼으로 본다.

모델마다 무엇을 공유하고 무엇을 나누나

공식 문서는 격리를 컨트롤 플레인 격리와 데이터 플레인 격리로 나눈다. 컨트롤 플레인 격리는 "누가 어떤 API 오브젝트를 보고 바꿀 수 있나"(RBAC, Quota, namespace), 데이터 플레인 격리는 "실제로 도는 컨테이너가 서로 무엇을 나누나"(네트워크, 노드, 커널, 저장소)다. 모델 ① 은 둘 다 정책으로 쌓고, ② 는 컨트롤 플레인을 진짜로 나누고, ③ 은 둘 다 물리적으로 나눈다.

Capsule

여섯 겹은 무엇이고 각각 무엇을 막나

PoC 는 테넌트마다 쿠버네티스 기본 오브젝트로 여섯 겹을 친다. 핵심은 겹마다 강제하는 주체가 다르다는 점이다. 1·2·3·5겹은 API 서버가 요청을 받을 때(어드미션·인가) 막고, 4겹은 CNI(Cilium)가 패킷이 흐를 때 막고, 6겹은 Argo CD 가 배포를 계획할 때 막는다. 강제 주체가 다르니 한 주체가 뚫리거나 설정이 빠져도 다른 겹은 남는다.

API 요청이 지나는 길

모든 쓰기는 API 서버의 관문 여섯 개를 지난다

kubectl, Argo CD, 우리 컨트롤 플레인 모두 클러스터를 바꿀 때는 kube-apiserver 에 HTTP 요청을 보낸다. API 서버는 요청을 etcd 에 저장하기 전에 정해진 순서로 검사한다. 울타리 여섯 겹 중 네 겹(1·2·3·5)이 이 관문 안에 있다. 그래서 이 그림 하나를 기억하면 "왜 거절됐나" 의 절반을 설명할 수 있다.

파드는 대개 컨트롤러가 만든다: 에러가 kubectl 에 안 보이는 이유

Deployment 를 apply 하면 첫 번째 관문 통과는 Deployment 오브젝트에 대한 것이다. 파드는 그 뒤에 ReplicaSet 컨트롤러가 자기 신분으로 API 서버에 따로 만든다. ResourceQuota 와 PSA enforce 는 파드 생성 요청에서 걸리므로, 거절은 kubectl 이 아니라 ReplicaSet 의 이벤트에 남는다. 이것이 "apply 는 성공했는데 파드가 없다" 의 정체다.

단계별 세부: 인증 결과, 어드미션 플러그인, 웹훅

① 인증 (Authentication)

설정된 인증기를 차례로 시도하고, 하나라도 성공하면 사용자 정보(username, uid, groups, extra)를 얻는다. 모두 실패하면 401. 익명 요청이 허용되면 system:anonymous 가 된다. ServiceAccount 토큰이면 username 은 system:serviceaccount:<ns>:<이름>, groups 에 system:serviceaccounts 와 system:serviceaccounts:<ns> 가 붙는다. kind 의 관리자 kubeconfig 는 클라이언트 인증서이고, 인증서의 O(조직) 필드가 그룹이 된다 【확인 필요: kind 버전별 관리자 그룹 이름 kubeadm:cluster-admins 또는 system:masters】.

② 인가 (Authorization)

설정된 인가기(--authorization-mode, 보통 Node,RBAC)를 차례로 묻는다. 어떤 인가기가 허용하면 즉시 통과, 명시적으로 거부하면 즉시 403, 모두 의견 없음이면 403. RBAC 는 거부 규칙이 없고 "허용 목록의 합집합" 만 있다.

③ 변경 어드미션 → ④ 스키마 검증 → ⑤ 검증 어드미션

어드미션 컨트롤러는 API 서버에 컴파일된 플러그인과, 밖에 있는 웹훅(MutatingAdmissionWebhook, ValidatingAdmissionWebhook)·CEL 정책(ValidatingAdmissionPolicy, MutatingAdmissionPolicy)으로 이뤄진다. 변경 단계는 객체를 고칠 수 있고, 검증 단계는 고치지 못하고 허용·거절만 한다. 한 플러그인이라도 거절하면 요청 전체가 거절된다. 어드미션은 생성·수정·삭제·connect 에만 돌고 읽기(get, list, watch)에는 돌지 않는다. 본문을 객체로 디코드할 때 API 타입의 기본값 규칙(예: limits 만 있으면 requests = limits)이 먼저 적용된다.

Namespace 와 Pod Security (1겹)

방 하나와, 방에서 노드로 나가는 문 잠그기

Namespace 는 이름의 범위다. 같은 namespace 안에서 이름이 겹치면 안 되고, 다른 namespace 와는 겹쳐도 된다. 그 자체로는 아무것도 막지 않지만, Quota·LimitRange·NetworkPolicy·Role 이 전부 namespace 단위로 걸리기 때문에 나머지 다섯 겹의 "적용 단위" 가 된다. Node, Namespace, ClusterRole, PersistentVolume, RuntimeClass 같은 클러스터 범위 리소스는 namespace 에 속하지 않으므로 테넌트에게 줄 수 없다.

Pod Security Admission(PSA) 은 namespace 라벨만으로 켜는 내장 어드미션이다. Pod Security Standards(PSS) 라는 세 단계 기준표 중 하나를 고르고, 위반 시 행동(거절·감사 기록·경고)을 고른다. 컨테이너가 노드로 나가는 통로(privileged, hostPath, hostNetwork 등)를 잠그는 첫 번째 자물쇠다.

모드 셋과 버전 라벨, 평가 흐름

라벨 모양은 pod-security.kubernetes.io/<모드>: <단계> 와 pod-security.kubernetes.io/<모드>-version: <버전> 이다. 모드는 셋이다.

enforce
위반하면 파드 생성을 거절한다. Deployment 같은 워크로드 객체 자체는 거절하지 않는다(그 안의 파드가 나중에 거절된다).
audit
위반하면 감사 로그(audit log) 이벤트에 주석을 단다. 파드와 워크로드 객체 모두 검사한다.
warn
위반하면 응답에 경고(HTTP Warning 헤더)를 붙여 kubectl 화면에 보인다. 파드와 워크로드 객체 모두 검사한다.

버전 라벨은 "어느 쿠버네티스 버전의 기준표로 볼까" 다. latest 는 API 서버 버전의 기준표를 쓰고, v1.33 처럼 고정하면 클러스터를 올려도 기준이 그대로다. 기준표가 버전마다 조금씩 엄격해질 수 있어서 운영에서는 고정이 안전하고, PoC 는 latest 로 단순하게 갔다.

ResourceQuota (2겹)

테넌트 전체가 쓸 수 있는 합계 한도

ResourceQuota 는 namespace 하나에 거는 "합계 상한" 이다. 이 namespace 안 모든 파드의 requests·limits 합계, 파드 개수, 서비스 개수 등이 hard 값을 넘는 생성 요청을 API 서버가 거절한다. 옆집 소음을 "테넌트 단위" 로 막는 장치다. 한 테넌트가 아무리 파드를 늘려도 정해진 몫 이상은 못 가져간다.

중요한 성질 두 개. ① 거절은 생성 시점에만 일어난다. 이미 떠 있는 파드는 hard 를 낮춰도 쫓겨나지 않는다. ② 실제 사용량(top 으로 보는 CPU)이 아니라 선언한 값(requests, limits)을 센다. 그래서 선언이 없는 파드는 셀 수가 없다.

무엇을 셀 수 있고, 어떻게 세나

ResourceQuota 가 셀 수 있는 것은 세 종류다.

  • 컴퓨트 자원: requests.cpu, requests.memory, limits.cpu, limits.memory (cpu, memory 는 requests 와 같은 뜻), hugepages-<크기>, 확장 자원 requests.nvidia.com/gpu 같은 것.
  • 저장소: requests.storage, persistentvolumeclaims, StorageClass 별 <sc>.storageclass.storage.k8s.io/requests.storage.
  • 오브젝트 개수: pods, services, services.loadbalancers, services.nodeports, configmaps, secrets 같은 짧은 이름과, 일반형 count/<리소스>.<그룹> (예: count/deployments.apps, count/services.serving.knative.dev).

LimitRange (3겹)

컨테이너 하나 단위의 기본값과 최대값

LimitRange 는 namespace 안 컨테이너(또는 파드, PVC) 하나하나에 대한 규칙이다. 두 가지 일을 한다. ① resources 를 안 적은 컨테이너에 기본 requests/limits 를 채운다(변경). ② 너무 크거나 작은 값을 거절한다(검증). ResourceQuota 가 합계를 보는 반면 LimitRange 는 한 개를 본다. 그래서 "한 컨테이너가 테넌트 몫을 혼자 다 쓰는 것" 도 막는다.

필드 다섯 개와 채우는 규칙

default
limits 가 없을 때 채울 기본 limits.
defaultRequest
requests 가 없을 때 채울 기본 requests.
max
limits(와 requests)가 넘으면 안 되는 상한. 넘으면 거절.
min
requests(와 limits)가 내려가면 안 되는 하한. 모자라면 거절.
maxLimitRequestRatio
limits ÷ requests 의 최대 배수. 오버커밋 정도를 제한한다.

자원 하나(cpu 또는 memory)마다 경우가 넷이다. 핵심은 "limits 만 적은 경우 requests 는 defaultRequest 가 아니라 limits 와 같아진다" 는 점이다. 이건 LimitRange 이전에 파드 API 자체의 기본값 규칙(requests 가 없고 limits 가 있으면 requests = limits)이 먼저 적용되기 때문이다.

# 기본 limits 를 자동으로 붙여 주는 LimitRange 가 짝으로 꼭 필요하다.
apiVersion: v1
kind: LimitRange
metadata:
  name: tenant-limits
  namespace: {{ .Values.name }}
spec:
  limits:
    - type: Container
      default:
        cpu: {{ .Values.limitRange.default.cpu | quote }}
        memory: {{ .Values.limitRange.default.memory | quote }}
      defaultRequest:
        cpu: {{ .Values.limitRange.defaultRequest.cpu | quote }}
        memory: {{ .Values.limitRange.defaultRequest.memory | quote }}
      max:
        cpu: {{ .Values.limitRange.max.cpu | quote }}
        memory: {{ .Values.limitRange.max.memory | quote }}
  • type: Container: 컨테이너 단위. Pod 타입은 파드 안 컨테이너 합계에 min/max 를 걸고(기본값은 없음), PersistentVolumeClaim 타입은 저장 용량에 건다.

  • values 기본값: default 200m/128Mi, defaultRequest 50m/64Mi, max 1/512Mi. 테넌트 파일에서 덮어쓰지 않아 tenant-a·b 모두 같다.

세부: 순서, 충돌, 기존 파드

  • 어드미션 순서: LimitRanger 는 변경 단계에서 값을 채우고 검증 단계에서 다시 검사한다. ResourceQuota 는 검증 단계의 끝에 있어서, LimitRange 가 채운 값까지 합계에 넣는다. 그래서 iso-hog 처럼 아무것도 안 적은 파드도 quota 에 limits.cpu 200m 으로 계산된다.
  • 생성 시점에만: LimitRange 를 새로 만들거나 바꿔도 이미 떠 있는 파드는 바뀌지 않는다. 새로 만들어지는 파드부터 적용된다.
  • 모순된 설정: 컨테이너가 requests 만 적었는데 그 값이 default(limits)보다 크면, 채운 limits 가 requests 보다 작아져 파드가 거절된다(requests ≤ limits 위반). 예: 이 namespace 에서 requests.cpu 300m 만 적으면 limits 가 200m 으로 채워져 거절된다. 공식 문서가 경고하는 함정이다.
  • 여러 장: 한 namespace 에 LimitRange 가 여러 장이면 어느 기본값이 적용될지 정해져 있지 않다. 한 장만 두는 게 원칙이다.
  • initContainers: 같은 규칙이 initContainer 에도 적용된다. 파드의 실효 requests 는 "일반 컨테이너 합" 과 "가장 큰 initContainer" 중 큰 값이다.

requests, limits, QoS

requests 는 자리 예약, limits 는 천장

requests 는 "최소 이만큼은 보장해 줘" 다. 스케줄러가 노드에 자리가 있는지 계산할 때 쓰고, CPU 가 붐빌 때 몫을 나누는 비율이 된다. limits 는 "이 이상은 못 쓴다" 다. 같은 천장이라도 CPU 와 메모리는 넘으려 할 때 결과가 완전히 다르다.

  • CPU 는 압축 가능(compressible): 넘으려 하면 커널이 그 컨테이너를 잠깐 멈춘다(스로틀링, throttling). 죽지는 않고 느려진다.
  • 메모리는 압축 불가(incompressible): 넘으면 커널 OOM killer 가 프로세스를 죽인다(OOMKilled). 재시작 정책에 따라 다시 뜬다.

QoS 등급 셋과 쫓겨나는 순서

쿠버네티스는 파드의 requests/limits 모양을 보고 QoS 등급을 자동으로 붙인다(status.qosClass). 노드 메모리가 모자라 kubelet 이 파드를 쫓아낼 때(node-pressure eviction)와 커널 OOM killer 가 고를 때 이 등급이 순서를 정한다.

cpu_millicores() {
  local ns="$1" pod="$2" secs="${3:-10}"
  kubectl -n "$ns" exec "$pod" -- sh -c '
    read_us() {
      if [ -f /sys/fs/cgroup/cpu.stat ]; then awk "/^usage_usec/{print \$2}" /sys/fs/cgroup/cpu.stat
      elif [ -f /sys/fs/cgroup/cpuacct/cpuacct.usage ]; then echo $(( $(cat /sys/fs/cgroup/cpuacct/cpuacct.usage) / 1000 ))
      else echo $(( $(cat /sys/fs/cgroup/cpu,cpuacct/cpuacct.usage) / 1000 )); fi
    }
    a=$(read_us); sleep '"$secs"'; b=$(read_us)
    echo $(( (b - a) / '"$secs"' / 1000 ))'
}
  • 컨테이너 안의 /sys/fs/cgroup 는 자기 cgroup 이다. 그래서 metrics-server 없이도 "이 컨테이너가 실제로 쓴 CPU 시간" 을 읽는다.
  • cgroup v2 는 cpu.stat 의 마이크로초, v1 은 cpuacct.usage 의 나노초(÷1000 으로 맞춤).
  • (b−a) 마이크로초 ÷ 초 ÷ 1000 = 초당 밀리초 = 밀리코어.

Burstable 의 oom_score_adj: 대략 1000 − (1000 × 메모리 requests ÷ 노드 메모리 용량) 을 2~999 범위로 자른다. requests 를 작게 적을수록 먼저 죽는다 【확인 필요: 정확한 식은 kubelet 버전별】.

RBAC (5겹)

"누가, 어디서, 무엇을, 어떻게" 의 허용 목록

RBAC(Role-Based Access Control) 는 API 서버의 인가 단계(그림 3-4 의 ②)에서 "이 사용자가 이 namespace 의 이 리소스에 이 동작(verb)을 해도 되나" 를 판단한다. 규칙은 허용만 있다. 아무 규칙에도 걸리지 않으면 거부(403)다. 그래서 "최소 권한(least privilege)" 은 "필요한 것만 하나씩 적는다" 로 자연스럽게 구현된다.

오브젝트는 네 가지다. 권한 목록인 Role(namespace 안)과 ClusterRole(namespace 없음), 그리고 그 목록을 누구에게 줄지 정하는 RoleBinding(namespace 안에서 효력)과 ClusterRoleBinding(클러스터 전체에서 효력).

규칙 한 줄의 구성과 판정

Role 의 rules 한 항목은 apiGroups(core 는 빈 문자열 ""), resources(복수형 소문자, 하위 리소스는 pods/log 처럼 슬래시), verbs, 선택적으로 resourceNames(특정 이름만)로 이뤄진다. 요청은 "사용자·그룹 → 바인딩들 → 규칙들" 을 따라가며 하나라도 맞으면 허용이다.

세부: 집계, 권한 상승 방지, impersonation, 점검 명령

집계(aggregation)

ClusterRole 에 aggregationRule.clusterRoleSelectors 를 두면, 그 라벨을 가진 다른 ClusterRole 들의 규칙을 컨트롤러가 자동으로 합쳐 넣는다. 기본 사용자용 ClusterRole admin, edit, view 가 이 방식이다. 예를 들어 Knative 가 설치되면 rbac.authorization.k8s.io/aggregate-to-edit: "true" 라벨이 붙은 ClusterRole 로 ksvc 권한이 edit 에 더해진다 【확인 필요: Knative 버전별 집계 라벨 제공 여부】. 테넌트에게 기본 edit 를 RoleBinding 으로 주면 편하지만, 집계 때문에 나중에 설치한 CRD 권한까지 따라 들어온다는 점이 최소 권한과 충돌한다. PoC 는 그래서 직접 쓴 Role 을 쓴다.

권한 상승 방지

RBAC API 는 "자기가 가진 것보다 큰 권한을 담은 Role 을 만들거나 바인딩하는 것" 을 막는다. 예외는 대상 Role 에 대해 escalate(Role 생성·수정) 또는 bind(바인딩) verb 를 가진 경우다. 바인딩의 roleRef 는 만든 뒤 바꿀 수 없고, 바꾸려면 지우고 다시 만든다.

impersonation 과 kubectl auth can-i

관리자는 요청 헤더 Impersonate-User, Impersonate-Group 으로 다른 사용자인 척 요청할 수 있다. kubectl 의 --as, --as-group 이 이 헤더를 붙인다. 인가는 먼저 "요청자가 impersonate 권한이 있나" 를 보고, 그다음 "흉내 낸 사용자가 그 동작을 할 수 있나" 를 본다. kubectl auth can-i 는 SelfSubjectAccessReview API 로 실제 동작 없이 yes/no 만 받는다. 흉내 낸 ServiceAccount 는 --as=system:serviceaccount:<ns>:<이름> 이다.

  그렇지 않으면: ClusterRole 모양 + 테넌트 ns 마다 RoleBinding
  확인: kubectl auth can-i --list --as=system:serviceaccount:ns:이름 -n 대상

왜 이걸 골랐나 (대안)

ServiceAccount 와 토큰

프로그램용 신분증

ServiceAccount(SA) 는 사람이 아니라 프로그램의 신분이다. 사람 사용자와 달리 쿠버네티스 안에 객체로 저장되고 namespace 에 속한다. 파드는 spec.serviceAccountName 의 SA 로 API 서버에 말하고, 밖의 프로그램(우리 MCP 서버)도 SA 의 토큰을 받아 쓸 수 있다. RBAC 바인딩의 subjects 에 SA 를 적어 권한을 준다.

토큰은 짧게 살고 대상이 정해진 JWT 다. 쿠버네티스 1.24 부터는 SA 를 만들어도 영구 토큰 Secret 이 자동으로 생기지 않는다. 대신 TokenRequest API 로 필요할 때 유효 시간이 있는 토큰을 받는다.

두 가지 발급 경로: 파드 안 자동 토큰, 밖으로 꺼내는 토큰

파드 안: ServiceAccount 어드미션이 파드에 projected 볼륨을 붙이고, kubelet 이 TokenRequest 로 토큰을 받아 /var/run/secrets/kubernetes.io/serviceaccount/token 에 쓴다. 이 토큰은 그 파드에 묶여(bound) 있어서 파드가 지워지면 무효다. kubelet 은 만료가 다가오면(수명의 80% 경과 또는 24시간 경과) 새 토큰으로 갈아 끼운다. 클라이언트 라이브러리는 파일을 다시 읽어야 한다. 컨트롤 플레인 Deployment 의 serviceAccountName: control-plane 이 이 경로다.

밖으로: kubectl create token <SA> --duration=8h 는 TokenRequest API 를 직접 불러 토큰 문자열을 받는다. 파드에 묶이지 않고, 만료되면 끝이다. 05 의 make-agent-kubeconfig.sh 가 이 경로로 MCP 서버용 kubeconfig 를 만든다.

세부: audience, 최대 수명, 옛 Secret 토큰

  • audience: TokenRequest 에 audiences 를 주면 토큰의 aud 가 그 값이 된다. 다른 서비스(예: Vault)에 보여 줄 토큰을 API 서버용과 분리할 수 있다. API 서버는 자기 audience(--api-audiences, 기본은 발급자)가 없는 토큰을 거절한다. kubectl create token --audience=... 로 지정한다.
  • 수명: kubectl create token 의 기본 수명은 1시간이고, API 서버의 --service-account-max-token-expiration 이 최대값을 자를 수 있다 【확인 필요: kind 기본 설정의 최대값】. 파드 projected 토큰의 expirationSeconds 기본은 3607초이며, 하위 호환을 위해 API 서버가 실제로는 더 길게 발급하고 사용 시 경고를 남기는 설정이 있다 【확인 필요: 확장 만료 동작의 현재 기본값】.
  • 옛 방식: type: kubernetes.io/service-account-token Secret 을 직접 만들면 만료 없는 토큰이 생긴다. 공식 문서는 피하라고 한다. 1.24 이후 자동 생성은 멈췄고, 오래 안 쓴 옛 토큰을 정리하는 기능도 들어왔다.
  • automountServiceAccountToken: false: API 를 부를 일이 없는 파드(함수 파드)는 토큰을 아예 마운트하지 않는 것이 최소 권한이다. PoC 의 ksvc·hello-fn 은 이 설정을 쓰지 않았다(default SA 는 권한이 거의 없어 실해는 적다).

Argo CD AppProject (6겹)

배포 경로에 치는 울타리

Argo CD 는 클러스터 관리자 권한으로 매니페스트를 적용한다. 그래서 테넌트가 Argo CD Application 을 쓸 수 있다면, RBAC 로 막아 둔 일도 Argo CD 를 통해 할 수 있게 된다. AppProject 는 Argo CD 안의 울타리다. Application 마다 하나의 Project 에 속하고, Project 가 "어느 저장소에서, 어느 클러스터·namespace 로, 어떤 종류의 리소스까지" 를 정한다. 위반하면 Argo CD 가 sync 전에 거절한다.

Project 가 검사하는 칸들

sourceRepos
이 Project 의 Application 이 매니페스트를 가져올 수 있는 저장소 URL 목록(와일드카드 가능).
destinations
배포할 수 있는 (클러스터, namespace) 쌍. 여기 없는 곳이면 거절.
clusterResourceWhitelist / Blacklist
Namespace, ClusterRole 같은 클러스터 범위 리소스 중 허용·금지 목록. 화이트리스트가 비어 있으면 하나도 못 만든다.
namespaceResourceWhitelist / Blacklist
namespace 안 리소스 종류(group, kind) 허용·금지.
roles, syncWindows, sourceNamespaces

세부: 블랙리스트의 빈틈과 RBAC 와의 관계

  • 블랙리스트 vs 화이트리스트: 블랙리스트는 새 리소스 종류(예: 새 CRD)가 생기면 자동으로 허용된다. 화이트리스트(namespaceResourceWhitelist)는 반대로 안전하지만 테넌트가 쓸 종류를 미리 다 알아야 한다. hard 멀티테넌시라면 화이트리스트가 맞다.
  • 빠진 것: PodDisruptionBudget, ServiceAccount, Secret, Knative Service, ResourceQuota 와 겹치는 count/... 우회는 없다. ServiceAccount 를 만들 수 있지만 Role·RoleBinding 을 못 만드니 권한은 생기지 않는다. 다만 PDB 는 노드 drain 을 막는 데 쓰일 수 있다(08장 B12 참고) 【확인 필요: 테넌트 PDB 를 막을지 정책 결정】.
  • Argo CD 는 RBAC 를 대신하지 않는다: AppProject 는 Argo CD 를 거친 배포만 막는다. 테넌트가 kubectl 로 직접 API 서버에 오면 5겹 RBAC 가 막는다. 두 경로를 둘 다 막아야 한다.
  • default Project: 아무것도 제한하지 않는다. 테넌트가 default Project 의 Application 을 만들 수 있으면 6겹이 통째로 사라진다. 그래서 Application 객체를 만드는 권한(argocd ns 의 RBAC, Argo CD 자체 RBAC)을 테넌트에게 주지 않는다.

ApplicationSet 은 Application 을 찍어 내는 틀이다. generator(목록)가 항목을 만들고, 항목마다 template 에 값을 끼워 Application 을 하나씩 만든다. PoC 는 Git files generator 를 쓴다. Git 의 poc/03-tenant-isolation/tenants/*.yaml 에 맞는 파일 하나가 항목 하나이고, 파일 안의 키(name)가 템플릿 변수가 된다. 같은 파일이 차트 values 로도 쓰이므로 "파일 한 장 = 테넌트 정의 전부" 다.

      name: '{{ .name }}'

        - resources-finalizer.argocd.argoproj.io

      project: default
      source:
        repoURL: https://github.com/Pionia5375/Softbank_Study_1
        targetRevision: main
        path: poc/03-tenant-isolation/charts/tenant
        helm:

            - '../../tenants/{{ .path.filename }}'

        server: https://kubernetes.default.svc
        namespace: '{{ .name }}'
      syncPolicy:

          selfHeal: true

  • valueFiles: '../../tenants/...': 차트 폴더 기준 상대 경로. 같은 저장소 안이면 차트 밖 파일도 values 로 쓸 수 있다.
  • finalizers: resources-finalizer.argocd.argoproj.io: Application 이 지워질 때 그것이 만든 리소스도 지운다(cascade). 이게 오프보딩의 핵심이다.
  • applicationsSync: sync: ApplicationSet 이 Application 생성·수정·삭제 모두 한다. 다른 값은 create-only, create-update(삭제 안 함), create-delete(수정 안 함).

세부: 파일을 지우면 무슨 일이 일어나나

파일 삭제는 테넌트 삭제다. 순서대로 따라가면 이렇다.

  1. ApplicationSet 컨트롤러가 다음 조정 때 generator 결과에서 tenant-c 가 빠진 것을 본다. applicationsSync: sync 이므로 Application tenant-c 를 삭제한다.
  2. Application 에 finalizer 가 있으므로 Argo CD 가 Application 이 관리하던 리소스(Namespace 포함 11장 또는 10장)를 먼저 지운다.
  3. Namespace 가 지워지면 Terminating 상태가 되고, namespace 컨트롤러가 그 안의 모든 객체를 지운다. 테넌트 함수(05 가 API 로 만든 ksvc, Knative Revision), Secret, 다른 Application 이 넣은 객체까지 전부다. 이 동안 NamespaceLifecycle 어드미션이 새 객체 생성을 거절한다.
  4. AppProject tenant-c 는 argocd namespace 에 있으므로 2번 단계의 리소스 삭제로 따로 지워진다. 남아 있는 Application 이 그 Project 를 쓰고 있으면 Argo CD 는 사용 중인 Project 삭제를 막는다 【확인 필요: AppProject 의 finalizer 동작】.

파드가 API 서버에 저장되면 spec.nodeName 이 비어 있다. kube-scheduler 는 이런 파드를 감시하다가 하나씩 꺼내 ① 갈 수 없는 노드를 거르고(Filter) ② 남은 노드에 점수(Score)를 매겨 ③ 가장 높은 노드에 묶는다(Bind). 묶는다는 것은 API 서버에 "이 파드의 nodeName = 그 노드" 를 기록하는 것이고, 그 노드의 kubelet 이 이를 보고 컨테이너를 띄운다. 거를 때 쓰는 조건이 이 장 뒤쪽의 nodeSelector, affinity, taint, 자원 여유다.

끌어당기는 도구와 밀어내는 도구

노드 배치 도구는 방향이 둘이다. 끌어당기기: 파드가 "나는 이런 노드에만 가겠다" 고 말한다(nodeSelector, node affinity). 밀어내기: 노드가 "허가증 없는 파드는 오지 마라" 고 말한다(taint). 허가증이 toleration 이다. 둘은 독립적이다. toleration 이 있다고 그 노드로 가는 것이 아니고, nodeSelector 가 있다고 taint 를 통과하는 것이 아니다. 그래서 "build 노드에는 빌드만, 빌드는 build 노드에서만" 을 만들려면 taint + toleration + nodeSelector 셋을 다 쓴다(04 README 1.2절).

네 도구의 동작

라벨 (label)
노드에 붙는 key=value 이름표. 그 자체로는 아무것도 막지 않는다. kind 설정의 labels: {pool: exec} 로 붙인다. 쿠버네티스가 자동으로 붙이는 라벨(kubernetes.io/hostname, kubernetes.io/os, node-role.kubernetes.io/control-plane 등)도 있다.
nodeSelector
파드 스펙의 라벨 맵. 모든 키=값이 일치하는 노드만 후보(AND).
node affinity
nodeSelector 의 확장. requiredDuringSchedulingIgnoredDuringExecution(필수, Filter)과 preferredDuringSchedulingIgnoredDuringExecution(가중치, Score). 연산자 In, NotIn, Exists, DoesNotExist, Gt, Lt. nodeSelectorTerms 사이는 OR, 한 term 안의 matchExpressions 는 AND. "IgnoredDuringExecution" 은 파드가 뜬 뒤 라벨이 바뀌어도 쫓아내지 않는다는 뜻이다.
taint / toleration
노드의 key=value:effect. 파드의 toleration 이 key·value·effect 와 맞으면(operator Equal) 또는 key 만 맞으면(operator Exists) 견딘다. effect 셋: NoSchedule(새 파드 금지, 있는 파드는 그대로), PreferNoSchedule(가능하면 피함, Score 감점), NoExecute(새 파드 금지 + 이미 있는 파드도 쫓아냄, tolerationSeconds 동안은 머무를 수 있음).

poc/04-faas-runtime/platform/runtimeclass-gvisor.yaml발췌
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: gvisor
handler: runsc
# runsc 는 exec 풀에만 깔려 있으니, 다른 노드로 가면 "no runtime for runsc" 로 실패한다 → 여기서 막는다
scheduling:
  nodeSelector:
    pool: exec
  tolerations:
    - key: pool
      operator: Equal
      value: exec
      effect: NoSchedule
overhead:
  podFixed:
    cpu: 50m
    memory: 64Mi

RuntimeClass 어드미션이 runtimeClassName: gvisor 인 파드에 이 nodeSelector 를 합치고(파드의 nodeSelector 와 충돌하면 거절) toleration 을 더한다. 그래서 "런타임이 설치된 노드" 라는 사실을 런타임 정의 한 곳에 두고, 파드 작성자는 런타임 이름만 고르면 된다.

세부: toleration 일치 규칙과 NoExecute

  • 일치 규칙: operator: Equal 은 key, value, effect 가 모두 같아야 한다(toleration 의 effect 를 비우면 모든 effect 와 일치). operator: Exists 는 value 를 적지 않는다. key 도 비우고 Exists 면 모든 taint 를 견딘다. Cilium 같은 DaemonSet 이 이렇게 해서 모든 노드에 뜬다.
  • 여러 taint: 노드의 taint 중 파드가 견디지 못하는 것이 하나라도 NoSchedule 이면 못 간다. 견디지 못하는 PreferNoSchedule 만 남으면 갈 수는 있되 감점이다.
  • NoExecute 와 tolerationSeconds: 노드에 NoExecute taint 가 새로 붙으면, 견디지 못하는 파드는 바로 쫓겨나고, 견디되 tolerationSeconds 가 있는 파드는 그 시간 뒤에 쫓겨난다. 노드 컨트롤러가 붙이는 node.kubernetes.io/not-ready, node.kubernetes.io/unreachable 가 NoExecute 이며, DefaultTolerationSeconds 어드미션이 모든 파드에 300초 toleration 을 기본으로 붙인다. 06 단계의 "tolerationSeconds 20" 이 이 값을 줄여 노드 장애 시 파드를 더 빨리 옮기는 설정이다(08장).
  • DaemonSet: DaemonSet 컨트롤러는 not-ready, unreachable, disk-pressure 등에 대한 toleration 을 자동으로 추가한다. 사용자 taint(pool=build)는 자동으로 견디지 않으므로, 모든 노드에 떠야 하는 에이전트는 Exists toleration 이 필요하다.
  • kind 에서 확인: kubectl describe nodes | grep -E "^Name:|^Taints:", kubectl get nodes -L pool (04 README 1단계).

노드 풀 설계

system / build / exec: 무엇이 어디에, 왜

노드 풀(node pool) 은 같은 라벨·taint·기계 종류를 가진 노드 묶음이다. PoC 는 용도별로 셋을 둔다. 플랫폼 부품은 system, 이미지 빌드는 build, 사용자 함수는 exec. 나누는 이유는 셋이다. ① 빌드의 CPU·디스크 폭주가 함수와 플랫폼을 흔들지 않게(옆집 소음을 풀 단위로). ② 남의 코드(함수)가 도는 노드를 따로 두어, 탈출해도 플랫폼 비밀(Argo CD, 컨트롤 플레인 토큰)이 그 노드에 없게. ③ 클라우드에서 풀마다 기계 종류와 구매 방식(스팟/온디맨드)을 다르게.

"기본 착지점" 을 어디로 둘 것인가: 로컬과 EC2 가 다른 이유

taint 를 어느 풀에 걸지 결정하는 질문은 "toleration 을 아무것도 적지 않은 파드가 어디로 가야 하나" 다. taint 가 없는 풀이 기본 착지점이 된다.

07 의 근거는 이렇다(07 README 결정 3, 10절). 실행 풀에도 taint 를 걸면 모든 함수와 앞 단계 앱에 toleration 을 달아야 하고 하나만 빠져도 그 앱은 갈 곳이 없다. 반대로 taint 없이 라벨만 두면 아무 파드나 시스템·빌드 노드에 떠서 Argo CD·빌드와 메모리를 다툰다. 그래서 EC2 에서는 함수(가장 많고 자주 바뀌는 것)를 기본 착지점에 두고, 수가 적고 한 번 설치하는 시스템 부품에 명시적으로 toleration 을 준다. k3s 의 CriticalAddonsOnly 는 k3s 기본 부품(CoreDNS 등)이 이미 견디는 키라서 고를 수 있었다. 4단계 ksvc 의 exec toleration 은 taint 가 없는 노드에서는 그냥 무시되므로 EC2 에 그대로 가져가도 된다.

# 결과 한 줄 기록: record <이름> <기대> <실제> <걸린 ms>
record() {
  local name="$1" expected="$2" actual="$3" ms="$4" ok
  if [ "$expected" = "$actual" ]; then ok=PASS; PASS=$((PASS+1)); else ok=FAIL; FAIL=$((FAIL+1)); fi
  printf '  %-4s  %-48s 기대=%-8s 실제=%-8s %6sms\n' "$ok" "$name" "$expected" "$actual" "$ms"
  echo "$name,$expected,$actual,$ok,$ms" >> "$CSV"
}

# 3초 안에 응답이 없으면 BLOCKED (NetworkPolicy 는 거절이 아니라 "버림"이라 타임아웃으로 보인다)
probe() {
  local from_ns="$1" url="$2"
  if kubectl -n "$from_ns" exec iso-client -- curl -s -o /dev/null --max-time 3 "$url" >/dev/null 2>&1; then
    echo OK
  else
    echo BLOCKED
  fi
}
  • record 는 문자열 비교 하나로 PASS 를 정한다. 실험마다 "실제값" 을 OK/BLOCKED, REJECTED/ACCEPTED, CAPPED/UNCAPPED, THROTTLED/FREE, yes/no, DENIED/ALLOWED 같은 두 값 중 하나로 정규화하는 것이 설계의 핵심이다.
  • probe 는 curl 의 종료 코드만 본다. 이름 해석 실패(DNS 차단)도 BLOCKED 로 나오므로, BLOCKED 의 원인이 DNS 인지 정책인지는 Hubble 로 따로 본다(04장, README 7절의 DNS 깨뜨리기).
  • fn-demo(울타리 없는 namespace)에서 b 를 부르는 항목은 "보내는 쪽에 정책이 없어도 받는 쪽 default-deny 가 막는다" 를 확인한다.

  • Deployment 의 파드 거절이 kubectl 이 아니라 ReplicaSet 이벤트에 남는 이유를 설명할 수 있다.
  • PSS 세 단계와 PSA 세 모드, 버전 라벨, enforce 가 워크로드 객체가 아니라 파드에만 작동한다는 점을 안다.
  • ResourceQuota 가 선언값(requests/limits)을 세고, 컴퓨트 quota 가 있으면 선언 없는 파드를 거절하는 이유와 LimitRange 가 짝인 이유를 안다.
  • LimitRange 의 default, defaultRequest, max, min, maxLimitRequestRatio 와 "limits 만 적으면 requests = limits" 규칙을 안다.
  • CPU limit 은 CFS 스로틀링, 메모리 limit 은 OOM kill 이며, QoS 세 등급의 판정 규칙을 안다.
  • Role, ClusterRole, RoleBinding, ClusterRoleBinding 의 조합과 "ClusterRole 모양 + 테넌트별 RoleBinding" 패턴, 하위 리소스 pods/log, impersonation 으로 권한을 시험하는 법을 안다.
  • ServiceAccount 토큰이 TokenRequest 로 발급되는 짧게 사는 JWT 이고 audience·만료·바운드 객체로 검증된다는 것을 안다.
  • AppProject 의 sourceRepos, destinations, clusterResourceWhitelist, namespaceResourceBlacklist 와, 울타리·함수를 다른 Project 로 나눈 이유를 안다.
  • ApplicationSet Git files generator 로 파일 하나가 테넌트 하나가 되고, 파일 삭제가 finalizer 를 거쳐 namespace 삭제까지 이어진다는 것을 안다.
  • 스케줄러의 Filter → Score → Bind 와, nodeSelector·affinity(끌어당김)와 taint·toleration(밀어냄)의 역할 분담, RuntimeClass scheduling 을 안다.
  • kind 에서 kubeadmConfigPatches 로 taint 를 거는 법과, 로컬과 EC2 에서 기본 착지점이 다른 이유를 안다.

본선에서 떠올릴 패턴

강제 주체를 섞은 다층 방어

한 정책 엔진에 다 몰지 말고 "요청 시점(API)", "실행 시점(커널·네트워크)", "배포 시점(GitOps)" 처럼 다른 주체에 겹을 나눈다. 데이터 플랫폼이면 "쿼리 권한 / 행 수준 필터 / 네트워크 / 배포 파이프라인" 으로 옮긴다.

모양은 한 번, 문은 테넌트마다

ClusterRole 로 권한 모양을 정의하고 RoleBinding 으로 쓸 곳을 연다. IAM 이라면 "정책 문서 하나 + 리소스 태그별 조건", DB 라면 "역할 하나 + 스키마별 GRANT".

기본값이 있어야 한도가 산다

합계 한도(Quota)는 개별 기본값(LimitRange) 없이는 선언 없는 요청을 셀 수 없다. API 레이트 리밋이라면 "테넌트 합계 한도 + 요청별 기본 비용" 짝으로.

파일 하나 = 테넌트 하나

Git 의 파일 목록을 생성기로 쓰면 온보딩이 PR 하나, 감사가 git log 가 된다. 삭제가 연쇄 삭제라는 점을 같이 설계한다(보호 장치 또는 수동 승인).

기본 착지점을 먼저 정한다

"아무 설정도 안 한 것이 어디로 가나" 를 가장 흔한 워크로드 쪽으로 둔다. 큐 라우팅, 기본 리전, 기본 스토리지 클래스 같은 주제에서도 같은 질문이다.

증상 위치와 원인 위치를 분리해서 본다

apply 성공, Synced, READY 는 "그 단계까지" 의 성공이다. 장애 답변은 "어디에 증거가 남나" 부터 말한다.
