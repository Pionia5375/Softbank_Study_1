장애 주입과 관측

노드를 일부러 죽이고, 옆 테넌트를 폭주시키고, 나쁜 버전을 내보내고, 남의 방을 두드려 본 뒤 "언제 알았고, 무엇이 막았고, 언제 돌아왔나" 를 같은 시계로 설명할 수 있게 된다. 쿠버네티스가 죽은 노드를 알아채는 내부 순서(노드가 "살아 있다" 고 보내는 하트비트 → 노드 상태 조건 → 노드에 붙는 표시(taint) → 파드 내보내기(축출))와, 그 시간을 줄이는 설정 세 가지(파드가 죽은 노드에 머무는 시간 tolerationSeconds, 파드를 노드마다 흩어 놓기, 한 번에 빼도 되는 파드 수의 약속 PDB)를 공식 문서 수준으로 이해한다.

이 장의 지도

01~05 단계(가이드 1~7장)는 플랫폼을 세웠다. 이 장은 그것을 부순다. 일부러, 통제된 방식으로 고장을 넣고 시스템의 반응을 재는 일을 장애 주입(fault injection)이라 한다. 진짜 클러스터 faas 를 직접 치지 않고, 같은 모양(워커 풀 system/build/exec, 풀 = 같은 역할을 맡은 노드 묶음)을 작게 흉내 낸 대역 클러스터 chaos 위에서 장애 네 가지를 넣는다. 결과로 남는 것은 측정 CSV(쉼표로 나눈 표 파일), 방어 설정 파일, 런북(runbook, 알림을 받은 사람이 그대로 따라 할 절차서) 네 개다. 같은 시나리오는 07 단계(가이드 9장)의 EC2(AWS 의 가상 서버) 위에서 AWS FIS(Fault Injection Service, AWS 가 제공하는 장애 주입 서비스)로 "진짜 스팟 회수"(스팟 = 싸게 빌리되 AWS 가 2분 예고 뒤 회수할 수 있는 EC2)로 다시 돌릴 수 있게 설계되어 있다.

읽기 전에, 이 장 전체에서 계속 나오는 쿠버네티스 기초 낱말을 한 줄씩 적어 둔다. 1~7장을 읽었다면 건너뛰어도 된다. 그 밖의 용어는 처음 나오는 자리에서 바로 설명한다.

클러스터 / 노드
쿠버네티스가 관리하는 서버 묶음이 클러스터(cluster), 그 서버 한 대가 노드(node)다. kind 는 쿠버네티스를 도커 컨테이너 안에 띄우는 도구라서, kind 클러스터에서는 노드 하나 = 맥 위의 도커 컨테이너 하나다. 그래서 이 장은 "노드 전원 차단" 을 docker pause 로 흉내 낼 수 있다.
컨트롤 플레인
클러스터를 지휘하는 부품 묶음(control plane). API 서버(모든 명령과 상태가 지나가는 창구), etcd(그 상태를 저장하는 키-값 데이터베이스), 스케줄러(kube-scheduler, 새 파드를 어느 노드에 놓을지 고르는 것), kube-controller-manager(아래의 컨트롤러들을 한 프로세스에 모아 돌리는 것)로 이루어진다. 7장의 "컨트롤 플레인(함수 배포 API 를 가진 Spring 서비스)" 과는 다른 말이라, 이 장에서는 쿠버네티스 쪽을 뜻한다.
kubelet
노드마다 하나씩 도는 에이전트. API 서버에서 "이 파드를 띄워라" 를 받아 컨테이너 런타임에 시키고, 노드와 파드의 상태를 API 서버에 보고한다. 노드가 얼면 kubelet 도 같이 언다는 점이 이 장의 출발점이다.
파드 (Pod)
쿠버네티스가 컨테이너를 돌리는 최소 단위. 컨테이너 한두 개가 IP 하나를 같이 쓴다. 이 장의 "함수 파드", "프로브 파드", "공격자 파드" 가 전부 파드다.
Deployment / ReplicaSet
"이 파드 템플릿을 N개 유지하라" 는 선언이 Deployment, 그 아래에서 실제 개수를 세고 모자라면 만드는 것이 ReplicaSet 이다. 파드 템플릿을 고치면 새 ReplicaSet(새 리비전)이 생기고, 각 ReplicaSet 의 파드에는 pod-template-hash 라는 구분용 라벨이 붙는다.
Service / EndpointSlice
파드 묶음에 고정 이름(DNS)과 IP 를 주고 요청을 나눠 주는 것이 Service, 그 뒤에서 "지금 요청을 받을 수 있는 파드 주소 목록" 을 담는 리소스가 EndpointSlice 다. 노드마다 있는 kube-proxy(또는 Cilium)가 이 목록대로 요청을 보낸다. 파드가 Ready 가 아니면 목록에서 빠진다.
컨트롤러 (controller)
"원하는 상태" 와 "실제 상태" 를 끊임없이 비교해 맞추는 프로그램. ReplicaSet 컨트롤러, EndpointSlice 컨트롤러, node lifecycle controller 가 이 장의 주인공이다.
namespace / 테넌트
리소스 이름과 권한을 나누는 칸이 namespace. 이 PoC 는 namespace 하나 = 고객(테넌트) 하나로 쓴다(tenant-a 가 피해자, tenant-b 가 나쁜 이웃).
kubectl / 컨텍스트
API 서버에 명령을 보내는 CLI 가 kubectl. 어느 클러스터에 보낼지는 컨텍스트(context) 설정이 정한다(kind-faas, kind-chaos). 엉뚱한 클러스터를 부수지 않으려면 컨텍스트부터 본다.

1. 카오스 엔지니어링: 일부러 부숴서 배운다

무엇이고 왜 하나

카오스 엔지니어링(Chaos Engineering)은 운영 중인 시스템에 일부러, 통제된 방식으로 고장을 넣고 시스템이 어떻게 버티는지 관찰하는 실험 방법이다. 넷플릭스가 서버를 무작위로 끄는 Chaos Monkey 로 알려졌다. 핵심은 "고장 내기" 가 아니라 "가설을 검증하는 실험" 이라는 점이다. "노드 하나가 죽어도 괜찮다" 는 누구나 말할 수 있다. "죽여 봤더니 이 구간에서 요청 일부가 실패했고, 그래서 이 설정을 넣었다" 는 직접 해 본 사람만 말할 수 있다. 본선 심사에서 요구하는 "대안과 버린 이유 + 측정 근거" 가 바로 이 형식이다.

Principles of Chaos Engineering 은 이것을 "운영 환경의 난류 같은 조건을 시스템이 견딜 수 있다는 확신을 쌓기 위해, 시스템에 실험을 수행하는 분야" 로 정의하고, 실험을 네 단계로 적는다. (1) 시스템이 정상일 때 밖으로 내는 결과(처리량, 에러율, 지연)를 "평소 상태(steady state)" 로 정의한다. (2) 대조군과 실험군 모두에서 평소 상태가 유지된다는 가설을 세운다. (3) 서버 정지, 디스크 고장, 트래픽 급증 같은 실제 사건을 변수로 넣는다. (4) 대조군과 실험군의 평소 상태 차이를 찾아 가설을 반증하려 한다. 06 단계에서는 주입 전 BASELINE 구간(장애가 없는 같은 시스템)이 대조군, 주입 후 구간이 실험군이며, 평소 상태는 합성 프로브(진짜 사용자 대신 정해진 주기로 함수를 부르는 작은 파드, 11절)의 성공률과 p95 지연(요청 100개 중 느린 5개를 뺀 나머지의 최대 지연, 즉 "95% 의 요청이 이 시간 안에 끝났다")이다. 아래 다섯 단계 그림은 이 네 단계에 "고치고 다시 잰다" 를 더한 것이다.

원칙 다섯 개와 우리 PoC 의 대응

Principles of Chaos Engineering 은 실험을 이렇게 설계하라고 한다. 이 다섯 원칙이 06 단계의 구조를 거의 그대로 정한다.

원칙뜻06 단계에서
평소 상태 행동에 대한 가설 (Build a Hypothesis around Steady State Behavior)내부 지표(CPU 등)가 아니라 시스템이 밖으로 내는 결과(처리량, 에러율, 지연)로 "정상" 을 정의한다합성 프로브의 성공률과 p95 가 평소 상태다. 모든 시나리오가 주입 전 일정 시간(BASELINE) 동안 평소 상태를 먼저 잰다

실험 한 번의 구조 (모든 s*.sh 공통)

네 스크립트는 생김새가 다르지만 뼈대가 같다. 이 뼈대를 알면 새 시나리오(예: 네트워크 지연)를 같은 모양으로 추가할 수 있다.

반복 회수만큼:
  대상 확인        // 피해자 파드가 Ready 인가, 지난 회차 잔여물이 없나
  probe.sh start   // 사용자 시점 기록 시작
  sleep BASELINE   // 평소 상태 (가설의 기준선)
  T0 = now()       // 이 순간이 모든 시간의 0
  고장 주입        // docker pause / 폭주 Deployment / 나쁜 args / 공격 파드
  반복 1초마다:
    쿠버네티스 상태 확인  → 처음 바뀐 시각을 T0 기준으로 기록
    알림 firing 확인      → 처음 firing 된 시각을 기록 (Prometheus 없으면 n/a)
    전부 기록됐거나 TIMEOUT 이면 탈출
  잠깐 더 관찰     // 복구 직후 흔들림까지 로그에 남긴다
  probe.sh stop    // 로그 회수
  원상 복구        // unpause·uncordon / 폭주 삭제 / 좋은 버전
  analyze.py --t0 T0 --extra "시나리오별 열"   // CSV 한 줄

세 가지 설계가 눈에 띈다. (1) T0 를 스크립트가 직접 찍는다: 모든 감지 시각이 같은 원점에서 측정되므로 서로 비교할 수 있다. (2) 관찰은 폴링(polling, 1초마다 물어보기): API 서버의 변경 알림을 구독(watch)하는 것보다 단순하지만 측정 해상도가 1초다. (3) 원상 복구가 실험의 일부: 영향 범위 최소화 원칙을 코드로 강제한다. 중간에 Ctrl+C 로 끊으면 이 단계가 빠지므로 README 4.1 이 손으로 되살리는 명령을 따로 적어 둔다.

2. 시간을 재는 말: t0, 감지, 완화, 복구

장애 하나를 시간축 위에 놓기

장애를 숫자로 말하려면 "언제부터 언제까지" 의 기준점이 먼저 있어야 한다. 06 단계는 다섯 개의 순간을 쓴다.

t0
고장을 넣은 순간. 스크립트가 T0=$(now) 로 찍는다. 모든 시간 열의 원점.
감지 (detect)
시스템이나 사람이 "고장났다" 를 안 순간. 무엇이 알았느냐에 따라 여러 개다(노드 NotReady, 알림 firing(Prometheus 규칙이 "울림" 상태가 된 것, 10절), 카나리 분석 Failed(새 버전을 자동 검사하는 Argo Rollouts 분석이 불합격을 낸 것, 8절)).
완화 (mitigate)
사용자 피해가 멈추기 시작한 순간. 예: 죽은 파드가 Service 에서 빠짐, Rollout abort(카나리 배포를 거두고 옛 버전만 남기는 것).
복구 (recover)
평소 상태로 완전히 돌아온 순간. 예: 원하는 수의 파드가 다른 노드에서 Ready, 나쁜 파드 0개.
MTTD / MTTR
Mean Time To Detect(평균 감지 시간) / Mean Time To Recover(평균 복구 시간, Repair 라고도 쓴다). t0 → 감지, t0 → 복구의 평균. "평균" 이므로 여러 번(README 기준 3회 이상) 재야 한다.

Google 의 SRE(Site Reliability Engineering, 운영을 소프트웨어 공학으로 다루는 직군) 책의 모니터링 장은 증상(symptom) 과 원인(cause) 을 나누라고 한다. "사용자가 에러를 본다" 는 증상이고 "노드가 NotReady" 는 원인이다. 위 표에서 프로브가 재는 열(errors, outage_s)은 증상이고, 쿠버네티스 상태 열(t_notready_s)은 원인 쪽 신호다. 둘을 같은 시계로 재야 "원인을 알아챈 시각" 과 "사용자가 아팠던 시간" 의 차이가 보인다.

같은 장은 서비스 하나를 볼 때 꼭 재야 할 네 가지 황금 신호(four golden signals) 를 든다: 지연(latency, 요청이 걸린 시간), 트래픽(traffic, 초당 요청 수), 에러(errors, 실패한 요청의 비율), 포화(saturation, 자원이 얼마나 꽉 찼나). 프로브 로그의 "걸린초" 와 "응답코드" 가 지연과 에러이고, 프로브의 요청률이 트래픽, 쿼터 사용률과 CPU throttling(7절)이 포화다. 네 신호는 모두 증상 쪽이라 "사용자가 아픈가" 를 원인보다 먼저 알려 준다. 06 의 CSV 열이 이 네 신호 중 지연·에러를 중심으로 짜인 이유다.

평균의 함정과 측정 해상도

  • 폴링 해상도: 상태 확인 루프가 1초 간격이므로 t_*_s 는 실제보다 최대 약 1초(+ kubectl 호출 시간) 늦게 찍힌다. 프로브 간격은 0.1초 + curl 시간이라 사용자 시점 열이 더 촘촘하다.
  • 노드 시계 vs 맥 시계: 프로브 로그의 시각은 kubectl logs --timestamps 가 붙인 노드(컨테이너 런타임) 시각이고, T0 는 맥의 perl 시각이다. kind 는 같은 기계라 차이가 무시할 만하지만, EC2(07)에서는 노드마다 시계가 따로 있어 NTP(Network Time Protocol, 네트워크로 시계를 맞추는 프로토콜) 동기화가 전제가 된다. 07 README 와 Terraform 에는 시계 동기 절차가 따로 없다 【확인 필요: 07 의 Ubuntu 24.04 AMI 에서 chronyc tracking 또는 timedatectl 로 Amazon Time Sync Service(169.254.169.123) 동기 여부를 보면 확정된다】.
  • MTTR 의 정의를 고정: "파드 수 복구" 와 "사용자 에러 끝" 은 다른 값이다. 결정 표에 숫자를 옮길 때 어느 열인지 반드시 적는다. 5절에서 보듯 한 설정이 한쪽만 줄인다.
  • 평균보다 범위: 회수가 적을 때는 평균보다 최소~최대 범위가 정직하다. README 8절 표도 범위를 같이 적는다.

4. 노드 장애의 내부: 쿠버네티스는 죽은 노드를 어떻게 아나

한 문단 요약

3절에서 "쿠버네티스 상태" 층이 가장 늦게 안다고 했다. 왜 늦는지는 이 층의 내부 순서를 알아야 보인다. 노드의 kubelet 은 주기적으로 "살아 있다" 는 표시(하트비트, heartbeat)를 API 서버에 남긴다. kube-controller-manager 안의 node lifecycle controller(노드 생명주기 컨트롤러)가 이 표시가 일정 시간(--node-monitor-grace-period, 기본 50초) 동안 안 오면 노드의 Ready 조건(노드 오브젝트의 status.conditions 에 적히는 상태 항목 중 하나)을 Unknown 으로 바꾸고, 노드에 node.kubernetes.io/unreachable taint 를 붙인다. taint(오염 표시)는 노드에 붙이는 "이런 파드는 여기 놓지 마 / 여기서 내보내" 라는 표시이고, 파드는 toleration(관용)을 적어 특정 taint 를 견딜 수 있다. 그 노드의 파드는 Ready=False 가 되어 Service 의 엔드포인트(요청을 받을 파드 주소 목록)에서 빠진다. 파드가 그 taint 를 견디는 시간(tolerationSeconds, 기본 300초)이 지나면 파드가 축출(evict, 컨트롤러가 파드를 삭제 대상으로 표시해 내보내는 것)되고, ReplicaSet 이 다른 노드에 새로 만든다. 노드 장애의 시간 = 판정 대기 + 견디는 시간 + 재생성 시간 이다.

하트비트 두 가지, 판정, 축출, 재스케줄

하트비트 두 가지

공식 문서는 노드 하트비트를 두 형태로 정의한다.

  • Node 의 .status 갱신: kubelet 은 노드 상태(조건, 할당 가능한 자원, 이미지 목록 등)를 기본 10초마다(nodeStatusUpdateFrequency) 계산해 바뀌었으면 쓰고, 바뀌지 않았어도 일정 간격(nodeStatusReportFrequency, 기본 5분)마다 .status 를 갱신한다. 크고 무거운 쓰기다.
  • kube-node-lease namespace 의 Lease: Lease(임대)는 "누가 언제까지 살아 있다" 를 적는 작은 리소스다. 노드마다 Lease 오브젝트가 하나 있고, kubelet 이 이를 만들고 기본 10초마다(nodeLeaseDurationSeconds 40초의 4분의 1) spec.renewTime 을 갱신한다. 작고 가벼운 쓰기다. 갱신이 실패하면 200ms 에서 시작해 최대 7초까지 지수 백오프(실패할수록 간격을 두 배씩 늘리는 재시도)로 다시 시도한다.

Lease 가 생긴 이유는 성능이다. 노드가 수천 대인 클러스터에서 모든 노드가 큰 .status 를 10초마다 쓰면 etcd 부하가 크다. 그래서 "살아 있음" 은 작은 Lease 로, "상태 내용" 은 변화가 있을 때만 .status 로 나눴다.

판정: node lifecycle controller

kube-controller-manager 의 node lifecycle controller(공식 문서의 node controller)는 기본 5초(--node-monitor-period)마다 각 노드를 검사한다. 마지막 하트비트(Lease 갱신 또는 status 갱신)로부터 --node-monitor-grace-period(기본 50초)가 지났으면 그 노드의 Ready 조건을 Unknown 으로 바꾼다. kubelet 이 살아서 스스로 "준비 안 됨" 을 보고하면 False 다.

taint 두 종류: NoSchedule 과 NoExecute

컨트롤러는 같은 키로 두 효과(effect)의 taint 를 다룬다. NoSchedule 은 "새 파드를 여기 놓지 마", NoExecute 는 "이미 있는 파드도 내보내" 다. 공식 문서(Taints and Tolerations)는 이 둘을 따로 적는다. "Taint Nodes by Condition" 절: node lifecycle controller 는 노드 조건(Ready False/Unknown, 메모리·디스크·PID 압박, 네트워크 미준비, cordon 의 unschedulable)에 대응하는 NoSchedule taint 를 자동으로 붙인다. "Taint based Evictions" 절(v1.18 GA): 같은 컨트롤러가 not-ready 와 unreachable 에 대해 NoExecute taint 도 붙이고, 이 taint 에 맞는 toleration 이 없거나 tolerationSeconds 가 지난 파드를 축출한다. 소스(node_lifecycle_controller.go)에서도 NoSchedule 쪽은 doNoScheduleTaintingPass, NoExecute 쪽은 processTaintBaseEviction 이 각각 붙인다. 그래서 죽은 노드에는 node.kubernetes.io/unreachable 키로 NoSchedule 과 NoExecute 두 taint 가 함께 붙는다. 이 점이 5절의 nodeTaintsPolicy 계산에서 중요해진다.

파드 Ready 의 두 출처: 프로브와 컨트롤러

파드에도 노드처럼 Ready 조건이 있다. 평소에 이 값을 정하는 것은 그 노드의 kubelet 이다. kubelet 은 파드 스펙에 적힌 프로브(probe, 컨테이너가 살아 있는지·요청을 받을 수 있는지 주기적으로 찔러 보는 검사)를 돌린다. 프로브는 세 종류다. startupProbe 는 느리게 뜨는 컨테이너가 준비될 때까지 나머지 프로브를 미루고, livenessProbe 는 실패하면 컨테이너를 재시작하며, readinessProbe 는 실패하면 파드를 Ready=False 로 두어 Service 의 목록에서 빼되 재시작은 하지 않는다. 검사 방법은 httpGet(응답 코드 200 이상 400 미만이면 성공), tcpSocket(포트가 열렸나), exec(컨테이너 안에서 명령을 실행해 종료 코드 0 이면 성공), grpc 네 가지이고, 공통 필드는 periodSeconds(검사 간격, 기본 10초), timeoutSeconds(한 번의 제한 시간, 기본 1초), failureThreshold(연속 몇 번 실패하면 실패로 보나, 기본 3), successThreshold(기본 1)다. 대역의 hello Deployment 는 readinessProbe 를 periodSeconds: 2 로 둔다(12절). 그런데 노드가 얼면 kubelet 도 얼어서 프로브를 돌리지도, 결과를 보고하지도 못한다. 이때는 두 번째 출처인 node lifecycle controller 가 노드 Ready 를 False/Unknown 으로 판정하는 순간 "이 노드의 파드는 전부 Ready=False" 라고 대신 써 준다. EndpointSlice 컨트롤러는 누가 썼든 파드 Ready 만 보고 목록을 고친다. EndpointSlice 의 주소마다 ready(Ready 이고 삭제 중이 아님), serving(삭제 중이어도 Ready 면 참), terminating(삭제 중) 세 조건이 붙고, kube-proxy 는 기본적으로 ready 인 주소로만 보낸다.

엔드포인트에서 빠지기와 축출

노드가 Unknown 이 되면 컨트롤러는 그 노드 파드들의 Ready 조건을 False 로 표시한다. EndpointSlice 컨트롤러는 Ready 가 아닌 파드를 서비스 엔드포인트의 준비된 목록에서 뺀다. 이 순간 Service 로 가는 요청이 살아 있는 파드로만 간다. 즉 사용자 장애는 판정(약 grace period)에서 끝난다. 그 뒤 파드가 NoExecute taint 를 견디는 시간(tolerationSeconds)이 지나면 축출되고, 원래 Deployment 의 ReplicaSet 이 "원하는 수보다 적다" 를 보고 새 파드를 만든다. 스케줄러가 살아 있는 노드에 놓고, 그 노드 kubelet 이 띄워 Ready 가 되면 복구가 끝난다.

영역 규칙의 이유: 한 가용 영역(AZ, availability zone, 클라우드 데이터센터 한 동)이 컨트롤 플레인과 네트워크로 끊기면 그 영역 노드가 한꺼번에 Unknown 이 된다. 실제로는 노드가 살아 있을 수 있으므로 성급하게 전부 축출하면 더 큰 장애가 된다. 그래서 한 영역의 비정상 비율이 높으면 속도를 늦추거나(큰 클러스터) 멈춘다(작은 클러스터). 한 영역의 노드가 전부 아프면 그 영역은 정말 죽은 것으로 보고 정상 속도로 축출한다. 단 모든 영역이 다 아프면 컨트롤러는 "컨트롤 플레인 쪽 연결 문제" 로 보고 축출을 아예 하지 않는다. 영역은 노드 라벨 topology.kubernetes.io/zone 으로 나누며, kind 대역처럼 라벨이 없으면 노드 전부가 이름 없는 영역 하나로 묶인다(공식 문서: 여러 AZ 에 걸치지 않으면 영역별 판단을 하지 않는다). 그래서 대역에서 노드 1대만 죽이는 s1 은 늘 정상 속도(0.1/초)이고, 대역의 노드 5대 중 3대를 동시에 얼리면 "부분 장애 + 작은 클러스터" 라서 축출이 아예 멈춘다는 점은 알아 둘 만하다.

반복 매 node-monitor-period(5초):
  각 노드 n 에 대해:
    last = max(n 의 Lease.renewTime, n.status 의 마지막 하트비트)
    만약 now - last > node-monitor-grace-period(50초):
      n.Ready = Unknown
      n 에 unreachable taint (NoSchedule, NoExecute) 추가
      n 의 파드들 Ready = False          // → EndpointSlice 에서 빠짐
  각 NoExecute taint 가 붙은 노드의 파드 p 에 대해:   // taint 기반 축출
    t = p 의 toleration 중 그 taint 에 맞는 것
    만약 t 없음: 즉시 축출 대상
    만약 t.tolerationSeconds 없음: 영원히 남음 (DaemonSet 파드)
    아니면 taint 추가 시각 + t.tolerationSeconds 가 지나면 축출 대상
  축출은 eviction-rate 와 영역 규칙에 맞춰 속도 제한

엣지 케이스

  • Terminating 에 멈춘 옛 파드: 축출은 API 에서 삭제 표시(metadata.deletionTimestamp 필드에 시각이 찍힘)를 하는 것이고, 실제로 컨테이너를 끄고 "끝났다" 고 확인하는 것은 그 노드 kubelet 이다. kubelet 이 얼어 있으니 옛 파드는 Terminating 으로 남는다. 공식 문서도 "통신이 끊긴 노드에서는 삭제 대상 파드가 계속 돌 수 있다" 고 적는다. s1-node-down.sh 는 deletionTimestamp 가 있는 파드를 Ready 수에서 빼고 센다.
  • 정말 죽은 노드 정리(non-graceful node shutdown, v1.28 GA): 노드가 돌아오지 않는다고 관리자가 확신하면 kubectl taint nodes <노드> node.kubernetes.io/out-of-service=nodeshutdown:NoExecute 를 손으로 붙인다. 그러면 kubelet 의 확인 없이 그 노드의 파드가 강제로 지워지고 볼륨도 즉시 떼어진다. 노드 오브젝트를 통째로 지우는 kubectl delete node(RB-01)보다 좁은 조치다. 06 에서는 unpause 로 노드가 돌아오므로 쓰지 않았다.
  • DaemonSet 파드: DaemonSet 은 "모든(또는 라벨이 맞는) 노드에 파드를 1개씩 두라" 는 리소스다(CNI, 로그 수집기 등). 이 파드에는 not-ready·unreachable 에 대해 tolerationSeconds 없는 NoExecute toleration 이 자동으로 붙어 축출되지 않는다.
  • graceful node shutdown: 노드가 OS 종료 신호(systemd 의 inhibitor lock)를 받으면 kubelet 이 파드를 정상 종료할 시간을 갖는다. 기본은 꺼져 있다(kubelet 설정 shutdownGracePeriod 와 shutdownGracePeriodCriticalPods 의 기본값 0). 07 은 k3s 의 kubelet-arg 로 60초/10초를 켠다(07 README 1.6). docker pause 는 신호 없이 얼리므로 이 경로를 타지 않는다. 07 의 스팟 회수는 OS 종료 신호가 오므로 이중 안전장치가 된다.
  • Lease 갱신과 status 갱신의 차이: 공식 문서의 Lease 문단은 status 기본 간격(5분)이 "unreachable 판정 시간보다 훨씬 길다" 고 설명한다. 그래서 실제 판정은 사실상 Lease 가 결정한다.

우리 PoC 에서는

s1-node-down.sh 의 hard 모드는 docker pause <노드> 로 kind 노드 컨테이너의 모든 프로세스(kubelet 포함)를 얼린다. docker stop 을 쓰지 않는 이유: kind 노드는 stop/start 하면 IP 가 바뀌어 클러스터가 꼬일 수 있다. unpause 는 깨끗이 돌아온다. EKS(AWS 의 관리형 쿠버네티스) 같은 관리형 서비스(managed, 컨트롤 플레인을 클라우드가 운영해 사용자가 그 설정을 못 만지는 형태)에서는 --node-monitor-grace-period(컨트롤 플레인 설정)를 못 바꾸므로, 우리가 바꿀 수 있는 것은 파드 쪽 설정뿐이라는 전제로 방어를 설계했다.

증상: 노드가 NotReady 인데 파드가 계속 그 노드에 Running 으로 보이고 몇 분째 옮겨 가지 않는다. 볼 곳: kubectl get pod <파드> -o jsonpath='{.spec.tolerations}'(-o jsonpath = 응답 JSON 에서 일부만 뽑는 출력 형식)에서 unreachable 의 tolerationSeconds, kubectl get events -A --field-selector reason=TaintManagerEviction(taint 기반 축출이 남기는 이벤트). 고치는 법: 기본 300초를 기다리는 중이면 정상이다. 급하면 RB-01 조치 2(kubectl delete node), 근본적으로는 5절 tolerationSeconds.

왜 이걸 골랐나 (대안)

대안 (가) --node-monitor-grace-period 를 줄이기: kind 에서는 되지만 관리형 클러스터에서는 못 바꾸고, 너무 줄이면 잠깐의 네트워크 흔들림에 노드를 죽었다고 오판해 멀쩡한 파드를 옮긴다. 그래서 컨트롤 플레인은 기본값에 두고, 파드 쪽(tolerationSeconds, 흩어 놓기)과 앞단 재시도로 대응한다.

5. 노드 다운 방어 3종: tolerationSeconds, 흩어 놓기, PDB

세 설정이 각각 어느 구간을 고치나

4절에서 노드 장애의 시간이 "판정 대기 + 견디는 시간 + 재생성 시간" 이고 판정 대기는 컨트롤 플레인 설정이라 우리가 못 줄인다는 것을 알았다. 그 타임라인에서 파드 쪽 설정으로 손댈 수 있는 곳은 세 군데다.

tolerationSeconds 20

죽은 노드에 묶여 있는 시간(기본 300초)을 20초로. 복구(파드 수) 를 앞당긴다.

topologySpreadConstraints

파드 2개를 반드시 다른 노드에. 노드 하나가 죽어도 절반은 산다. 노드가 죽은 뒤 새 파드가 산 노드에 뜨게.

PodDisruptionBudget (PDB)

"파드 중단 예산". 예고가 있는 장애(drain)에서 한 번에 다 빼지 않게. 예고 없는 장애에는 효과 없음.

poc/06-fault-injection/defenses/fn-resilience-patch.yaml전체 (주석 일부 생략)
spec:
  template:
    spec:
      tolerations:
        - key: node.kubernetes.io/not-ready
          operator: Exists
          effect: NoExecute
          tolerationSeconds: 20
        - key: node.kubernetes.io/unreachable
          operator: Exists
          effect: NoExecute
          tolerationSeconds: 20
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: DoNotSchedule
          nodeTaintsPolicy: Honor
          matchLabelKeys: [pod-template-hash]
          labelSelector:
            matchLabels: { app: hello }
poc/06-fault-injection/defenses/pdb.yaml전체 (주석 생략)
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: hello
  namespace: tenant-a
spec:
  minAvailable: 1
  selector:
    matchLabels: { app: hello }
  • 패치 파일은 apiVersion 이 없는 "조각" 이다. 대역에서는 kubectl -n tenant-a patch deploy hello --patch-file … 로 strategic merge patch(kubectl patch 의 기본 방식. YAML 조각을 기존 리소스에 겹쳐 쓰되 목록은 키 기준으로 합친다)로 붙인다. 파드 template 이 바뀌므로 파드가 새로 만들어진다.
  • toleration 두 개는 not-ready(False)와 unreachable(Unknown) 각각을 덮는다. operator: Exists 는 값과 상관없이 키만 맞으면 된다는 뜻이다. effect 는 NoExecute 만 적었다: NoSchedule taint 는 견디지 않는다(아래 Honor 계산에서 중요).
  • 흩어 놓기 한 줄 = "kubernetes.io/hostname(노드 하나) 단위로, app=hello 이면서 같은 리비전인 파드의 개수 차이가 1을 넘지 않게. 못 지키면 띄우지 마. taint 붙은 노드는 계산에서 빼고".
  • PDB = "app=hello 파드는 자발적 중단 중에도 최소 1개는 살아 있어야 한다". replicas 2 이면 한 번에 1개까지 뺄 수 있다(kubectl get pdb 의 ALLOWED DISRUPTIONS 열이 1).
  • 두 파일 모두 app: hello 라벨을 고른다. 이것은 대역 클러스터의 hello Deployment 라벨이다. 진짜 클러스터의 함수 파드(Knative 가 만드는 Deployment)는 이 라벨이 없으므로, 본선에서는 같은 필드를 함수 차트의 파드 template 과 PDB 셀렉터에 함수 라벨로 옮겨 적어야 한다(12절).

tolerationSeconds 와 DefaultTolerationSeconds 어드미션

파드 스펙에 not-ready·unreachable toleration 을 쓰지 않아도, 실제 파드를 열어 보면 두 toleration 이 tolerationSeconds: 300 으로 들어 있다. API 서버의 DefaultTolerationSeconds 어드미션 플러그인이 파드 생성 때 넣는 것이다. 어드미션(admission)은 API 서버가 요청을 etcd 에 저장하기 직전에 끼어들어 내용을 바꾸거나(mutating) 거부하는(validating) 단계이고, 플러그인은 그 단계의 부품 하나다. 공식 문서: "파드에 이미 toleration 이 없으면 not-ready:NoExecute 와 unreachable:NoExecute 를 5분 동안 견디는 기본 toleration 을 넣는다". 5분이라는 값은 kube-apiserver 플래그 --default-not-ready-toleration-seconds 와 --default-unreachable-toleration-seconds(둘 다 기본 300)로 바꿀 수 있지만 관리형에서는 못 만진다. 우리가 같은 키·효과의 toleration 을 직접 쓰면 플러그인은 그것을 덮어쓰지 않으므로 20초가 적용된다.

20초를 고른 이유: 판정(grace period) 자체가 이미 "50초 동안 소식 없음" 을 확인한 뒤다. 거기에 20초를 더 기다려 노드가 정말 안 돌아오는지 한 번 더 본다. 0이나 5처럼 너무 짧게 하면 잠깐의 네트워크 흔들림만으로 파드를 버리고 새로 만드는 일이 잦아진다(파드가 상태를 갖거나 콜드 스타트(파드가 새로 떠서 첫 요청을 받기까지의 준비 시간)가 비싸면 손해). 긴 값(공식 문서 예시의 6000초)은 로컬 상태가 큰 앱이 네트워크 분할(network partition, 네트워크가 끊겨 양쪽이 서로를 못 보는 상태)의 회복을 기다릴 때 쓴다. 함수는 상태가 없어서 짧은 쪽이 맞다.

topologySpreadConstraints: 흩어 놓기

tolerationSeconds 는 "복구" 를 앞당길 뿐이고, 노드 하나가 죽어도 절반이 살아 있으려면 애초에 파드가 흩어져 있어야 한다. 그 일은 스케줄러(kube-scheduler) 몫이다. 스케줄러는 새 파드를 놓을 노드를 고를 때 필터(놓을 수 없는 노드를 거름)와 점수(남은 노드에 순위를 매김) 두 단계를 거치며, topologySpreadConstraints 는 그 중 "토폴로지 분산" 제약이다. 용어부터 정리한다.

topologyKey
노드 라벨 키. 같은 값을 가진 노드들이 한 도메인이다. kubernetes.io/hostname 이면 노드 하나가 도메인 하나다. topology.kubernetes.io/zone 이면 AZ 하나가 도메인이다.
skew (치우침)
어떤 도메인의 매칭 파드 수 − 전역 최소(자격 있는 도메인들 중 가장 적은 매칭 파드 수).
maxSkew
허용하는 최대 치우침. 1 이면 "가장 적은 도메인보다 1개 넘게 많을 수 없다".
whenUnsatisfiable
DoNotSchedule(기본): 못 지키면 놓지 않는다(파드가 Pending, 즉 놓을 노드를 못 찾아 기다리는 상태로 남는다). ScheduleAnyway: 그래도 놓되 치우침을 줄이는 노드에 점수를 더 준다.
자격 있는 도메인
nodeAffinityPolicy 와 nodeTaintsPolicy 의 조건을 통과한 노드들의 도메인. 전역 최소는 이 도메인들로만 계산한다.
nodeAffinityPolicy
파드의 nodeSelector/nodeAffinity(파드를 특정 라벨의 노드에만 놓으라는 조건. nodeAffinity 는 그것의 표현력이 큰 형태)를 계산에 반영할지. 기본 Honor(반영). 그래서 hello(nodeSelector pool=exec)는 system·build 노드를 도메인으로 세지 않는다.
nodeTaintsPolicy
노드 taint 를 반영할지. 기본 Ignore(모든 노드 포함). Honor 면 taint 없는 노드 + 파드가 견디는 taint 만 가진 노드만 포함.
matchLabelKeys
파드 자기 라벨 중 이 키들의 값을 labelSelector 에 더해 "같은 값끼리만" 센다. pod-template-hash(Deployment 가 ReplicaSet 마다 붙이는 리비전 구분 라벨)를 쓰면 같은 리비전끼리만 센다.

(다)가 성립하는 조건이 하나 있다. Honor 는 "파드가 견디는 taint 만 가진 노드" 는 포함한다. 스케줄러 소스(podtopologyspread/filtering.go 의 matchNodeInclusionPolicies)는 노드의 NoSchedule·NoExecute taint 중 파드 toleration 이 하나도 견디지 못하는 것이 있으면 그 노드를 뺀다(tolerationSeconds 는 보지 않는다). 우리 파드는 unreachable 의 NoExecute 를 견디므로, 죽은 노드에 NoExecute taint 만 있었다면 계산에 포함됐을 것이다. 4절에서 본 대로 죽은 노드에는 같은 키의 NoSchedule taint 도 붙고, 우리 toleration 은 effect 를 NoExecute 로 한정했으므로 그 노드는 제외된다. 반대로 toleration 의 effect 를 비워 두면(모든 효과를 견딤) 죽은 노드가 자격 도메인에 다시 들어와 (나)처럼 Pending 이 되고, 게다가 NoSchedule 까지 견디므로 스케줄러가 새 파드를 죽은 노드에 놓을 수도 있다. 그래서 패치의 effect: NoExecute 는 생략하면 안 되는 줄이다. spot 모드의 cordon 은 node.kubernetes.io/unschedulable:NoSchedule taint 를 붙이므로 같은 이유로 제외된다.

PodDisruptionBudget

흩어 놓기로 노드 하나가 죽어도 절반이 산다. 그런데 사람이 노드를 비우는 "예고된" 작업에서는 두 파드를 한꺼번에 빼 버릴 수 있다. 그것을 막는 것이 PodDisruptionBudget 이다. 공식 문서는 중단(disruption)을 둘로 나눈다. 비자발적: 하드웨어 고장, 커널 패닉(OS 핵심이 멈춤), 노드가 네트워크에서 사라짐, 클라우드 VM 삭제, 자원 부족 축출. 자발적: 노드 drain(수리·업그레이드·축소 전에 파드를 비움), Deployment 삭제, 파드 직접 삭제. PDB 는 Eviction API 를 거치는 자발적 중단만 제한한다(kubectl delete pod 는 Eviction API 가 아니라 그냥 DELETE 라서 PDB 를 지나친다). 그래서 hard(전원 차단)에는 효과가 없고, spot(예고 → drain)에만 효과가 있다.

Eviction API 응답

  • 200 OK: 허용. Eviction 하위 리소스가 생기고 파드는 DELETE 와 같은 방식으로 지워진다(삭제 표시 → kubelet 이 컨테이너에 종료 신호(SIGTERM) → EndpointSlice 에서 제거 → terminationGracePeriodSeconds(기본 30초) 뒤 강제 종료).
  • 429 Too Many Requests: PDB 때문에 지금은 안 된다. 나중에 다시. API 속도 제한 때문에도 올 수 있다.
  • 500 Internal Server Error: 설정 오류. 예: 한 파드를 PDB 여러 개가 고른다.
  • PDB 가 없으면 항상 200.

topology spread 엣지 케이스

  • matchLabelKeys 와 배포: 아래 그림처럼 롤링 배포(Deployment 의 기본 방식. 파드를 몇 개씩 새 리비전으로 바꿔 간다) 중에는 옛 ReplicaSet 파드와 새 ReplicaSet 파드가 같이 있다. labelSelector 가 app=hello 만이면 둘을 합쳐 세므로, 새 파드들이 옛 파드가 없는 노드로 몰리고, 옛 파드가 사라지면 새 파드끼리는 한 노드에 몰려 있게 된다. matchLabelKeys: [pod-template-hash] 는 새 파드 자신의 해시 값을 셀렉터에 더해 같은 리비전끼리만 센다. 공식 문서: v1.27 부터 beta 로 기본 활성, v1.34 부터는 키-값이 labelSelector 에 명시적으로 합쳐진다. labelSelector 가 없으면 쓸 수 없고, 같은 키가 둘 다에 있으면 안 된다.
  • 축소는 재조정하지 않는다: 제약은 스케줄 순간에만 본다. 파드가 지워져 치우침이 생겨도 스케줄러가 옮기지 않는다(Descheduler(이미 떠 있는 파드를 규칙에 따라 내쫓아 다시 스케줄되게 하는 별도 프로젝트) 몫). 그래서 s1-node-down.sh 는 매 회차 끝에 rollout restart 로 다시 흩는다.
  • 도메인은 존재하는 노드에서만 안다: 노드가 0대인 풀(영역)은 도메인으로 세지 않는다. 노드 수를 자동으로 늘리고 줄이는 환경(cluster autoscaler, Karpenter)에서 함정이 된다.
  • minDomains(v1.30 GA): "최소 이만큼의 도메인에 흩어라". DoNotSchedule 과 함께만 쓸 수 있고, 자격 도메인 수가 이보다 적으면 전역 최소를 0 으로 본다. 지정하지 않으면 1 로 본다. 우리는 쓰지 않았다. 쓰면(예: 2) exec 노드 한 대가 죽었을 때 Honor 로 자격 도메인이 1개가 되어 전역 최소가 0 이 되고, 산 노드에 두 번째 파드를 놓으면 치우침 2 라서 (나)와 같은 Pending 이 문서 규칙 그대로 다시 생긴다.
  • nodeTaintsPolicy, nodeAffinityPolicy: v1.26 beta, v1.33 GA. nodeAffinityPolicy 기본 Honor, nodeTaintsPolicy 기본 Ignore.

우리 PoC 에서는

증상 1: 노드 다운 뒤 새 파드가 Pending, Events 에 didn't match pod topology spread constraints. 볼 곳: kubectl get deploy hello -o yaml | grep -A8 topologySpread 에 nodeTaintsPolicy 가 있나. 고치는 법: nodeTaintsPolicy: Honor. 증상 2: 배포 직후 두 파드가 같은 노드. 볼 곳: kubectl -n tenant-a get pods -o wide. 고치는 법: matchLabelKeys: [pod-template-hash], 이미 몰렸으면 rollout restart. 증상 3: kubectl get pdb 의 ALLOWED DISRUPTIONS 가 0. drain 이 영원히 안 끝난다(6절, 14절).

왜 이걸 골랐나 (대안)

tolerationSeconds: 기본 300 은 복구가 너무 늦고, 5 는 오판이 잦다 → 20. 흩어 놓기: ScheduleAnyway 는 평소 쏠림, DoNotSchedule+Ignore 는 노드 다운 후 Pending → DoNotSchedule+Honor+matchLabelKeys. 대안 podAntiAffinity(같은 라벨의 파드를 같은 노드에 두지 말라는 조건, required 는 "반드시")는 "노드당 1개" 를 강제해 replicas 가 노드 수보다 많아지면 Pending 이 되므로 버렸다. PDB: replicas 와 같게(=0 허용)는 drain 을 영원히 막고, 0(PDB 없음)은 drain 이 두 파드를 동시에 뺄 수 있어 → minAvailable 1. 비율(50%)은 replicas 가 늘어날 때 유리하지만 2개에서는 같은 값이라 단순한 정수를 택했다.

6. 예고 있는 장애 vs 갑작스러운 장애: spot 과 hard

같은 "노드가 사라짐" 인데 결과가 다르다

5절의 세 방어 중 PDB 는 "예고가 있는 장애" 에서만 일한다고 했다. 그 예고의 대표가 스팟 회수다. AWS 스팟 인스턴스(남는 용량을 싸게 빌리는 EC2. 대신 AWS 가 필요하면 회수한다)는 회수 2분 전에 예고를 준다. 예고는 두 길로 온다: 인스턴스 메타데이터(IMDS, Instance Metadata Service, EC2 안에서 169.254.169.254 로 자기 정보를 읽는 HTTP 서비스)와 EventBridge(AWS 의 이벤트 버스) 이벤트다. 이 예고를 받아 노드를 미리 비우면(cordon + drain), 노드가 꺼질 때 그 위에는 이미 파드가 없다. 사용자 요청은 drain 중 정상 종료 경로(EndpointSlice 에서 먼저 빠짐)를 타므로 거의 실패하지 않는다. 예고가 없거나 무시하면 4절의 hard 경로를 그대로 탄다. 06 README 의 결론: 사용자 장애를 크게 줄이는 것은 tolerationSeconds 가 아니라 "미리 비우기" 다.

s1-node-down.sh 의 두 모드

T0=$(now); DRAIN_S=""

  kubectl cordon "$NODE" >/dev/null

  • kubectl cordon: 노드에 spec.unschedulable=true 를 쓴다. node lifecycle controller 가 이를 보고 node.kubernetes.io/unschedulable:NoSchedule taint 를 붙이므로 새 파드가 이 노드로 오지 않는다. kubectl get nodes 에는 SchedulingDisabled 로 보인다.
  • kubectl drain: 먼저 cordon 한 뒤 노드의 파드마다 Eviction API 를 부른다. --ignore-daemonsets 는 DaemonSet 파드를 건너뛰고(어차피 그 노드에 다시 생김), --delete-emptydir-data 는 emptyDir(파드가 사는 동안만 있는 임시 디스크)을 쓰는 파드도 그 데이터를 잃어도 된다는 동의다. 이 두 옵션이 없으면 drain 은 해당 파드에서 멈춘다. --timeout=110s 는 2분 예고 안에 끝내야 한다는 뜻이다.
  • drain 이 실패해도 스크립트는 docker pause 로 간다. 예고 시간이 끝나면 AWS 는 기다려 주지 않기 때문이다. CSV 의 drain_s 열에 걸린 초 또는 timeout 이 남는다.
  • 예고를 받는 주체는 PoC 에서는 스크립트지만, 실물에서는 AWS Node Termination Handler(NTH, 노드마다 DaemonSet 으로 떠서 IMDS 를 주기적으로 읽다가 예고가 오면 cordon + drain 을 대신 해 주는 AWS 공식 프로젝트) 또는 Karpenter(노드를 직접 만들고 없애는 오토스케일러. 예고를 받으면 스스로 노드를 비운다)의 interruption 처리다. 07 은 NTH 를 Argo CD Application 으로 넣는다(enableSpotInterruptionDraining: true).

7. 시나리오 2: 노이지 네이버 (함수 폭주)

무엇이 무엇으로부터 누구를 지키나

시나리오 1 이 "노드가 사라지는" 장애였다면, 시나리오 2 는 노드는 멀쩡한데 옆집이 자원을 다 쓰는 장애다. 노이지 네이버(noisy neighbor, 시끄러운 이웃)는 같은 노드나 같은 풀을 쓰는 다른 테넌트가 CPU·메모리·노드 자리를 다 가져가서 내 함수가 느려지거나 아예 못 뜨는 상황이다. 시나리오 2 는 tenant-b 의 "버그 난 함수" 가 오토스케일로 30개까지 늘어나는 상황을 흉내 낸다. 각 파드는 CPU 0.5코어를 예약(requests, 스케줄러가 노드 자리를 셀 때 쓰는 "이만큼은 보장해 달라")하고 1코어까지(limits, "이 이상은 못 쓴다") 무한 루프로 태운다. 03 단계(가이드 3장)에서 넣은 ResourceQuota(namespace 단위 자원 상한)·LimitRange(컨테이너 단위 기본값과 최대치)가 정말 막는지, 그리고 그 벽을 빼면 어떻게 되는지를 같은 스크립트로 잰다. 네 개념의 자세한 뜻은 3장 ResourceQuota·LimitRange·requests, limits, QoS 절에 있고, 이 절은 장애 주입에 필요한 만큼만 다시 적는다.

네 개념의 정확한 뜻

개념단위누가 집행넘으면대역 값 (standin/targets.yaml)
requests컨테이너스케줄러 (노드 할당 가능량 − 이미 예약된 합)놓을 노드가 없으면 Pending폭주 500m, hello 50m

8. 시나리오 3: 나쁜 배포와 자동 롤백

카나리 + 분석 = 자동 롤백, 그리고 Git 은 여전히 나쁘다

시나리오 1·2 는 인프라와 이웃이 일으키는 장애였고, 시나리오 3 은 우리 자신이 일으키는 장애, 즉 버그 난 새 버전 배포다. 02 단계(가이드 2장)의 Argo Rollouts 카나리를 대역에서 작게 재현한다. Argo Rollouts 는 Deployment 대신 Rollout 리소스를 두어 카나리(새 버전을 일부 파드·트래픽에만 먼저 내보내 보는 배포 방식)와 그 자동 판정을 해 주는 컨트롤러다(2장 4절). Rollout api 는 파드 4개, 첫 단계 setWeight: 25(카나리 파드 1개), 다음 단계에서 분석(AnalysisTemplate = "무엇을 어떻게 재서 합격·불합격을 가를지" 의 틀, 그것을 실행한 결과가 AnalysisRun, 2장 6절)을 돌린다. 분석이 실패하면 Rollout 이 abort(카나리 단계를 중단하고 거둠)해 카나리 파드를 0으로 줄이고 트래픽은 안정(stable) 버전으로만 간다. 이것이 자동 롤백이다. 단, 롤백은 클러스터 안에서만 일어난다. GitOps(Git 에 적힌 상태를 클러스터가 따라가게 하는 운영 방식, 1장)라면 Git 에는 여전히 나쁜 버전이 적혀 있어 Argo CD 화면에서는 Synced(클러스터가 Git 과 같음)인데 Degraded(리소스 건강 상태가 나쁨)로 보인다. 진짜 정리는 git revert(그 커밋을 되돌리는 새 커밋) + push 다(RB-03).

두 모드: kubectl 과 git, 그리고 selfHeal

s3-bad-deploy.sh 는 나쁜 버전을 넣는 방법이 둘이다. kubectl 모드는 스크립트가 Rollout 의 컨테이너 args 를 JSON patch(RFC 6902, "이 경로의 값을 이렇게 바꿔라" 를 연산 목록으로 적는 patch 형식)로 직접 바꾼다. git 모드는 사람이 나쁜 값을 커밋·push 한 뒤 엔터를 치면 그 순간을 t0 로 잡는다. 왜 둘인가? 진짜 클러스터의 Rollout 은 Argo CD Application 이 selfHeal(5절에서 본, 클러스터가 Git 과 달라지면 되돌리는 옵션, 1장 "자동 동기화, prune, selfHeal")로 지킨다. kubectl 로 고치면 Argo CD 가 몇 초 만에 Git 값으로 되돌리므로, "Rollouts 가 롤백했다" 가 아니라 "Argo CD 가 되돌렸다" 를 재게 된다. 그래서 스크립트는 Argo CD 가 관리하는 흔적(리소스에 남기는 argocd.argoproj.io/tracking-id 주석 또는 app.kubernetes.io/instance 라벨)이 보이면 kubectl 모드를 거부한다.

사용자 피해 ≈ 카나리 비율 × 감지 시간 × 요청률. 분석 간격·count·failureLimit 를 줄이면 감지가 빨라지고 피해가 준다. 대신 일시적 흔들림에 멀쩡한 버전을 롤백하는 "거짓 롤백" 이 는다. 첫 단계를 25% 에서 10% 로 낮추면 같은 감지 시간에 피해 요청이 준다.

  • 네트워크 시도는 000(연결 실패)만 PASS 다. 403 처럼 숫자가 찍히면 "연결은 됐고 그 뒤에서 거절" 이므로 FAIL 이다. 네트워크 벽이 없다는 뜻이기 때문이다(14절 실습 3).
  • RBAC 시도는 kubectl --as=system:serviceaccount:tenant-b:default 로 그 계정 행세를 한다(impersonation, 관리자가 다른 주체인 척 요청을 보내는 공식 기능. 인가는 그 주체 기준으로 평가된다). 파드 안에서 토큰을 꺼내 부르는 것과 인가 결과가 같고, N3 이 막혀 있어도 RBAC 만 따로 시험할 수 있다.
  • 결과마다 CSV 에 date,id,attempt,expected,actual,verdict,seconds 한 줄. seconds 는 거절까지 걸린 시간: 네트워크는 타임아웃(3초 근처), API 거절은 즉시.
  • 감지: P1 시각부터 TenantPolicyDenied 알림이 firing 될 때까지 최대 90초 기다려 D1 줄로 남긴다. 그 밖에 apiserver 403 시계열 수, PSA 거부 시계열 수를 출력하고, hubble CLI 가 있으면(Cilium 일 때) tenant-b 에서 나간 DROPPED 흐름 20개를 보여 준다.
  • Hubble 로 증거 남기기: Cilium(eBPF 로 커널 안에서 패킷을 처리하는 CNI, 진짜 클러스터 faas 의 CNI)에는 Hubble 이라는 흐름 관측기가 붙어 있어, 어떤 파드에서 어떤 파드로 가는 연결이 어떤 정책 판정(verdict)을 받았는지 흐름 단위로 보여 준다. hubble observe --from-namespace tenant-b --verdict DROPPED --last 20 처럼 출발 namespace(--from-namespace), 판정(--verdict FORWARDED|DROPPED|AUDIT|…), 개수(--last)로 거른다(hubble CLI 의 observe 플래그). N1~N4 가 PASS 인데 DROPPED 흐름이 안 보이면 연결이 정책이 아니라 다른 이유(DNS 실패 등)로 끊긴 것이므로, 000 만으로는 모자란 "왜 막혔나" 를 여기서 확인한다. 자세한 사용법은 4장 10절 Hubble.

  • CNI 가 정책을 집행하는지는 YAML 로 모른다: NetworkPolicy 는 API 서버에 저장만 될 뿐, 실제로 패킷을 막는 것은 CNI 플러그인이다. kind 의 기본 CNI 인 kindnet 은 kind v0.24 부터 kube-network-policies 라는 부속 컨트롤러로 NetworkPolicy 를 집행한다(kind 릴리스 노트, 대역 kind-config.yaml 주석). 그런데 06 README 8.4 는 클라우드 컨테이너 환경에서 그 집행이 커널 문제로 동작하지 않아 N1~N4 가 FAIL 이었고, 같은 YAML 을 Calico(또 다른 CNI) 클러스터에 넣으니 전부 PASS 였다고 적는다. 정책을 "써 둔 것" 과 "집행되는 것" 은 다르다. 이 스크립트처럼 한 번 뚫어 봐야 안다.
  • PSA 레벨 차이: 대역 namespace 는 enforce: restricted(가장 엄격. 비루트, 권한 상승 금지, 기본 seccomp 등), 03 차트는 enforce: baseline(privileged·hostPath·호스트 네트워크 같은 알려진 탈출 수단만 금지) + warn: restricted(위반하면 경고만) 다. P1(privileged + hostPath)은 baseline 에서도 막혀 결과는 같고 메시지만 baseline:latest 로 바뀐다.

10. Prometheus 알림 규칙: 사람을 깨우는 층

규칙 하나 = 조건 + 지속 시간 + 꼬리표

9절까지가 "자동으로 막고 고치는" 층이었다면, 이 절은 그 결과를 사람에게 알리는 층이다. Prometheus 는 지표를 주기적으로 긁어(scrape) 자기 시계열 데이터베이스(TSDB)에 쌓고 PromQL 로 질의하는 모니터링 서버다(02 단계에서 설치, 2장 8절). 그 Prometheus 의 알림 규칙(alerting rule)은 PromQL 식 하나다. 정해진 주기마다 식을 평가해서 결과 시계열이 하나라도 나오면 그 시계열마다 알림이 "활성" 이 된다. for 동안 계속 활성이면 firing(울림) 이 된다. 06 단계는 규칙 다섯 개를 그룹 fault-injection 으로 넣고, 각 규칙의 runbook 주석이 해당 런북 파일을 가리킨다. 알림은 자동 복구를 하지 않는다. 자동 복구는 쿠버네티스와 Rollouts 가 하고, 알림은 사람에게 "무엇이 일어났고 어느 문서를 열라" 를 전달하는 층이다.

상태, 평가 주기, 라벨과 주석

  • 평가 주기: 규칙 그룹은 evaluation_interval(전역 또는 그룹별 interval)마다 평가된다. 그룹 안 규칙은 순서대로 평가된다.
  • for: "처음 결과가 나온 뒤 이 시간 동안 매 평가마다 계속 나와야 firing". 순간적인 흔들림을 거르는 대가로 감지가 그만큼 늦다. 없거나 0s 면 첫 평가에서 바로 firing. keep_firing_for 는 반대로, 조건이 사라진 뒤에도 일정 시간 firing 을 유지해 들쭉날쭉(flapping)을 줄인다(우리 규칙은 안 씀).
  • labels: 알림에 붙는 추가 라벨. severity(critical/warning)는 Alertmanager 가 라우팅·묶기에 쓰는 관례다. scenario 는 우리가 붙인 분류다. 값은 템플릿이 가능하다.
  • annotations: 사람용 정보. 공식 문서가 "설명이나 runbook 링크" 를 예로 든다. {{ $labels.node }}, {{ $value }} 로 알림 인스턴스의 라벨과 값을 넣는다.
  • Alertmanager: 알림 규칙은 "지금 무엇이 깨졌나" 만 판단한다. 묶기·무음·발송(Slack 등)은 Alertmanager 몫이다(아래). 02 차트 values 는 Alertmanager 를 껐고, 06 도 켜지 않는다. 그래서 06 의 "알림 시각" 은 발송 시각이 아니라 firing 시각이다.

Alertmanager: PoC 에서는 안 썼고, 본선에서는 이렇게 쓴다

Prometheus 는 firing 이 된 알림을 설정(alerting.alertmanagers)에 적힌 Alertmanager 로 HTTP 로 보낸다(pending 은 보내지 않는다). Alertmanager 는 공식 문서대로 "여러 Prometheus 가 보낸 같은 알림의 중복 제거, 묶기(grouping), 수신자(receiver)로의 라우팅, 그리고 무음(silence)과 억제(inhibition)" 를 맡는 별도 프로그램이다. 묶기는 group_by 라벨이 같은 알림을 한 통지로 합치고(group_wait 기본 30초 동안 모아서 보냄, 같은 묶음의 새 알림은 group_interval 기본 5분마다, 바뀐 것이 없어도 repeat_interval 기본 4시간마다 다시 보냄), 억제는 "같은 노드의 critical 이 울리는 동안 warning 은 보내지 않는다" 같은 규칙(inhibit_rules), 무음은 사람이 "이 라벨의 알림은 몇 시간 동안 꺼 둬" 라고 걸어 두는 것, 라우팅은 severity 같은 라벨로 트리를 타고 내려가 Slack·PagerDuty·이메일 같은 receiver 를 고르는 것이다. 본선에서 "노드 하나가 죽으면 FnNodeNotReady 와 FnReplicasUnavailable 이 동시에 울린다" 를 사람이 한 통지로 받게 하려면 이 묶기와 억제가 필요하고, 런북 링크(runbook 주석)를 클릭 가능한 URL 로 바꾸는 것도 Alertmanager 의 통지 템플릿에서 한다(13절).

Helm values 두 겹과 configmapReload

진짜 클러스터의 Prometheus 는 02 단계에서 Helm 차트 prometheus-community/prometheus(29.37.0)로 깔았다(Helm = 쿠버네티스 패키지 도구, 차트 = 패키지, values = 설치 때 넣는 설정값 파일). 알림 규칙도 그 차트의 values(serverFiles.alerting_rules.yml)로 넣으면 차트가 ConfigMap(설정 파일을 담는 리소스. 파드에 파일로 마운트된다) prometheus-server 안의 규칙 파일로 렌더링한다. 그래서 06 의 파일은 02 values 위에 덧붙이는 values 다.

규칙 다섯 개를 한 줄씩

poc/06-fault-injection/defenses/prometheus-alerts-values.yaml발췌
kube-state-metrics:
  enabled: true
configmapReload:
  prometheus:
    enabled: true

      - name: fault-injection
        rules:
          - alert: FnNodeNotReady
            expr: kube_node_status_condition{condition="Ready",status="true"} == 0
            for: 0s
            labels: { severity: critical, scenario: s1 }
            annotations:
              summary: "노드 {{ $labels.node }} NotReady"
              runbook: poc/06-fault-injection/runbooks/RB-01-node-down.md
          - alert: FnReplicasUnavailable
            expr: |
              kube_deployment_status_replicas_available{namespace=~"tenant-.*"}
                < kube_deployment_spec_replicas{namespace=~"tenant-.*"}
            for: 30s
          - alert: TenantQuotaNearLimit
            expr: |
              kube_resourcequota{type="used"}
                / ignoring(type) kube_resourcequota{type="hard"} > 0.9
          - alert: RolloutAborted
            expr: rollout_info{phase="Abort"} == 1
          - alert: TenantPolicyDenied
            expr: sum(increase(pod_security_evaluations_total{decision="deny",mode="enforce"}[5m])) > 0
FnNodeNotReady
kube-state-metrics 는 노드 condition 마다 status 라벨이 true/false/unknown 인 시계열 세 개를 내고, 현재 상태인 것만 값 1 이다. status="true" 시계열이 0 이면 False 든 Unknown 이든 "Ready 가 아님". == 0 은 비교 필터라 조건에 맞는 시계열만 남는다. 노드 장애는 이미 K8s 판정(grace period)을 거친 신호라 for: 0s(더 기다릴 이유가 없다). critical 인 유일한 규칙.
FnReplicasUnavailable
같은 라벨(namespace, deployment)끼리 일대일로 비교한다(PromQL 의 벡터 매칭: 양쪽 시계열의 라벨이 모두 같아야 짝이 된다). 정규식 tenant-.* 로 테넌트 namespace 만. 배포 중에는 잠깐 available 이 모자라는 게 정상이라 for: 30s 로 거른다. 원인이 노드든 폭주든 증상 쪽 알림이다.
TenantQuotaNearLimit
kube_resourcequota 는 쿼터의 자원마다 type="used", type="hard" 두 시계열을 낸다. 나누려면 양쪽 라벨이 같아야 하는데 type 만 다르므로 ignoring(type) 으로 그 라벨을 빼고 맞춘다. 결과 라벨에 resource(requests.cpu 등)가 남아 주석에서 쓴다. 쿼터가 없으면 시계열 자체가 없어 알림도 없다(7절 깨뜨리기).
RolloutAborted
Rollouts 컨트롤러 지표 rollout_info 의 phase 라벨. 주의: Rollout 의 status.phase 는 Degraded 지만 지표의 phase 라벨 값은 Abort 다(파일 주석, 대역 실측). 그래서 규칙을 쓸 때 Prometheus 화면에서 라벨 값을 먼저 확인한다(README 3절 빈칸 3). 이 지표는 차트 기본 긁기 목록에 없어 extraScrapeConfigs 로 추가했다.
TenantPolicyDenied
API 서버 지표 pod_security_evaluations_total 의 decision="deny", mode="enforce". counter(계속 올라가기만 하는 누적 지표 종류)라 값 자체가 아니라 increase(…[5m]) 로 5분 증가량을 보고 sum 으로 합친다. 5분 창이라 한 번 거부되면 약 5분 동안 firing 이 유지되고, 그 뒤 꺼진다. 반대로 Q1(쿼터·LimitRange 거부)이나 R1(RBAC 403)은 이 규칙에 안 잡힌다.

    if not vals:
        return None
    v = sorted(vals)
    k = max(0, min(len(v) - 1, int(round(p / 100.0 * len(v) + 0.5)) - 1))
    return v[k]

13. 런북: 새벽 3시의 사람을 위한 문서

런북은 알림과 짝이다

10절의 알림은 "무엇이 깨졌나" 를 전하고 끝난다. 그 다음 "무엇을 하나" 가 런북이다. 런북(runbook)은 알림을 받은 사람이 생각하지 않고 그대로 따라 할 수 있는 절차서다. 06 의 알림 규칙 다섯 개는 모두 runbook 주석으로 RB-01~04 중 하나를 가리킨다. 네 런북은 같은 뼈대를 쓴다: 언제 여나 → 영향 → 1분 안에 확인 → 판단 → 조치 → 복구 확인 → 재발 방지 → 기록. 이것은 일반적인 사고 대응 순서 감지 → 진단 → 완화 → 확인 → 후속 에 그대로 대응한다.

런북이 좋은지 판단하는 기준

  • 명령에 기대 출력이 붙어 있다: "kubectl get nodes → 전부 Ready" 처럼. 결과를 해석할 필요가 없어야 새벽 3시에 쓸 수 있다.
  • 판단은 표로: "보이는 것 → 뜻 → 할 일". 런북 네 개 모두 이 형식이다.
  • 자동으로 되는 것과 손으로 할 것을 나눈다: 사람이 자동 복구와 경쟁하면(예: 쿠버네티스가 옮기는 중에 손으로 지우기) 상황이 더 꼬인다.
  • GitOps 와의 관계를 명시: RB-02·03·04 는 "selfHeal 이 kubectl 변경을 되돌린다" 를 적고 Git 경로를 준다. RB-01 은 반대로 "Argo CD 는 손대지 않는다" 를 적는다.
  • 실측으로 갱신: 런북의 "영향" 표는 측정 CSV 에서 온다. 숫자가 바뀌면 런북도 바꾼다. 설정도 마찬가지다: RB-01 의 "넣은 것" 줄은 한동안 흩어 놓기를 첫 조합(ScheduleAnyway)으로 적고 있다가 최종 설정(DoNotSchedule + Honor + matchLabelKeys)으로 갱신됐다. 이렇게 코드는 바뀌었는데 문서가 옛 값을 가리키는 것이 런북이 늙는 전형적인 모습이다.
  • 사후 분석과 이어진다: SRE 책의 Postmortem Culture 는 비난 없는(blameless, 누가 잘못했나가 아니라 무엇이 그렇게 만들었나를 묻는) 사후 분석을 권한다. "기록할 것" 칸이 그 재료다: t0, 감지, 복구, 피해, 무엇이 막았나.

정리

핵심 개념 체크리스트

  • 카오스 실험의 다섯 원칙(평소 상태 가설, 실제 사건, 운영 환경, 자동화, 영향 범위 최소화)을 말하고, 06 이 운영 환경 원칙을 일부러 어긴 이유를 댈 수 있다.
  • t0, 감지, 완화, 복구를 구분하고, MTTD/MTTR 이 어느 CSV 열인지 짚을 수 있다.
  • 감지 세 겹(프로브·알림·상태)이 장애를 아는 순서와 각각이 놓치는 것을 설명할 수 있다.
  • kubelet 의 Lease 갱신(기본 10초) → node lifecycle controller 검사(5초) → grace period(50초) → Ready=Unknown → unreachable taint(NoSchedule 과 NoExecute 둘 다) → 파드 Ready=False → EndpointSlice 제외 → tolerationSeconds 뒤 축출 → 재생성의 순서를 그릴 수 있다.
  • 파드 Ready 를 쓰는 두 출처(kubelet 의 readinessProbe, 노드가 죽었을 때의 node lifecycle controller)와 EndpointSlice 가 그것을 따르는 방식을 말할 수 있다.
  • DefaultTolerationSeconds 가 300초를 넣는 방식과, 우리 20초가 덮어쓰는 조건을 안다.
  • tolerationSeconds 가 줄이는 것은 "파드 수 복구" 이지 "사용자 장애" 가 아님을 타임라인으로 설명할 수 있다.
  • topology spread 의 skew 계산을 손으로 하고, nodeTaintsPolicy Ignore 에서 노드 다운 후 Pending 이 나는 이유와 Honor 가 고치는 이유를 말할 수 있다.
  • matchLabelKeys(pod-template-hash)가 배포 중 쏠림을 막는 원리를 안다.
  • PDB 가 자발적 중단(Eviction API)에만 작동하고, 429 와 drain 재시도의 관계, "PDB = replicas" 의 함정을 안다.
  • "축출" 네 가지(taint 기반, API 주도, 노드 압박, 선점) 중 PDB 가 끼어드는 것이 어느 것인지 가른다.
  • requests·limits·ResourceQuota·LimitRange 가 각각 누가(스케줄러, 커널, 어드미션) 언제 집행하는지 구분한다.
  • Rollouts 의 abort 는 클러스터 안의 롤백일 뿐, Git 정리(revert)가 따로 필요함을 안다. selfHeal 이 kubectl 실험을 무의미하게 만드는 이유도.
  • 침범 8시도와 막는 벽을 짝지을 수 있고, "정책이 있다" 와 "집행된다" 를 구분한다.
  • 알림의 inactive → pending → firing, for, labels/annotations(runbook), 지연의 구성(scrape + eval + for)을 설명할 수 있다. Alertmanager 가 그 뒤에서 하는 네 가지(중복 제거·묶기·억제/무음·라우팅)와 06 이 그것을 안 쓴 이유를 안다.
  • Helm -f 두 번의 덮어쓰기 순서와 configmapReload 의 역할을 안다.
  • 런북의 뼈대(언제 여나 → 확인 → 판단 → 조치 → 복구 확인 → 재발 방지 → 기록)를 안다.

시간 분해

장애 시간을 "판정 대기 + 견디는 시간 + 재생성" 처럼 구간으로 쪼개고, 각 구간을 누가 소유하는지(컨트롤 플레인, 파드 설정, 앞단) 적는다. 손댈 수 있는 구간만 고친다. DB 장애 조치(failover), 캐시 만료, DNS TTL 에도 같은 분해가 된다.

예고가 있으면 미리 비운다

스팟 회수, 배포, 노드 업그레이드처럼 예고가 있는 사건은 "그때 대응" 보다 "미리 비우기" 가 훨씬 싸다. 큐 소비자 graceful shutdown, 커넥션 드레인도 같은 원리.

안전장치도 시험한다

PDB, 분석, NetworkPolicy 처럼 "막아 주는 것" 은 일부러 나쁜 입력을 넣어 실제로 막는지 확인한다. 틀린 안전장치는 없는 것보다 나쁠 수 있다.
