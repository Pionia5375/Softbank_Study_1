멀티테넌트 FaaS PoC, 한 장으로 보기

코드만 HTTP 로 보내면 쿠버네티스 위에서 함수가 빌드되고, 테넌트 울타리 안에서 0개와 N개 사이를 오가며 응답하는 플랫폼. 7단계로 쌓은 이 PoC 의 전체 구조, 요청 다섯 가지가 흐르는 길, 이름과 경계를 이 장 하나로 머릿속에 그린다. 다음 장들은 이 그림의 한 칸씩을 확대한다.

이 장의 지도

이 장은 특정 기술 하나가 아니라 가이드 전체의 지도다. 아래 그림에서 테두리 전체가 이 장이 다루는 범위이고, 안의 칸 하나하나가 다음 장들이다. 아래층(기반)이 무너지면 위층이 다 같이 무너진다는 점을 기억해 두면 장애를 추적할 때 순서가 생긴다. 그림 안의 이름(Argo CD, Knative, Cilium, kaniko, gVisor, MCP, k3s …)은 아직 몰라도 된다. 이 장을 위에서 아래로 읽는 동안 처음 나오는 자리에서 하나씩 풀어 쓴다. 점선 밑줄과 번호가 붙은 말은 그 단락 옆(좁은 화면에서는 아래)의 주석에 뜻이 있다.

이 장의 절과 한 줄 요약. 순서대로 읽으면 앞 절이 다음 절의 바탕이 된다.

  • 이 PoC 는 무엇인가: 한 문장 정의, 무엇을 어디서 어떻게 만들었나, 이 장 전체에서 쓰는 쿠버네티스 기본 말.
  • 이 가이드를 읽는 법: 깊이 세 단계와 읽는 순서.
  • 장 목록: 가이드 아홉 장과 PoC 일곱 단계의 대응.
  • 전체 아키텍처: 큰 그림 한 장과 층 쌓기 그림. 이름·포트·풀이 전부 여기 있다.
  • 두 갈래: GitOps 와 API: 플랫폼은 Git, 함수는 API. 왜 나눴고 어디서 만나나.
  • 유즈케이스: 누가 이 플랫폼으로 무엇을 하나. UML 그림과 표.
  • 컴포넌트 카탈로그: namespace 와 부품 전부, 어느 풀에 뜨고 어떻게 깔렸나. Argo CD Application 나무.
  • 디렉토리 지도: poc/ 의 폴더가 실행 중인 어느 부품이 되나.
  • 핵심 흐름 다섯: 함수 배포, 호출과 콜드 스타트, git push, 카나리 롤백, 노드 장애. 그리고 함수의 일생.
  • 설치 순서: run-all.sh 의 단계와, 클러스터를 왜 한 번만 만드나.
  • 신뢰 경계: 관리자, 컨트롤 플레인, 에이전트, 테넌트, 빌드가 각각 무엇을 할 수 있나.
  • 로컬 kind 와 EC2 k3s: kind 와 k3s 의 같은 점과 다른 점.
  • 용어집: 본문에서 이미 풀어 쓴 말 105개를 참고용으로 다시 모은 것과, 설명한 장.
  • 정리: 체크리스트, 결정 표, 본선에서 떠올릴 패턴, 스스로 답해 볼 질문, 그리고 다음 장으로.

이 PoC 는 무엇인가

한 문장으로: "Run your function over HTTP" 를 직접 운영하는(self-managed) 쿠버네티스 위에 세운 멀티테넌트 FaaS 플랫폼이다. 말을 하나씩 풀면 이렇다. 쿠버네티스(Kubernetes)는 컨테이너를 여러 서버에 걸쳐 배치하고, 죽으면 다시 띄우는 오케스트레이터다. 직접 운영한다는 것은 EKS 같은 관리형 서비스가 아니라 노드와 컨트롤 플레인을 우리가 세운다는 뜻이다. 멀티테넌트(multi-tenant)는 한 플랫폼을 여러 고객 조직(테넌트, tenant)이 서로 모른 채 나눠 쓴다는 뜻이고, FaaS(Function as a Service)는 코드 조각만 올리면 빌드·배포·확장·축소를 플랫폼이 맡는 서비스 모양이다.

컨테이너(container)
프로그램과 그것이 기대는 라이브러리·설정을 한 묶음으로 격리해 돌리는 단위. 같은 묶음이면 어느 서버에서 띄워도 같게 돈다.
EKS
AWS 의 관리형 쿠버네티스. 컨트롤 플레인을 AWS 가 대신 돌려 주고 시간당 과금한다.
노드(node)
컨테이너가 실제로 도는 서버 한 대. 이 PoC 의 kind 에서는 Docker 컨테이너 하나가 노드 하나다.

함수 개발자는 파이썬 함수 파일 하나를 POST /api/v1/tenants/tenant-a/functions 로 보낸다. 플랫폼은 클러스터 안에서 컨테이너 이미지를 kaniko 로 빌드하고, 이미지 내용의 지문인 digest 로 고정해 Knative Service 로 띄운다. 요청이 없으면 파드를 0개로 줄였다가 첫 요청이 오면 다시 띄운다.

이미지(image)
코드와 실행 환경을 담은, 어디서 띄워도 같은 파일 묶음. 컨테이너는 이미지를 실행한 것이다.
kaniko
Docker 없이 컨테이너 안에서 이미지를 만드는 빌드 도구.
digest
이미지 내용 전체의 SHA-256 해시. 이름표인 태그와 달리 내용이 바뀌면 값도 바뀐다.
Knative Service(ksvc)
Knative 는 쿠버네티스 위에서 요청량에 따라 파드 수를 0 과 N 사이로 조절하는 서버리스 계층이고, Knative Service(줄여서 ksvc)는 거기서 "함수 하나" 에 해당하는 리소스다.
파드(Pod)
쿠버네티스가 컨테이너를 띄우는 최소 단위. 같은 노드에서 함께 뜨는 컨테이너 한두 개를 묶은 것.

테넌트끼리는 Namespace, ResourceQuota, NetworkPolicy, RBAC 같은 울타리 여러 겹으로 나누고, 남의 코드를 돌리는 실행 노드는 별도 풀로 떼어 gVisor 샌드박스를 쓸 수 있게 했다.

Namespace
이름과 권한을 나누는 칸. 이 PoC 는 테넌트 하나에 namespace 하나.
ResourceQuota
칸 하나가 쓸 수 있는 CPU·메모리·파드 수의 총량 한도.
NetworkPolicy
파드 사이 통신을 라벨로 허용하는 규칙.
RBAC(Role-Based Access Control)
누가 어떤 쿠버네티스 API 를 부를 수 있는지 정하는 권한 체계.
풀(pool)
같은 역할의 노드 묶음. 여기서는 system·build·exec 셋.
gVisor
컨테이너와 호스트 커널 사이에 끼어 시스템 콜을 대신 받아 주는 격리 런타임. 아래 그림 0-4 에서 다시 설명.

플랫폼 자체(Argo CD, Rollouts, 울타리, 컨트롤 플레인)는 Git 이 정답인 GitOps 로 관리하고, 사용자 함수는 컨트롤 플레인이 쿠버네티스 API 로 직접 만든다. 이 두 갈래가 이 PoC 의 가장 중요한 구조 결정이다. 그 위에 AI 운영 에이전트가 MCP 도구와 좁은 권한의 토큰 하나로 지표를 보고, 스케일을 조정하고, 사람 승인을 받아 롤백한다.

GitOps
원하는 상태를 Git 에 적어 두면 클러스터 안의 에이전트가 그것을 읽어 클러스터를 맞추는 방식. 그 에이전트가 Argo CD 다.
컨트롤 플레인
이 PoC 에서는 함수 배포 API 를 가진 Spring Boot 서비스. 쿠버네티스 자체의 컨트롤 플레인과는 다른 말이다(아래 단락).
MCP(Model Context Protocol)
AI 모델이 외부 도구를 표준 방식으로 부르는 규약. 여기서는 Claude Code 가 MCP 서버 ops_mcp 를 통해 클러스터를 다룬다.

무엇을 만들었나

함수 배포 API, 클러스터 안 빌드, 0↔N 서버리스 실행, 테넌트 격리, 점진 배포와 자동 롤백, AI 운영 도구, 장애 주입 실험, EC2 이전 코드.

왜 이렇게 나눴나

본선(11/7~8)에서 "왜 이 구조인가, 깨지면 어디를 보나" 에 답하려고. 단계마다 결정 3개와 대안, 깨뜨렸다 고치는 실험이 붙어 있다.

이 장 전체에서 계속 쓰는 쿠버네티스 기본 말을 여기서 정해 둔다. 클러스터(cluster)는 노드 여러 대와 그것을 지휘하는 부품을 합친 전체다. 지휘하는 부품은 API 서버, etcd, 스케줄러, 컨트롤러이고, 이 넷을 쿠버네티스의 컨트롤 플레인이라 부른다. 노드마다는 kubelet 과 containerd 가 돈다.

API 서버
모든 요청이 들어오는 하나의 문. 사람의 kubectl 도, 아래 모든 컨트롤러도 여기로 말한다.
etcd
클러스터의 모든 상태를 저장하는 키-값 저장소.
스케줄러
새 파드를 어느 노드에 둘지 고르는 부품.
컨트롤러
원하는 상태와 실제 상태를 비교해 계속 맞추는 루프. 쿠버네티스는 이런 루프의 집합이다.
kubelet
API 서버가 정한 파드를 그 노드에 실제로 띄우고 상태를 보고하는 노드 에이전트.
containerd
kubelet 의 지시로 컨테이너를 실제로 만들고 돌리는 컨테이너 런타임.

사람은 kubectl 명령으로 API 서버에 말하고, 어느 클러스터에 어떤 계정으로 붙을지는 kubeconfig 파일에 적는다. 리소스(resource)는 API 서버에 저장되는 오브젝트 한 장이고, 매니페스트(manifest)는 그것을 적은 YAML 파일이다. 자주 나오는 리소스 셋: Deployment 는 같은 파드를 N 개 유지하며 새 버전으로 굴려 바꾸는 리소스, Service 는 파드가 바뀌어도 변하지 않는 안정된 주소, 라벨(label)은 리소스에 붙이는 키=값 꼬리표로 "어떤 파드" 를 고르는 열쇠다. annotation 은 같은 키=값이지만 고르는 데는 쓰지 않는 메모다. 컨트롤 플레인이라는 말은 이 PoC 에서 두 가지 뜻으로 쓰인다. 방금 말한 쿠버네티스의 것과, 우리가 만든 함수 배포 API 서비스. 이 장에서 그냥 "컨트롤 플레인" 이라 하면 후자다.

Deployment
실제로 N 개를 유지하는 일은 그 아래 ReplicaSet 이 한다. 버전마다 ReplicaSet 이 하나씩 생긴다.

우리 PoC 에서는

단계 번호(PoC 01~07)와 이 가이드의 장 번호(01~09)는 다르다. PoC 는 만든 순서대로, 가이드는 기술 주제별로 나눴다. 예를 들어 PoC 04 단계 하나에 노드 풀, Cilium 재설치, Knative, kaniko, gVisor 가 다 들어 있어서, 가이드에서는 3·4·5·6장으로 쪼개 설명한다. 아래 장 목록의 표가 그 대응이다.

Cilium

전체 아키텍처

한 장으로 보는 구조

장 목록까지가 안내였고, 여기부터가 본문이다. 아래 그림이 이 가이드 전체의 기준 그림이다. 왼쪽 열은 플랫폼을 쓰는 사람과 에이전트(입구), 가운데 점선 영역은 클러스터 안의 플랫폼 부품(우리 플랫폼의 컨트롤 플레인), 그 아래 점선 상자는 노드 풀, 오른쪽 열은 클러스터 밖 저장소, 아래쪽 띠는 차례로 데이터 플레인, 관측, 설계 원칙이다. 선의 종류가 뜻을 가진다: 회색 실선은 API 호출, 보라 점선은 비동기·승인 대기, 주황은 배포·생성, 파랑은 사용자 트래픽, 청록 점선은 관측, 초록은 Git, 빨강 점선은 차단 지점.

데이터 플레인
사용자 요청이 실제로 지나는 길. 지시하는 쪽이 컨트롤 플레인, 실어 나르는 쪽이 데이터 플레인이다.

그림을 읽는 순서를 하나 정해 두면 설명할 때 덜 흔들린다. 사람(왼쪽) → 무엇을 바꾸나(가운데) → 어디에 뜨나(노드 풀) → 사용자는 어떻게 닿나(데이터 플레인) → 어떻게 확인하나(관측). 이 순서는 아래 핵심 흐름의 다섯 시퀀스와 1:1 로 맞는다.

영역별로 무엇을 하나

입구 (왼쪽 열)

사람과 에이전트가 플랫폼에 닿는 길은 네 가지다. 각 길마다 쥔 권한이 다르다는 점이 핵심이다. 플랫폼 운영자는 Git 쓰기 권한과 관리자 kubeconfig 를 갖는다. 함수 개발자는 컨트롤 플레인 API 만 부른다(지금은 인증 없음, 알려진 한계). AI 에이전트는 tenant-a 하나에 묶인 ops-agent ServiceAccount 토큰만 갖고, 롤백은 사람이 터미널에서 승인해야 실행된다. 최종 사용자는 맥 8081 포트로 HTTP 만 보낸다.

관리자 kubeconfig
모든 것을 할 수 있는 cluster-admin 계정이 적힌 접속 파일. kind 가 클러스터를 만들 때 맥에 써 준다.

컨트롤 플레인 (가운데 점선)

쿠버네티스 자체의 컨트롤 플레인(API 서버, etcd, 스케줄러)과 구별해서, 이 영역은 우리 플랫폼의 컨트롤 플레인이다. 무엇을 어디에 몇 개 띄울지 정하고 지시하는 부품들이다. Argo CD 는 Git 을 원하는 상태로 삼아 클러스터를 맞추고, Argo Rollouts 는 그 위에서 새 버전을 조금씩 내보내며(카나리 배포) Prometheus 숫자로 판정한다. Knative Serving 은 함수 하나를 Revision·오토스케일러·주소로 펼친다. 컨트롤 플레인 API(Spring Boot)는 사람 말(함수 이름, 코드)을 쿠버네티스 말(Job, ConfigMap, Knative Service)로 번역하고, 쓸 때는 server-side apply 를 쓴다. Cilium 은 모든 노드의 커널에 eBPF 프로그램을 꽂아 파드 사이 패킷을 나르고 NetworkPolicy 를 강제한다.

Revision
함수 설정(template)이 바뀔 때마다 생기는 불변 스냅샷.
Job
끝나면 멈추는 일회성 파드를 돌리는 리소스.
ConfigMap
설정이나 파일을 담아 파드에 꽂는 리소스.
server-side apply(SSA)
"내가 적은 필드는 이 값" 을 API 서버가 필드 주인별로 기억하며 합치는 쓰기 방식. 같은 리소스를 여러 주체가 나눠 쓸 수 있다.
커널
운영체제의 핵심. 프로세스·메모리·네트워크·파일을 관리한다.
eBPF
커널 안에서 안전하게 도는 작은 프로그램.

노드 풀 (가운데 아래 점선)

kind 노드 4개가 맥 위 Docker 컨테이너로 뜬다. 워커 3대에 pool 라벨을 붙이고, build·exec 두 풀에는 NoSchedule taint 를 걸었다. taint 는 노드가 "이것을 견디는 파드만 와라" 고 거는 표시, toleration 은 파드가 "나는 견딘다" 고 다는 통과증, nodeSelector 는 파드가 "이 라벨 노드로만 가겠다" 는 조건이다. 설치 YAML 을 하나도 고치지 않아도 Argo CD·Knative 같은 플랫폼 파드는 toleration 이 없으니 taint 없는 system 노드로만 간다. 빌드 Job 과 함수 파드만 toleration 과 nodeSelector 를 둘 다 달고 자기 풀로 들어간다.

저장소 (오른쪽 열)

클러스터 밖에 있지만 클러스터가 기대는 것들. GitHub 의 main 브랜치는 플랫폼의 정답 원천이고, kind-registry 는 클러스터 안에서 빌드한 함수 이미지를 올리고(push) 받는(pull) 저장소다. 같은 레지스트리를 파드(kaniko)는 kind-registry:5000, 노드(containerd)는 localhost:5001 로 부르고, 노드 설정 hosts.toml 이 두 이름을 같은 곳으로 돌린다. 함수의 이력은 Git 이 아니라 Knative Revision 과 감사 로그에 남는다.

데이터 플레인 (파란 띠)

맥 8081 → kind 의 extraPortMappings → control-plane 노드의 NodePort 31080 → Kourier. Kourier 는 HTTP Host 헤더 <함수>.<namespace>.faas.local 로 어느 함수인지 고른다. 파드가 있으면 바로 파드의 queue-proxy(8012) → 사용자 컨테이너(8080). 파드가 0개면 activator 가 요청을 붙잡고 autoscaler 에 수요를 알리고, 파드가 준비되면 넘긴다. 이 0→1 구간이 콜드 스타트다. tenant-a 파드로 들어가는 순간 Cilium 이 NetworkPolicy 를 검사한다.

extraPortMappings
노드 컨테이너의 포트를 맥 포트에 묶는 kind 설정.
NodePort
모든 노드의 같은 포트를 열어 바깥에서 Service 로 들어오게 하는 방식.
Kourier
Knative 의 입구 역할을 하는 Envoy 프록시.
queue-proxy
Knative 가 함수 컨테이너 옆에 끼워 넣는 작은 프록시. 동시 요청 수를 센다.
activator
파드가 없을 때 대신 요청을 받아 붙잡아 두는 Knative 부품.
autoscaler
동시 요청 수를 보고 파드 수를 정하는 Knative 부품.

관측과 설계 원칙 (아래 두 띠)

관측 띠는 "무슨 일이 일어났나" 를 볼 곳 여섯 가지다. 같은 사건을 서로 다른 눈으로 본다: Prometheus(숫자), Hubble(패킷 흐름), Argo CD(Git 과의 차이), kubectl(쿠버네티스 상태), 감사 로그(누가 무엇을 했나), 합성 프로브(사용자가 겪은 것). 설계 원칙 띠는 결정 여섯 개를 한 문장씩 줄인 것이다. 본선 발표에서 그대로 말할 수 있게 썼다.

합성 프로브
정해진 주기로 함수를 불러 성공·실패를 기록하는 스크립트. 사용자가 실제로 겪은 것의 대리.

같은 구조를 층으로 쌓으면

그림 0-3 은 "누가 누구를 부르나" 를 보여 준다. 그림 0-4 는 같은 구성 요소를 "무엇이 무엇 위에 서 있나" 로 다시 쌓았다. 장애를 추적할 때는 이 그림을 아래에서 위로 훑는다: 맥의 Docker 메모리가 모자라면 노드 컨테이너가 흔들리고, 그러면 kubelet 이, 그러면 API 서버가 보는 노드 상태가, 결국 맨 위 함수 응답이 흔들린다.

RuntimeClass
파드가 어느 컨테이너 런타임으로 돌지 고르는 쿠버네티스 리소스.
runc
호스트 커널을 그대로 쓰는 기본 컨테이너 런타임.
runsc
gVisor 의 런타임. RuntimeClass gvisor 의 handler 이름.
시스템 콜(syscall)
프로그램이 파일 열기·소켓 보내기처럼 커널 기능을 부르는 호출.

맥에서 클러스터로 들어가는 문

로컬 PoC 에서 맥과 클러스터를 잇는 문은 다섯 개다. 그중 둘은 port-forward 다. 포트 번호가 겹치면 엉뚱한 곳으로 가므로 컨트롤 플레인은 8090 으로 연다. run-all.sh 의 CP_PORT 기본값이고 05 README 의 port-forward 명령도 같은 값이다. 05 README 에 나오는 8080 은 맥에서 mvn spring-boot:run 으로 컨트롤 플레인을 직접 띄울 때의 포트라, 그때 Argo CD UI port-forward 를 같이 열면 겹친다.

port-forward
kubectl 이 맥의 포트를 클러스터 안 Service 로 터널링하는 명령. 터미널을 닫으면 끊긴다.

두 갈래: GitOps 와 API

앞 절의 그림 0-3 에서 가운데 영역으로 들어오는 선이 두 종류였다. 위에서 오는 초록(Git)과 왼쪽에서 오는 회색(API). 이 절은 그 두 선이 왜 따로 있는지다.

무엇이 Git 으로 가고 무엇이 API 로 가나

이 PoC 에는 클러스터를 바꾸는 길이 둘 있다. 플랫폼 변경(Argo CD 설정, Rollouts, 테넌트 울타리, 컨트롤 플레인 자체)은 Git 에 YAML 을 쓰고 push 하면 Argo CD 가 pull 방식으로 끌어와 맞춘다. 사용자 함수는 컨트롤 플레인이 받아서 쿠버네티스 API 로 직접 만든다. 둘은 tenant-a namespace 에서 만난다: 울타리는 Git 이, 그 안의 함수는 API 가 만든다.

pull 방식
클러스터 안의 Argo CD 가 스스로 Git 을 읽어 오는 것. CI 서버가 바깥에서 클러스터에 밀어 넣는 push 방식의 반대.

왜 함수는 Git 을 거치지 않나

05 README 결정 1 의 요지다. 함수도 GitOps 로 보내는 대안(컨트롤 플레인이 매니페스트를 Git 에 커밋 → Argo CD 가 반영)은 이력과 롤백이 Git 으로 공짜라는 장점이 있다. 그래도 버린 이유는 네 가지다.

  1. 속도: 배포마다 커밋 → push → Argo CD 감지(폴링 최대 120 + 60초, 또는 refresh) → sync 가 더해진다. "Instantly" 와 멀어진다.
  2. 권한: 컨트롤 플레인에 Git 쓰기 토큰이 들어가야 한다. 플랫폼 레포에 쓸 수 있는 토큰은 플랫폼 전체를 바꿀 수 있다.
  3. 레포 오염: 사용자 함수(런타임 데이터)가 플랫폼 설정 레포를 커밋으로 채운다.
  4. selfHeal 충돌: 에이전트가 min-scale 을 patch 하면 Argo CD 의 selfHeal 이 되돌린다.
min-scale
파드 수 하한을 적는 Knative annotation. 에이전트의 scale 도구가 바꾸는 값이다.
selfHeal
Git 과 다르게 손으로 바꾼 것(드리프트)을 Git 대로 되돌리는 Argo CD 옵션.

대가도 분명하다. 함수 이력이 Git 에 없으니 클러스터를 통째로 다시 만들면 함수는 다시 배포해야 한다(05 알려진 한계 3). 컨트롤 플레인 자체는 여전히 GitOps(platform-05 Application)로 깔린다는 점이 중요하다: "누가 함수를 만들 수 있나" 를 정하는 RBAC 는 Git 에 있다.

변경 하나가 들어오면:
  만약 플랫폼의 모양을 바꾸는 것이면 (울타리, 부품 설정, 권한, 컨트롤 플레인 이미지 태그):
      Git 에 YAML 로 적고 push   // 리뷰 · 이력 · 되돌리기를 Git 이 준다
      Argo CD 가 폴링으로 알아채 sync, selfHeal 이 손 변경을 되돌림
  아니면 사용자가 올린 런타임 데이터면 (함수 코드, 함수 스케일):
      컨트롤 플레인이 검사 → 빌드 → digest → server-side apply   // 빠름, 사람 말 → 쿠버네티스 말
      이력은 Revision + 감사 로그, 롤백은 traffic 전환

왜 이걸 골랐나 (대안)

(가) 전부 GitOps: 함수 배포가 느리고 Git 토큰이 컨트롤 플레인에 들어간다. (나) 전부 API(kubectl apply 스크립트): 드리프트를 못 잡고 클러스터 재생성 때 무엇을 다시 깔아야 하는지 사람 기억에 의존한다. (다) 두 갈래(선택): 바뀌는 속도와 주인이 다른 것을 다른 길로 보낸다. 본선에서 "왜 GitOps 를 쓰면서 함수는 API 로?" 라는 질문에 이 네 가지 이유로 답한다.

Argo CD Application 나무

Application 은 10개(root, hello-fn, bye-fn, podinfo, tenant-a, tenant-b, tenant-a-hello, tenant-b-hello, faas-functions, platform-05), ApplicationSet 은 1개(tenants)다. 사람이나 스크립트가 kubectl apply 로 직접 붙인 것은 Application 6개 + ApplicationSet 1개 = 7개이고, 나머지 Application 4개는 Argo CD 자신이 Git 을 읽고 만든다(App of Apps 가 2개, ApplicationSet 이 2개).

프로젝트(AppProject)도 같이 기억한다. 울타리를 까는 tenant-a·tenant-b Application 은 default 프로젝트(어디든 무엇이든)로, 테넌트의 함수 Application(tenant-a-hello)은 tenant-a 프로젝트로 돈다. tenant-a 프로젝트는 목적지를 tenant-a namespace 하나로 묶고 ResourceQuota·LimitRange·NetworkPolicy·CiliumNetworkPolicy·Role·RoleBinding 을 금지 목록에 넣었다. 그래서 테넌트가 Git 으로 자기 울타리를 지우려 해도 Argo CD 가 거절한다.

함수 하나는 쿠버네티스 오브젝트 몇 개인가

컨트롤 플레인이 만드는 것은 Knative Service(ksvc) 한 장이다. 나머지는 Knative 컨트롤러가 펼친다. 상태 조회, 롤백, 스케일 조정이 각각 어느 오브젝트를 건드리는지 알려면 이 나무를 알아야 한다.

컨트롤 플레인이 함수에 붙이는 표지: ksvc 라벨 faas.poc/tenant, faas.poc/function, app.kubernetes.io/managed-by: faas-control-plane, template annotation faas.poc/build-id. 상태 조회는 이 build-id 와 가장 최근 빌드 Job 의 build-id 를 비교해 "아직 DEPLOYING 인가" 를 판단한다.

깨지면 이렇게 보인다

  • Application 이 Synced(Git 과 같음)인데 Degraded(잘 안 돎): Git 대로 깔았지만 파드가 안 뜬다(이미지 이름, Pending). kubectl -n argocd describe application <이름> 의 마지막 20줄.
  • tenant-a 가 오래 안 생김: ApplicationSet 이 Git 을 읽는 데 약 3분 걸릴 수 있다(폴링). 급하면 kubectl -n argocd annotate applicationset tenants argocd.argoproj.io/application-set-refresh=true (RUN-ALL.md 4절 4번. ApplicationSet 은 Application 의 argocd.argoproj.io/refresh 와 주석 이름이 다르다).
  • tenant-a-hello 가 sync 거절: tenant-a AppProject 의 금지 목록에 걸리는 종류를 넣었거나, 목적지가 tenant-a 가 아니다.
  • faas-functions 만 Degraded: 대개 hello-gvisor 가 안 뜬다. Docker Desktop 에서 gVisor 가 안 도는 경우 (04 README "9절 보충").

여기까지가 "무엇이 어디에 있나" 였다. 이제 그 부품들이 실제로 어떤 순서로 서로를 부르는지 본다. 이 플랫폼을 설명할 때 반드시 나오는 요청 다섯 가지를 시퀀스 다이어그램으로 따라간다. 화살표 하나하나가 "여기가 끊기면 어떤 증상이 나나" 의 후보다. ANALYSIS.md 2절의 네 가지에 노드 장애(06)를 더했다.

흐름 1. 함수 배포 (poc/05 · 7장)

개발자가 코드를 보내면 1초 안에 HTTP 202 Accepted 를 받고, 그 뒤 상태를 몇 번 물어보다 READY 와 URL 을 받는다. 그 사이 클러스터 안에서 빌드 Job, digest, Knative Service 가 차례로 생긴다.

202 Accepted

흐름 3. git push → 클러스터 반영 (poc/01 · 1장)

플랫폼 운영자는 클러스터를 직접 만지지 않는다. Git 을 고치면 Argo CD 가 폴링으로 알아채서 맞춘다. 반대로 누가 클러스터를 손으로 고치면 Argo CD 가 Git 쪽으로 되돌린다. Argo CD 는 안에서 두 부품으로 일한다: repo-server(Git 을 받아 매니페스트로 렌더)와 application-controller(렌더 결과를 클러스터와 비교해 apply).

흐름 4. 나쁜 버전 배포와 자동 롤백 (poc/02 · 2장)

나쁜 버전이 Git 에 들어가도 사용자 전체가 맞지 않는다. Rollouts 가 파드 5개 중 1개만 새 버전으로 바꾸고, Prometheus 숫자가 나쁘면 사람 없이 멈춘다. 클러스터는 안전해지지만 Git 은 여전히 나쁜 상태라서, 마지막 정리는 git revert 다.

sequenceDiagram
  participant O as 플랫폼 운영자
  participant AC as Argo CD
  participant RO as Rollouts 컨트롤러
  participant RS as ReplicaSet stable과 canary
  participant AR as AnalysisRun
  participant PR as Prometheus
  O->>AC: git push (나쁜 이미지 또는 설정)
  AC->>RO: Rollout spec 변경 sync
  RO->>RS: canary ReplicaSet 1개 (setWeight 20, 5개 중 1개)
  RO->>AR: AnalysisRun 시작 (startingStep 1, canary-hash 인자)
  loop initialDelay 30초 뒤부터 15초마다
    AR->>PR: 카나리 파드만의 2xx 비율 (최근 1분 rate)
    PR-->>AR: 결과 값 또는 결과 없음
  end
  alt 0.95 이상이 계속
    RO->>RS: setWeight 60, 그다음 100, stable 교체
  else 0.95 미만이 failureLimit 1 을 넘음, 또는 질의 실패가 연속
    AR-->>RO: Failed 또는 Error
    RO->>RS: abort, canary 0개, stable 100%
    AC-->>O: Synced 그러나 Degraded
    O->>AC: git revert 로 Git 을 안전한 버전으로
  end
  1. 비율 = 파드 수: 트래픽 라우터 없이 Rollouts 는 파드 수로 비율을 흉내 낸다. replicas 5, setWeight 20 → canary 1 + stable 4. Service 가 두 종류 파드를 고르게 부르니 약 20% 가 카나리로 간다.
  2. 카나리만 재기: 파드 라벨 rollouts-pod-template-hash 를 Prometheus 가 지표 라벨 rollouts_pod_template_hash 로 복사한다. AnalysisTemplate 은 이 값(podTemplateHashValue: Latest)으로 카나리 파드만 고른다. path="root" 로 헬스체크를 뺀다.
  3. 판정 네 가지: Successful(계속), Failed(failureLimit 초과 → abort), Error(질의 실패가 consecutiveErrorLimit 4 초과 → abort), Inconclusive(pause). 질의 주소가 틀려도 abort 되는 것이 fail-closed.
  4. 부하가 필요한 이유: 요청이 0 이면 rate 가 0/0 = NaN → 판정 불가. 그래서 scripts/load.sh 로 클러스터 안에서 계속 부른다.
  5. GitOps 와의 엇갈림: abort 뒤 클러스터는 stable 100% 지만 Rollout spec 은 Git 의 나쁜 버전 그대로다. Argo CD 는 Synced + Degraded 로 보인다. kubectl argo rollouts undo 로 고치면 selfHeal 이 Git 상태로 다시 바꾼다. 그래서 Git 을 고친다.
트래픽 라우터
Istio 나 NGINX 인그레스처럼 요청을 비율로 나눠 주는 장치. Rollouts 는 있으면 쓰고, 없으면 파드 수로 흉내 낸다.

흐름 5. 노드 장애와 복구 (poc/06 · 8장)

대역 클러스터 chaos 의 exec 노드 하나를 docker pause 로 얼린다. 쿠버네티스는 하트비트가 끊긴 지 일정 시간이 지나야 노드를 NotReady 로 보고, 그때부터 그 노드 파드를 Service 에서 빼고, 다시 일정 시간 뒤 다른 노드로 옮긴다. 방어 설정(tolerationSeconds 20, 파드를 노드마다 흩어 놓기, PDB)은 이 두 번째 시간을 줄이고 첫 번째 시간의 피해를 나눈다.

PDB(PodDisruptionBudget)
drain 같은 자발적 중단 때 최소 몇 개는 남겨 두라는 약속. 여기선 minAvailable 1.
sequenceDiagram
  participant S as s1-node-down.sh
  participant N as exec 노드
  participant NL as 노드 수명 컨트롤러
  participant EP as EndpointSlice
  participant RS as ReplicaSet과 스케줄러
  participant PM as Prometheus 알림
  participant PB as 합성 프로브
  S->>N: docker pause (t0)
  PB->>N: 그 노드 파드로 간 요청은 응답 없음
  N--xNL: kubelet Lease 하트비트 끊김
  Note over NL: node-monitor-grace-period 기본 50초
  NL->>N: Ready Unknown, taint unreachable NoExecute
  NL->>EP: 그 노드 파드 Ready False, 엔드포인트에서 빠짐
  PB->>EP: 남은 파드로 요청 성공
  PM-->>S: FnNodeNotReady firing
  Note over NL,RS: tolerationSeconds 20 (방어 후, 기본 300)
  NL->>RS: 파드 축출
  RS->>RS: 다른 exec 노드에 새 파드 (DoNotSchedule, nodeTaintsPolicy Honor)
  S->>N: docker unpause, uncordon, CSV 한 줄
  1. 감지까지: kubelet 은 kube-node-lease namespace 의 Lease 를 주기적으로(기본 10초마다) 갱신한다. kube-controller-manager 의 --node-monitor-grace-period(기본 50초) 동안 갱신이 없으면 노드 Ready=Unknown. 이 50초 동안 그 노드 파드로 간 요청은 응답이 없다.
  2. Service 에서 빠짐: NotReady 가 되면 그 노드 파드들이 Ready=False 로 표시되고 EndpointSlice 에서 빠진다. 프로브 에러가 이 순간 멈춘다. "NotReady 가 Service 를 고친다" 는 이 뜻이다.
  3. 옮기기: 노드에 node.kubernetes.io/unreachable:NoExecute taint. 파드는 이 taint 를 기본 300초 견딘다(DefaultTolerationSeconds). 06 방어는 이를 20초로 줄였다.
  4. 어디로: topologySpreadConstraints(maxSkew 1, DoNotSchedule, nodeTaintsPolicy Honor, matchLabelKeys pod-template-hash)가 평소엔 파드를 노드마다 흩고, 노드가 죽으면 죽은 노드를 계산에서 빼서 새 파드가 산 노드에 뜰 수 있게 한다.
  5. 스팟 모드: spot 은 2분 예고를 흉내 내 cordon + drain 뒤 멈춘다. drain 은 PDB(여기선 minAvailable 1)를 지킨다. PDB 를 2 로 너무 세게 하면 drain 이 안 끝나 예고 없는 장애와 같아진다(06 README 4.4).
Lease
kubelet 이 주기적으로 갱신하는 하트비트용 작은 리소스.
kube-controller-manager
쿠버네티스의 여러 컨트롤러를 묶어 돌리는 컨트롤 플레인 프로세스.
EndpointSlice
Service 뒤에 지금 붙어 있는 파드 주소 목록.
topologySpreadConstraints
파드를 노드·존마다 고르게 흩는 규칙. maxSkew 가 허용하는 치우침, whenUnsatisfiable 이 못 지킬 때의 행동이다.
cordon
노드에 새 파드 배치를 금지하는 것.
drain
노드에 있는 파드를 PDB 를 지키며 다른 노드로 내보내는 것.

함수의 일생

컨트롤 플레인의 상태 조회가 돌려주는 phase 는 여섯 가지다. 바깥 상태는 "빌드와 배포" 를, READY 안쪽 상태는 Knative 가 하는 "0개와 N개 사이" 를 나타낸다. 상태 조회는 상태를 저장하지 않고 매번 Job 과 ksvc 를 읽어 계산한다는 점이 중요하다(그래서 컨트롤 플레인이 재시작해도 조회는 맞다).

상태 계산 의사코드와 엣지 케이스

함수 상태(tenant, name):
  job  = faas-build 에서 라벨 tenant·function 이 맞는 Job 중 가장 최근
  ksvc = tenant namespace 의 Knative Service name
  만약 job 없음 그리고 ksvc 없음: 반환 NOT_FOUND (HTTP 404)
  만약 job 있음 그리고 끝나지 않음: 반환 BUILDING
  만약 job 있음 그리고 실패: 반환 BUILD_FAILED (+ kubectl logs 힌트)
  만약 ksvc 없음 또는 ksvc.template.annotation[build-id] ≠ job.build-id:
      반환 DEPLOYING          // 백그라운드가 apply 하기 직전 (또는 영영 못 한 경우)
  ready = ksvc.status.conditions[Ready]
  반환 True → READY, False → FAILED, 그 밖 → DEPLOYING
  • 컨트롤 플레인이 빌드 중에 죽으면: Job 은 끝나지만 기다리던 가상 스레드가 사라져 ksvc 가 안 생긴다. 상태는 영원히 DEPLOYING (05 알려진 한계 1, ANALYSIS B10). 고치는 설계: 시작할 때 "끝났는데 반영 안 된 Job" 을 찾아 이어 하기, 또는 오퍼레이터로 바꿔 reconcile 루프에 맡기기.
  • 빌드가 오래 걸리면: 처음엔 application.yml 의 build-timeout: 5m 이 Job 의 activeDeadlineSeconds: 600 보다 짧아서, 5~10분 사이에 끝나는 빌드는 기다림이 먼저 끝나 DEPLOYING 에 고착될 수 있었다. 지금은 11m 으로 고쳐서 쿠버네티스가 먼저 Job 을 끝내고 컨트롤 플레인이 그 결과를 읽는다 (7장).
  • tenant-b 로 배포하면: tenant-b 도 tenant=tenant-b 라벨이 있어 404 를 통과하고, faas-build 의 Job 생성도 된다. 그러나 컨트롤 플레인의 ksvc 권한 RoleBinding 이 tenant-a 에만 있어 백그라운드 apply 에서 403 이 나고, 상태 조회는 Job 성공 + ksvc 없음이라 DEPLOYING 에 머물 것이다 【확인 필요: 실제 클러스터 미검증. scripts/deploy-fn.sh tenant-b hello samples/hello-v1.py 를 돌려 컨트롤 플레인 로그의 AUDIT deploy.apply 줄에 403 이 찍히는지 보면 확정된다】. 테넌트 추가 때 k8s/platform/control-plane/tenant-*.yaml 도 같이 늘려야 한다.

클러스터가 자라는 모양

왜 최종 모양 클러스터 하나인가

각 단계는 만들 때 자기에게 필요한 만큼의 클러스터를 썼다. 01 은 워커 1대 + kindnet, 03 은 Cilium + 워커 3대, 04 는 여기에 노드 풀 taint, 8081 포트, containerd 레지스트리 설정을 더했다. 03·04 로 넘어갈 때마다 클러스터를 다시 만들었으니 순서대로 따라 하면 앞에서 깐 것이 사라진다. run-all.sh 는 이 문제를 "가장 나중 모양을 먼저 만든다" 로 푼다. 앞 단계 부품은 새 모양에서도 돈다(예: podinfo 는 taint 없는 system 풀 노드로 간다).

단계 README 순서:  01(클러스터 A) → 02(A 위에) → 03(A 삭제, B 생성) → 04(B 삭제, C 생성) → 05(C 위에)
                    // 02 의 Rollouts·Prometheus 는 03 에서 사라짐
run-all 순서:      C 생성 → 01 → 04 → 02 → 03 → 05   // 클러스터는 한 번만
조건:              뒤 단계 부품이 앞 단계 부품에 기대지 않는다 (Argo CD 만 예외: 제일 먼저)

왜 이걸 골랐나 (대안)

대안 1은 "단계마다 클러스터를 따로" 다. 깔끔하지만 맥 메모리가 버티지 못하고, 02 의 카나리와 05 의 함수 배포를 한 화면에서 볼 수 없다. 대안 2는 "전부 Argo CD 로" 다. Helm 두 개와 Application 4개까지 root 아래에 넣으면 run-all 이 더 짧아지지만, 단계 README 가 가르치는 "손으로 붙여 보기" 가 사라진다. 지금 모양은 학습 순서와 실행 순서를 분리한 타협이다.

권한의 "모양"(ksvc get·list·create·patch)은 ClusterRole 로 한 번 정의하고, 쓸 수 있는 곳은 테넌트마다 RoleBinding 한 장씩 연다. kube-system 에는 RoleBinding 이 없으니 컨트롤 플레인 코드에 버그가 있어도(예: tenant 라벨 검사를 건너뜀) 거기에 ksvc 를 못 만든다. 파일 주석이 스스로 말하듯, 이 RoleBinding 을 03 의 tenant 차트로 옮기면 테넌트가 늘 때 손댈 곳이 없어진다(지금은 tenant-a 하나뿐).

  • namespace 는 get 만: tenantExists 는 이름으로 하나만 읽는다. list 를 주면 모든 테넌트 이름이 보이므로 주지 않는다.
  • ConfigMap delete 없음: 지우는 일은 Job 의 ownerReference 를 보고 쓰레기 수집기(garbage collector)가 한다.
  • 에이전트 토큰은 짧게: make-agent-kubeconfig.sh 가 kubectl create token ops-agent --duration=8h 로 만든다. 이 명령이 부르는 것이 TokenRequest API 다. 시간이 지나면 저절로 무효다.
  • X-Actor 는 신뢰하지 않는다: 컨트롤 플레인 API 의 X-Actor 헤더(기본 anonymous)는 감사 로그에 쓰일 뿐 인증이 아니다. 본선 설계에서는 API 게이트웨이의 OIDC 토큰에서 테넌트와 사용자를 꺼내야 한다.
  • Argo CD 컨트롤러의 권한: Helm 차트 10.10.5 의 기본값(createClusterRoles: true, controller.clusterRoleRules.enabled: false)은 application-controller 에 모든 apiGroup·리소스·동사가 * 인 ClusterRole 을 준다. 그래서 테넌트 경계는 AppProject(대상 ns·리소스 종류 제한)가 지킨다. 줄이려면 controller.clusterRoleRules.rules 에 직접 적어야 하는데 이 PoC 는 하지 않았다.
TokenRequest API
ServiceAccount 의 짧게 사는 토큰을 발급하는 쿠버네티스 API.

우리 PoC 에서는

깨지면 이렇게 보인다

  • 에이전트가 다른 테넌트를 건드림: 있어서는 안 된다. 범위 고정(1겹)은 코드라 버그로 뚫릴 수 있어도 RBAC(2겹)는 뚫리지 않아야 한다. 일어났다면 MCP 서버가 ops-agent 토큰이 아니라 관리자 kubeconfig 를 쓰고 있다(OPS_MCP_KUBECONFIG 미설정). 2겹이 사라진 것이다.

  • tenant-a → tenant-b curl 이 성공함: NetworkPolicy 가 적용 안 된 것이다. kubectl -n tenant-b get networkpolicy 로 default-deny 가 있는지, cilium status 로 Cilium agent 가 모든 노드에 떠 있는지 본다. 01 의 kind-config(kindnet)로 만든 클러스터면 Cilium 자체가 없다.

왜 이걸 골랐나 (대안)

EKS 는 관리형 컨트롤 플레인 비용(시간당 과금)이 PoC 예산($5 알람)을 바로 넘는다. kubeadm 은 설치 단계가 많다. k3s 는 바이너리 하나와 설정 YAML 로 서버·에이전트가 붙고, Terraform 의 user_data 한 장으로 끝난다. 본선에서 "왜 EKS 가 아니냐" 는 질문에는 "비용과 학습 범위. 노드 풀·스팟·taint 설계는 EKS managed node group 으로 그대로 옮겨진다" 가 답이다.

쿠버네티스 기본

컨테이너 (container)
프로그램과 그 실행 환경을 한 묶음으로 격리해 돌리는 단위. 이미지(image)는 그 묶음을 담은 파일이고, 레지스트리(registry)는 이미지를 올리고(push) 받는(pull) 저장소다. 6장
클러스터 / 노드 (node)
노드는 파드가 실제로 도는 서버 한 대, 클러스터는 노드들과 그것을 지휘하는 컨트롤 플레인을 합친 전체. kind 에선 노드 하나가 Docker 컨테이너 하나. 3장
파드 (Pod)
쿠버네티스가 컨테이너를 띄우는 최소 단위. 같은 노드에서 함께 뜨는 컨테이너 한두 개(예: 함수 + queue-proxy)를 묶는다. 5장
API 서버 · etcd · 스케줄러 · 컨트롤러
쿠버네티스의 컨트롤 플레인. 모든 요청이 들어오는 문, 상태 저장소, 파드의 자리 고르기, 원하는 상태와 실제를 계속 맞추는 루프. 3장
kubelet · containerd
노드마다 도는 에이전트(파드를 실제로 띄우고 상태를 보고)와 컨테이너 런타임(컨테이너를 실제로 만들고 돌림). kubelet 의 하트비트가 끊기면 노드 장애가 시작된다. 8장
Deployment / ReplicaSet
같은 파드를 N 개 유지하며 새 버전으로 굴려 바꾸는 리소스와, 그 아래에서 실제로 N 개를 유지하는 리소스(버전마다 하나). Rollout 은 Deployment 의 자리에 들어가는 대체품. 2장
Service / EndpointSlice
파드가 바뀌어도 변하지 않는 안정된 주소와, 그 뒤에 지금 붙어 있는 파드 주소 목록. 파드가 NotReady 면 목록에서 빠진다. 8장
Job / ConfigMap
끝나면 멈추는 일회성 파드를 돌리는 리소스(빌드)와, 설정이나 파일을 담아 파드에 꽂는 리소스(함수 소스). 7장
라벨 (label) / annotation
리소스에 붙이는 키=값. 라벨은 "어떤 파드" 를 고르는 열쇠(Service, NetworkPolicy, 스케줄링), annotation 은 고르기에 쓰지 않는 메모(min-scale, build-id). 3장
kubectl / kubeconfig / 매니페스트
API 서버에 말하는 명령, 어느 클러스터에 어떤 계정으로 붙을지 적은 파일, 리소스를 적은 YAML. 1장
커널 / 시스템 콜 (syscall)
운영체제의 핵심(프로세스·메모리·네트워크·파일 관리)과, 프로그램이 그 기능을 부르는 호출. 컨테이너는 호스트 커널을 공유하므로 gVisor 가 시스템 콜을 가로채 격리한다. 6장

GitOps 와 배포

GitOps
클러스터의 원하는 상태를 Git 에 두고, 클러스터 안의 에이전트가 Git 을 읽어 맞추는 방식. 사람은 클러스터 대신 Git 을 고친다. 1장
Argo CD
GitOps 에이전트. Git 을 폴링해 렌더하고, 클러스터와 비교해 apply 한다. 이 PoC 는 Helm 차트 10.10.5(v3.5.5). 1장
Application
Argo CD 의 기본 단위. "이 레포의 이 폴더를 이 클러스터의 이 namespace 에" 라는 한 장짜리 약속. 최종 클러스터에 10개. 1장
App of Apps
Application 들을 담은 폴더를 가리키는 Application(root). 폴더에 YAML 을 더하고 push 하면 새 Application 이 생긴다. 1장
ApplicationSet
생성기(generator)로 Application 을 찍어 내는 틀. 03 은 Git files generator 로 tenants/*.yaml 하나마다 Application 하나. 3장
AppProject
Application 묶음의 울타리. 갈 수 있는 namespace, 만들 수 없는 리소스 종류를 정한다. 테넌트 project 는 자기 ns 만, Quota·NetworkPolicy·RBAC 금지. 3장
Sync 상태 (Synced / OutOfSync)
Git 과 클러스터가 같은가. 비교를 못 하면 Unknown. Health 와 따로 본다. 1장
Health 상태 (Healthy / Progressing / Degraded)
리소스가 잘 도는가. Healthy·Progressing·Degraded 외에 Suspended(일시 중지)·Missing(없음)·Unknown 이 있다. 카나리 abort 뒤에는 Synced + Degraded 가 된다. 2장
자동 치유 (selfHeal)
누가 클러스터를 손으로 바꾸면 Argo CD 가 Git 상태로 되돌리는 옵션. 1장
정리 (prune)
Git 에서 지운 리소스를 클러스터에서도 지우는 옵션. 1장
폴링 주기 (timeout.reconciliation)
Argo CD 가 Git 을 다시 보는 간격. 이 PoC 는 120초 + jitter 60초. 1장
Helm
템플릿 + values 로 매니페스트를 만드는 패키지 도구. Argo CD 는 helm template 으로만 쓴다. 1장
valuesObject
Application 안에 Helm values 를 직접 적는 필드. bye-fn 이 hello-fn 차트를 메시지만 바꿔 재사용한다. 1장
Argo Rollouts
Deployment 대신 Rollout 리소스로 카나리·블루그린을 하는 컨트롤러. v1.10.1. 2장
카나리 (canary)
새 버전을 일부에만 먼저 보내 보고 넓히는 배포. podinfo 는 20% → 60% → 100%. 2장
setWeight / pause
Rollout 단계. 트래픽 라우터가 없으면 비율을 파드 수로 흉내 낸다. 2장
AnalysisTemplate / AnalysisRun
"무엇을 재서 어떻게 판정하나" 의 틀과 그 실행. 성공률 0.95 미만이면 Failed. 2장
abort
분석이 실패하면 카나리를 0 으로 줄이고 stable 로 돌아가는 것. Git 은 그대로라 revert 가 따로 필요하다. 2장
fail-closed
판단이 불가능하면(질의 오류) 안전한 쪽(멈춤)을 고르는 설계. 2장
Prometheus
지표를 긁어 모으고(scrape) PromQL 로 묻는 시계열 DB. 10초마다 긁는다. 2장
pod-template-hash
Deployment 가 만든 ReplicaSet 마다 다른 파드 라벨. Rollout 은 같은 역할의 rollouts-pod-template-hash 를 쓴다. 02 는 후자로 카나리 파드만 골라 재고, 06 은 전자를 흩어 놓기 기준(matchLabelKeys)으로 쓴다. 2장

테넌트와 네트워크

멀티테넌시 (multi-tenancy)
한 클러스터를 여러 고객(테넌트)이 서로 모른 채 나눠 쓰는 것. 이 PoC 는 namespace 하나 = 테넌트 하나. 3장
namespace
이름과 권한을 나누는 칸. 패킷과 CPU 는 나누지 않는다. 그래서 울타리 리소스가 더 필요하다. 3장
tenant 차트
03 의 Helm 차트. namespace, ResourceQuota, LimitRange, NetworkPolicy, RBAC, AppProject 를 한 번에 만든다. 3장
ResourceQuota
namespace 전체의 CPU·메모리·파드 수 한도. tenant-a 는 파드 10, tenant-b 는 5. 3장
LimitRange
컨테이너 하나의 기본값과 상한. requests 를 안 적은 파드도 Quota 계산에 들어가게 해 준다. 3장
PSA (Pod Security Admission)
namespace 라벨로 파드 보안 수준(privileged·baseline·restricted)을 강제하는 기본 기능. 테넌트는 baseline 강제 + restricted 경고. 3장
RBAC
Role·ClusterRole(권한 목록)과 RoleBinding·ClusterRoleBinding(누구에게, 어디서). 이 PoC 의 "진짜 벽". 3장
ServiceAccount
파드나 프로그램이 API 서버에 쓰는 계정. control-plane, ops-agent, deployer. 7장
노드 풀 (node pool)
같은 역할의 노드 묶음. 라벨 pool=system|build|exec. 3장
taint / toleration
노드가 "이것을 견디는 파드만 와라" 고 거는 표시와, 파드가 "견딘다" 고 다는 표시. 3장
nodeSelector
파드가 "이 라벨 노드로만" 가겠다는 조건. toleration 과 짝을 이뤄야 풀에 고정된다. 3장
NetworkPolicy
파드 사이 연결을 라벨로 허용하는 규칙. 아무것도 없으면 전부 허용, 하나라도 고르면 그 파드는 허용 목록만(들어오는 ingress 와 나가는 egress 방향별로 따로). 4장
default-deny
모든 파드를 고르고 허용 규칙은 비운 정책. 그 위에 같은 ns · DNS · 플랫폼 ns 허용을 쌓는다. 4장
allow-from-namespaces
tenant-a 에서 knative-serving·kourier-system 출발 연결을 여는 정책. 없으면 "READY 인데 타임아웃". 4장
CNI (Container Network Interface)
노드에 파드 네트워크를 꽂는 플러그인 표준과 그 구현(kindnet, Cilium, flannel). NetworkPolicy 집행도 CNI 구현의 일이다. kind 기본 kindnet 도 kind v0.24 부터 표준 NetworkPolicy 를 집행한다(kube-network-policies 내장). Cilium 을 고른 이유는 집행 여부가 아니라 Hubble 관측과 L7 정책이다. 4장
Cilium
eBPF 기반 CNI. 정책을 커널에서 집행한다. 1.20.3. 4장
eBPF
커널 안에서 안전하게 도는 작은 프로그램. Cilium 이 패킷 경로에 붙인다. 4장
Hubble
Cilium 의 흐름 관찰 도구. hubble observe --verdict DROPPED 로 막힌 패킷을 본다. 4장
Kourier
Knative 용 가벼운 인그레스(Envoy). Host 헤더로 함수를 고른다. 4장
Host 헤더 라우팅
같은 IP·포트로 들어와도 Host 값(hello.tenant-a.faas.local)으로 대상을 고르는 것. 4장
NodePort
모든 노드의 같은 포트로 Service 를 여는 방식. Kourier 는 31080. 4장
extraPortMappings
kind 노드 컨테이너의 포트를 맥 포트에 묶는 설정. 맥 8081 → 31080. 4장

서버리스, 빌드, 런타임

FaaS (Function as a Service)
코드 조각만 올리면 플랫폼이 빌드·배포·확장·축소를 맡는 서비스 모양. 5장
Knative Serving
쿠버네티스 위의 서버리스 계층. 요청 수로 파드를 0 까지 줄이고 늘린다. v1.23.0. 5장
Knative Service (ksvc)
함수 하나. Configuration·Revision·Route 를 만들어 낸다. 5장
Revision
template 이 바뀔 때마다 생기는 바꿀 수 없는 스냅샷. 롤백은 "traffic 을 옛 Revision 으로". 5장
traffic
Revision 별 비율. 기본은 latestRevision: true, percent: 100. 에이전트 rollback 은 특정 Revision 에 고정한다. 5장
scale-to-zero
요청이 없으면 파드를 0개로. 자원은 아끼고 첫 요청은 느려진다. 5장
콜드 스타트 (cold start)
파드 0개 상태에서 첫 요청이 파드가 뜰 때까지 기다리는 것. 5장
activator
파드가 0개일 때 요청을 대신 받아 붙잡고, 파드가 뜨면 넘기는 Knative 부품. 파드가 있어도 여유 용량(target-burst-capacity)이 모자라면 요청 경로에 계속 끼어 있다. 우리 설정(기본값 211)에서는 항상 끼어 있다. 5장
autoscaler (KPA)
동시 요청 수를 보고 파드 수를 정하는 Knative 부품. PodAutoscaler 리소스를 쓴다. 5장
queue-proxy
함수 컨테이너 옆에 붙는 사이드카. 동시 요청 수를 재어 autoscaler 가 1초마다 긁어 가는 지표로 내놓고(알리는 게 아니라 긁어 가는 구조), containerConcurrency 를 넘는 요청은 줄 세운다. 5장
min-scale / max-scale
파드 수 하한·상한 annotation. 컨트롤 플레인은 max 5 만 적고, min 은 에이전트 몫으로 비워 둔다. 5장
containerConcurrency
파드 하나가 동시에 받는 요청 수 상한. 05 함수는 10. 5장
stable window
autoscaler 가 평균을 내는 시간. 짧으면 빨리 줄어든다. 04 함수는 6초. 5장
kaniko
Docker 데몬 없이 컨테이너 안에서 이미지를 빌드·push 하는 도구. v1.23.2. 프로젝트는 아카이브되어 더 개발되지 않는다(본선이면 BuildKit rootless 같은 대안 검토). 6장
digest (sha256)
이미지 내용의 해시. 태그와 달리 바뀌지 않는다. 05 는 digest 로 배포해 "무엇이 도는지" 를 고정한다. 6장
termination message
컨테이너가 끝날 때 /dev/termination-log 에 쓴 글. kaniko 가 digest 를 여기 남긴다. 7장
kind-registry
맥의 Docker 에서 도는 registry:2. 노드에선 kind-registry:5000(push), kubelet 은 localhost:5001(pull, hosts.toml 로 연결). 6장
RuntimeClass
파드가 어떤 컨테이너 런타임 핸들러로 돌지 고르는 리소스. gvisor → runsc. 6장
gVisor (runsc)
사용자 공간 커널로 시스템 콜을 가로채는 샌드박스 런타임. 남의 코드를 돌릴 때 커널 공격면을 줄인다. 6장
runc
기본 컨테이너 런타임. 호스트 커널을 그대로 쓴다. 6장

컨트롤 플레인과 에이전트

컨트롤 플레인 (이 PoC 의 뜻)
함수 배포 API 를 가진 Spring Boot 서비스. 쿠버네티스 컨트롤 플레인(API 서버·etcd·스케줄러·컨트롤러 매니저가 도는 control-plane 노드)과 다른 말이다. 각 장은 쿠버네티스 쪽을 말할 때 "control-plane 노드" 또는 "쿠버네티스 컨트롤 플레인" 이라고 구분해 쓴다. 7장
fabric8
자바용 쿠버네티스 클라이언트. Job 생성, watch, server-side apply 를 한다. 7장
가상 스레드 (virtual thread)
JVM 이 가볍게 만드는 스레드. 빌드 대기처럼 오래 막히는 일을 요청 스레드에서 떼어 낸다. 7장
202 Accepted + Location
"받았다, 결과는 저 주소로 물어봐라" 응답. 오래 걸리는 작업의 표준 모양. 7장
멱등 (idempotent)
같은 요청을 몇 번 보내도 결과가 같은 성질. 같은 코드 = 같은 buildId = 빌드 재사용. 7장
server-side apply (SSA)
"내가 적은 필드는 이 값" 을 API 서버가 필드 주인(field manager)별로 관리하는 apply. 7장
field manager
SSA 에서 필드의 주인 이름. 컨트롤 플레인은 faas-control-plane. 7장
ownerReference
"이 리소스의 주인은 저것" 표시. 주인이 지워지면 쓰레기 수집기가 같이 지운다. 소스 ConfigMap → 빌드 Job. 7장
ttlSecondsAfterFinished
끝난 Job 을 몇 초 뒤 지울지. 빌드 Job 은 3600. 7장
MCP (Model Context Protocol)
AI 애플리케이션(호스트·클라이언트)이 외부 서버의 도구(tools)·자원(resources)·프롬프트를 표준 방식으로 쓰게 하는 규약. 전송은 stdio 또는 Streamable HTTP. ops_mcp 는 stdio 로 get_metrics·scale·rollback 세 도구를 낸다. 7장
가드레일 (guardrail)
에이전트가 할 수 있는 일을 좁히는 겹겹의 장치. 범위 고정 · RBAC · 승인 · 한도/dry-run · 감사. 7장
사람 승인 (human-in-the-loop)
되돌리기 어려운 동작은 사람이 터미널에서 승인해야 실행. 1회용, 900초, 인자에 묶임. 7장
감사 로그 (audit log)
누가 언제 무엇을 시도했고 결과가 무엇인지 남긴 줄. 거절도 남긴다. 7장
TokenRequest
ServiceAccount 의 짧게 사는 토큰을 발급하는 API. kubectl create token. 7장

장애와 클라우드

장애 주입 (fault injection)
일부러 노드·배포·설정을 망가뜨려 시스템의 반응을 재는 실험. 8장
대역 클러스터 (stand-in)
06 이 쓰는 kind-chaos. faas 와 노드 역할은 비슷하지만 taint 없음, kindnet. 8장
NotReady / Unknown
노드 하트비트가 grace period(기본 50초) 넘게 없을 때의 노드 상태(Unknown). kubelet 이 살아 있어도 CNI 가 안 깔려 파드 네트워크가 준비 안 되면(NetworkReady=false) NotReady 가 된다. 8장
Lease (kube-node-lease)
kubelet 이 주기적으로 갱신하는 하트비트 리소스. 8장
tolerationSeconds
NoExecute taint 를 몇 초 견딘 뒤 쫓겨날지. 기본 300, 06 방어는 20. 8장
topologySpreadConstraints
파드를 노드·존마다 고르게 흩는 규칙. maxSkew, whenUnsatisfiable, nodeTaintsPolicy. 8장
PodDisruptionBudget (PDB)
drain 같은 자발적 중단 때 최소 몇 개는 남겨 두라는 약속. 노드 장애(비자발적)는 막지 못한다. 8장
cordon / drain
노드에 새 파드를 막기 / 기존 파드를 PDB 를 지키며 내보내기. 스팟 예고 대응의 기본. 8장
합성 프로브 (synthetic probe)
밖에서 정해진 주기로 함수를 불러 성공·실패를 기록하는 스크립트. 사용자 체감의 대리 지표. 8장
런북 (runbook)
알림이 울렸을 때 사람이 따라 할 절차. RB-01 ~ RB-04. 8장
k3s
바이너리 하나로 된 가벼운 쿠버네티스 배포판. 기본 CNI flannel, 기본 인그레스 Traefik, NetworkPolicy 는 내장 컨트롤러(kube-router 기반)가 집행. 9장
스팟 인스턴스 (Spot)
남는 EC2 를 싸게 쓰되 2분 예고 후 회수될 수 있는 구매 방식. exec 풀에 쓴다. 9장
ASG (Auto Scaling Group)
같은 Launch Template 으로 EC2 수를 유지하는 묶음. 예약으로 매일 23:00 에 0. 9장
NTH (Node Termination Handler)
스팟 회수 예고를 받아 노드를 cordon·drain 하는 AWS 도구. 9장
FIS (Fault Injection Service)
AWS 의 장애 주입 서비스. 스팟 중단 예고를 일부러 보낸다. 9장
SSM 포트 포워딩
인바운드 포트를 열지 않고 AWS Systems Manager 로 6443 에 터널을 뚫는 방법. 9장
Terraform
인프라를 코드로 선언하고 plan/apply 로 맞추는 도구. 07 의 VPC·EC2·ASG·예산. 9장

정리

여기까지 읽었으면 그림 0-3 의 칸 전부에 이름과 역할이 붙었을 것이다. 아래는 그것을 스스로 확인하는 도구다.

핵심 개념 체크리스트

  • 요청 두 갈래(함수 배포 / 함수 호출)가 각각 어떤 부품을 지나는지 말할 수 있다.
  • 노드 풀 세 개의 역할과, 함수·빌드 파드가 거기 고정되는 장치(nodeSelector + toleration)를 설명할 수 있다.
  • Argo CD 가 관리하는 것(Application 10개 + AppSet 1개)과 스크립트·Helm 이 직접 까는 것을 구분할 수 있다.
  • run-all.sh 가 단계 README 순서를 따르지 않는 이유를 한 문장으로 말할 수 있다.
  • 함수 phase 여섯 가지와 각 phase 를 판정하는 근거(Job 상태, ksvc buildId, Ready 조건)를 안다.
  • 콜드 스타트에서 activator 가 하는 일과, tenant-a 의 NetworkPolicy 가 왜 knative-serving 을 열어야 하는지 안다.
  • 카나리 abort 뒤 Argo CD 가 Synced + Degraded 로 보이는 이유와 마무리(git revert)를 안다.
  • 노드 장애에서 "감지까지 50초" 와 "옮기기까지 300초(방어 후 20초)" 가 다른 시계라는 것을 안다.
  • 신뢰 경계의 진짜 벽 두 개(RBAC, NetworkPolicy)와 가장 약한 고리(인증 없는 컨트롤 플레인 API)를 짚을 수 있다.
  • 로컬 kind 와 EC2 k3s 의 taint 전략이 왜 반대인지 설명할 수 있다.

본선에서 떠올릴 패턴

  • 원하는 상태 + 조정 루프: Argo CD, Knative autoscaler, Rollouts, ReplicaSet 이 모두 같은 모양이다. 새 주제가 나오면 "누가 원하는 상태를 적고, 누가 어떤 주기로 맞추나" 부터 그린다.
  • 비동기 작업 = 202 + 상태 조회 + 멱등 ID: 빌드뿐 아니라 리포트 생성, 대량 업로드, 결제 확인에도 그대로 쓴다. 상태를 메모리에 두면 재시작 때 고아가 생긴다는 한계까지 같이 말한다.
  • 권한의 모양과 범위를 나누기: ClusterRole(모양) + 테넌트별 RoleBinding(범위). SaaS 의 역할·조직 모델에도 같은 구조다.
  • 코드 검사 뒤에 진짜 벽: 앱 안의 검사는 뚫린다고 가정하고, 플랫폼 계층(RBAC, NetworkPolicy, IAM)에 한 겹을 더 둔다.
  • 안전한 기본값 + 좁은 예외: default-deny 후 허용, taint 후 toleration, PSA baseline 강제. 예외는 이름이 붙은 정책으로 남긴다.
  • 자동 판정과 사람 승인의 경계: 되돌리기 쉬운 것(카나리 abort, scale ±2)은 자동, 어려운 것(트래픽 고정 롤백)은 사람 승인.
  • 두 시계 분리: "감지까지" 와 "복구까지" 를 따로 재고 따로 줄인다. 장애 질문에는 늘 이 둘로 답한다.
