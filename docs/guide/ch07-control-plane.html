사용자가 코드만 HTTP 로 던지면 빌드 Job 과 Knative Service 가 생기는 Spring Boot 컨트롤 플레인, 그리고 AI 운영 에이전트가 테넌트 하나 안에서만 지표를 읽고 스케일·롤백을 하게 만드는 MCP 서버를 코드 한 줄 단위까지 읽는다. 다 읽고 나면 "쿠버네티스 앞에 플랫폼 API 를 하나 세우는 법" 과 "LLM 에게 클러스터 열쇠를 작게 쥐여 주는 법" 을 다른 주제에 옮겨 쓸 수 있다.

컨트롤 플레인과 데이터 플레인

두 층으로 나눠 부르는 이유

데이터 플레인(data plane)은 실제 요청을 처리하는 곳이다. 우리 PoC 에서는 exec 풀에서 도는 함수 파드와, 그 앞의 입구인 Kourier Envoy 와 activator 다. 컨트롤 플레인(control plane)은 "무엇을, 어디에, 몇 개" 를 정하고 지시하는 곳이다. 사용자는 컨트롤 플레인만 만나고, 데이터 플레인은 컨트롤 플레인이 적어 둔 원하는 상태를 따라 움직인다.

exec 풀
함수 실행 전용 노드 묶음. pool=exec 라벨과 taint 가 붙은 워커 노드들.
파드(pod)
쿠버네티스가 컨테이너를 띄우는 최소 단위. 컨테이너 하나 이상이 한 파드에 들어가 네트워크와 저장소를 나눠 쓴다.
Kourier
Knative 의 입구 프록시. Envoy 하나와 작은 컨트롤러로 이루어진다(05장).
activator
파드가 0개일 때 요청을 잡아 두고 파드를 깨우는 Knative 구성 요소.

이렇게 나누는 가장 큰 이유는 실패의 영향 범위다. 컨트롤 플레인이 죽어도 이미 떠 있는 함수는 계속 응답한다. 새 배포만 못 할 뿐이다. 반대로 함수 하나가 폭주해도 배포 API 는 멀쩡하다. 두 번째 이유는 확장 방식이 다르다는 것이다. 데이터 플레인은 요청 수에 비례해 늘어야 하므로 Knative 오토스케일러가 요청 수를 보고 파드 수를 정하고, 컨트롤 플레인은 배포 빈도에 비례할 뿐이라 파드 하나로 충분하다.

쿠버네티스도 같은 말을 쓴다. API 서버, etcd, 스케줄러, 컨트롤러 매니저가 컨트롤 플레인이고, 노드의 kubelet 과 컨테이너 런타임이 데이터 플레인이다. 우리가 만드는 것은 그 위에 한 겹 더 얹는 플랫폼의 컨트롤 플레인이다. 그래서 이 PoC 에는 "컨트롤 플레인" 이 세 겹 있다.

API 서버
쿠버네티스의 모든 요청이 들어오는 REST 창구. kubectl 도 컨트롤러도 전부 여기로 말한다.
etcd
API 서버가 객체를 저장하는 키-값 저장소.
스케줄러
새 파드를 어느 노드에 둘지 정하는 구성 요소.
컨트롤러 매니저
원하는 상태와 실제 상태의 차이를 메우는 루프(컨트롤러)들을 한 프로세스에 모아 돌리는 것.
kubelet
노드마다 하나씩 떠서 API 서버가 정한 파드를 실제로 띄우고 상태를 보고하는 에이전트.
컨테이너 런타임
containerd 처럼 컨테이너를 실제로 실행하는 프로그램.
queue-proxy
Knative 가 모든 함수 파드에 붙이는 사이드카(보조 컨테이너). 요청 수를 세어 오토스케일러에 알린다.
kaniko
Docker 데몬 없이 컨테이너 안에서 Dockerfile 을 빌드하는 도구(06장).
레지스트리
컨테이너 이미지를 저장·배포하는 서버. 이 PoC 에서는 kind-registry:5000.

책임이 어떻게 나뉘나

층마다 "무엇을 원하나" 를 받아 아래 층에 맞는 말로 바꿔 넘긴다. 위층은 아래 층의 세부를 모르고, 아래 층은 위층이 왜 그걸 원하는지 모른다. 표에 나오는 ConfigMap 과 Deployment 는 쿠버네티스의 기본 객체이고, Knative 는 Service 하나를 받아 Configuration, Revision, Route, PodAutoscaler 로 풀어 쓴다(05장).

ConfigMap
설정 파일 묶음을 담는 쿠버네티스 객체. 여기서는 사용자 코드를 담아 빌드 파드에 파일로 꽂아 준다.
Deployment

Revision

Route

PodAutoscaler

표의 "상태를 어디에 두나" 열이 중요하다. Knative 와 쿠버네티스는 상태를 전부 API 서버(뒤의 etcd)에 두기 때문에 다시 떠도 이어서 일한다. 우리 컨트롤 플레인은 "어느 빌드를 기다리는 중인가" 를 메모리에만 둔다. 이게 뒤의 알려진 한계 1번이다.

공식 정의와 우리 코드의 대응

쿠버네티스 문서는 컨트롤 플레인 구성 요소를 "클러스터에 대한 전역 결정을 내리고, 클러스터 이벤트를 감지하고 반응하는" 것으로 정의한다. 그리고 컨트롤러는 "현재 상태를 원하는 상태에 가깝게 만드는 제어 루프(control loop)" 다. 우리 컨트롤 플레인은 앞의 정의(결정)는 하지만 뒤의 정의(루프)는 하지 않는다. 요청이 올 때 한 번 지시하고, 백그라운드 스레드가 한 번 기다렸다가 한 번 반영하고 끝난다. 그래서 정확히는 "명령형 API 서버"이고, 루프로 바꾸면 오퍼레이터가 된다.

우리 PoC 에서는

컨트롤 플레인 파드는 faas-system 에 1개(replicas: 1)다. 파드가 1개여도 괜찮은 이유가 바로 이 절의 내용이다. 함수 호출 경로(localhost:8081 → Kourier → 함수 파드)에 컨트롤 플레인이 없다. 컨트롤 플레인이 죽은 동안의 증상은 "배포가 안 됨" 뿐이다.

깨지면 이렇게 보인다

증상: kubectl -n faas-system delete pod -l app=control-plane 직후 deploy-fn.sh 가 curl: (7) Failed to connect 또는 port-forward 끊김. 같은 순간 curl -H "Host: hello.tenant-a.faas.local" localhost:8081 은 정상 응답.
볼 곳: kubectl -n faas-system get pods -w. Deployment 가 새 파드를 띄우는 것이 보인다. port-forward 는 파드가 바뀌면 끊기므로 다시 실행.
고치는 법: 새 파드가 Ready 가 되면 그대로 복구. 단, 지우던 순간 빌드 중이던 함수는 깨지면 2번처럼 반영이 빠진다.

port-forward
kubectl(쿠버네티스 명령줄 도구)이 맥의 포트를 클러스터 안 Service 나 파드로 터널링하는 기능. 맥의 8090 → 컨트롤 플레인이 이것이다.

왜 이렇게 나눴나 (대안)

대안은 사용자에게 kubectl 이나 Argo CD 를 직접 쓰게 하는 것이다. 층이 하나 줄지만 사용자가 YAML·이미지·레지스트리를 알아야 하고, 권한 경계가 사용자 손에 넘어간다. 해커톤 주제가 "Run Your Functions Instantly over HTTP" 였다는 점(05 README 1.2)을 생각하면 입구는 HTTP API 하나여야 했다.

컨트롤 플레인 = 검사 + 번역기

05 README 의 표현을 그대로 빌리면 컨트롤 플레인은 "검사 + 번역기"다. 사람 말(함수 이름, 코드)을 쿠버네티스 말(ConfigMap, Job, Knative Service)로 바꾸고, 바꾸기 전에 "이 요청을 해도 되나" 를 검사한다. 이 한 겹이 하는 일은 넷이다.

1. 추상화

사용자는 {name, code} 만 보낸다. Dockerfile, 레지스트리 주소, nodeSelector 와 toleration, digest, securityContext 는 전부 템플릿 안에 있다.

nodeSelector
파드를 어느 라벨의 노드에 보낼지 정하는 파드 필드.
toleration
taint("이 노드에 오지 마" 표시)가 붙은 노드에도 파드가 갈 수 있게 허락하는 필드.
digest
이미지 내용의 해시. @sha256:… 모양으로 이미지를 고정한다.
securityContext
컨테이너가 어떤 권한으로 도는지(루트 여부, 권한 상승 금지 등) 적는 필드.

2. 테넌트 확인

경로의 {tenant} 가 진짜 테넌트 namespace 인지, 즉 라벨 tenant=<이름> 이 붙은 namespace 인지 본다. kube-system 으로 보내면 404.

라벨
객체에 붙이는 키=값 꼬리표. 셀렉터로 골라내거나 여기처럼 표식으로 쓴다.

3. 감사

누가(X-Actor), 언제, 어느 테넌트에, 무엇을, 결과는. AUDIT 로거로 JSON 한 줄.

4. 최소 권한

쿠버네티스 권한은 컨트롤 플레인 ServiceAccount 하나만 갖는다. 사용자에게는 kubeconfig 를 주지 않는다.

ServiceAccount(SA)
사람이 아닌 프로그램이 API 서버에 자기 신분을 밝힐 때 쓰는 계정.
kubeconfig
클러스터 주소와 자격 증명을 담은 설정 파일. kubectl 이 읽는다.

검사가 어디에 몇 겹 있나

같은 위험("다른 namespace 에 함수를 만든다")을 여러 겹이 따로 막는다. 한 겹에 버그가 있어도 다음 겹이 막도록 겹을 서로 다른 메커니즘으로 만든 것이 핵심이다.

  • k8s.namespaces().withName(tenant).get(): GET /api/v1/namespaces/{tenant} 한 번. fabric8 의 get() 은 404 면 예외 대신 null 을 돌려준다. 그래서 없는 namespace 는 ns != null 에서 걸린다.
  • 라벨 키는 application.yml 의 faas.tenant-label: tenant. 03장의 tenant Helm 차트(charts/tenant/templates/namespace.yaml)가 tenant: {{ .Values.name }} 를 붙인다. 두 단계가 이 문자열 하나로 이어져 있다.
  • 값까지 비교한다. 라벨이 있기만 하면 통과가 아니라 값이 namespace 이름과 같아야 한다. 누가 kube-system 에 tenant=tenant-a 라벨을 붙여도 통과하지 못한다.
  • 권한은 namespaces 에 get 하나뿐이다. list 를 주면 모든 테넌트 이름이 보이므로 일부러 안 준다(rbac.yaml 주석).
fabric8
쿠버네티스 API 를 자바에서 부르는 오픈소스 클라이언트 라이브러리(io.fabric8:kubernetes-client). 이 앱의 모든 쿠버네티스 호출이 이것을 거친다.
Helm 차트
쿠버네티스 매니페스트를 변수(values)로 찍어 내는 패키지.

REST API 설계: 202 Accepted 와 상태 조회

엔드포인트 두 개로 끝난다

앞 절에서 컨트롤 플레인이 하는 네 가지 일을 봤다. 이제 사용자가 실제로 만나는 입구, HTTP API 의 모양부터 본다. API 는 두 개뿐이다.

메서드와 경로본문성공 응답뜻
POST /api/v1/tenants/{tenant}/functions{"name": "hello", "code": "def handle(body): ..."}202 Accepted + Location 헤더 + DeployAccepted JSON접수했다. 결과는 Location 주소에서 봐라
GET /api/v1/tenants/{tenant}/functions/{name}없음200 + FunctionStatus JSON (없으면 404 + phase: NOT_FOUND)지금 어디까지 왔나

202 Accepted 는 HTTP 표준(RFC 9110 15.3.3)이 정한 "요청을 받았지만 처리는 끝나지 않았다" 응답이다. 빌드는 수십 초가 걸린다. 그동안 요청을 붙잡고 있으면 클라이언트·프록시·port-forward 어딘가의 타임아웃에 걸리고, 사용자가 다시 누르면 같은 일이 두 번 시작된다. 그래서 "접수증" 만 바로 주고, 진행 상황은 따로 묻게 한다. 이 모양을 흔히 비동기 요청-응답 패턴(asynchronous request-reply) 이라 부른다. 빌드를 기다리는 일은 가상 스레드(Spring 절)가 백그라운드에서 맡는다.

가상 스레드(virtual thread)
Java 21 이 제공하는 아주 가벼운 스레드. 기다리는 동안 OS 스레드를 차지하지 않아 수천 개를 만들어도 부담이 적다.
폴링(polling)
클라이언트가 일정 간격으로 같은 조회를 반복해 결과를 확인하는 방식. 끊겨도 다시 물으면 그만이라 단순하고 튼튼하다.

Jackson
Spring Boot 웹 앱이 기본으로 쓰는 JSON 변환 라이브러리. 자바 객체 ↔ JSON 을 맡는다.

컨트롤러 한 줄씩

control-plane/src/main/java/com/example/controlplane/api/FunctionController.javadeploy, status (25~71행)
@RestController
@RequestMapping("/api/v1/tenants/{tenant}/functions")
public class FunctionController {

    // 테넌트 이름 = namespace 이름. DNS 라벨 규칙 (소문자·숫자·하이픈, 63자 이하)
    static final String TENANT_PATTERN = "[a-z0-9]([-a-z0-9]{0,61}[a-z0-9])?";

    private final FunctionDeployer deployer;
    private final FaasProperties props;

    public FunctionController(FunctionDeployer deployer, FaasProperties props) {
        this.deployer = deployer;
        this.props = props;
    }

    /**
     * 함수 배포. 202 Accepted + Location 헤더(상태 조회 주소)를 돌려준다.
     * 빌드는 수십 초 걸리니 요청을 붙잡고 기다리지 않는다.
     */
    @PostMapping
    public ResponseEntity<DeployAccepted> deploy(
            @PathVariable @Pattern(regexp = TENANT_PATTERN) String tenant,
            @Valid @RequestBody DeployRequest request,
            @RequestHeader(value = "X-Actor", defaultValue = "anonymous") String actor) {
        // 1) 코드 크기 한도. ConfigMap 은 1MiB 가 한계라 그보다 작게 막는다 → 413
        if (request.code().getBytes(StandardCharsets.UTF_8).length > props.maxCodeBytes()) {
            throw new ResponseStatusException(HttpStatus.CONTENT_TOO_LARGE, "code 는 " + props.maxCodeBytes() + " 바이트 이하");
        }
        // 2) 테넌트 확인. 테넌트 라벨이 없는 namespace(kube-system 등)는 없는 것으로 친다 → 404
        if (!deployer.tenantExists(tenant)) {
            throw new ResponseStatusException(HttpStatus.NOT_FOUND, "테넌트가 없다: " + tenant);
        }
        // 3) 빌드 시작 (Job 생성까지만 하고 바로 돌아온다)
        DeployAccepted accepted = deployer.startDeploy(tenant, request, actor);
        // 4) 202 + Location
        return ResponseEntity.accepted().location(URI.create(accepted.statusUrl())).body(accepted);
    }

    /** 상태 조회. 클라이언트는 READY 나 *_FAILED 가 나올 때까지 이걸 반복해서 부른다 */
    @GetMapping("/{name}")
    public ResponseEntity<FunctionStatus> status(
            @PathVariable @Pattern(regexp = TENANT_PATTERN) String tenant,
            @PathVariable String name) {
        FunctionStatus s = deployer.status(tenant, name);
        return "NOT_FOUND".equals(s.phase()) ? ResponseEntity.status(HttpStatus.NOT_FOUND).body(s) : ResponseEntity.ok(s);
    }
}
  • @RequestMapping("/api/v1/tenants/{tenant}/functions"): 경로에 테넌트를 넣는 계층형 URL. 버전(v1)을 경로 앞에 두어 나중에 v2 와 나란히 둘 수 있다. 쿠버네티스 API 자신도 /apis/serving.knative.dev/v1/namespaces/{ns}/services 처럼 같은 모양이다.
  • @PathVariable @Pattern(...): 경로 변수에 제약 어노테이션을 직접 붙였다. Spring Framework 6.1 부터는 컨트롤러 메서드 파라미터에 제약 어노테이션이 있으면 내장 메서드 검증이 돈다. Spring Boot 4 가 쓰는 Framework 7 도 같다. 조건은 컨트롤러 클래스에 @Validated 가 없어야 한다는 것이다. 있으면 AOP 프록시 방식의 메서드 검증이 대신 적용되어 예외 종류가 달라진다. 이 컨트롤러에는 없으니 내장 검증이 맞고, 위반하면 HandlerMethodValidationException 이 나서 400 이 된다. 이 PoC 테스트는 이 경로(경로 변수 규칙 위반)를 검사하지 않는다.
  • @Valid @RequestBody DeployRequest: JSON 을 레코드로 바꾼 뒤 레코드 필드의 @NotBlank, @Pattern 을 검사. 실패하면 메서드 본문에 들어오지도 않는다.
  • @RequestHeader(value = "X-Actor", defaultValue = "anonymous"): 인증이 없으니(알려진 한계 2) "누가" 는 클라이언트가 자기 이름을 적는 헤더다. 감사 로그의 actor 가 된다. 믿을 수 있는 값이 아니라는 점을 기억한다.
  • 크기 검사는 String.length()(UTF-16 문자 수)가 아니라 UTF-8 바이트 수로 한다. ConfigMap 한도(1MiB)는 바이트 단위이고, 한글 한 글자는 UTF-8 로 3바이트다.
  • ResponseEntity.accepted().location(URI.create(...)): 202 와 Location: /api/v1/tenants/tenant-a/functions/hello. 상대 경로 URI 다. HTTP 표준은 Location 에 상대 참조를 허용한다.
  • status() 는 NOT_FOUND 일 때도 본문을 준다. 클라이언트가 404 와 함께 phase 를 읽을 수 있어서 "아직 아무것도 없다" 와 "경로가 틀렸다" 를 구분할 수 있다.

입력 검사 규칙의 숫자

함수 이름 정규식은 [a-z]([-a-z0-9]{0,28}[a-z0-9])?, 즉 1~30자다. 왜 30자인가. Job 이름이 "build-" + name + "-" + 해시10자 이므로 6 + 30 + 1 + 10 = 47자. 쿠버네티스 객체 이름 중 라벨 값으로도 쓰이는 것은 63자 한도가 있다. Job 이름이 그렇다. Job 컨트롤러가 파드에 batch.kubernetes.io/job-name 라벨(호환을 위해 옛 job-name 도 함께)로 Job 이름을 붙이기 때문이다. 그리고 Knative 는 Service 이름에 -00001 같은 Revision 접미사와 -deployment, -private 등을 더 붙인다. 30자면 그 모든 경우에 여유가 있다.

코드 크기 한도 262144 바이트(256KiB)도 같은 계산이다. ConfigMap 의 data 전체가 1MiB 를 넘을 수 없고, 같은 ConfigMap 에 server.py 와 Dockerfile 도 들어간다. 그리고 etcd 의 요청 크기 한도도 비슷한 크기다. 4분의 1 로 잡아 두면 걱정할 일이 없다.

가상 스레드 두 곳

  1. application.yml 의 spring.threads.virtual.enabled: true: 톰캣이 HTTP 요청마다 가상 스레드를 쓴다. 요청 처리 대부분이 API 서버 응답 기다리기라 맞다.

쿠버네티스 = REST API 서버 하나

앞 절의 KubernetesClient 빈이 부르는 상대가 쿠버네티스 API 서버다. 다음 절의 FunctionDeployer 코드는 전부 이 API 호출이므로, 먼저 클라이언트 입장에서 API 서버를 정리한다. 클라이언트 쪽에서 보면 쿠버네티스 API 서버는 아주 큰 REST 서버 하나다. kubectl, Argo CD, Knative 컨트롤러, 우리 컨트롤 플레인, 운영 에이전트 모두 같은 HTTP API 를 부르는 클라이언트일 뿐이다. 보통의 REST 서버와 다른 점은 셋이다.

  1. 모든 것이 리소스다. 파드, Job, ConfigMap, Knative Service 가 전부 같은 모양의 JSON 객체(apiVersion, kind, metadata, spec, status)이고, URL 경로도 같은 규칙을 따른다.
  2. "바뀌면 알려 줘"(watch) 가 기본 기능이다. 폴링하지 않고 HTTP 연결 하나로 변경 이벤트를 계속 받는다.
  3. 모든 객체에 버전 번호(resourceVersion) 가 있어서, 남이 바꾼 것을 모르고 덮어쓰는 일을 서버가 막는다(낙관적 동시성).
디스커버리(discovery)
API 서버가 자기에게 어떤 그룹·버전·리소스가 있는지 알려 주는 API(/apis, /apis/그룹/버전). kubectl 과 fabric8 이 Kind 에서 URL 을 만들 때 쓴다.

동사, HTTP 메서드, 그리고 watch

RBAC 의 verbs 는 결국 HTTP 요청 종류다. 컨트롤 플레인 rbac.yaml 을 읽을 때 이 표가 있으면 "코드의 호출 하나 → verb 하나" 대응이 바로 보인다.

watch 의 원리는 이렇다. 먼저 list 로 현재 목록과 그 시점의 resourceVersion 을 받는다. 그다음 ?watch=1&resourceVersion=그 값 으로 요청하면 서버는 연결을 닫지 않고 그 이후 변경을 ADDED / MODIFIED / DELETED 이벤트로 한 줄씩 흘려 준다. 너무 오래된 resourceVersion 으로 watch 하면 서버가 410 Gone 을 주고, 클라이언트는 다시 list 부터 해야 한다.

요청 하나가 API 서버 안에서 지나는 길

위의 모든 요청은 API 서버 안에서 같은 관문을 차례로 지난다. 이 순서를 알면 뒤에 나오는 401·403·409 와 dry-run, 그리고 "RBAC 가 마지막 벽" 이라는 말이 전부 한 그림에 들어온다.

  1. 인증(authentication): "누구인가". 요청의 Authorization: Bearer 토큰을 보고 호출자를 정한다. 컨트롤 플레인 파드의 토큰은 system:serviceaccount:faas-system:control-plane 이라는 사용자 이름이 된다. 토큰이 틀리거나 만료됐으면 401 Unauthorized다(에이전트 토큰이 8시간 뒤 만료되면 이게 난다).
  2. 인가(authorization): "이 사용자가 이 리소스에 이 verb 를 해도 되나". RBAC 가 여기서 판정한다. 허락 규칙이 하나도 없으면 403 Forbidden이고, 메시지에 사용자·verb·리소스·namespace 가 다 들어 있다.
  3. 어드미션(admission): 허락된 요청의 내용을 검사하거나 고치는 플러그인들. 먼저 변경(mutating) 플러그인이 기본값을 채우고, 그다음 검증(validating) 플러그인이 거부할지 정한다. Pod Security Admission 과 Knative 가 설치한 웹훅이 이 단계다. 거부되면 4xx 와 사유 메시지가 돌아온다.
  4. 스키마 검증: 타입에 맞는 필드인가. 모르는 필드는 기본 fieldValidation=Warn 에서 경고와 함께 버려지고 요청은 성공한다(Strict 면 400).
  5. 저장: etcd 에 쓰고 resourceVersion 을 올린다. 그다음 이 객체를 watch 하던 클라이언트들에게 이벤트가 간다. dryRun=All 요청은 이 단계 직전에서 끝난다. 즉 드라이런도 인증·인가·어드미션을 전부 통과해야 한다.
Pod Security Admission
namespace 라벨로 파드 보안 수준(privileged·baseline·restricted)을 강제하는 쿠버네티스 내장 어드미션 기능. 줄여서 PSA.
웹훅(admission webhook)
API 서버가 요청 내용을 바깥 HTTP 서버에 보내 검사하거나 고치게 하는 어드미션 플러그인. Knative 의 webhook 파드가 ksvc 필드를 검사한다.

resourceVersion 과 낙관적 동시성, fabric8 의 두 가지 객체

resourceVersion 은 객체가 바뀔 때마다 API 서버가 새로 매기는 불투명한 문자열이다. 공식 문서는 "클라이언트는 이 값을 해석하지 말고 그대로 돌려줘야 한다" 고 한다(숫자처럼 보여도 크기 비교 금지). 쓰기에서 이 값이 하는 일은 낙관적 동시성 제어(optimistic concurrency)다. 잠그지 않고 먼저 읽은 뒤, 쓸 때 읽은 시점의 버전을 같이 보내고, 그 사이에 누가 바꿨으면 서버가 거절하는 방식이다.

쓰기 방법은 네 가지다. 우리 PoC 는 이 중 두 개를 고른다. Knative Service 가 CRD 로 등록된 타입이라는 점이 선택에 영향을 준다.

fabric8 의 두 가지 객체 모양

fabric8 은 내장 타입(Job, Pod, ConfigMap, Namespace)은 타입 있는 자바 클래스(io.fabric8.kubernetes.api.model.batch.v1.Job)로, CRD 로 등록된 타입처럼 모르는 타입은 GenericKubernetesResource로 다룬다. 후자는 metadata 만 자바 필드이고 spec, status 는 Map<String, Object>(getAdditionalProperties()) 안에 들어 있다. 그래서 FunctionDeployer 에 맵을 경로로 따라 내려가는 도우미 at(r, "status", "conditions") 가 있다.

  • genericKubernetesResources("serving.knative.dev/v1", "Service"): apiVersion 과 Kind(GVK)를 주면 fabric8 이 API 서버 디스커버리(/apis/serving.knative.dev/v1)를 물어 복수형 리소스 이름 services(GVR)와 namespace 범위 여부를 찾는다. 그래서 테스트의 가짜 서버에 expectCustomResource(KSVC) 로 이 정보를 등록해 둔다.
  • instanceof Map<?, ?> map: Java 16+ 패턴 매칭. 중간에 맵이 아니면(경로가 없으면) null. 상태가 아직 비어 있는 새 ksvc 를 다룰 때 NPE 없이 지나가게 한다.

컨트롤 플레인이 부르는 API 는 모두 아홉 가지다: Namespace get, Job get/list/watch/create, ConfigMap create, Pod list, Knative Service get/patch(apply). apply 는 객체가 없으면 생성까지 하므로 RBAC 로는 Knative Service create 까지 열 개를 연다. rbac.yaml 의 verbs 와 정확히 맞춰 보면 이 장 RBAC 절의 표가 된다. 운영 에이전트(파이썬)는 공식 파이썬 클라이언트의 CustomObjectsApi 로 같은 REST 경로를 부른다(knative.py).

깨지면 이렇게 보인다

증상: 컨트롤 플레인 로그에 the server could not find the requested resource 또는 404 가 Knative Service 쪽에서만. 볼 곳: kubectl api-resources --api-group=serving.knative.dev (CRD 가 설치됐나), kubectl get crd services.serving.knative.dev. 고치는 법: 04단계(Knative 설치)가 끝났는지. 디스커버리가 GVK→GVR 를 못 찾으면 fabric8 도 경로를 못 만든다.

왜 이걸 알아야 하나

RBAC 규칙(GVR + verb), 에러 코드(403/404/409/410/422), 감사 로그, kubectl -v=8 출력이 전부 이 REST 모양으로 되어 있다. "자바 메서드 하나 = HTTP 요청 하나 = RBAC verb 하나" 로 읽을 수 있으면 권한 설계와 장애 분석이 같은 일이 된다.

FunctionDeployer: startDeploy 와 finishDeploy

두 메서드, 두 스레드

API 서버를 부르는 법을 봤으니, 이제 그 호출을 실제로 하는 코드다. 배포의 실제 일은 deploy/FunctionDeployer.java 한 클래스에 있다. 05 README 가 "꼭 한 번 위에서 아래로 읽기" 라고 한 파일이다. 일을 두 토막으로 자른 것이 설계의 전부다.

  • startDeploy(요청 스레드, 1초 안): 빌드 ID 계산 → 빌드 Job 이 이미 있나 확인 → 없으면 Job 과 소스 ConfigMap 생성 → 감사 → 백그라운드에 finishDeploy 제출 → 202.
  • finishDeploy(가상 스레드, 최대 11분 = build-timeout): Job 이 끝나길 watch → digest 읽기 → Knative Service server-side apply → 감사.

    public DeployAccepted startDeploy(String tenant, DeployRequest req, String actor) {
        String name = req.name();
        String buildId = BuildIds.of(tenant, name, req.code());
        String jobName = "build-" + buildId;
        String buildNs = props.buildNamespace();

        Map<String, String> vars = Map.of(
                "TENANT", tenant,
                "NAME", name,
                "BUILD_ID", buildId,
                "BUILD_NAMESPACE", buildNs,
                "PUSH_IMAGE", props.registryPush() + "/" + tenant + "/" + name + ":" + buildId);

        Job job = k8s.batch().v1().jobs().inNamespace(buildNs).withName(jobName).get();
        boolean reused = job != null;
        if (!reused) {
            Job desired = renderer.render("build-job.yaml", vars, Job.class);
            requireName(desired.getMetadata().getName(), jobName, "build-job.yaml");
            job = k8s.batch().v1().jobs().inNamespace(buildNs).resource(desired).create();

            ConfigMap source = new ConfigMapBuilder()
                    .withNewMetadata()
                        .withName("src-" + buildId)
                        .withNamespace(buildNs)
                        .addToLabels(LABEL_TENANT, tenant)
                        .addToLabels(LABEL_FUNCTION, name)
                        .withOwnerReferences(new OwnerReferenceBuilder()
                                .withApiVersion("batch/v1").withKind("Job")
                                .withName(job.getMetadata().getName()).withUid(job.getMetadata().getUid())
                                .build())
                    .endMetadata()
                    .addToData("handler.py", req.code())
                    .addToData("server.py", renderer.readRuntimeFile("python/server.py"))
                    .addToData("Dockerfile", renderer.readRuntimeFile("python/Dockerfile"))
                    .build();
            // Job 파드는 ConfigMap 이 생길 때까지 ContainerCreating 에서 기다렸다가 뜬다 (kubelet 이 다시 시도)
            k8s.configMaps().inNamespace(buildNs).resource(source).create();
        }
        audit.record(actor, "deploy.accepted", tenant, name, "ok", "buildId=" + buildId + (reused ? " (같은 코드, 빌드 재사용)" : ""));

        if (inFlight.add(buildId)) {
            executor.submit(() -> finishDeploy(tenant, name, buildId, actor));
        }
        String statusUrl = "/api/v1/tenants/" + tenant + "/functions/" + name;
        return new DeployAccepted(tenant, name, buildId, "BUILDING", statusUrl);

  1. BuildIds.of(tenant, name, code): tenant + "\n" + name + "\n" + code 의 SHA-256 을 16진으로 바꿔 앞 10자. 구분자 \n 은 ("ab","c") 와 ("a","bc") 가 같은 해시가 되는 것을 막는다. 10자 = 40비트라 충돌은 현실적으로 없다(같은 테넌트·같은 이름 안에서만 의미가 있다).
  2. PUSH_IMAGE 는 kind-registry:5000/tenant-a/hello:hello-3f2a9c01be. 태그로 올리지만 나중에 digest 로 받는다. 태그는 사람이 레지스트리에서 찾아보기 위한 이름표일 뿐이다.
  3. jobs()...withName(jobName).get(): "이미 했나?" 의 답. DB 가 아니라 쿠버네티스가 진실이다.
  4. renderer.render("build-job.yaml", vars, Job.class): 템플릿을 채워 fabric8 Job 객체로. 그다음 requireName 으로 템플릿의 metadata.name 이 정확히 build-ID 인지 확인한다. 템플릿을 고친 사람이 이름 규칙을 깨면 Job 은 생기는데 다음 GET 이 못 찾는 조용한 버그가 되므로, 만들기 전에 시끄럽게 실패시킨다.
  5. .resource(desired).create(): POST /apis/batch/v1/namespaces/faas-build/jobs. 응답에 서버가 매긴 uid 가 들어 있다.
  6. ConfigMap 의 ownerReferences 에 Job 의 이름과 uid 를 넣는다. 쿠버네티스 가비지 컬렉터는 주인(owner)이 지워지면 딸린 객체도 지운다. Job 은 ttlSecondsAfterFinished: 3600 으로 1시간 뒤 지워지니 소스 ConfigMap 도 같이 사라진다. 그래서 RBAC 에 configmaps delete 가 필요 없다.
  7. 순서가 Job 먼저, ConfigMap 나중인 이유: ownerReference 에 Job 의 uid 가 필요하기 때문이다. 그 사이 몇 밀리초 동안 Job 파드는 볼륨(ConfigMap)이 없어 ContainerCreating 에서 기다리고, kubelet 이 다시 시도해서 붙는다.
  8. 사용자 코드는 addToData("handler.py", req.code()) 로 객체의 필드에 들어간다. 템플릿 문자열에 끼워 넣지 않으므로 코드에 --- 나 들여쓰기 문자가 있어도 YAML 이 깨지거나 다른 필드가 주입될 수 없다.
  9. inFlight.add(buildId): ConcurrentHashMap.newKeySet() 의 add 는 원자적이고, 새로 넣었을 때만 true. 같은 빌드에 대해 기다리는 스레드는 항상 하나다.
  10. 응답 phase 는 항상 BUILDING 이다. 재사용이라 이미 끝난 빌드여도 그렇다. 실제 상태는 다음 GET 이 계산한다.

    void finishDeploy(String tenant, String name, String buildId, String actor) {
        String jobName = "build-" + buildId;
        try {
            Job done = k8s.batch().v1().jobs().inNamespace(props.buildNamespace()).withName(jobName)
                    .waitUntilCondition(j -> j == null || isFinished(j), props.buildTimeout().toSeconds(), TimeUnit.SECONDS);
            if (done == null || !isSucceeded(done)) {
                audit.record(actor, "deploy.build", tenant, name, "failed", "job=" + jobName);
                return;
            }
            String digest = readDigest(jobName);
            String image = props.registryPull() + "/" + tenant + "/" + name + "@" + digest;

            GenericKubernetesResource ksvc = renderer.render("ksvc.yaml", Map.of(
                    "TENANT", tenant,
                    "NAME", name,
                    "BUILD_ID", buildId,
                    "IMAGE", image), GenericKubernetesResource.class);
            requireName(ksvc.getMetadata().getName(), name, "ksvc.yaml");

            //   - 처음이면 생성, 있으면 내가 주인인 필드만 갱신
            //   - forceConflicts: 다른 주인(예: 에이전트가 롤백으로 바꾼 traffic)이 있어도 새 배포가 이긴다
            //   - 내가 안 적은 필드(에이전트가 바꾼 min-scale)는 건드리지 않는다
            knativeServices(tenant).resource(ksvc).fieldManager(FIELD_MANAGER).forceConflicts().serverSideApply();

        }

  2. isFinished = status.succeeded > 0 || status.failed > 0. Job 에 backoffLimit: 0 이라 실패가 한 번이면 끝이다. nz() 는 상태 필드가 아직 null 일 때 0 으로 본다.

  5. serverSideApply() 앞의 두 수식어가 이 장의 SSA 절 전체다. fieldManager("faas-control-plane") = 내 이름표, forceConflicts() = 다른 주인과 부딪히면 내가 가져간다.

  7. finally { inFlight.remove(buildId) }: 성공·실패·예외 어느 경우든 비운다. 그래야 같은 코드를 다시 보냈을 때 다시 기다릴 수 있다.

    static String fill(String template, Map<String, String> vars, String templateName) {
        // 주석(#) 줄은 빼고, 아직 안 채운 빈칸이 있으면 바로 알려 준다
        template.lines()
                .filter(line -> !line.strip().startsWith("#") && line.contains("___"))
                .findFirst()
                .ifPresent(line -> {
                    throw new IllegalStateException(templateName + " 에 아직 채우지 않은 빈칸이 있다: " + line.strip());
                });
        Matcher m = PLACEHOLDER.matcher(template);
        StringBuilder out = new StringBuilder();
        while (m.find()) {
            String value = vars.get(m.group(1));
            if (value == null) {
                throw new IllegalStateException(templateName + " 의 ${" + m.group(1) + "} 에 넣을 값이 없다. 쓸 수 있는 키: " + vars.keySet());
            }
            m.appendReplacement(out, Matcher.quoteReplacement(value));
        }
        m.appendTail(out);
        return out.toString();
    }
  • "\\$\\{([A-Z_]+)}": 자바 문자열 안이라 백슬래시가 두 번. 정규식으로는 \$\{([A-Z_]+)}, 즉 ${ + 대문자·밑줄 + }. 소문자 키나 ${a.b} 는 치환 대상이 아니다.
  • ___ 감시: 이 레포는 학습용 뼈대(빈칸 ___)에서 출발했다. 빈칸이 남은 템플릿을 그대로 쓰면 backoffLimit: ___ 같은 값이 YAML 파서에서 이상한 에러를 내거나, 더 나쁘게는 문자열로 들어가 API 서버가 거절한다. 그 전에 "어느 줄이 빈칸인지" 를 사람이 읽을 메시지로 멈춘다. 주석 줄은 건너뛰어 설명문 속 ___ 에는 반응하지 않는다. scripts/check-solution.sh 의 1단계도 같은 규칙으로 grep 한다.
  • Matcher.quoteReplacement(value): appendReplacement 는 대체 문자열의 $ 와 \ 를 특별하게 해석한다($1 = 그룹 참조). 값에 $ 가 들어 있어도 글자 그대로 넣게 한다.

  • getKubernetesSerialization().unmarshal(yaml, type): fabric8 의 Jackson 기반 YAML → 객체 변환. fabric8 모델은 모르는 필드를 오류 내지 않고 additionalProperties 맵에 담아 둔다(@JsonAnySetter). 그래서 필드 이름 오타(backofLimit)는 파싱 단계에서 안 잡히고, Job 객체의 backoffLimit 은 null 로 남은 채 API 서버로 간다. max-scale: "5" 의 계산(05 README 결정 2)은 템플릿 주석에 적힌 대로 메모리와 CPU 를 같이 본다. 메모리는 넉넉하다. 03장 ResourceQuota 가 limits.memory: 2Gi 이고, 함수 컨테이너 limits 128Mi 에 Knative 가 붙이는 queue-proxy 사이드카의 128Mi 를 더해도 파드 하나 256Mi, 다섯 개면 1.25Gi 다. queue-proxy 의 128Mi 는 limits 를 안 적은 컨테이너에 03장 LimitRange 가 붙이는 기본값이다. 먼저 닿는 것은 limits.cpu: 2 다. 함수 컨테이너는 limits.cpu 를 일부러 안 적어서 LimitRange 기본값 200m 이 붙고 queue-proxy 도 200m 이라 파드 하나가 400m 인데, 같은 테넌트의 hello-fn 파드 둘이 이미 400m 을 쓰고 있다. 남는 1600m 으로 함수 파드는 네 개까지만 뜨고 다섯 번째는 ResourceQuota 에 막힌다. 05 README 결정 표는 메모리(2Gi ÷ (128Mi + queue-proxy))로만 계산하라고 하지만, 실제 천장은 CPU 가 먼저다. 한도의 뜻은 03장 ResourceQuota 와 LimitRange 에 있다.

Server-Side Apply 와 필드 주인

한 객체를 두 주인이 나눠 갖는다

앞 절의 템플릿을 클러스터에 넣는 한 줄 serverSideApply() 가 이 절의 주제다. 컨트롤 플레인과 운영 에이전트가 같은 Knative Service 를 고친다. 컨트롤 플레인은 배포 때 이미지·라벨·max-scale·traffic 을 쓰고, 에이전트는 운영 중에 min-scale 과 (롤백 때) traffic 을 쓴다. 서로 상대가 쓴 값을 모르고 덮어쓰면 안 된다.

Server-Side Apply(SSA) 는 이 문제를 API 서버가 풀게 한다. 클라이언트는 "내가 의견이 있는 필드만" 적어 보내고(부분 객체), API 서버는 필드마다 주인(field manager) 을 metadata.managedFields 에 기록한다. 다음에 같은 주인이 apply 하면 그 주인의 필드만 갱신되고, 남의 필드는 그대로 둔다.

배포 → 스케일 → 롤백 → 재배포 순서로 보면

여기서 두 가지 규칙이 일한다.

  1. apply 는 자기가 적은 필드만 책임진다. 컨트롤 플레인이 이전 apply 에서 적었다가 이번에 빼면 그 필드는 지워진다(주인이 자기 뿐일 때). 하지만 한 번도 적은 적 없는 min-scale 은 컨트롤 플레인과 무관하다. 그래서 ksvc.yaml 에 min-scale 을 "적지 않는 것" 이 곧 권한 분할이다.
  2. apply 가 남의 필드 값을 바꾸려 하면 충돌이다. update/patch(operation: Update) 쪽은 충돌로 실패하지 않고 그냥 주인이 된다. apply 쪽만 실패하고, force=true 면 값을 바꾸면서 남의 주인 기록을 지운다.

managedFields, 충돌, 리스트 병합

요청의 실제 모양은 이렇다. fabric8 의 .fieldManager("faas-control-plane").forceConflicts().serverSideApply() 는 아래 HTTP 하나가 된다.

HTTP 요청 (설명용)server-side apply
PATCH /apis/serving.knative.dev/v1/namespaces/tenant-a/services/hello?fieldManager=faas-control-plane&force=true
Content-Type: application/apply-patch+yaml

{ "apiVersion": "serving.knative.dev/v1", "kind": "Service", "metadata": {...}, "spec": {...} }
  • apply 는 PATCH 다. 그래서 RBAC 에 patch 가 있어야 하고, 객체가 없으면 같은 요청으로 생성까지 된다. 공식 문서가 말하는 apply 의 의도가 "있으면 맞추고 없으면 만든다" 이기 때문이다. 이 생성 경로에서 API 서버는 create 권한을 따로 한 번 더 확인한다. apiserver 의 patch 핸들러가 apply 패치에 한해 생성을 허용하면서, 생성 직전에 verb 를 create 로 바꿔 인가를 다시 묻기 때문이다. 이 때문에 컨트롤 플레인 ClusterRole 에 create 도 같이 둔다. 빠지면 함수의 첫 배포만 403 이고, 두 번째 배포부터는 patch 만으로 된다.
  • fieldManager 는 apply 에서 필수다. 비어 있으면 API 서버가 거절한다.
  • force=true 는 kubectl 의 --force-conflicts 와 같다.

apply 뒤 객체의 managedFields 는 대략 이런 모양이 된다 (kubectl -n tenant-a get ksvc hello -o yaml --show-managed-fields, 설명용으로 줄인 예시).

충돌을 푸는 세 방법(공식 문서): ① 덮어쓰기(force) — 값을 바꾸고 남의 기록에서 그 필드를 지운다. ② 내 apply 설정에서 그 필드를 뺀다 — 남이 주인이 되게 둔다. ③ 남과 같은 값으로 적는다 — 공동 주인이 된다. 우리 설계는 traffic 에 ①, min-scale 에 ② 를 쓴 셈이다.

리스트 병합: SSA 는 리스트를 스키마의 x-kubernetes-list-type 에 따라 다룬다. atomic 이면 리스트 통째로 주인이 하나, map/set 이면 원소별로 주인이 갈린다. 리스트 타입 표시가 없으면 atomic 으로 본다. Knative Serving 1.23 의 Service CRD 스키마에서 spec.traffic 에는 리스트 타입 표시가 없다. 그래서 atomic, 즉 리스트 통째로 한 주인이다. 에이전트의 merge patch 역시 JSON merge patch 규칙(RFC 7386)상 리스트를 통째로 바꾼다. 두 쪽 모두 "traffic 은 한 덩어리" 로 다루므로 어긋나지 않는다.

API 서버가 apply(manager=M, 부분 객체 P, force) 를 받으면:
  현재 = etcd 의 객체 (없으면 빈 객체 → 생성)
  각각 P 의 필드 f:
    만약 f 의 값이 현재와 같음: M 을 공동 주인으로 추가
    아니면 만약 f 의 주인이 M 뿐 또는 주인 없음: 값 바꿈, 주인 = M
    아니면 만약 force: 값 바꿈, 다른 주인 기록에서 f 제거, 주인 = M
    아니면: 충돌 목록에 추가
  만약 충돌 목록이 비어 있지 않음: 반환 409 Conflict (어느 필드, 누구 소유)
  각각 M 이 전에 가졌는데 P 에 없는 필드 g:
    만약 g 의 주인이 M 뿐: g 삭제                     // "적지 않으면 지운다"
    아니면: M 만 주인 목록에서 빠짐
  저장, resourceVersion 증가

빌드 결과를 "내용의 지문" 으로 고정

SSA 로 넣는 템플릿의 ${IMAGE} 값은 어디서 오나. 빌드가 끝나면 컨트롤 플레인은 이미지 주소를 알아야 한다. 태그(:hello-3f2a9c01be)는 알고 있지만, 태그는 나중에 다른 이미지를 가리키게 바꿀 수 있다. 그래서 Knative Service 에는 digest(@sha256:...)를 넣는다. digest 는 내용이 바뀌면 같이 바뀌니 "Revision 3 = 이 이미지" 가 영원히 참이다. 롤백이 믿을 만해지는 이유다.

문제는 digest 를 빌드 파드에서 컨트롤 플레인으로 어떻게 넘기느냐다. 로그를 파싱하려면 pods/log 권한이 필요하고, 레지스트리에 물어보려면 레지스트리 클라이언트가 필요하다. 이 PoC 는 쿠버네티스의 종료 메시지(termination message) 를 우편함처럼 쓴다.

종료 메시지의 규칙

  • 컨테이너의 terminationMessagePath 기본값이 /dev/termination-log 다. 컨테이너가 끝날 때 kubelet 이 이 파일 내용을 status.containerStatuses[].state.terminated.message 에 넣는다.
  • 공식 문서 한도: 메시지 하나는 4096 바이트에서 잘리고, 파드의 모든 컨테이너 합이 12KiB 다. digest 는 71자(sha256: + 64자)라 여유롭다.
  • terminationMessagePolicy: FallbackToLogsOnError 로 바꾸면 파일이 비고 실패했을 때 로그 끝부분을 대신 넣는다. 우리는 기본값(File)이다. 실패한 빌드의 원인은 BUILD_FAILED 메시지에 넣은 kubectl logs 명령으로 사람이 본다.
  • kaniko 의 --digest-file 은 push 한 이미지의 digest 를 지정한 파일에 쓴다. 그 파일을 종료 메시지 경로로 지정하면 두 기능이 그대로 이어진다.

    /** kaniko 의 --digest-file=/dev/termination-log 덕분에, 끝난 컨테이너 상태의 message 에 digest 가 들어 있다 */
    private String readDigest(String jobName) {
        List<Pod> pods = k8s.pods().inNamespace(props.buildNamespace()).withLabel("job-name", jobName).list().getItems();
        return pods.stream()
                .flatMap(p -> p.getStatus() == null || p.getStatus().getContainerStatuses() == null
                        ? java.util.stream.Stream.<ContainerStatus>empty()
                        : p.getStatus().getContainerStatuses().stream())
                .filter(cs -> KANIKO_CONTAINER.equals(cs.getName()))
                .map(cs -> cs.getState() == null || cs.getState().getTerminated() == null ? null : cs.getState().getTerminated().getMessage())
                .filter(Objects::nonNull)
                .map(String::trim)
                .filter(m -> m.startsWith("sha256:"))
                .findFirst()
                .orElseThrow(() -> new IllegalStateException("빌드 파드에서 digest 를 못 찾았다. build-job.yaml 의 컨테이너 이름이 " + KANIKO_CONTAINER
                        + " 이고 --digest-file=/dev/termination-log 가 있는지 확인"));
    }
  1. withLabel("job-name", jobName): Job 컨트롤러가 자기 파드에 붙이는 라벨. 공식 표기는 1.27 부터 접두어가 붙은 batch.kubernetes.io/job-name 이고, 접두어 없는 옛 job-name 도 호환을 위해 계속 같이 붙는다. API 소스 주석도 쿠버네티스가 일관성을 위해 접두어 없는 라벨을 계속 인식한다고 적는다. 코드는 옛 키를 쓰므로 동작하지만, 접두어 키로 바꾸는 편이 앞으로 안전하다. RBAC 는 pods list.
  2. flatMap: 파드가 여럿일 수 있다(backoffLimit 0 이라 보통 하나). 상태가 아직 없는 파드는 빈 스트림으로.
  3. filter(KANIKO_CONTAINER.equals(...)): initContainer(copy-source)는 initContainerStatuses 에 따로 있어 섞이지 않지만, 컨테이너 이름으로 한 번 더 고른다. 템플릿의 컨테이너 이름이 kaniko 여야 하는 이유이고, 템플릿 주석에도 적혀 있다.
  4. trim() 후 startsWith("sha256:"): 메시지 앞뒤 공백·줄바꿈 제거, digest 모양만 통과. 다른 문자열이 들어 있으면 버린다.
  5. 못 찾으면 IllegalStateException: 백그라운드라 사용자에게 500 이 가지는 않고, 감사 로그 deploy.apply error 에 이 메시지가 그대로 남는다. 상태는 DEPLOYING 에 머문다.

배포 상태 머신

상태를 저장하지 않고 매번 계산한다

배포가 Job → digest → apply 로 흘러가는 동안 사용자는 GET 으로 "어디까지 왔나" 를 묻는다. 상태 응답의 phase 는 여섯 값 중 하나다: NOT_FOUND, BUILDING, BUILD_FAILED, DEPLOYING, READY, FAILED. 중요한 점은 컨트롤 플레인이 이 값을 어디에도 저장하지 않는다는 것이다. GET 이 올 때마다 쿠버네티스의 두 객체(가장 최근 빌드 Job, Knative Service)를 읽어 계산한다. 그래서 컨트롤 플레인이 재시작해도 상태 조회는 정확하다. 진실은 쿠버네티스에 있다.

RBAC 설계와 kubectl auth can-i

코드가 부르는 API 만큼만 연다

지금까지 본 쿠버네티스 호출 하나하나에 권한이 필요하다. 그 권한을 적는 방식이 RBAC 다. RBAC(Role-Based Access Control)는 "누가(subject) 무엇을(resource) 어떻게(verb) 어디서(namespace)" 를 허락 목록으로만 적는 방식이다. 거부 규칙은 없다. 적지 않은 것은 전부 403 이다. 원칙은 rbac.yaml 첫 주석 그대로 "FunctionDeployer.java 가 실제로 부르는 API 만 연다".

Role
권한 목록. 한 namespace 안에서만 의미가 있다.
ClusterRole
권한 목록. namespace 가 없는 리소스(Namespace, Node)에 쓰거나, 여러 namespace 에서 재사용할 "모양" 으로 쓴다.
RoleBinding
"누구에게 어떤 Role(또는 ClusterRole)을 이 namespace 에서" 준다.
ClusterRoleBinding
클러스터 전체에서 준다. 꼭 필요할 때만.

  반환 거부 → 403 Forbidden                 // 거부 규칙은 없다. 허락이 하나도 없으면 거부

/**
 * 감사 로그: "누가, 언제, 어느 테넌트에, 무엇을, 결과는" 을 JSON 한 줄로 남긴다.
 * 로거 이름이 AUDIT 이라 `kubectl logs ... | grep '"audit"'` 로 따로 뽑을 수 있다.
 * PoC 라 표준 출력에만 쓴다. 운영이면 Loki 같은 곳으로 보내고 지울 수 없게 보관한다 (README 결정 표).
 */
@Component
public class AuditLog {

    private static final Logger log = LoggerFactory.getLogger("AUDIT");

    public void record(String actor, String action, String tenant, String target, String result, String detail) {
        Map<String, String> e = new LinkedHashMap<>();
        e.put("audit", "control-plane");
        e.put("ts", Instant.now().toString());
        e.put("actor", actor);
        e.put("action", action);
        e.put("tenant", tenant);
        e.put("target", target);
        e.put("result", result);
        e.put("detail", detail == null ? "" : detail);
        log.info(toJson(e));
    }

    private static String toJson(Map<String, String> m) {
        return m.entrySet().stream()
                .map(x -> "\"" + x.getKey() + "\":\"" + escape(x.getValue()) + "\"")
                .collect(Collectors.joining(",", "{", "}"));
    }

    private static String escape(String s) {
        if (s == null) return "";
        return s.replace("\\", "\\\\").replace("\"", "\\\"").replace("\n", "\\n");
    }
}
  • LoggerFactory.getLogger("AUDIT"): 클래스 이름이 아닌 고정 이름. 로그백 설정에서 이 로거만 따로 파일/원격으로 보내기 쉽다.
  • LinkedHashMap: 키 순서를 고정한다. 사람이 읽을 때와 diff 할 때 편하다.
  • escape: 백슬래시 → 따옴표 → 줄바꿈 순서로. 백슬래시를 먼저 바꿔야 뒤에서 넣은 백슬래시를 다시 바꾸지 않는다. 줄바꿈을 이스케이프하는 이유는 한 사건 = 한 줄(JSON Lines)을 지키기 위해서다. 예외 메시지에 줄바꿈이 섞여도 줄이 쪼개지지 않는다. 다른 제어 문자(탭 등)는 처리하지 않는다. Jackson 을 쓰지 않은 것은 의존성을 늘리지 않으려는 PoC 선택이다.
  • actor 는 클라이언트가 보낸 헤더라 위조할 수 있다. 감사 로그의 가치는 actor 의 신뢰도에 묶인다. 인증이 들어오면 인증된 주체로 바꾼다(알려진 한계 2).

MCP 란 무엇인가

LLM 앱과 바깥 도구 사이의 표준 플러그

여기까지가 컨트롤 플레인이다. 이제 같은 Knative Service 를 다른 길로, 훨씬 좁은 권한으로 만지는 운영 에이전트로 넘어간다. 먼저 그 에이전트가 쓰는 규약부터다.

LLM 은 글을 읽고 쓰는 모델이라 혼자서는 클러스터를 만질 수 없다. 대신 도구 호출(tool call) 이라는 방식을 쓴다. 호스트 앱이 "이런 함수들이 있다(이름·설명·인자 모양)" 를 모델에게 알려 주면, 모델은 답을 글로만 쓰는 대신 "이 함수를 이 인자로 실행해 달라" 는 구조화된 요청을 내고, 앱이 실제로 실행한 결과를 다시 모델에게 돌려준다. MCP(Model Context Protocol)는 그 도구를 LLM 애플리케이션 바깥의 서버가 제공하는 방법을 표준화한 프로토콜이다. 규격을 따르는 서버를 하나 만들면 Claude Code, Claude Desktop, 다른 MCP 지원 앱 어디에서든 같은 도구가 붙는다.

세 역할이 있다.

호스트(host)
사용자가 쓰는 LLM 앱. 여기서는 Claude Code. 서버 연결을 관리하고, 어떤 도구를 모델에 보여 줄지, 사용자 승인을 받을지 정한다.
클라이언트(client)
호스트 안에서 서버 하나와 1:1 로 연결을 유지하는 부분. 서버가 셋이면 클라이언트도 셋.
서버(server)
도구(tools, 모델이 실행을 요청하는 함수), 자원(resources, 모델이 읽을 데이터), 프롬프트(prompts, 사용자가 고르는 대화 템플릿)를 제공하는 프로그램. 여기서는 ops_mcp.server 파이썬 프로세스이고 도구만 낸다.
stdio(standard input/output)
표준 입출력. 부모 프로세스가 자식의 stdin 에 쓰고 stdout 에서 읽는 가장 단순한 프로세스 사이 통신.
JSON-RPC
원격 호출을 JSON 으로 적는 가벼운 규약. 요청·응답·알림 세 가지 메시지뿐이다(다음 절).

전송 두 가지와 대화 순서

MCP 메시지는 JSON-RPC 2.0 이다. 요청(id, method, params), 응답(id, result 또는 error), 알림(id 없음, 응답 없음) 세 종류. 이걸 실어 나르는 표준 전송(transport)은 둘이다.

stdioStreamable HTTP
연결클라이언트가 서버를 자식 프로세스로 띄운다서버는 독립 프로세스, 엔드포인트 하나(예: /mcp)가 POST 와 GET 을 받는다
메시지 구분줄바꿈. 메시지 안에 줄바꿈 금지HTTP 요청 하나에 메시지 하나, 응답은 JSON 또는 SSE 스트림
stdoutMCP 메시지만. 로그는 stderr 로해당 없음
세션프로세스 수명 = 세션MCP-Session-Id 헤더, 버전은 MCP-Protocol-Version 헤더
보안OS 프로세스 경계. 포트가 없다Origin 헤더 검사 필수(DNS 리바인딩 방지. 틀리면 403), 로컬이면 127.0.0.1 바인딩 권장, 인증
쓰임로컬 도구 (우리)원격·공유 서버. 2024-11-05 판의 HTTP+SSE 전송을 대체
SSE(Server-Sent Events)
서버가 HTTP 응답 하나를 열어 두고 이벤트를 한 줄씩 흘려 보내는 방식. 브라우저의 EventSource 가 읽는 그 형식이다.
DNS 리바인딩
공격자 사이트가 자기 도메인의 주소를 127.0.0.1 로 바꿔, 피해자의 브라우저가 로컬에 떠 있는 서버를 대신 부르게 하는 공격. Origin 검사로 막는다.

이 장의 MCP 설명은 2025-11-25 판 스펙 기준이다. 레포가 고정한 파이썬 SDK(mcp>=1.20,<2)가 이 판을 최신으로 구현하고, initialize 에서 버전 협상이 안 되면 2025-03-26 판으로 떨어진다. 그 뒤에 나온 2026-07-28 판은 변경 목록 기준으로 initialize 핸드셰이크와 MCP-Session-Id 헤더를 없애고 server/discover 를 넣는 등 수명 주기와 전송이 꽤 바뀌었다. 본선에서 SDK 를 올리면 이 절의 그림을 그 판 문서와 다시 맞춰야 한다.

도구 정의 = LLM 에게 주는 설명서

tools/list 가 돌려주는 도구 하나는 name, description, inputSchema(JSON Schema), 선택으로 title, outputSchema, annotations 를 갖는다. 우리 scale 도구는 대략 이런 모양으로 나간다. FastMCP 가 타입 힌트로 만든 스키마를 모양만 보여 주는 예시다.

  • description 은 프롬프트다. 모델은 이 문장만 보고 언제 이 도구를 쓸지, 무엇을 넣을지 정한다. 그래서 한도(-2~+2, 0~5), 부작용(승인 필요 여부), 용도(콜드 스타트, 비용)를 짧게 정확히 쓴다. server.py 주석: "여기 docstring 은 그대로 LLM 에게 도구 설명서로 간다."
  • 설명에 tenant-a 를 박아 넣는다(f-string). 모델은 "이 도구는 tenant-a 전용" 임을 알고, 스키마에는 tenant 인자가 아예 없다. 프롬프트로 범위를 알려 주고, 구조로 범위를 강제한다.
  • 스펙은 오류를 둘로 나눈다. 모르는 도구나 잘못된 요청 같은 프로토콜 오류는 JSON-RPC error 로 돌려주고, 도구가 실행 중에 실패한 도구 실행 오류는 결과에 isError: true 를 붙여 모델이 읽고 고칠 수 있게 한다. 우리 서버는 거부를 isError 없이 정상 결과 {"denied": ...}, {"forbidden": ...} 로 돌려준다. 모델이 이유를 읽는다는 목적은 같고, 테스트(test_거부는_에러가_아니라_이유로_돌아온다)가 이 선택을 고정한다. 클라이언트 UI 에 "실패" 로 표시되게 하려면 isError 로 바꾸는 편이 스펙에 더 가깝다.
  • 스펙은 annotations(예: readOnlyHint, destructiveHint)로 도구 성격을 표시할 수 있게 하고, 동시에 "신뢰할 수 있는 서버가 아니면 annotations 를 믿지 말라" 고 한다. 우리 서버는 annotations 를 쓰지 않는다. get_metrics 에 readOnly, rollback 에 destructive 를 붙이면 호스트가 승인 UI 를 다르게 띄울 수 있다(개선점).
  • 스펙의 보안 권고: 서버는 입력 검증·접근 제어·호출 빈도 제한·출력 정리를 해야 하고(MUST), 클라이언트는 민감한 작업에 사용자 확인을 받고 도구 사용을 감사용으로 기록하는 것이 좋다(SHOULD). 그리고 "도구 호출을 거부할 수 있는 사람이 항상 고리 안에 있어야 한다". 스펙 개요가 세우는 네 원칙(사용자 동의와 통제, 데이터 프라이버시, 도구 안전, 샘플링 통제)도 같은 방향이다. 우리 5층 가드레일이 이 문장들의 구현이다.

MCP 가 다루는 것은 도구만이 아니다. PoC 는 쓰지 않지만 본선에서 자리가 있는 기능을 적어 둔다.

FastMCP 와 ops_mcp 구조

데코레이터 한 줄 = 도구 하나

규약을 봤으니 그 규약을 구현한 우리 서버다. MCP 공식 파이썬 SDK 인 mcp 패키지(pyproject.toml 에서 mcp>=1.20,<2)에 들어 있는 FastMCP 는 파이썬 함수 하나를 도구 하나로 바꿔 주는 고수준 서버 클래스다. 함수에 @mcp.tool() 을 붙이면 함수 이름이 도구 이름, 파라미터 타입 힌트가 inputSchema, 반환값이 결과가 된다. JSON-RPC, 수명 주기, 전송은 SDK 가 처리한다.

def build_server(tools: OpsTools) -> FastMCP:
    mcp = FastMCP("faas-ops")
    tenant = tools.s.tenant

    @mcp.tool(description=(
        f"테넌트 {tenant} 의 함수 하나의 상태를 읽는다 (읽기 전용, 승인 불필요). "
        "Ready 여부, 트래픽 분배, min/max-scale, 오토스케일러 desired/actual, 파드 수·재시작 수, CPU/메모리, "
        "probe=true 면 함수에 요청 5번을 보내 에러율과 지연(ms)을 잰다."))
    def get_metrics(function: str, probe: bool = True) -> dict:
        return _call(tools.get_metrics, function=function, probe=probe)

    @mcp.tool(description=(
        f"테넌트 {tenant} 함수의 min-scale(항상 떠 있는 최소 파드 수)을 delta 만큼 바꾼다. "

        "콜드 스타트를 줄이려고 미리 데우거나, 트래픽이 끝나 비용을 줄일 때 쓴다. dry_run=true 면 검사만 한다."))
    def scale(function: str, delta: int, dry_run: bool = False) -> dict:
        return _call(tools.scale, function=function, delta=delta, dry_run=dry_run)

    @mcp.tool(description=(
        f"테넌트 {tenant} 함수의 트래픽 100% 를 지금과 다른 이미지를 가진 직전 Ready Revision 으로 되돌린다. "
        "위험한 행동이라 사람 승인이 필요하다: approval_id 없이 부르면 승인 요청만 만들고 approval_id 를 돌려준다. "
        "사람이 승인한 뒤 같은 function 과 approval_id 로 다시 부르면 실행된다. dry_run=true 면 승인 없이 계획만 검사한다."))

        return _call(tools.rollback, function=function, approval_id=approval_id, dry_run=dry_run)

def _call(fn, **kwargs) -> dict:
    """거부는 예외 대신 이유를 담은 dict 로 돌려준다 → 에이전트가 이유를 읽고 행동을 고칠 수 있다
    - {"denied": ...}: 파이썬 가드레일(1·3·4층)이 막음
    - {"forbidden": ...}: 쿠버네티스 RBAC(2층)이 막음. 에이전트에게 "권한 밖이니 사람에게 넘겨라" 신호
    """
    try:
        return fn(**kwargs)
    except GuardrailError as e:
        return {"denied": str(e)}
    except ApiException as e:
        if e.status == 403:
            return {"forbidden": f"쿠버네티스 RBAC 가 거부했다 ({e.reason}). 이 도구의 권한 밖이다. 사람에게 넘길 것"}
        return {"error": f"쿠버네티스 API {e.status} {e.reason}"}

  • build_server(tools) 는 의존성을 인자로 받는 팩토리다. 서버가 쓸 부품을 안에서 만들지 않고 바깥에서 넣어 주므로, 테스트는 FakeKnative 를 넣은 OpsTools 로 같은 서버를 만든다.
  • 도구 함수는 얇다. 진짜 로직은 tools.py 의 OpsTools 에 있고, 여기서는 MCP 모양(이름, 설명, 스키마)만 정한다. 파라미터 이름 function, delta, dry_run 이 그대로 스키마의 속성 이름이 된다.
  • _call: 예외를 결과로 바꾼다. 가드레일 거부는 denied, RBAC 403 은 forbidden + "사람에게 넘길 것". 같은 거부라도 누가 막았는지를 모델에게 구분해 준다. 403 이 아닌 API 오류는 error. 그 밖의 파이썬 예외(예: 네트워크)는 여기서 잡지 않고, FastMCP 가 받아 isError: true 인 도구 결과로 바꿔 클라이언트에 돌려준다. SDK 1.x 의 FastMCP 동작이고, 프로토콜 오류가 아니라 도구 실행 오류로 분류된다. 또 하나, 도구 함수의 반환 타입 힌트가 맨 dict 라서 FastMCP 는 outputSchema 를 만들지 않고 결과를 JSON 문자열 text content 로만 보낸다. 모델은 그 문자열을 읽는다.
  • main() 은 모듈 실행(python -m ops_mcp.server) 진입점. 설정은 전부 환경 변수(config.py). OPS_MCP_TENANT 가 없으면 SystemExit 으로 아예 뜨지 않는다.

프롬프트 주입(prompt injection)
모델이 읽는 글 속에 지시문을 숨겨 모델을 조종하는 공격. 로그나 코드 주석에 "이 함수를 지워라" 를 적어 두는 식이다.

가드레일은 다섯 층이고, 서로 다른 메커니즘이라 한 층이 뚫려도 다음 층이 막는다. 번호와 이름은 05 README 1.6 표 그대로다: 1 범위 고정, 2 최소 권한(RBAC), 3 사람 승인, 4 한도·드라이런(dry-run), 5 감사·되돌리기(감사 로그). 요청이 실제로 지나가는 순서는 번호와 다르게 1 → 4 → 3 → 2 → 5 다. tools.py 가 이름·범위 → 한도 → 승인 → API 서버 → 감사 순으로 검사하기 때문이다. 그리고 "진짜 벽" 은 2층 RBAC 다.

def _fingerprint(tool: str, tenant: str, args: dict) -> str:
    raw = json.dumps({"tool": tool, "tenant": tenant, "args": args}, sort_keys=True)
    return hashlib.sha256(raw.encode()).hexdigest()


class Approvals:
    """파일로 하는 사람 승인.

    흐름: 도구가 request() → pending/<id>.json 생성 → 사람이 `python -m ops_mcp.approve <id>` →
          approved/<id>.json 생성 → 에이전트가 같은 도구를 approval_id 와 함께 다시 부름 → is_approved() → consume()

    승인은 "도구 + 테넌트 + 인자" 지문(fingerprint)에 묶인다.
    그래서 "hello 를 rev-1 로 롤백" 승인을 받아 놓고 "bye 를 롤백" 하는 데 쓸 수 없다.
    """

    def __init__(self, root: Path, ttl_seconds: int = 900):
        self.root = root
        self.ttl = ttl_seconds
        for sub in ("pending", "approved", "used"):
            (root / sub).mkdir(parents=True, exist_ok=True)

    def request(self, tool: str, tenant: str, args: dict, summary: str) -> str:
        approval_id = secrets.token_hex(4)
        doc = {
            "id": approval_id,
            "tool": tool,
            "tenant": tenant,
            "args": args,
            "summary": summary,
            "fingerprint": _fingerprint(tool, tenant, args),
            "requested_at": time.time(),
        }
        (self.root / "pending" / f"{approval_id}.json").write_text(json.dumps(doc, ensure_ascii=False, indent=2))
        return approval_id

    def is_approved(self, approval_id: str, tool: str, tenant: str, args: dict) -> tuple[bool, str]:
        if not re.fullmatch(r"[0-9a-f]{8}", approval_id or ""):
            return False, "approval_id 형식이 틀렸다"
        path = self.root / "approved" / f"{approval_id}.json"
        if not path.exists():
            return False, "아직 사람이 승인하지 않았다"
        doc = json.loads(path.read_text())
        if doc["fingerprint"] != _fingerprint(tool, tenant, args):
            return False, "승인받은 행동과 지금 요청한 행동이 다르다 (대상 Revision 이 바뀌었을 수 있음). 다시 요청할 것"
        if time.time() - doc["approved_at"] > self.ttl:
            return False, f"승인이 {self.ttl}초가 지나 만료됐다. 다시 요청할 것"
        return True, "ok"

    def consume(self, approval_id: str) -> None:
        """한 번 쓴 승인은 used/ 로 옮긴다 → 같은 승인으로 두 번 실행 못 한다."""
        src = self.root / "approved" / f"{approval_id}.json"
        src.rename(self.root / "used" / f"{approval_id}.json")
  • secrets.token_hex(4): 8자리 16진 id. 추측하기 어렵게 암호학적 난수.
  • re.fullmatch(r"[0-9a-f]{8}", ...): id 를 파일 경로에 쓰기 전에 모양을 검사한다. ../../etc/x 같은 경로 조작(path traversal)을 막는다.
  • 지문 = sha256(JSON(tool, tenant, args), sort_keys). sort_keys=True 로 키 순서가 달라도 같은 지문. args 는 {"function", "to_revision"}.
  • 만료는 approved_at(사람이 승인한 시각) 기준 900초. 요청 시각이 아니다. 오래 묵은 승인으로 나중에 엉뚱한 때 실행되는 것을 막는다.
  • rename 으로 옮기기: 같은 파일 시스템 안에서 원자적이라, 같은 승인을 두 번 쓰는 경쟁이 생기면 하나만 성공한다.

정리

핵심 개념 체크리스트

  • 컨트롤 플레인과 데이터 플레인을 나누는 이유(실패 범위, 확장 방식)와 이 PoC 의 세 겹 컨트롤 플레인을 말할 수 있다.
  • 플랫폼 API 의 네 가지 일(추상화, 테넌트 확인, 감사, 최소 권한)과 검사 순서가 왜 중요한지 안다.
  • POST → 202 + Location → GET 폴링 패턴과, 에러 모델(400/404/413/500/502)을 설명할 수 있다. 403 이 왜 502 로 나가는지 안다.
  • Spring 빈 연결: 설정 레코드, KubernetesClient 자동 설정(맥 vs 파드), 생성자 주입, 가상 스레드 두 곳.
  • 쿠버네티스 REST 경로, GVK 와 GVR, verb 와 HTTP 메서드의 대응, list + watch 와 resourceVersion, 410 Gone 을 안다.
  • API 서버 요청 파이프라인(인증 → 인가 → 어드미션 → 스키마 검증 → 저장)과 401/403 의 차이, 드라이런이 어디서 멈추는지 안다.
  • startDeploy / finishDeploy 를 순서대로 말할 수 있고, BuildIds 가 멱등성과 복구 수단이 되는 이유를 안다.
  • ManifestRenderer 의 ${KEY} 치환, ___ 감시, 사용자 코드를 템플릿에 넣지 않는 이유를 안다.
  • Server-Side Apply 의 필드 주인, 충돌, force, "적지 않으면 내 필드가 아니다" 를 그림으로 그릴 수 있다.
  • kaniko digest 가 종료 메시지로 컨트롤 플레인까지 오는 길과 태그 대신 digest 를 쓰는 이유를 안다.
  • phase 여섯 개와 status() 판정 순서, READY 가 "요청이 성공한다" 를 뜻하지 않는다는 점을 안다.
  • Role / ClusterRole / RoleBinding / ClusterRoleBinding 조합과 kubectl auth can-i --as 사용법을 안다.
  • platform-05(directory recurse, prune, selfHeal)와 kind load 로 컨트롤 플레인이 올라가는 길을 안다.
  • 알려진 한계 넷과 오퍼레이터(CRD + reconcile) 대안의 장단점을 비교할 수 있다.
  • MCP 의 호스트·클라이언트·서버, JSON-RPC, stdio 와 Streamable HTTP, initialize → tools/list → tools/call 을 설명할 수 있다.
  • 도구 설명이 곧 LLM 프롬프트라는 점, 스펙의 isError 와 우리 서버의 denied/forbidden 선택을 안다.
  • 5층 가드레일(1 범위, 2 RBAC, 3 승인, 4 한도·dry-run, 5 감사)과 요청이 지나는 순서 1 → 4 → 3 → 2 → 5, "진짜 벽은 RBAC", 그리고 승인 저장소의 약점을 말할 수 있다.
  • TokenRequest 토큰 kubeconfig 와 claude mcp add 등록을 직접 할 수 있다.
  • 세 가지 깨뜨리기 실험의 예상 증상과 볼 곳을 말할 수 있다.

본선에서 떠올릴 패턴

검사 + 번역기

어떤 인프라든 사용자 앞에 얇은 API 를 두고, 사람 말을 인프라 말로 바꾸기 전에 테넌트·크기·이름을 검사한다. 쿠버네티스가 아니라 AWS(Lambda, ECS)여도 같다.

긴 작업 = 202 + 상태 URL

빌드, 프로비저닝, 데이터 처리처럼 수십 초 이상 걸리는 일은 접수증을 주고 상태를 따로 묻게 한다. 상태는 저장하지 말고 실제 리소스에서 유도한다.

내용 주소로 멱등성

입력의 해시를 리소스 이름에 넣으면 "이미 했나" 를 DB 없이 묻고, 재시도가 공짜로 안전해진다. 캐시 키, 이미지 태그, 업로드 파일 이름에 그대로 쓴다.

필드 주인 나누기

두 자동화(배포기와 운영 에이전트, 또는 HPA 와 GitOps)가 한 객체를 만지면 SSA 로 필드 주인을 나누고, 한쪽 템플릿에서 상대 몫 필드를 빼 둔다.

열쇠를 작게

AI 든 CI 든 자동화에게는 "코드가 부르는 API 목록 = 권한 목록" 인 전용 계정과 짧은 토큰을 준다. 프롬프트·코드 검사는 그 위에 얹는 층이다.

위험도별 층

읽기는 자유, 작은 쓰기는 한도 안 자동, 큰 쓰기는 대상에 묶인 1회용 사람 승인. 모든 결정은 감사 한 줄.

메모리 속 기다림은 한계

프로세스가 기다리는 일은 재시작에 약하다. 원하는 상태를 API 서버(또는 DB)에 남기고 루프가 차이를 메우게 하면(reconcile) 튼튼해진다.

READY ≠ 동작함

오케스트레이터의 Ready 와 사용자가 받는 응답은 다르다. 진짜 요청(probe)이나 에러율 지표로 따로 확인한다.
